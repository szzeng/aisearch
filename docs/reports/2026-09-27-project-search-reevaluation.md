# 全项目搜索性能与质量重新评估（2026-09-27）

## 1. 结论与范围

**建议保留 SQLite / LanceDB / 本地单体 / 稳定资产与人工知识底座，优先调整检索执行计划、增量发布与前后台资源安排，并重新打开 ANN 实验路线。当前证据不支持“电脑硬件不够”，也不支持“LanceDB 已没有优化空间”。**

用户对照：小米、vivo，约 **8 万张照片，自然语言搜索很快**。这是有效的体验输入；不是已计时的同图库、同查询、同网络条件基准。应增加 8 万/10 万同规模体验档，继续保留 30 万正式验收档。不能用规模差异单独解释本项目 10 万档仍达秒级的现状。

本轮为架构与工程重新评估，基线 **d370022**，开工工作树干净。读取主架构和 V3.1 策略全文、当前 P4-03A/P4-02K 卡、P4 性能/恢复报告、检索/索引/API/worker 边界；只修改评估报告、状态与建议任务卡。未扫描真实图库、未下载模型、未改变既有契约或产品行为。唯一新执行实验是 **3 行隔离合成表的 SDK 能力核验**；另复用既有预算重算工具。本轮不是逐文件全仓主审、独立 DS-H 审查或容量/性能 PASS。

## 2. 为什么电脑可以更强，却搜得更慢

建库与搜索必须分开：建库读取图片、解码并提取向量/OCR/人脸；搜索应主要读取提前生成的索引、编码一次查询，再取少量候选与缩略图。GPU 编码快，不能消掉 Python 调用、SQL 枚举、向量引擎重复查询或写锁等待。

当前代码在无用户筛选的普通语义搜索中也走权威候选块路径：`retrieval.py::vector_channel`，每块 5000，30 万约 60 次引擎调用；10 万约 20 次。这是保持正确性的慢回退被用于所有请求的执行策略问题。并非每次搜索重新编码全部照片，也不能笼统说每块一定重读所有向量；完整标量索引可减少扫描，但仍有多次规划、过滤、调用与返回成本。

另一个放大因素是 `store.py::search_candidates`：为保证大量并列距离下的 `(distance, asset_id)` 全序，它向引擎请求 `limit=len(ids)`，在块内排序后才取 K。因此，即使最后只展示 20 张，每块也可能返回 5000 行元数据，整次查询累计最多约 30 万行。列投影已避免返回完整向量，但调用与行物化成本仍在。不能直接改为每块只取 K：那会重新引入并列截断错误。应通过引擎可证全序或边界并列补齐实验解决。

原始 30 万×512×4 字节向量约 **0.6144 GB**，属于单机可处理的规模；它不代表峰值 RAM/VRAM或可保证的延迟。仓库测到单次全代引擎精确 pass 中位约 347 ms，说明存在明显算法与执行层空间；该值未含权威证据、补页、模型和 HTTP，不能写成产品能 347 ms 完成。

厂商资料也确认这不是只有关键词匹配的对照：小米说明支持自然语言检索设备内容，vivo 说明可用自然语言找照片。小米另说明内容分析、分类和自动标签等能力。其具体索引类型、云端参与、查询完整性、机型/版本及你的离线体验均未核实，不能宣称手机一定使用 ANN、一定端侧或靠云端算力。[小米自然语言搜索](https://privacy.mi.com/AIEngine/zh_CN/)、[小米相册搜索](https://www.mi.com/global/support/faq/details/KA-367221/)、[vivo 官方说明](https://aikefu.vivo.com.cn/imgtextdata/ssr/imagetext/c2f78d2db8b045dda12c90920d3ace4d)

## 3. 当前瓶颈地图与证据等级

| 项 | 当前事实 | 判断与下一步 |
|---|---|---|
| 检索执行 | 5000-ID 块、约 60 次引擎调用；块内请求所有候选以保全序 | 首要结构性瓶颈；快路径须有成员资格与发布证据，小候选/复杂条件保留精确回退 |
| 返回/排序 | 每块最多返回 5000 行，再 Python 排序/合并 | 独立测传输与物化；不能盲目降低 limit |
| pending 补页 | `binding is not None` 时调用；即使没有待同步项也要判断不存在，当前从 assets 驱动 `NOT READY` 查询 | 30 万既有样本约 359 ms；优化空集判断/反连接/候选入口，不直接跳过补页 |
| 精确 total | `authoritative_page` 执行精确 COUNT，普通语义页也调用 | 复杂筛选计划须测；不能把精确 total 静默改成估计/下界 |
| 标量索引覆盖 | P4-02J 有惰性刷新；维护开始检查后，drain 新增行使覆盖再次不完整 | 已有修复应保留，但“一开始完整”不能保证整个维护期完整；测增量维护周期与查询争用 |
| 前台写入 | `service.py` 在 FTS 查询前 `documents.catch_up`；队列非空时有写事务 | 与后台写入竞争的结构已确认，4/9 拒绝的具体锁来源未确认；先测 commit/checkpoint/写锁边界 |
| HTTP 执行 | `async post_search` 直接调用同步 `search_request`，没有 await/线程隔离 | 静态确认阻塞事件循环的风险；未测并发健康/缩略图延迟。迁移到线程需解决连接、快照与 session 并发，不能只包 to_thread |
| 真模型接入 | `ApiContext` 默认无 encoder_factory；无适配器时诚实拒绝语义通道 | 功能测试可注入适配器，发行闭环仍需核查；P0 真 GPU demo不等于现有 HTTP 真模型闭环 |
| 建库解码 | P0 历史样本解码约 360 ms/图，GPU 推理约 12 ms/图 | 历史线索；要在当前正式导入入口重新分段测。查询瓶颈不能归因于这个建库数字 |
| 调度领取/修复 | P4-02E/F1、P4-02C 恢复与幂等已有收口 | 不追溯当成当前未修缺陷；继续保护 aging/lease/revision |
| 质量 | P0 评测规则标签可复现，但不是人工自然语言相关性标注 | 不能据现有 nDCG直接判断“比手机准确/不准确”；需固定人工标注保留集 |

定位：`src/photo_search/search/retrieval.py::vector_channel/pending_projection_page/authoritative_page`，`indexing/store.py::search_candidates/ensure_scalar_index`，`search/service.py::search_assets`，`search/documents.py::catch_up`，`api/routes.py::post_search`，`api/context.py::query_encoder`。

## 5. 本轮新发现：ANN 的 SDK 能力结论应更正

旧 `tools/diagnostics/ann_scale_benchmark.py:2298` 固定写着锁定SDK的 `LanceQueryBuilder` 无 `nprobes/refine_factor`。本轮核对本地 **lancedb 0.38.0**：

- 通用基类不是实际向量查询对象；`table.search(vector)` 返回 **LanceVectorQueryBuilder**。
- 三行隔离表上，`nprobes(7)`、`refine_factor(3)` 可调用，`to_query_object()` 中minimum/maximum_nprobes均为7、refine_factor为3。
- `bypass_vector_index()` 的精确执行返回[1,2]；`where('id >= 2', prefilter=True)`加精确绕过返回[2]。
- 核验 **5/5**，JUnit：`test-results/search-reevaluation-sdk.xml`；JSON：`test-results/search-reevaluation-sdk.json`。没有建立ANN索引；它证明接口存在/参数传播和精确预过滤可执行，不证明ANN效果或性能。

旧“没有调参接口”的泛化判断不成立，建议新实验纠正测量工具与决策依据。不能推断历史报告一定使用了错误检查代码；可证事实是其文本与当前同版本实际向量对象不一致。旧低召回数值仍是原配置的测量，不能删除或重写为通过；随机合成向量的低召回也不能代表所有真实照片向量。

官方资料也说明nprobes控制搜索分区、refine_factor控制候选精确重评分；最终仍以锁定版本实际执行为准。[LanceDB向量检索说明](https://docs.lancedb.com/search/vector-search)

**建议重新做同引擎内 exact / IVF_FLAT / IVF_PQ 参数曲线**，先核对0.38实际可建类型，记录训练量、度量、分区、probe、refine、索引覆盖、新增数据与真实Recall/延迟。低压缩或不压缩索引仅作实验候选，不预设胜出。不新增第二生产后端、不升级依赖、不把ANN塞入ADR-0012的精确A3证书。

## 6. 必须拆开的两种“准确”

1. **成员/数据正确性是硬约束**：hidden/状态、人物地点时间条件、未确认行、旧revision、模型空间、人工锁与恢复不得错；这不是可用ANN丢失率换掉的内容。
2. **近邻召回近似是质量指标**：ANN相对同模型精确向量排序可有经评测接受的损失；主架构已有Recall@20≥0.95初始目标，并未要求所有自然语言查询逐项等于精确排序。
3. **用户语义相关性是另一指标**：向量精确Recall=1并不意味着搜“孩子在海边骑车”的结果都正确。模型、结构化条件、OCR、融合与用户查询分布都影响结果。

ADR-0012 当前专门冻结的是与完整候选块路径逐项等价的A3快路径，因此不能以ANN≥0.95来代替它的证书。合理的两条路线是：A3保持精确等价做现有P4-02I；ANN另开测量/决策，在明确质量与过滤正确性后再申请产品路线。两者可比较，不能偷换。

P0的ViT-L/14候选在人为规则标签holdout中仅从0.2415到0.2430、显存成本明显增加；此证据不支持为了速度问题先换大模型。它也不是人类标注的语义性能上限。优先保留Chinese-CLIP基线，先分辨候选缺失、排名靠后、OCR错误与错误解析，然后再试升级或20～50候选可选精排。

## 8. 突破路径与顺序

**第一优先：8万/10万/30万同口径重新测检索计划。** 下一张建议卡P4-02L先纠正SDK能力假设，在独立合成表验证ANN参数真实执行，输出同SDK内速度/召回曲线；再用有授权的真向量研究模型分布。缺真权重/授权时记录限制，不声称质量通过。独立于P4-02I的精确等价实验。

**第二优先：保留精确语义的执行优化。** 对pending补页做EXPLAIN、空集/少量/大量待修复对照，测从pending入口驱动的候选与现有assets反连接等价；对块内全序与边界ties测最少返回量；有筛选请求按选择性测路由。语义未变可优化SQL/索引；改变total、补页、缓存或资格定义需另卡与契约裁决。

**并列高优先：可用性与资源隔离。** 为4/9被拒建立第三方写锁、commit和checkpoint计时；测健康API/缩略图与搜索并发。SQLite WAL允许读写并发但仍只有一个writer，checkpoint也是独立成本，不能仅凭开启WAL就假定前台不会等锁。[SQLite官方WAL说明](https://www.sqlite.org/wal.html)

线程池/独立检索执行器、协调写入、维护限速、在批次边界让交互优先是候选；必须验证连接生命周期、快照、取消、会话并发和outbox恢复。不得直接把Lance写移出保护事务，或通过吞掉锁错误假装成功。

**随后：真实模型+HTTP+第一屏验证。** 记录编码排队、GPU执行、SQL、Lance、融合、发布、HTTP和缩略图，统一样本记录避免桶重叠。产品真实worker与API连接是交付项。固定查询、人类相关性保留集，分别报告日常物体/动作/属性、多人、日期地点、截图数字、无相关图、离线来源。

最终仍按§12.2：30万暖机API P95≤1s、第一屏≤2s、后台普通搜索≤1.5s；RTX4060与GTX1660分别记录。8万档是体验诊断而非容量承诺缩水。P50/P95样本量、失败率、回退率、冷/暖、正在写入/空闲分别报告；单次最快和分量相加不构成验收。

**有退出条件的后端决策**：同LanceDB内快路径/SQL/已支持ANN调参都经真实质量、混合负载与Windows恢复测试仍不合适，再写ADR比较“替换一个后端”的收益、迁移、过滤和恢复成本。现在没有证据值得立刻重写项目或增加第二后端。
