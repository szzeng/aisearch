## 发现

1. **[P1] 首页详情的浏览器 Back 丢失原浏览页。**从首页某图库网格点击缩略图进入 `/#/asset/{id}` 后使用浏览器 Back，实际回到来源列表，而不是原网格。`app.js` 的 `handleHash()` 在 hash 不匹配时直接 `showView("sources")`；该导航没有保存或恢复原图库筛选、列表与滚动状态。详情内“返回浏览”按钮本身可以恢复网格；但在人物详情往返后，浏览器 Back 回到照片详情，再点“返回浏览”会把原图库筛选从指定来源重置为“全部图库”。违反主卡关于浏览器 Back 和来源列表状态恢复的验收项。
2. **[P2] 搜索预览没有按 canonical person ID 去重。**`search.js` 先按原始 `assigned_person_id` 建 `unique`，解析 `/persons/{id}` 后把按钮目标转换成 `canonical_person_id`，但没有对 canonical ID 再去重。搜索页把共享组件的 `people` 关闭，因此 `photo-info.js` 已有的 canonical 去重不覆盖该入口；合并到同一人的两个旧 ID 会显示重复人物按钮。
3. **[P2] `has_more` 可能被空页分支掩盖。**共享面板 `renderPeople()` 在 `byPerson.size === 0` 时提前显示“没有已归属的人物”并返回；搜索预览也在 `loaded.people.length === 0` 时提前返回。若前 200 张脸没有有效归属、后续页还有已归属人脸，界面会把“本页未发现”说成“整张照片没有”，且不提示截断范围。`/assets/{id}/faces` 明确可返回 `has_more`，应在空页分支也如实显示范围。

### 对原 canonical 重复发现的更正

再次核对 `/assets/{id}/faces` 的实际实现：`_face_view()` 在返回 `assigned_person_id` 前调用 `resolve_canonical_person_id()`。因此，同一 API 响应中的旧 ID 会先归一成同一 canonical ID；原复核把“不同 assigned ID”当成当前 API 可返回形态，证据不足，应将该项从产品缺陷重分类为**前端防御性去重**。合成浏览器通过两个旧归属指向同一人的真实只读 API 结果确认只显示一个入口；新增 JS 交互测试另行覆盖非规范/别名响应的二次去重分支。
