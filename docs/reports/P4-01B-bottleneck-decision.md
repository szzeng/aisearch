## 2. 决策 1：无过滤全库查询与「每块一次引擎查询」的取舍

**证据（30 万，同一查询，结果完全一致）**：

| 配置 | blocks | 单次搜索 | top-20 与基线一致 |
|---|---:|---:|---|
| 生产默认 `SCOPE_BLOCK_SIZE=1000`，无任何索引 | 300 | **92 195 ms** | 基线 |
| 块 5 000 | 60 | 19 757 ms | ✅ 相同 |
| 块 25 000 | 12 | 7 282 ms | ✅ 相同 |
| 块 100 000 | 3 | 5 466 ms | ✅ 相同 |
| 块 1 000 + `asset_id` 标量索引（BTREE，80 ms 建好） | 300 | 6 618 ms | ✅ 相同 |
| 块 5 000 + 标量索引 | 60 | 3 602 ms | ✅ 相同 |
| 块 100 000 + 标量索引 | 3 | 3 518 ms | ✅ 相同 |
| 块 100 000 + IVF_PQ 索引 | 3 | 2 077 ms | ✅ 相同 |
| （参考）引擎单次**无过滤**全库查询 | 1 | 374 ms | 精确 top-k |

**关键性质**：`vector_channel` 合并的是**每块的 top-k**，任一条全局 top-k 必然落在它所属块的 top-k 里，
所以**放大块大小不改变结果**（上表每行都实测 top-20 完全一致）。这是一次纯参数/索引层修复，不动检索语义。

**候选**：

| 方案 | 收益 | 代价 / 反例 |
|---|---|---|
| A1 只放大 `SCOPE_BLOCK_SIZE`（1 000 → 5 000 或 25 000） | 30 万 92 s → 20 s / 7.3 s，零语义变化，零新依赖 | 每块 SQL 会一次取 5 000/25 000 个 id；引擎过滤表达式变长（约 40 KB/200 KB 文本）。已在 30 万上实测通过，但需要补一个「过滤选择性极低时块内 id 变少」的回归 |
| A2 A1 + `asset_id` 标量索引（BTREE） | 再降到 3.5 s；建索引 80 ms、增量维护便宜 | 多一份派生索引，需要纳入「世代重建/修复」流程；索引缺失时要有确定性的回退（现在是全表扫描，正确但慢） |
| A3 无过滤（scope 恒真）时走一次全局查询 | 374 ms（比 A2 再快 9×） | 语义上需要确认：§9.3 第 4 条禁止「全库 Top-K 后过滤」，无过滤时二者等价；但把它做成「有过滤也走全局」就会违反 §9.3，必须严格限定 `scope` 恒真时才启用，并写清阈值与反例 |
| A4 更高 `top_k`/多路召回顺序调整 | — | 与主架构 §9.2 的 Top 200 起始参数绑定，属于召回质量参数，不是本瓶颈的修复手段 |

**推荐**：**A2**（先 A1 再 A2，两者都作为独立可回退的改动），并把 **A3 作为可选第二优化**交给用户裁决。
理由：A1/A2 结果不变、工程量最小、不新增依赖；A3 收益大但触及「无过滤」判定的边界，需要用户确认后单独测。

**A2 之后仍剩的差距（不要掩盖）**：3.5 s 仍高于 §12.2 的 1.5 s。要进 1.5 s 之内，几乎必然要用 A3 或
更高的 `top_k` 折叠策略，二者都需要用户裁决；本卡不预设。

## 3. 决策 2：ANN 参数与召回承诺

**证据**（P4-01 §3.3 + 本轮）：30 万 IVF_PQ（585 分区/64 子向量）Recall@20 **0.100**；
20 000 行独立新表单变量归因：64→128 子向量把 Recall@20 从 0.229 提到 0.395（clustered）/0.241→0.408
（uniform），分区 39→9 只到 0.276/0.283；clustered 与 uniform 差 ≤0.02；锁定版
`LanceQueryBuilder` 不暴露 `nprobes`/`refine_factor`。

**候选**：

| 方案 | 收益 | 代价 / 反例 |
|---|---|---|
| B1 不引入 ANN，走决策 1 的精确路径 | 召回 **1.000**（已实测），无召回承诺风险 | 延迟仍是秒级；需要保证 A1/A2 的回归覆盖 |
| B2 ANN 仅作粗筛 + 精确重排（refine/候选集内重算） | 有望同时拿到低延迟与高召回 | 需要在锁定版上验证「拿回候选后精确重算」的 API 路径；候选漏掉就无法补救（召回上限由粗筛决定） |
| B3 换索引类型（如 IVF_HNSW） | 可能提升单位延迟下的召回 | P4-01 明确「不得顺手改成另一套 ANN 方案」；换类型必须先在真模型夹具上做对照，属于新的设计/测量轮次 |
| B4 下调 §12.3 的 `Recall@20 ≥ 0.95` 承诺并写 ADR | 立刻消解「达不到目标」的冲突 | 会**缩小产品承诺**：必须由用户裁决并写入 ADR，不能由执行卡自行降低 |

**推荐**：**B1 为主**（先让精确路径变快、保持召回 1.0），B2 作为下一轮候选；**B3/B4 不在本卡**。
同时明确一条未验证项：`Recall@20 ≥ 0.95` 的可行性必须在**真实 Chinese-CLIP 向量**上复测，
本机没有 pinned 权重，合成向量上的 0.10～0.41 不能直接当作真实模型空间的结论。

## 4. 决策 3：索引维护的批量写入与修复审计

**证据（30 万行派生表）**：

| 写法 | 每行成本 | 说明 |
|---|---:|---|
| 每行一次 `merge_insert`（生产当前路径） | **48.87 ms/行** | 20 行实测 977 ms |
| 一次 `merge_insert` 写 500 行 | **0.115 ms/行** | 57.6 ms 写完；**424×** |
| 批量写入整表（夹具物化，生产 schema） | 0.0051 ms/行 | 30 万行 1.53 s（P4-01 §2） |

另外 `audit_and_schedule_repairs` 每资产调用 `LanceVectorIndex.has()`，而 `has()` 走 `rows()`
把整张 generation 物化 ⇒ `O(资产数 × 行数)`（200 资产实测 3 052 ms，30 万行上不可运行）。

**候选**：

| 方案 | 收益 | 代价 / 反例 |
|---|---|---|
| C1 `LanceVectorIndex` 增加批量 upsert（一次 `merge_insert` 多行），`IndexCoordinator` 按批 drain（例如 200～500 行/次） | 维护吞吐提升约 2～3 个数量级；逐事件 outbox 确认语义不变 | 需要明确「一批里部分行失败」的处理：**必须保持逐事件幂等与确认**，批次失败时整批重放（merge 幂等）而不是部分确认；报告要给出「同批重放不产生逻辑重复」的注入 |
| C2 `has()` 改为定点查询（按 `record_id`/`asset_id` 过滤一次）或按 generation 一次性取 id 集合 | 审计从 `O(N²)` 降到可运行 | 需要确认锁定版过滤查询的成本；`rows()` 仍保留给诊断使用 |
| C3 用 `DELETE_VECTOR` 事件补全删除语义 | — | 主架构 §7.4 有 `delete`，但当前没有生产者；属独立加性功能，不在本卡 |

**推荐**：**C1 + C2**。这是三条瓶颈里唯一「改了也不动任何外部契约」的一组（只动派生存储的写路径与
内部审计实现），建议在用户确认后优先实现。

## 5. 决策 4：过滤的 `COUNT(*)` 退化

**证据（30 万，`EXPLAIN QUERY PLAN` + 计时，预算 20 s）**：

| 档位 | `COUNT(*)` | 带 `LIMIT 5` 的分页 |
|---|---:|---:|
| wide（拍摄时间下界，72%） | 375 ms | 12.4 ms |
| half（来源 1 + 城市 1..5 后代） | **TIMEOUT >20 s** | **0.2 ms** |
| narrow（城市 1 后代，10%） | 600 ms | 0.1 ms |
| thin（城市 1 + 人物 1&2 all，≈1%） | **TIMEOUT >20 s** | **TIMEOUT >20 s** |

计划文本已按档位记录在 `test-results/p4-01b-design.json` 的 `filter_plans[].plan`。结论：
**退化的不是过滤谓词本身，而是「为了算 total 而做的整表计数」**；同一条件的
`ORDER BY asset_id LIMIT n` 只要 0.1～12 ms（half 档 0.2 ms）。P4-01 里 `thin` 的分页也超时，
说明该组合还需要单独的解释计划分析（本卡已记录计划，具体改法留给实现卡）。

**候选**：

| 方案 | 收益 | 代价 / 反例 |
|---|---|---|
| D1 `authoritative_page` 的 `total` 改为**有界计数**（例如先取 `LIMIT 1001` 判定 `truncated`，`total` 标成 `≥1000`）或惰性计算 | 消除分钟级退化；语义上必须写清 `total` 的含义变化 | 会**改变响应字段语义**（`total` 从精确值变成下界），属协议面 ⇒ 需要用户裁决 + 可能触发 Sol 聚焦终审 |
| D2 只加索引/改写谓词，保留精确 `total` | 不改语义 | 需要在 SQLite 上真正把该组合的计数计划变好；本轮计划文本是唯一线索，需一轮实现级实验（含 `EXPLAIN` 前后对照） |
| D3 在 API 层对「组合条件」设置超时并返回 `INDEX_UPDATING`/降级提示 | 不做慢查询 | 引入新的错误路径与用户可见行为，属协议面 |

**推荐**：**D2 优先**（先证明能否在不改语义的前提下修好计数计划）；若 D2 证明不可行，再请用户裁决 D1
或 D3，并接受随之而来的语义/协议讨论（那条路必须走 Sol 聚焦终审）。

### 9.1 「300 次引擎查询」问题的量化与修法

根因是 `vector_channel` 的候选分块遍历：`blocks = ceil(候选数 / SCOPE_BLOCK_SIZE)`，而**每块一次引擎查询都要
扫描整张 generation**（无 ANN 索引时），于是总成本 ≈ `blocks × 全表扫描`，即 `O(候选数 × 行数 / 块大小)`。
30 万全库查询 = 300 块 × 全表扫描。

三个独立杠杆（30 万，同一查询，**top-20 与基线逐条一致**）：

| 杠杆 | 配置 | 单次搜索 | 相对基线 |
|---|---|---:|---:|
| 基线 | 块 1 000，无索引 | 92 195 ms | 1× |
| ① 放大块 | 块 5 000 | 19 757 ms | 4.7× |
| ① 放大块 | 块 25 000 | 7 282 ms | 12.7× |
| ① 放大块 | 块 100 000（=3 块） | 5 466 ms | 16.9× |
| ② + `asset_id` 标量索引（80 ms 建好） | 块 5 000 | 3 602 ms | 25.6× |
| ② + 标量索引 | 块 100 000 | 3 518 ms | 26.2× |
| ③ 有 ANN 索引时 | 块 100 000 | 2 077 ms | 44.4× |
| ④ 换成**一次**全局查询（仅无过滤适用） | 1 块 | **374 ms**（精确） | 246× |

**结论**：①②是纯参数/索引层修法，结果不变、零新依赖，合计把 30 万全库搜索从 92 s 降到 ~3.5 s；
④再降到 ~0.37 s，但它只在 `scope` 恒真时与语义等价（有过滤时就是「全库 Top-K 后过滤」，违反 §9.3 第 4 条），
因此必须由用户单独授权并限定触发条件。③不推荐靠它达标（见 9.3）。

### 9.2 filter + vector 的顺序分析

先把「谁能下推到向量引擎」查清楚（30 万，`--mode strategy` 的 `engine_pushdown`）：

| 探针 | 20 000 行 | 300 000 行 |
|---|---:|---:|
| 引擎无过滤扫描（1 次查询） | 24.7 ms | 317～369 ms |
| 引擎内 `array_contains(source_ids, 1)` 过滤 | 27.4 ms | 449 ms（**比不过滤更慢**） |
| `create_scalar_index("source_ids", index_type="LabelList")` | — | **被拒绝**：`Unknown index type LabelList` |

而 `place`/`person`/`capture` 这三类权威条件**根本不在派生投影里**（P2-03 的 Lance schema 只有
`asset_id`/`vector`/`source_ids`/`visible`/revision 等），所以它们只能留在 SQLite 侧，
**不可能**通过「向量引擎预过滤」实现。顺序分析因此收敛为：

1. **权威先行（现状）是唯一正确顺序**：SQLite 决定成员 → 候选 `asset_id` 流按块交给引擎排序 → 合并
   → 回 SQLite 复核。任何「向量先行再过滤」的写法在有条件时都会缺结果，违反 §9.3 第 4 条。
2. **真正的代价不在「顺序」，而在过滤谓词的查询计划**。同一 `--mode strategy` 在 30 万上用
   块 5 000 实测：wide（72%）215 998 候选 / 44 块 / **18 085 ms**；narrow（10%）30 000 / 6 块 / **2 754 ms**；
   而 half（来源 + 地点后代）与 thin（地点 + 人物 all）**连一块都取不出来**（>60 s 被中断）。
   在 20 000 行上更能看清量级：wide 3 块 400 ms、narrow 1 块 62 ms，但 **half 2 块 19 380 ms**、
   **thin 1 块 143 406 ms**。
3. 与 §5 的 `COUNT(*)` 现象合并看：同一条件在不同语句上的表现是 wide/half/narrow/thin =
   `COUNT` 375 ms / >20 s / 600 ms / >20 s、分页 12 ms / **0.2 ms** / 0.1 ms / >20 s、遍历 18.1 s /
   >60 s / 2.8 s / >60 s。也就是说 **`file_locations`（source）与 `face_person_links`（person）
   这两个相关 EXISTS 子查询的计划是共同病灶**：它们让「按资产逐行重扫来源/人物集合」的成本叠加到
   每一条用到该谓词的语句上。
4. 因此顺序分析给出的实际修复顺序是：**先修谓词计划（D2），再谈块大小与索引**。在谓词仍是坏计划时，
   放大块只能救 wide/narrow，救不了 half/thin。

### 9.3 ANN 方案比较：「优化现有检索路径」vs「替换 ANN」

同一夹具、同一查询集、每个方案一张全新表（`--mode strategy --scheme-list`）：

**20 000 行（39 分区，200 查询，clustered）**

| 方案 | Recall@20 | Recall@50 | 查询 P50 | 建索引 |
|---|---:|---:|---:|---:|
| 无索引（精确） | **1.000** | **1.000** | 28.0 ms | 0 ms |
| `IVF_PQ` 64 子向量（现状） | 0.232 | 0.271 | 13.1 ms | 4 299 ms |
| `IVF_PQ` 128 子向量 | 0.408 | 0.433 | 11.3 ms | 8 507 ms |
| `IVF_FLAT` | **0.671** | 0.660 | 11.1 ms | **229 ms** |
| `IVF_SQ` | 0.654 | 0.644 | 10.7 ms | 225 ms |
| `IVF_HNSW_FLAT` | 0.638 | 0.646 | 11.0 ms | 623 ms |
| `HNSW_FLAT` | 0.642 | 0.662 | 10.9 ms | 630 ms |

**300 000 行（100 查询）**

| 方案 | 分区 | Recall@20 | 查询 P50 | 建索引 |
|---|---:|---:|---:|---:|
| 无索引（精确） | — | **1.000** | 300 ms | 0 ms |
| `IVF_FLAT` | 585（默认） | 0.150 | 15.3 ms | 4 353 ms |
| `IVF_SQ` | 585 | 0.157 | 13.4 ms | 3 558 ms |
| `IVF_FLAT` | 16（单变量） | 0.150 | 16.1 ms | 3 847 ms |
| `IVF_SQ` | 16（单变量） | 0.147 | 13.4 ms | 3 400 ms |

**读法（不要过度解读）**：

1. 在 20 000 行上，**换掉 `IVF_PQ` 是明显划算的**：`IVF_FLAT`/`IVF_SQ` 把 Recall@20 从 0.232 提到
   0.65～0.67，且建索引快 19 倍（229 ms vs 4 299 ms）；HNSW 系列同档。
2. 在 300 000 行上，**所有被测方案都掉到 0.15 附近**，而且把分区从 585 降到 16 并不改善
   （0.150 → 0.150）——说明在锁定版里主导因素既不是量化精度也不是分区数，而是**查询实际覆盖到的
   数据比例，而控制它的 `nprobes`/`ef_search` 开关在这个 API 里没有暴露**。
3. 因此按主架构 §12.3 的 `Recall@20 ≥ 0.95`：**本构建内没有任何 ANN 方案达标**；而「优化现有检索路径」
   保持 Recall = 1.000，同时在 30 万上把无过滤搜索从 92 s 压到 ~3.5 s（或 0.37 s，若授权 ④）。
4. 附带结论（供后续索引策略参考，不是本卡建议立刻实施）：若将来确实需要 ANN 加速，
   **`IVF_FLAT`/`IVF_SQ` 应优先于当前 `IVF_PQ`**（同延迟下召回更高、建索引快 19 倍）；
   是否把 ANN 作为默认路径，应等真实模型向量复测后再决定。
