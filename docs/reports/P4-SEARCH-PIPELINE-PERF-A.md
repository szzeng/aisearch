## 诊断覆盖和实现

在 `X-Search-Perf: 1` 请求中新增请求级结构化 `phase_tree`，并保留兼容的平铺 JSON 字段。它将 Worker 排队/连接、地点与意图准备、搜索准备、完整检索、候选转换、重排、会话创建、页面渲染、发布检查、会话注册、响应构造和地点搜索收尾分组；父子计时不重复计入 `non_overlapping_ms`，报告 `unaccounted_ms`、覆盖率及未测的 HTTP 序列化/网络传输。单独提供 place SQL 调用/行数、别名查询、行政映射、OSM/GeoNames 候选和匹配数量；SQLite trace 只数语句类型/读语句数，不保留 SQL 文本。HTTP 传输、缩略图和视口图片就绪沿用浏览器样本指标，与后端 `search_execution_ms` 分开。

计时、SQLite trace 和地点包装只在当前请求启用诊断时运行；普通请求仍不安装详细 SQL trace，也不触发模型解析或推理。新增阶段诊断没有新增 API、数据库迁移、索引/模型调整或额外模型调用。

## 定量瓶颈与修复

合成地点候选数据包含 400 个 OSM 行政区和 5,000 个 GeoNames 地点，每地点一个活动别名，只有一个文本匹配。阶段 A 的三次串行基线为 529.861 / 520.475 / 550.467 ms；中位数 529.861 ms，最大观测值 550.467 ms（仅 3 次观测，不称统计 P95）。其中 5,000 次逐地点别名查询 + 400 次逐行政区映射查询令查询方法总数达到 5,404，SQLite 读取时间合计 537.566 ms。

基于这项具体证据，`places/choices.py` 将别名和行政区映射改成每批最多 400 个绑定参数的只读查询。候选身份、活动数据集/版本、别名 `alias_id` 顺序、行政区优先级和文本匹配规则保持不变；没有新增缓存或 schema 变更。相同规模/数据的最终三次结果为 24.591 / 24.265 / 22.246 ms，中位数 24.265 ms、最大值 24.591 ms；SQLite 读取时间 14.584 ms。查询方法总数从 5,404 降到 18，别名查询从 5,000 降到 13，行政区映射从 400 降到 1。该合成用例的整体候选生成中位数降低约 95.4%，不外推为图库搜索的延迟收益。

测试核对候选 ID 顺序与 Catalog SQL oracle 一致、OSM/GeoNames 列表分界正确、活动和退役别名处理及文本匹配结果；意图计划、地点契约、分页/会话和重排回归共同验证 127 passed、1 skipped。跳过项是可选 OSM 准备依赖未安装，不影响该受影响单元范围。
