# P4-SEARCH-PLACE-NL-A — 地点自然语言搜索分析与任务划分

日期：2026-10-08。状态：**分析与立卡完成 / 功能未实施**。基线：`5d7bc139b2b73de5f30c77fbee9e6a1cc648f108`。
本轮仅阅读源码、文档和相关测试，执行隔离的解析函数诊断，新增方案/任务卡/状态交接。未启动用户服务、读取真实 catalog/照片、加载模型或修改功能代码。

## 1. 用户目标

在“搜索图片”输入日常描述，直接得到想看的照片。例如“在济南拍的照片”应显示当前地点规则下的全部济南照片，而不是只展示地点相册入口，也不是在济南范围内再搜“照片”这个词。个人使用，简单定向测试即可；本轮先分析、划分任务和推荐模型。

## 2. 当前实现及可复现问题

现有 `POST /api/v1/search/place-aware` 已具备地点范围＋内容检索，以及不调用文本编码器的纯地点完整分页。无需重做搜索后端。

| 当前源码诊断输入 | 解析状态 | 实际留下的内容词 | 问题 |
|---|---|---|---|
| 济南 | recognized | 空 | 后端本来能走纯地点分页 |
| 在济南拍的照片 | recognized | 照片 | 通用说法被当成语义/FTS条件，不能保证返回全部济南成员 |
| 济南的所有照片 | recognized | 所有照片 | 同上 |
| 帮我找在济南拍的照片 | 未识别 | 由路由保留原句 | 请求前缀不支持 |
| 在济南拍摄的照片 | 未识别 | 由路由保留原句 | 仅支持“拍的”，不支持“拍摄的” |
| 济南的日落 | recognized | 日落 | 已有可复用正确路径 |
| 日落，在济南拍的 | 未识别 | 由路由保留原句 | 地点后置不支持 |
| 在 济南 拍的 日落 | recognized | 拍的 日落 | 匹配去空白，截取却用原字符串下标，内容错位 |

定位：`src/photo_search/api/routes.py::_place_aware_parse` 只识别纯名称、`地点的…`、`在地点拍的…`。词法规范化与内容截取使用不同坐标。两份同名候选诊断中，`济南的日落` 返回 ambiguous 且 content=None；页面选定地点后发送空内容，原本的“日落”会丢失。

诊断方式：用项目 `.venv/Scripts/python.exe`、`ast` 从当前源码抽取原函数，用内存假 catalog/假省份索引/假 CN choices 调用；没有导入应用或接触数据库。UTF-8重跑退出码0，得到上表；这是解析诊断，不是API/浏览器/产品测试PASS。首次输出编码不正确，未作为证据，UTF-8重跑已纠正。

页面同时加载 `search.js` 与 `search-place-entry.js`：

- 主搜索已经提交 place-aware 请求。
- 旧入口脚本把输入的整句话用于 city/province/district/country 四次相册名称查询；因此裸地名易命中，整句通常不命中。
- 旧提示仍写“地点相册入口（不改变普通搜索）”和“普通搜索仍按原规则执行”，与主路径不一致；该脚本还缺少输入变化后的响应资格检查。
- 搜索表单直接暴露 place_id、地点状态、包含后代等内部筛选，主提示强调有限表达式，缺少贴近日常用法的例句。

用户当前服务是否加载最新源码、实际活动地点包/人工地名别名是否齐全，本轮未核验。以上能证明源码问题，不能断言正在运行的页面只存在这些问题。实现后需记录合成服务加载的资源版本；真实运行需用户重启并刷新确认，不能在规划阶段归因于缓存。

## 3. Google 相册参考与本地取舍

Google 官方搜索帮助把人、内容和地点作为同一搜索框的描述条件，例如地点＋日落的短句；官方介绍也强调日常语言搜索和直接找到图片。[搜索帮助](https://support.google.com/photos/answer/15235862?co=GENIE.Platform%3DDesktop&hl=en)、[官方介绍](https://blog.google/products-and-platforms/products/photos/google-ask-photos-early-access/)。

借鉴其“输入描述→照片结果”的主流程。Google 的 Gemini Ask Photos 是另一个较复杂的体验，[官方说明](https://support.google.com/photos/answer/15318661)；本项目本次复用本地地名目录、规则解析和已有图文检索，不引入云、查询LLM或新模型。目标是常用地点描述可自然使用，不承诺任意对话、视觉推断拍摄地或回答照片中的事实。

## 4. 推荐的最小产品行为

| 输入示例 | 地点 | 内容词 | 结果 |
|---|---|---|---|
| 济南 / 济南的照片 / 在济南拍的照片 | 济南 | 空 | 当前济南成员全部可分页浏览 |
| 找一下在济南拍摄的所有照片 | 济南 | 空 | 同上 |
| 济南的日落 / 在济南拍的日落照片 | 济南 | 日落 | 济南范围内的相关照片 |
| 帮我找济南拍的夜景 / 济南 夜景 | 济南 | 夜景 | 同上，识别完整地点边界 |
| 日落照片，在济南拍的 | 济南 | 日落 | 同上，支持明确后置拍摄地点 |
| 山东省济南市拍的照片 | 山东省下的济南市 | 空 | 仅用实际目录父链消歧，不创建新地点 |
| 西湖区拍的照片 / 在杭州西湖区拍的日落 | 唯一或父链限定的西湖区 | 空 / 日落 | 复用已安装CN facet；真正同名时选择 |
| 日落 | 无 | 日落 | 原有普通搜索 |

通用“照片/图片/所有照片/帮我找”等只在已确认句式的请求框架中移除；不能全局删词。比如“老照片”“照片里的文字”“济南路上的夜景”“巴黎风格的房间”都不能被删坏或误设城市条件。否定、多地点、无可靠数据的景点/相对位置表达不默默抽取一个肯定地点；保留原文并给简短提示，明确尚未形成地点筛选。地点＋人物/时间继续通过现有显式筛选；本卡不新增自然语言人物、日期或多地点布尔解析。

地点为空结果时保留“地点：济南”条件和明确的空状态，由用户点击取消/放宽；不能偷偷全库补图。纯地点路径不调用编码器、不受语义Top5000限制；“全部”指当前权威成员与显式筛选的交集，不包括地点未知或被人工取消的照片。GPS附近城市仍诚实标来源；已安装的CN行政包继续走自己的成员规则，旧库不会因改解析器就自动获得行政区数据。

## 5. 任务划分与模型

**只生成一张可独立验收的功能卡：[P4-SEARCH-PLACE-NL-A](../tasks/P4-SEARCH-PLACE-NL-A.md)**，内部按顺序做三个工作包：

1. **解析与查询计划**：通用说法归一、地点前置/后置、父级消歧、保留内容和原句、负例保护；复用现有地点候选和搜索接口。
2. **搜索页面体验**：提交后直接显示照片网格；移除旧的并行地点入口提示链，保留导航里的地点浏览；可取消chip、歧义选择、空结果与重新搜索清楚可见，地点内部字段收进高级条件。
3. **个人小样本收口**：20～30张合成资产，定向pytest/JUnit、实际JS行为、一次真实浏览器闭环、Ruff/Node/diff-check；达到可用后结束。

这三个包共同组成“说一句话→看到照片”的闭环，不拆成契约/后端/页面三张独立卡。自然语言时间/人物、任意聊天、多地点否定逻辑、新模型和性能专项均后置，本轮不生成这些卡。

推荐 **DS-H：DeepSeek V4.1 Flash / 高推理**，由用户在Codex手动选择，同一会话完成实现、修复及验证。它需要同时理解解析、API和页面状态，不宜当作单纯文案小修交给低推理档。

用户本次再次明确个人使用/简单测试，沿用V3.1 §9.3个人组合搜索边界；不默认独立审查卡、全量套件或Sol终审。若实现必须更改稳定ID/人工控制/包激活/搜索revision协议等高风险边界，应缩回本卡方案并记录冲突；确需新增范围才按§2.4/§11独立DS-H受影响面主审，再由Sol high聚焦未决不变量。当前没有DeepSeek max升级证据。
