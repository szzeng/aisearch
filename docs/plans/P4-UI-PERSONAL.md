## 2026-10-13 UI 2.0 规范优先级

最新明确需求是**整体 UI 和统一照片时间轴一起改造**，权威设计为 [P4-UI-TIMELINE-V2](P4-UI-TIMELINE-V2.md)。新时间轴 UI 默认**可信拍摄时间 + 按日分组**，可切换入库时间及日/月/年；年/月**筛选**与**直接定位**为两个操作，连续滚动自动续页、失败手动重试、查看照片关闭返回原日期/位置。人物相册、人物合集、地点相册复用普通照片组件，待整理脸和批量管理保留工作流。旧 API `time_desc/capture_desc` 语义不变。原九张图片未画时间轴，仅作为外壳/配色参考；原“禁止时间轴”“零后端变更”仅对纯视觉卡继续有效，新 CORE/必要只读适配卡明确例外。不对用户真实图库做任何操作。
## 1. 需求与证据范围

参考会话「整理UI优化方案」能读取到的需求：现有入口和使用逻辑混乱；希望更像个人相册；部分借鉴谷歌相册，但面向个人使用。本次补充要求：方便为主、清新、核心代码和接口改动小。

引用会话的助手回复在读取工具中只返回内容引用占位符，没有可核对的完整方案；不把它当作已确认设计。下面的判断来自当前 HTML/CSS、前端调用链、API 路由、已有测试及项目策略，不是对真实运行页面的现场诊断。本轮未访问用户服务或真实照片。

借鉴的方向是照片优先、固定导航、搜索容易发现、整理操作贴近照片。具体布局为本项目设计；不引入分享、云备份、回忆推荐、自动故事或第二套相册数据模型。

## 2. 当前问题与可复用能力

| 当前证据 | 对个人使用的影响 | 优化方向 |
|---|---|---|
| `web/app.js::handleHash()` 无详情路由时 `showView("sources")`；首页六个混合入口 | 打开先面对来源和分析，而不是照片 | 已有照片时默认浏览；没有来源时提供添加入口；管理留次级入口 |
| 五页各自写导航，地图页只有返回图库，搜索/地点混入页内工具锚点 | 到另一页后导航位置、名称和返回逻辑都变 | 五页使用相同主导航和当前页标记；页内工具与主导航分开 |
| `index.html` 浏览页展示长时间语义说明、资产编号排序 | 信息密度偏高，常用筛选不突出 | 默认照片网格＋图库和排序；技术说明、少用条件折叠 |
| 搜索已有单输入框、条件标签、高级条件折叠，但前后仍有长技术说明 | 基础交互已经可用，视觉上仍像工具表单 | 强化已有输入框与可取消标签，精简首屏；不重写搜索 |
| 人物已实现个人相册、合集、待整理、隐藏/恢复及多页选择 | 有可用流程，重新开发容易破坏已修复行为 | 整理现有按钮层级，保留实现；不另造人物页面 |
| 地点相册和目录/地名包/批量操作/日志同时展开，暴露 `place_id`、`expected_revision` 等 | 看照片和管理地名混在一页，日常难以判断从哪开始 | 地点相册为主，地图为页内切换；原管理工具统一折叠 |
| `places.js::boot()` 加载地名包、目录和操作历史；搜索覆盖率已经按点击加载 | 折叠 UI 与减少后台请求是不同工作 | 首批只改入口；不把已有按需加载重新包装成新性能成果 |
| 详情已有 `AIPhotoInfo.render/open`，首页/搜索/人物/地点各保留自己的打开与返回流程 | 信息组件已共享，统一查看状态机将扩大风险 | 先统一视觉、按钮与说明位置；沿用各页原有导航/恢复逻辑 |
| `styles.css` 已有色彩变量、系统字体及暗色；`map.css` 单独硬编码样式 | 不需要另建 UI 技术栈，只需收敛已有样式 | 扩展既有变量，地图接入共同外观，保留地图容器尺寸与 resize |

## 3. 日常入口与页面结构

桌面：固定左侧导航，顶部搜索入口，右侧为照片内容。窗口变窄后导航改成紧凑横排，搜索另占一行；不用 hover 才能访问的菜单。

```text
我的相册                     [ 搜索照片、人或地点…… ]
│
├ 照片                       全部图库 ▾   最近加入 ▾   筛选
├ 人物                       照片网格 / 当前筛选结果
├ 地点
│                            点击照片 → 查看 → 关闭/返回原位置
└ 图库管理                   地点页内部：地点相册 | 地图
```

| 用户看到的入口 | 复用的页面/路由 | 主要内容 |
|---|---|---|
| 照片 | `/`，仍是 `index.html` | 现有浏览网格、来源筛选、排序、照片详情 |
| 搜索 | `/search` | 全局搜索框进入该页，现有查询与结果；搜索不再挤在工具导航中 |
| 人物 | `/persons`；保留 `?person_id=...` | 常用人物、未命名人物、已有合集；「整理一下」为次级操作 |
| 地点 | `/places` | 地点相册；进入照片、返回地点列表；「地点相册 / 地图」局部切换 |
| 地图 | `/map`；保留 `?asset_id=...` | 当前范围照片、已存在的聚合和地图返回状态 |
| 图库管理 | `/?view=sources`，计划新增的前端视图参数 | 现有来源卡、新增来源、建库/增量刷新；高级分析与维护折叠 |

`/?view=sources` 是拟采用的前端视图选择，不增加后端页面或业务 API。旧 `/`、`/#/asset/{id}`、人物和地点相册深链、地图聚焦链接仍有效。实施时详情深链和已有返回上下文优先于首页默认视图；未知参数安全回退。不会用“统一导航”清空已有筛选、游标或选择。

不新增泛用「相册」页：目前可用的来源图库、人物合集、地点相册已经足够。也不建立一个空「设置」页收纳尚不存在的升级/备份功能。现有设置能力只在原有真实入口中整理。

全局搜索是导航到已有搜索页的薄入口；不在首页执行第二套解析/检索。A 卡先提供固定可见的搜索入口；C 卡才增加文字跨页交接，只传查询文字，空输入直接进入并聚焦原输入框，沿用既有提交流程且只提交一次。人物相册内部搜索继续限制在当前人物，不被全局搜索覆盖。

## 4. 页面上的具体取舍

### 照片与图库管理

- 新时间轴默认拍摄时间/按日（可切换入库时间）；旧 `time_desc/capture_desc` API 排序含义不变。
- 照片占主要空间。图库筛选、排序、筛选展开按钮同一工具栏；资产编号排序移入高级区域。
- 正式实现日期分组、年/月跳转和筛选、滚动自动分页，失败保留手动重试；不能从当前页生成全库时间统计或前端全库排序。
- 照片缩略图本身可以打开详情。多选模式下点击的含义明确；普通浏览不把单击变成选择。
- 无来源：显示「添加照片文件夹」；有来源但未建库：显示来源与「开始建库」；已有照片但当前筛选无结果：显示「清除筛选」。这三个状态分开。
- 来源卡主操作是「看照片」与当前实际可执行的「开始建库/刷新」；改名为次级按钮，移除来源收进更多菜单，并明确只移除记录、不删除照片。
- 常用管理不藏太深，所有技术明细也不占首屏。暂停/恢复仅展示已有 API 真正支持的动作。

### 搜索

- 一个明显的输入框，下面放两个短例子；时间/人物/地点的已识别条件仍可单独取消。
- 首屏显示查询、条件与照片结果；常用筛选入口清晰；复杂 any/all、来源状态、地点技术条件保留在高级筛选。
- 「以图搜图」作为明确的次级入口，保留现有上传流程。必须提示它不支持当前人物/拍摄时间筛选；不声称与文字搜索条件完全一致。
- 搜索覆盖率保留按点击读取；算法口径、分数解释收进「搜索说明」。不把向量距离、覆盖率、高度匹配数改成准确率。
- 查询失败保留输入；缺编码器显示功能暂不可用；无结果给清除条件入口。过期会话、结果上限与需要重新搜索的提示不被隐藏。
- 搜索→预览→人物相册→浏览器返回，保留原条件、结果页与滚动；沿用既有快照，不另造会话系统。

### 人物

- 人物列表以头像、名字/未命名、唯一照片数为主；保留现有照片数排序、准确分类数量与合集。
- 「人物」与「整理一下」层级分明；「已忽略」放在次级入口，恢复可以找到。多页选择保留，不因新的工具栏刷新回首屏。
- 人物相册标题区保留常用取名、封面；合并、拆分、识别维护收进可见的次级入口。
- 当前新建人物已有用户指定的同会话工程复核与 F1 修复，真实少量试用待确认；不要求为 UI 重开旧复核。UI 优化保留「仅这张脸」「不支持撤销」的含义，不把创建包装成可撤销操作。
- 机器建议依旧是建议；展示简洁不等于自动确认、自动合并或扩大人工归属。

### 地点与地图

- 默认呈现城市地点卡，现有省/区县/国家切换保留；地图作为地点页内部同层入口，地图页也能返回地点相册。
- 无 GPS、没有地点包、没有当前范围照片分别提示；缺数据不显示假的城市卡或成功状态。
- 目录、地名包、创建/改名、建议批量操作、历史保留在「地点工具」内。本批仍使用现有按名字选择真实来源的流程。
- 不改同名消歧、OSM/GeoNames/CN 身份、不按名称合并地点，不改人工优先与恢复自动语义。
- 地图点不从照片网格当前页生成；保留 map API 的成员版本、聚合、范围查询和加载更多。

### 查看照片与反馈

- 各页照片查看统一为大预览、稳定关闭按钮、可展开的照片信息；详情按 `contain` 显示完整照片，长图与竖图适配窗口。
- 只在既有页面导航支持时展示上一张/下一张；本批不扩展地点/地图的跨页导航，也不合并查看器状态机。
- 信息面板保留分辨率、时间真实来源、文件位置、人物与地点入口；一次只展开当前照片的信息，不批量读取原图。
- 打开、关闭、Esc、键盘焦点和滚动返回一并验收；异步旧请求不得覆盖新的照片，地图组件关闭后释放。
- 正在保存、已保存、失败、冲突、可撤销/不可撤销各用短而准确的反馈；关键失败不只显示一闪而过的 toast。

## 5. 清新的视觉约束

延续现有系统字体与色彩变量，推荐亮色首轮：浅灰白背景 `#F6F8FA`、白色内容、深灰文字 `#25323D`、柔和青绿强调 `#238477`、浅青绿选中背景 `#EAF5F1`。色值是设计起点，实施时核对文字/按钮对比度；不以低对比度换清新感。保留系统暗色支持，不新增主题设置协议。

- 8/12/16/24 px 间距节奏；正文约 14–16 px；标题 20–24 px；主导航宽约 184–208 px；卡片圆角约 10–12 px。
- 每一区域一个明显主动作，其余用次级按钮/更多；危险动作不混入普通主按钮。
- 照片网格缝隙约 8 px、少边框、少阴影；缩略图允许裁切，详情显示完整照片。
- 图标带文字，使用已有/本地 SVG 或简单 CSS；不用 CDN、外部字体、远程示例照片或新的图标包。
- 桌面先验 1440×900 与 1024×768；小窗口再验 640 px 宽及 200% 缩放。错误、焦点、选中均可通过文字/轮廓区分。
- 不引入复杂动画、CSS框架、前端构建链或移动App，继续纯 HTML/CSS/JS；只在真实性能证据要求时增加局部区块回收，不强制复杂虚拟化。

## 6. 代码与接口预算

分层接口边界：**A/C 等纯外观改动仍零业务接口；CORE、必要地点日期查询及 SEARCH-MAP 可以扩展最小、有界、只读 API；原识别、搜索排名、身份/人工写协议、任务状态真值保持不变。索引/schema 修改必须有 SQL 证据、兼容设计和升级验收。**允许前端 DOM、样式、文案、薄视图路由与对现有行为的绑定；保留原 request_id、revision、CSRF、游标及操作日志路径。

| 改动类型 | 首批处理 |
|---|---|
| 色彩/布局/导航/文案/折叠区域 | 直接使用 `web/**` |
| 首页默认浏览、全局搜索的薄入口 | 前端限定修改，验证深链和返回；不重写请求层 |
| 既有写按钮换位置 | 保留原 DOM ID 与事件路径；验证请求和动作没有改变 |
| 年月直接跳转及真实统计确实缺少只读能力 | 由 CORE 等限定范围新增权威只读查询，禁止用本页前 50 张推算全库 |
| 清理巨大 JS、合并 API helper、统一查看状态机 | 暂缓；除非当前卡无法用局部变更实现，才说明最小例外 |
| 框架迁移/模型/任务调度/真图库重跑 | 不在 UI 本轮；仅有查询瓶颈证据且满足兼容/审查门槛时才单独考虑必要索引迁移 |

共享样式避免全局宽泛选择器；新增变量复用现有 `--fg/--bg/--panel/--accent` 等。主导航可先在五份 HTML 中维护相同短片段，不为消除几行重复引入模板系统；原脚本负责原页面的能力门控。若引入一个极薄公共脚本，必须确有必要、单次初始化、不接管业务状态。

> **大图库优先更新（2026-10-13）**：全部照片/人物/地点/搜索均按20万以上照片实际使用设计，30万做关键退化检查；拍摄日期未知独立按入库时间倒序，不实施手动修改、推断或回写拍摄时间。按 [统一时间轴§3.1](P4-UI-TIMELINE-V2.md) 测定向元数据/API/DOM 性能，旧“小库即可”的验收口径作废。

## 8. 执行、验证与复核策略

实现按 V3.1 实际风险拆卡：视觉 A 级；时间轴只读权威筛选/游标按对应 B 类受影响面复核。**20万以上时间轴/地点/搜索性能属于CORE/B/D/E/SEARCH-MAP各卡的必要专项验收，细则见 [UI2规范§3.1](P4-UI-TIMELINE-V2.md)**；一份复用20万元数据夹具+30万重点复核，不跑大规模真实图。每卡：相关现有/必要新增行为测试＋Node 语法＋相关 Ruff＋diff-check＋小型合成浏览器人工观察。浏览器用项目内 `.tmp/{ID}` 隔离数据与服务；建议 20～40 张合成照片，分页关键场景用两页；不默认启动全仓、模型、GPU、完整30万搜索容量或打包；**不得省略20万元数据级定向SQL性能和30万重点回归**，没测必须 PERF_PENDING。

## 9. 模型建议

原稿 UI 设计曾建议 **GPT-6.1 Sol / High**；2026-10-13 新规划建议复杂日期分页/状态使用 **GPT-6 / High**，纯文案可 Medium：入口重组需要一起理解五页、旧深链和返回上下文。纯文案/CSS 卡冻结范围后可选 **GPT-6 Luna / Medium**，复杂前端状态仍用 Sol High；无需默认 Astra/max。选择属于本次任务建议，不修改项目默认路由。

OpenAI Docs 将 GPT-6.1 Sol 定位为复杂编码的平衡选项，GPT-6 Luna 定位为聚焦任务的高效率选项；High 是推理档位，不是 Luna 的别名。[官方模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.1-sol)、[Luna 模型说明](https://developers.openai.com/api/docs/models/gpt-6-luna)。这支持模型类别区分；是否能做出满意界面仍应按本项目截图与交互验收。

独立工程复核保持项目 **DeepSeek V4.1 Flash / High（DS-H）** 建议；只有 V3.1 §2.2 已证实条件才升 max；高风险冻结/未决事项才用项目 C2 **GPT-5.6 Sol / High** 聚焦终审。所有选择由用户手动切换，不自动分派代理或轮换模型。
