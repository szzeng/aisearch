# 人物搜索与整理：个人使用简化方案

日期：2026-10-03。状态：**设计与代码调查完成；产品未修改，效果未验收**。

依据用户反馈：人物搜索、整理不方便；照片有很多脸却没有人物结果；怀疑阈值过高。默认使用逻辑是先找到熟人照片，偶尔整理，而不是维护一套人脸数据库。示例中的“爸爸/妈妈”是占位名字，用户可以使用任何名字。

调查与原始证据：[调查报告](../reports/P4-PERSON-UX-investigation.md)。唯一下一执行卡：[P4-PERSON-FACE-A](../tasks/P4-PERSON-FACE-A.md)。首页 P4-HOME-UX-A 保持原验收状态，本方案不覆盖其未提交改动。

## 1. 借鉴 Google 相册的使用逻辑

Google 官方帮助说明了这些流程：点人物头像查看照片；给分组加名字后按名字搜索；同一人分成多个组时合并；错误照片可以从人物组移除；照片详情可以修正已检测人脸的归属。

来源：[Google Photos — Set up & manage your face groups](https://support.google.com/photos/answer/6128838?co=GENIE.Platform%3DDesktop&hl=en-GBanswer%3D2716471)，2026-10-03 查询。借鉴其交互，不推断其模型、阈值、训练方法或准确率；它提到的服装/时间辅助归组不纳入本项目第一版。

本项目的核心体验：**点头像看照片 → 顺手取名 → 对少量疑似照片点“是/不是”**。内部 ID、revision、assignment、数据库和游标说明退出日常界面，仍由程序与服务器使用。

## 2. 只保留两个主要入口

### 人物

- 首页/搜索页有“人物”入口；进入后自动加载头像网格，不要求点“加载”。
- 上方只有“搜索名字”和“整理人物”。默认展示已命名人物，卡片只显示头像、名字、照片数。
- 点头像直接进入此人的照片相册，照片按拍摄时间浏览；拍摄时间未知的照片明确放在未知时间段。照片数按 asset_id 去重，多个文件位置不能重复计数。
- 尚未命名时直接展示未命名分组，并提示“点头像，给认识的人取个名字”；不展示一个没有用的空白已命名页。
- 第一版先按既有稳定分页展示；常用人物排序是后续可选体验，不能在客户端只对一页排序却宣称全库排序。名字查询必须是服务端有界检索，不能只筛当前页。
- 不新增收藏、亲属关系、宠物识别、智能推荐或设置面板。

### 整理人物

仍在同一个人物页面，进入后显示三个自然语言分类，不把内部状态混在一起：

| 分类 | 内容 | 常用动作 |
|---|---|---|
| 取个名字 | 已形成的未命名人物分组 | 命名；并入已有的人 |
| 确认一下 | 无有效人物归属、有机器建议的脸 | 是这个人；选择别人；先跳过 |
| 还没归类 | 无有效人物归属、无可用建议的脸；人工移除的脸单独标记 | 选择人物；查看原照片 |

重检测映射待确认另设“识别更新待确认”提示，不能混成“是同一个人”的普通建议；它会转移人工知识。没有记录就不占主界面。

“先跳过”第一版只让本次整理继续，不能冒充永久忽略。“人工移除”一直保持手动状态，后台不能自动把它归回来。低质量脸仍要可见，显示“脸较小/不清楚，需你确认”；不让低质量样本成为自动归组代表。

## 3. 五个日常操作

### 找一个人

人物 → 点“爸爸”头像 → 直接看到爸爸照片。最多两步进入照片，返回保留列表、滚动和已选人物。

相册里保留普通搜索框，选择人物后搜索“海边”，表示爸爸 + 海边，人物条件作为可取消 chip；清除文字仍是爸爸相册，移除人物 chip 则回到全范围内容搜索。

多人筛选用头像选择，按钮写“同框 / 任意一人”，复用 all/any 权威关系语义；不要求填写人物编号。组合搜索复用当前搜索的时间/地点/来源边界。

### 起名字

点未命名头像 → 输入名字 → 保存。旁边展示该组几张样本，用户知道自己在命名谁；不是在另一个页面填 person_id。

输入已有名字时展示已有人的头像和照片数，询问“并到这个人？”并说明可撤销；用户可以取消或换名字。不能靠前端预查保证同名不会误合并：现有 PUT name 在事务内自动执行同名合并，预查之后仍可能发生并发重名。落地此确认流程前，必须裁决一个服务端事务内校验的命名意图约束；保持旧客户端兼容，不把 UI 预查写成已解决。

### 同一个人分成两组

在未命名分组点“并入已有的人” → 按头像/名字选目标 → 确认一次。多个组可批量选中后一起并入，复用既有原子合并接口；不输入目标 ID，不逐组循环提交制造半完成结果。

### 某张照片里认错人

人物相册选照片 → “不是这个人”或“改为其他人”。合照有多个脸时，显示裁剪头像与原图预览，让用户选清楚要修改的脸；默认只定位本人物的成员脸。

提交仍精确到 face_id；同图妈妈、孩子不被连带修改。同一照片若还有另一张有效的爸爸人脸，它仍属于爸爸相册，这时明确解释保留原因。

普通照片详情也显示“照片中的人物”裁剪头像，点头像修改。当前详情没有该完整投影，要补按 asset_id 获取当前有效人脸的受保护只读入口；第一版不向浏览器暴露 bbox/landmarks。

### 看不出来的人

显示该脸的裁剪头像、对应原图和建议人物头像。点“是”后走人工指定接口，点“选择别人”走人物选择器；机器建议不直接进入已确认相册。

“不是”必须区分：仅跳过不写库；若用户要求以后不建议此人，需要独立定义排除动作，不能用现有 unassign 偷偷表达。第一版提供“先跳过”，不伪造长期学习能力。

所有完成通知显示“已保存 / 已合并 / 已移除”和“撤销”。复杂冲突只提示“人物信息已变化，请刷新后重试”，保留当前输入与选择；后台继续使用幂等和 revision，失败不能显示成功。

## 4. 人物相册是普通照片相册

- 默认展示整张照片网格，不把裁剪脸列表当作照片相册。详情复用首页正在修复的预览适配。
- 人物相册纯浏览不能依赖语义模型是否就绪，不能被语义 Top-K 截断；需按权威成员集合做有界分页。已有 search person filter 可用于内容搜索，但不能未经核对就用它代替不限 Top-K 的人物照片浏览。
- 相册顶部是头像 + 名字 + 照片数；更多菜单只放改名、并入、最近操作。
- 头像先用既有服务端代表图，缺图有占位；换头像并非当前核心闭环，不为它引入额外写契约。
- 整理前后的数量必须来自有效成员关系，建议数、人脸数与照片数分别表述，不用虚构计数。

## 5. 漏识别先修正确性，再测阈值

已复现的首要缺陷：原图长边 >1280 时，analyze_image 写出的 scale 大于 1，而产物校验只接受 [0,1]，extract_for_asset 会在保存前报 ARTIFACT_INVALID。原图坐标还原也用了相反缩放。详见调查报告；此缺陷应先修，降低阈值不能绕过它。

然后按三层区分：

1. **没完成分析**：未开始/排队/失败/模型不可用/离线/保存失败，显示对应状态与有界重试入口。成功处理且无脸才能显示“未检测到人脸”。
2. **没有检测到脸**：SCRFD 检测画布 640，检测门限 0.5；大合照中的小脸被缩小可能漏检。提高有界检测分辨率或重叠分块是候选方案，不宣称现有 ONNX 图支持任意尺寸。
3. **脸已检测但未归组**：工作栅格长边 1280，脸短边 <48、模糊度 <24 或检测分 <0.65 判 LOW；相似度 0.29～0.56、相近人物分数差 <0.08、同图冲突只给建议。这些脸要进入整理入口。

阈值不是一个滑块。当前自动归组门限 0.56 的校准只用 8 个公开身份及合成变体，不能证明个人图库、年龄变化、侧脸都适用。先修产物错误、补待整理可见性，再用小样本区分具体失败阶段。

若样本证明检测门限确实漏掉可辨认的人脸，可离线对比现值 0.5 与试验值 0.4/0.35；这些值只是实验条件。记录人工标注的人脸数、漏检、误检、低质量数、错归组与耗时。若主要问题是归组碎片化，再测相似度门限，不能把降低归组门限当成增加检测数量的方法。

先用公开/合成照片；真实样本需用户明确指定授权的小批照片，默认约10～20张，含合照、侧脸、小脸。同人对必须包含不同拍摄时刻，不能只复制同图或用同图变体充当个人准确率验证。禁止自动扫描/重建全库。

## 6. 落地顺序和停止点

1. **唯一下一任务 P4-PERSON-FACE-A**：修长图缩放/坐标及产物校验失败，验证小型合成端到端；严格保持人工知识与人脸身份版本纪律，不改检测/归组阈值。
2. 然后落实人物 UI：头像进入照片、命名/并入/单脸更正、完整待整理入口。补有界只读 API；命名意图的最小写契约先裁决。保留现有人工锁、排除、合并、撤销，不用前端简化掩盖后端行为差异。
3. 只有小样本仍证明漏检时，继续有界检测召回改进与阈值校准；不自动换模型，不下载大模型，不把“重新检测”包装成无成本刷新。

个人验收用一次完整流程：打开人物 → 给一个分组命名 → 查看照片 → 并入同人的另一组 → 从合照移除/改正一张脸 → 确认一张疑似脸 → 撤销 → 刷新后结果保持。后台验证按实际改动风险匹配 V3.1，JUnit 保留；本次设计不声称已经通过上述验收。

本次只完成方案、代码调查、无模型合成反例及交接。未修改产品、阈值、schema、依赖、真实库，未完成独立审查或真实识别率评测。
