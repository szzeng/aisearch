# 性能设计与验收规范

2026-10-18 生效。适用于后续新任务及再次激活的旧卡；不追认历史性能 PASS。目标是在设计时限制重复工作和资源成本，并用可复核证据阻止退化。性能结论始终限于已测场景、数据、设备和版本，不能保证所有真实图库永远达到某个延迟。

## 2. 个人库默认：三行检查，按需展开

普通功能和局部小改的任务卡默认只写三行，不要求先做性能研究或填满八个字段：

用户直接安排任务；执行者从 `AGENTS.md → development-status → 当前任务卡` 读取并应用这些教训，负责补本次短设计。无需用户手工改卡或重复提醒，旧卡不批量重写。

- **链路与风险**：这次哪里可能重复查询、处理整库、阻塞首屏或增加缓存/后台成本？无相关影响就写理由。
- **做法与边界**：选择最简单且能保留结果/人工状态的方案；说明只处理本页/候选还是确需全局工作，复用已有预算，不为每个按钮编造毫秒指标。
- **验证与停止**：列本次必要的定向测试、关键浏览器流程和可复用证据；已有卡顿或事前检查提示显著规模风险时才补测，满足本次功能与可接受体验即停。没有容量验收要求就注明“不新增规模性能结论”。

例如：“相册第一页有逐图附加查询风险；复用原全局排序，仅批量读取本页60张投影；验分页/人工状态及一次进入返回流程，未见卡顿即收口，不新增30万延迟结论。”实际出现慢点、改变共享/全局热路径、引入缓存/并发或需要容量承诺时，再按受影响项展开下面清单；它是查漏参考，不是每卡必填表：

1. **分级与理由**：按下一节选择验证范围。
2. **用户链路**：一个主要操作，从请求/排队到用户真正能使用结果；分清首屏、续页和后台。
3. **数据形状与工作边界**：图库资产数 N、本次候选数 K、页大小 P、人脸/位置/合集扇出、匹配密度；本次工作随哪个量增长。写明查询/请求、解码、内存、批次或并发的必要上限，以及仍需全局扫描/聚合的步骤。
4. **预算与来源**：沿用产品门槛或现有可信基线，写对应指标与允许退化边界；新链路先确定可接受预算。未知延迟可先做有界预实验再冻结门槛，不能看完最终结果后放宽以求 PASS。
5. **方案与正确性**：为何选择该访问路径；保留哪些成员、排序/游标、人工状态、身份、恢复及质量不变量；涉及缓存须列失效边界。
6. **验证与证据复用**：列定向测试、性能入口/数据、基线身份、需重测范围和真实浏览器要求；说明是否触发全量。
7. **审查**：按 V3.1 §2.4 确定方式；审查者检查本任务全部变化及性能设计与证据是否一致，不只看函数是否返回正确值。
8. **停止点**：达标条件、实验范围及遇到架构/数据语义变化时的收口方式；必测项缺失不得 PASS，不自动追加新的优化卡。

纯文档可压缩为 `PERF-N/A + 无运行时变化的理由 + 文档核对`。只有本卡明确验收的性能指标才需事前确定门槛；未知成本可在同一卡先做小实验，不能要求每项普通功能先建立SLA或基准平台。个人使用不追加正式发行/最低设备验收，原卡已有明确必测和数据安全要求仍保留。

## 3. 按风险选证据，避免每卡都跑大矩阵

| 分级 | 适用情况 | 必需证据 |
|---|---|---|
| PERF-N/A | 纯说明文档，或能证明不改变运行时工作量的改动 | 理由及链接/diff/交叉条款；样式改变图片加载、请求或可见性时不能据此豁免 |
| PERF-BOUNDED | 日常默认：局部且可界定的执行/加载变化，包括普通查询修改；未作新的容量承诺 | 定向正确性及必要的重复工作保护；高频 SQL 新增/实质改写先做简短工作量与索引检查，发现潜在大规模风险再补计划/小型对照；其余按需复用证据或观察关键流程，UI 按卡做真实浏览器。未测规模延迟不作承诺 |
| PERF-SCALE | 卡面明确验收30万容量/延迟；或实际瓶颈、执行计划/工作量证据显示大规模风险，且较小验证与既有证据不足以判定 | 说明升档理由，复用一个固定30万合成主夹具，仅验证受影响首/续页与必要偏斜形状；同输入对照及结果正确性，区分 API/模型/媒体/浏览器证据 |
| PERF-RELEASE | 正式容量、最低设备或发行资格 | V3.0 §12 与发行卡全部实机、端到端、质量、争用和恢复证据；不可用小型对照替代 |

分级依据实际风险，不按文件名或任务标题。发现全局查询、出现 JOIN、没有历史30万记录，都不单独构成大规模测量门槛；先看是否多做了不必要工作、实际规模与热点证据。`PERF-BOUNDED` 若发现缓存一致性或公共消费者影响无法界定，按影响补设计/验证；数据风险按 B/D 处理，不意味着必须做30万计时。需要改变冻结协议时按原决策流程处理。

复用时核对与本次结论相关的代码、输入和环境变化即可；只影响UI的小改不要求重新收集GPU/数据库版本或全部指纹。新的30万工作量路径没有适用证据时不能用小样本证明规模达标，但普通功能可在完成本卡必需验收后按局部范围收口；未承诺的容量/发行资格记“未验证/后置”，不自动阻塞普通功能。不得在必测失败后偷偷改成可选，也不得豁免原卡必测。历史卡明确例外保留，不重跑所有历史任务。

## 4. 设计检查：防止重复做大工作

**高频 SQL 编码前检查（即使小图库尚未卡顿）**：当新增或实质改写相册打开、列表/分页、搜索、统计及后台频繁调用的 SQL 时，先根据现有表结构与调用链判断一次操作会执行多少次查询、随图库 N／候选 K／页大小 P／关联扇出中的哪个量增长，以及是否存在 N+1、重复聚合、无索引筛选或为本页读取全库成员。对明显或无法排除的规模风险，再检查相关实际参数/数据形状的 `EXPLAIN QUERY PLAN`，必要时补小型合成对照；计划中出现 SCAN 不必然有错，没有 SCAN 也不代表性能通过。**这是轻量设计核对，不是每条 SQL 必跑 EXPLAIN，更不是每卡必测30万。** 无风险时将判断写进任务卡的既有三行即可。

| 受影响面 | 设计时必须回答 | 保留的正确性 |
|---|---|---|
| SQL / FTS / 成员过滤 | 查询是检查一页/一组候选，还是生成全范围结果？是否为每个候选重复 MATCH/聚合？核对执行计划及真实计时，按有界候选与大集合分别选路径，不能一律指定 IN 或 EXISTS | 统一权威谓词、ANY/ALL、固定相册交集、来源多位置去重；不能全库 Top-K 后过滤冒充完整召回 |
| 分页与投影 | 是否逐卡/逐图附加查询？可否先确定语义正确的一页，再批量读本页投影？全局排序/数量过滤所需聚合必须在分页之前完成 | 全局排序、稳定平局、去重、前瞻、旧游标/修订拒绝；不能先 LIMIT 再做全局排序 |
| UI / 首屏 | 默认隐藏区块是否发请求？卡片是否等待非关键统计？旧请求是否覆盖新筛选？分别记录 API 完成、首个可用内容和图片可见时间 | 必要入口仍可用；失败不能显示为0；返回/续页/迟到响应保持正确 |
| 媒体 / 后台 | 冷解码、生成与队列是否阻塞交互？并发、队列、预热和缓存是否有界？重复同资产是否重复解码？线程变更核对 SQLite 连接所有权 | 受控路径、内容身份、失败/取消/关闭和用户授权；后台预热成本不能从报告中消失 |
| 缓存 / 派生计算 | 缓存的是真实权威状态还是可重复计算结果？键含哪些内容/版本？容量、失效、写后读取、旧响应、失败和跨连接生命周期怎样处理？ | 实库校验不跳过；人工状态/revision/内容变动及时生效。大小/mtime 不能独自证明内容相同；TTL 不能代替必要的权威拒绝 |
| 模型 / 向量 | 是否无必要加载重型模型？冷启动/暖机、排队/编码/检索是否分开？批次/worker/全进程 RAM/VRAM 与索引空间是否在预算内？ | 空间/profile/generation 隔离、质量与召回；不靠减少候选、降质量或改变阈值悄悄换速度 |
| 测试 / 工具 | 是否每例重复创建昂贵但不变的基底？可否共享只读模板、每例复制独立数据库？测量是否串行且无测试干扰？ | 保留事务、兼容检查与断言；模板不被修改，不共享可写状态；不能以删断言/skip 换速度 |

工作量预算是设计约束，不是复杂度证明：SQL 文本短、查询次数少、出现索引或 EXPLAIN 没有 SCAN 都不能单独证明快速；合法的全局统计/FTS/精确检索可能仍需与 N 或命中数相关的工作。优先去掉不必要工作，再批量化、改善访问路径，最后在证据支持时增加缓存/并发/新架构。索引提示与阈值只用于已证明适合的范围，并保留其他形状的正确路径。

## 5. 性能证据的最小口径

本节用于实际测量或作性能结论时，不是所有任务的附加清单。普通任务保留定向测试、必要浏览器与简短观察即可；已有工具够用就不另造平台。

**配对与身份**：固定同一份隔离合成数据、查询、分页大小和配置；记录与结论相关的版本/设备，规模与正式对照再保留源码/依赖/夹具指纹及引擎环境。比较旧新实现只变目标因素，环境漂移要说明。已有缺陷的旧结果不能当正确真值，须用独立小型 oracle 或既有正确参考验证。

**场景**：只覆盖本次受影响链路，区分首次请求、热请求、续页、冷/热媒体和模型冷启动。按风险从常见词/稀疏命中/无匹配、同图多脸/大人物/大合集/多来源中选择必要偏斜，不做所有参数笛卡尔积。新缓存必须验证暖缓存后权威变更、失效/拒绝及回退；数据/并发变更补相应故障恢复。

**统计**：局部诊断可先串行重复2～3次看量级，只称观察，不作稳定加速比/P95保证；波动大或要宣传收益时再扩大配对，可交替顺序或旧→新→旧，记录样本与失败，不设每卡5组硬门槛。明确作正式性能验收时，按 V3.0 §12.2 每场景至少30个有效计时样本，记录 P50、样本P95、最大值与失败；失败不能丢弃。有非预期合法请求失败时该验收场景不通过。

**资源与用户结果**：影响资源时记录峰值 RAM/VRAM、队列/并发或磁盘增长；改动后台时记录与前台真实重叠及后台进度。UI 按 [AGENTS.md](../AGENTS.md) 用内置浏览器、127.0.0.1 和隔离合成数据验受影响关键流程；API计时、DOM桩及图片load事件不能单独替代实际可见/可交互证据。工具不支持时记 PENDING/BLOCKED，不伪造首屏性能 PASS。

**产物**：可复用基准、夹具生成、断言进 Git；正式支撑新性能结论的入口不能只存在某次 `.tmp/`。文档写可复现命令及前置数据/模型授权，保留原始样本JSON、JUnit与真实退出码到 `test-results/<任务>/`，失败不覆盖。普通 pytest 与正式性能测量分开，遵守项目本地缓存与临时目录规则；未运行 pytest 不需要制造 JUnit。原有只能本机复现的证据如实标注，不虚称干净克隆可复现。

**噪声**：不要同时跑大套测试、建库与前后台对照（有意测争用除外）；不清理用户系统缓存或访问真实图库。未清 OS 缓存的首轮叫“首次调用”，不称磁盘冷测。结果漂移或提升落在噪声内时，记录“未证实改善”，保留对照；达到正确性和预设预算且无退化可收口，但不能宣传加速比。

## 6. 审查与 PASS

审查按卡面逐项检查：用户关键路径是否完整；工作量是否有界且与分级相符；缓存/批量化/懒加载是否保留状态与分页不变量；证据是否覆盖全部受影响消费者；目标是否事前确定；剩余瓶颈、噪声和未验项是否如实说明。独立审查仍按 V3.1 §2.4，不用实现者自检代替，不自动改变模型或增加无关审核轮次。

只有本卡必需的功能、性能、状态/恢复和浏览器检查全部完成，才能按限定范围 PASS。功能已过但性能必测未完写 `IMPLEMENTED / VALIDATION PENDING`；已测超预算写 FAIL 并给差距，工具/设备缺失写 BLOCKED。性能段不能作为规避原卡必测项的豁免。

报告以一行表格说明 `场景/数据与设备/原值→新值/样本与口径/预算结论/未验边界`，再列复现命令与原始材料路径。前后无可比数据就不写加速比；SQL步骤改进不能上升为整个产品体验承诺。达到当前预算后停止，不为了“还能更快”自动开卡。

未开展计时的小任务只写功能验证与体验观察，无需空表。性能规范不自动新增独审阶段、强制换模型或拆新任务；风险触发时仍按原策略。实现方式可以在同一卡内调整，超出已接受范围或改变协议/数据语义才按原流程收口。30万支持目标保留，发行门槛不会自动变成每次日常开发的前置条件。

这是根据仓库证据整理的工程规则，不归因于某个模型的能力或推理档位。引用对话的回答正文不可读取时，不能声称逐条复现了原建议。

### 教训的适用边界：避免再次走向另一端

- **正确性设计和执行成本要一起看。** 统一权威谓词是必要的，但不代表每个入口都应构建完整成员集合；保留同一语义，可以换查询路径、加索引或批量投影，不必先推翻架构。
- **小样本通过只说明那些样本。** 在设计时问“这步会重复几次、随什么增长”，比每次机械跑大库更有用；只有风险证据或容量验收需要时才扩大测量。
- **定位最大等待，别只数SQL。** API快、少几个请求、移到线程都可能没有解决冷图等待；先定位当前主要耗时，一次解决一个主要问题。
- **缓存不是禁用项，校验也有成本。** 先去掉不必要工作，再用可正确失效的缓存复用；保护身份和人工状态，但不把“安全”理解成每次请求重新计算全部静态信息或重读整个模型文件。
- **不要从一次收益推导永久禁令。** 不强制所有查询 EXISTS/IN，不禁止必要全局扫描，不因暂用SQLite就永久固定技术栈；复杂缓存、后台预生成或换组件要和维护成本一起取舍。
- **优化也有预算。** 个人库按实际体验和功能价值排序，达到当前可接受目标即使用；可以明确接受首次稍慢、保留未验容量边界，不能接受丢照片、丢人工整理或隐瞒失败。

这些是从当前实现与报告归纳的预防措施；没有完整历史设计记录，不能把它们当作当时每项遗漏的已证实原因，也不能声称原对话两次提交的教训已穷尽。
