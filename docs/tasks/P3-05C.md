# P3-05C — P3-05 人物拆分与通用撤销独立 C2 审查（含必要最小修复）

本卡是 **审查任务**，不是新一轮功能实现。目标是让一个没有参与 P3-05A/P3-05B 实现的审查者，独立判断
ADR-0008 的冻结语义是否真的被实现、被测试、被拒绝，只在发现**确凿缺陷**时做最小修复。

执行模型：**C2（GPT-5.6 Sol / high）**。模型切换由用户在 Codex 中手动完成；不得自动切换、启动其他
Agent 或声称已切换。需要 ONNX/CUDA/DLL/Windows ACL/路径/PyInstaller 判断时，转 **C1 / GPT-5.6 Terra /
medium**；需要改变 ADR-0008 冻结语义时，停止并报告，不得自行修改冻结文件。

## 审查要点（至少逐项给出 PASS / FAIL / 无法判定 + 证据）

1. **迁移 0013**：是否只重建 `person_operations`/`person_operation_items`；`0001`～`0012` 是否逐字节未改；
   真实 v12 库上的 operation/item（含 `FACE_CONTROL` 的 `entity_key`）/UNDO 互引用/alias 引用是否逐列保留；
   `CHECK((entity_type <> 'FACE_CONTROL') = (entity_id IS NOT NULL))` 是否真的拒绝「`SPLIT_GROUP` 带 text
   key」与「`FACE_CONTROL` 带整数 id」；`PERSON_BUNDLE.after_revision >= 1` 是否仍被强制；备份、单事务、
   缺件、损坏回滚、过新拒写是否都成立。
2. **资格矩阵**：ADR-0008 §3 第 1～6 项逐条核对实现与拒绝；六值 `details.reason` 闭集是否与 companion
   完全一致、是否存在「先写后拒」或「拒绝后仍占 request_id」的路径；source canonicalize、旧 ID 提交、
   悬挂/环是否给出 `PERSON_REDIRECT_CYCLE`。
3. **人工事实与不变量**：所选脸是否恰好得到 `MANUAL_ASSIGNED` + 一个 `MANUAL/CONFIRMED`；
   `AUTO` 是否只降级为建议而检测/embedding 不动；source exclusion 是否激活、其他 exclusion 是否原样保留；
   同图未选 sibling、其他人物、图片是否完全不动；新 link revision 是否**严格高于**被替换行与既有同 key 行
   （含「降级后的建议行 revision」这一细节）。
4. **新人物身份**：name/name_key/alias/merged_into/revision 1 是否被正确写入且**不复制** source 名字与别名；
   头像是否只从同一 processor/space 的有效成员选择、是否额外增加 revision；失败时人物 ID 是否随事务消失。
5. **幂等与 payload**：门禁是否早于一切 revision/实体检查；digest 是否只含 contract version、endpoint
   family、**请求** source ID、期望 revision 与排序后的 face 三元组；同 key 异 payload 是否零写且不回显
   payload/hash；空集合、重复 face、501、非本地 face id 的拒绝码是否与 companion 一致。
6. **撤销冲突矩阵**：ADR-0008 §7 表格逐行核对；`group_changed` / `group_redirected` / `person_missing` /
   `face_control_changed` / `face_missing` / `effective_members_changed` 是否可分别复现；
   suggestion-only 与不相关改动是否**不阻止**撤销；item family/顺序/数量严格校验是否存在绕过；
   禁止 undo an UNDO 是否不能被绕开（包括用 UNDO 的 operation id 再撤销）。
7. **补偿语义**：control/link revision 是否始终向前（含 `restore_control_bundle` 的 floor 计算）；
   source 头像/成员是否恢复；created 是否**不被删除**、头像清空、redirect 到 source、revision forward；
   撤销后旧 created ID 是否按 ADR-0006 resolver 解析到 source；exclusion 行是否只切 active 而从不删除。
8. **权威→派生**：filter revision 是否最多 +1、cause 是否复用 `PERSON_CHANGED`、队列与
   `PENDING_REPAIR` 是否只在 changed 时发生；replay 是否零副作用；是否**误调**图片 projection refresh 或
   写图片向量 `index_outbox`；是否改动 embedding/space/generation。
9. **API/错误/隐私**：唯一 split 路径与共享 undo 的 envelope 是否与 ADR-0008 §6/companion 一致；HTTP 映射、
   错误码闭合、`additionalProperties: false` 是否成立；session/Host/Origin/CSRF 与脱敏是否无法绕过；
   响应/错误/日志/OpenAPI 是否不含路径、姓名/name_key/alias、bbox、landmark、向量、confidence、
   单对相似度、幂等 payload/hash 与内部 before/after snapshot。
10. **测试质量**：44 个新用例是否真正断言 ADR-0008 §10 的 12 组反例，而不是复述实现；是否存在
    「只断言不报错」「断言被 try/except 吞掉」「行快照比较被弱化成单字段」的情况；两处版本钉扎
    （`test_p3_face_correction_migration.py` 钉回 0012、`test_p3_person_migration.py` 的 `MOVE_FACE`）是否
    语义等价而非掩盖回归。

可以（并且应该）自己写**临时**探针复现怀疑点，但临时文件不得留在仓库里；不要为了「再审一遍」而复制
P3-05B 的测试文件。

## 允许修改

- 只允许修复审查中发现的确凿缺陷，且必须保持 ADR-0008 冻结语义不变。
- 允许范围：`src/photo_search/persons/**`、`src/photo_search/face/{index,processor}.py`、
  `src/photo_search/catalog/{schema,errors}.py`、`src/photo_search/scheduler/projection.py`、
  `src/photo_search/api/{models,routes,errors}.py`、新增 migration（**仅当** 0013 存在确凿缺陷时，且必须
  连续、不得修改 `0001`～`0013` 的历史语义）、`tests/**`（新增/修正用例）、本任务报告、状态与下一卡。
- 修复必须在报告中说明：缺陷、最小修复、为什么不是改冻结语义。

## 禁止修改

- ADR-0008 与 `p3-person-split-contracts.v1.json`、ADR-0001～0007、既有 contract JSON。
- `0001`～`0012` 逐字节；`pyproject.toml`、`uv.lock`、`PhotoSearch.spec`、前端资源。
- `face_id`/检测/质量/阈值/向量 space、候选 generation、embedding、每人每脸唯一 `CONFIRMED`、
  P1/P2/OCR/place/search/profile/feedback 既有协议。
- 真实私人照片或真实照片库；只用 `%TEMP%` 下的合成/公共领域夹具。

## 必须保持的不变量

与 P3-05B 任务卡 §「必须保持的不变量」一致，且逐条独立复核：SQLite 权威单一事实源；`face_id` 是最小
人工单位；`MANUAL_ASSIGNED`/`MANUAL_UNASSIGNED` 与「每脸至多一个 CONFIRMED」；无控制行 = revision 0；
`request_id` 全局幂等且被拒请求不占 key；split 无业务 no-op；undo 为向前补偿、不删历史；changed 至多一次
filter revision（`PERSON_CHANGED`）+ 队列 + `PENDING_REPAIR` 追赶；split/undo 不写图片向量、不改
embedding/space/generation；隐私闭集；不改依赖与 `0001`～`0012`。

## 验收

必需命令（项目内 `.uv-cache`；必须生成 JUnit XML；成功只保留 quiet 摘要）：

```text
uv run --no-sync pytest -q -p no:cacheprovider tests/unit tests/integration
uv run --no-sync ruff check .
git diff --check
uv run --no-sync uv lock --check
```

等级：**A + D 复核 + C 复核**（本任务默认不新增生产行为，因此不重复实现级 C；但**只要**改动了
`src/photo_search/**`（含 migration）就必须重跑 C 级：真实 onedir 重建 + 新建 D 盘中文/空格 smoke 目录运行
`packaged_api_smoke.py`，并核对 bundle 内 `0001`～`0013` 连续且 `0013` 与源码 hash 一致）。

审查必须至少**独立复现**以下 7 组（不得只读代码）：

1. v12→v13 在含 undo/alias/`FACE_CONTROL` 引用的真实库上逐列保留，且备份仍拒绝 `SPLIT`；
2. 同 `request_id` 同 payload 在 source revision 前进、所选 face 已被删除之后仍 replay；
   同 key 异 payload 零写冲突；
3. source / control / assignment 三种 stale 各自零写，且 `details` 只含安全 ID 与 revision；
4. 一次成功拆分后 source/created 的成员、头像、exclusion 与 filter revision/queue/candidate 的确切取值；
5. 后续 rename / merge / face edit / 第二次 split / 新增 `CONFIRMED` 成员分别阻止旧 undo；
   suggestion-only 与不相关改动不阻止；
6. 撤销后 created 不删除、头像清空、redirect 到 source、control/link revision 严格向前，
   且 `index_outbox`/embedding/space/generation 前后逐项不变；
7. 事务中途失败（派生阶段与人物/头像阶段各一次注入）后 person/operation/item/关系/filter/queue 全回滚，
   同一 request_id 之后仍可成功。

如需权威夹具/打包证据：真实 smoke 使用 P3-05B 的公共领域合照，在 `%TEMP%` 走
真实检测→合并→命名→拆分→重启→撤销→重启；不得使用私人照片。无法跑完任一必需项时不得标 PASS，
写 `VALIDATION PENDING` 或 `FAIL` 并说明缺口。
