## 不变量与行为

`GET /api/v1/health` 保持不变，且业务代码不得写死 ONNX、512 维、224 px、tokenizer 或设备（主架构 §11.3.4）。本任务只产出开发期准备物与证据：manifest 是模型身份的权威记录，权重文件本身可重下但必须可由 manifest 校验。所有结论必须来自本机真实推理，不得用示例速度、官方基准或“应该可行”替代。

在 `tools/prepare_models/` 实现可直接运行的脚本（下载/导出与校验可以分开成两个脚本），输出可机读 JSON：

1. 获取 Chinese-CLIP ViT-B-16 配套的图像塔、文本塔、tokenizer 与权重，记录来源 URL、revision、文件名、字节数与每个文件的 SHA-256；许可证以实际仓库声明为准并记录原文链接，不得臆造。
2. 导出 FP32 ONNX：图像塔与文本塔各一个模型，batch=1；记录输入/输出名称、形状、dtype、opset、导出脚本与依赖版本。动态 batch 只作为未验证项记录，不在本任务承诺。
3. 生成 manifest JSON，至少包含：模型与权重标识/revision、SHA-256、预处理（resize、center crop、插值、均值/标准差、通道顺序、dtype）、tokenizer（名称、词表文件与哈希、最大长度、截断与 padding 规则）、归一化（L2）、输出维度（预期 512，以实测为准）、度量（cosine）、backend 与 `onnxruntime` 版本、device/precision、像素与 token 上限、许可证。
4. 用固定夹具做 CPU batch=1 真推理：至少 1 张脚本生成的图片与至少 5 条固定中文查询；同时运行 PyTorch 参考实现与 ONNX，记录每路输出的形状、L2 范数、最大绝对差、cosine 相似度，以及图片-文本 Top-K 排序是否一致。
5. 单独记录 GPU：`onnxruntime` 可用 provider 列表、CUDA provider 是否可用、是否实际跑过；不可用就写清原因，不以硬件存在推断可用。CPU 结果为必测项。

异常路径：下载失败、SHA-256 不匹配、导出失败、ONNX 与参考输出差异超出实现设定的阈值或 Top-K 排序不一致时，脚本必须以非零退出并输出阶段、异常类型、消息与已完成步骤；不得掩盖为 PASS，也不得用“接近即可”跳过检查。若 ONNX 导出在本机成为实质阻碍，可依主架构 §8.1 记录决策后临时采用 PyTorch 参考后端完成效果验证，但必须写明这是临时决策、ONNX 未验证，不得声称已完成导出。

边界：只覆盖 ViT-B-16、FP32、batch=1、CPU 必测；不承诺动态 batch、FP16/量化、GPU 性能、吞吐、并发、模型质量或与官方基准的对比。夹具只用于数值一致性，不用于宣称检索质量。
