## 一、目标

在 UI 2.0 统一照片查看器顶部增加「找相似照片」按钮。

点击后，直接利用当前照片已经确认的图像向量搜索全图库，自动跳转至现有搜索结果页，按照相似程度显示其他照片。

用户不需要上传文件、不需要重新生成向量，也不需要等待照片重新进行 AI 分析。

**必须实现：**

1. 从普通照片、搜索结果、人物相册、合集、地点相册、地图等共享查看器入口均可使用。
2. 自动使用当前正在查看的照片作为搜索参考。
3. 默认搜索整个图库，不暗中继承当前页面的局部搜索范围。
4. 排除参考照片自身，但允许其他重复文件、近似照片正常命中。
5. 复用现有搜索结果网格、排序和分页。
6. 浏览器返回后恢复来源页面的有效浏览状态。

## 二、交互设计

### 2.1 照片查看器

在 `photo-info.js` 共享查看器的顶部操作区域增加：

`找相似照片`（搜索图标）

与「收藏」「加入照片合集」「完整详情」保持相同的 UI2.0 视觉体系。

- 不增加新的侧栏或弹窗。
- 按钮随当前照片切换更新 `asset_id`。
- 仅点击时检查能否搜索，不在打开每张照片时预先查询索引状态。
- 点击后防止重复触发。
- 不能影响缩放、拖动、双击、照片切换及关闭操作。
- 窄屏下按钮允许紧凑显示或收纳，但必须能够找到并操作。

### 2.2 搜索结果页

进入 `/search` 后直接执行一次查询。

页面顶部显示：

**相似照片搜索**

`[参考照片缩略图] IMG_1234.CR2`

`搜索范围：全部图库`

结果沿用现有照片网格、相关度顺序和自动加载下一页。

参考照片展示仅使用已有 thumbnail/preview，不重新解码原图。

对于图片查询，不显示不适用的文字匹配解释，也不将向量距离转换成未经验证的相似度百分比。

保留用户从结果中打开照片、收藏、手动加入普通合集等现有操作。

### 2.3 查询模式切换

本功能是独立的 `asset_image` 查询来源，不等于现有 `upload image`。

从照片启动相似搜索时，清除旧文字查询、上传图片、人物/合集固定范围及收藏筛选的执行状态。

相似搜索进行中，文字输入和高级筛选不得表面变化但实际不生效。用户选择文字搜索时，应明确结束当前相似查询，再执行文字搜索。

首版不实现相似搜索与人物、合集、地点等范围的组合筛选。

## 性能设计与验收（PERF-BOUNDED）

- **链路与风险**：点击后仅读取一张照片的 embedding artifact 并执行一次既有 TopK；主要风险是误触发全量向量读取、重复读取/检索和续页重排。
- **做法与边界**：定点查找当前 Profile/Generation 下单个 CONFIRMED artifact，复用既有分块候选、会话及分页；向量读取和检索沿用有界线程执行，不新增每张结果图查询。
- **验证与停止**：检查索引访问路径；定向验证首次一次 artifact 读取/检索、续页零读取/零检索、受影响浏览器关键往返；出现规模证据才补小型对照，不做 30 万基准或延迟承诺。

## 三、后端实现

### 3.1 新增最小接口

建议：

`POST /api/v1/search/by-asset`

输入以当前 `asset_id` 为核心，支持现有搜索协议允许的 `top_k`、`page_size`、`search_session_id` 和 `cursor`。

第一版不提供额外人物、合集、地点筛选参数。

复用现有会话认证、CSRF、错误返回及 `run_catalog_search` 有界线程执行机制。

返回复用现有 `SearchResultModel` 的命中、排名和分页结构，增加一个简短的 `asset_query` 信息块，用于展示参考资产身份。

不要强行使用上传搜图专属的 `image_query` 文件格式、解码耗时等字段。

### 3.2 直接读取已有向量

首次请求：

1. 检查 `asset_id` 对应有效照片资产。
2. 解析当前有效搜索 Profile 与索引世代。
3. 使用 `index_entries` 定点查找对应 Space/Generation 的 `CONFIRMED` 条目。
4. 校验关联 artifact 是当前照片内容对应的有效发布产物。
5. 使用现有 `ArtifactStore.read()` 读取并验证向量。
6. 校验向量维度与数值，调用既有 `search_request(query_vector=...)` 完成检索。

**禁止使用 `LanceVectorIndex.rows()` 全表读取向量，也禁止重新加载原图计算 embedding。**

如果某张 CR2 已有有效向量，即使预览暂时不可用，也不应因此阻止相似搜索。

如果向量缺失、失效、尚未确认或 artifact 损坏，应返回明确错误，不自动调用模型补建，也不把错误说成「没有相似照片」。

### 3.3 正确排除参考照片

在服务端候选检索前增加参数化排除条件：

`a.asset_id <> ?`

优先复用 `SearchScope.additional_condition_sql` 和 `additional_condition_parameters`，使该条件同时参与向量 TopK 和最终权威复核。

不能先取 TopK 再删掉参考照片，也不能仅在前端隐藏原图。

保持其他照片的正确排名、稳定平局排序及原有 TopK 上限。

### 3.4 搜索会话与版本

复用既有 `SearchSessionStore`：

- 首次查询读取向量并计算一次排名。
- 后续分页只读取已冻结的结果和执行必要的权威校验。
- **续页不得再次读取整个向量文件或重新执行向量排名。**

使用现有 `query_identity` 机制绑定参考资产及其有效向量身份。查询身份至少区分资产、artifact 内容版本与索引世代。

特别注意：当前 `search_request()` 的摘要计算不直接包含 `additional_condition_sql`。必须保证参考照片的排除身份通过 `query_identity` 一起进入会话绑定，不能仅依赖额外 SQL 参数。

续页时通过有界元数据查询确认参考照片及有效向量身份未变化。如果照片内容、artifact 或索引世代已经变化，拒绝旧会话并提示重新搜索。

保留原有游标、Profile/Generation、Catalog Revision 及过期会话的错误语义，不创建第二套分页协议。

## 四、前端接入与返回

### 4.1 页面交接

建议使用：

`/search?similar_asset=123`

只传资产 ID，不传向量、本地文件路径或图片字节。

搜索页在 `restoreOrStartSearch()` 中识别该入口，优先于旧搜索快照执行本次明确的相似查询。

处理以下情况：

- 首次进入恰好发起一次请求。
- 页面刷新仍以同一参考照片重新执行一次合法查询。
- 用户改为文字搜索后清理旧 `similar_asset` URL 状态。
- 非法 ID 或与 `scope_entry` 等入口冲突时明确提示，不执行其他意外查询。
- 不因浏览器前进、后退造成重复请求或旧结果覆盖新结果。

### 4.2 返回与历史记录

`photo-info.js` 已有 `pushState`、`popstate` 和关闭时的 `history.back()`。本次必须复用并正确协调这套逻辑。

点击「找相似照片」发生导航时，不能先执行一次关闭返回，再跳转搜索页，导致浏览器历史错位。

搜索页已有 `saveSearchSnapshot()` / `restoreSearchSnapshot()` 主要服务文字模式，本次需要按实际使用情况补充 `asset_image` 状态支持，不能把相似结果恢复成普通文字结果。

重点检查：

- 普通照片 → 相似搜索 → 返回；
- 搜索结果 → 打开照片 → 相似搜索 → 返回原搜索结果；
- 相似结果中再次点击另一张照片「找相似照片」→ 返回上一个有效结果。

采用最小必要的历史/快照管理，不为本任务新建通用路由框架。对无法恢复的过期搜索会话显示提示，不展示过期结果。

## 五、范围限制

本任务只实现全图库相似图片搜索。

**本次不做：**

- 按当前人物、合集或地点限定图片搜索；
- 任意图片区域裁剪搜索；
- 同一个人人脸相似搜索；
- 精确重复照片检测；
- 相似度阈值调节；
- 新的数据库表、迁移或索引类型；
- 后台自动向量补建；
- 按相似搜索直接保存为可刷新智能合集规则。

现有普通合集仍可手动添加搜索结果中的照片。

由于目前「从搜索结果保存合集/智能合集」依赖服务端搜索来源令牌，本功能不能伪造或错误复用该令牌。首版对不支持的整次结果保存操作明确隐藏或禁用，不影响逐张或手动批量收藏、加入普通合集。

## 六、性能要求

按 `docs/performance.md` 采用 **PERF-BOUNDED**。

**链路与风险**：新增一次参考照片向量定点读取与一次既有向量检索；风险主要是全表向量加载、重复编码、重复检索以及页面导航产生多次请求。

**实现边界**：只在点击时读取单个有效 embedding artifact；复用现有 TopK、候选分块、搜索会话和结果分页。不得改变既有精确排名或为每张列表照片增加 SQL 请求。向量读取与检索不得阻塞应用事件循环。

**验证与停止**：检查新增 SQL 的索引访问路径，验证首次一次检索、续页零重新编码与零重新检索；观察内置浏览器首屏、加载和返回。没有明确规模风险就完成本卡，不跑 30 万照片基准，也不编造毫秒级性能保证。

## 七、最小验收

采用隔离合成图库，不访问真实 `PhotoSearchData`。

| 用例 | 必须通过 |
|---|---|
| 正常参考照片 | 使用现有向量完成相似检索，返回其他照片 |
| TopK 排除 | 当前照片不占用结果名额，排名正确 |
| 向量缺失/损坏 | 清楚报错，不重新编码、不修改图库 |
| 分页/版本变化 | 续页不重新检索，错误会话正确拒绝 |
| 共享查看器 | 切图后引用正确，异步旧操作不影响新照片 |
| 搜索与返回 | 从普通浏览及搜索结果进入，返回状态正确 |
| 功能回归 | 上传搜图、文字搜索、缩放、收藏、普通合集仍正常 |

优先复用项目现有测试夹具，只补必要的后端定向测试、前端状态测试及 2～3 条内置浏览器关键流程。

按仓库已有测试规范生成 JUnit XML。浏览器使用 `127.0.0.1`、隔离数据与一次性会话链接，避免重复截图和无意义的长时间浏览器验收。

涉及向量身份、会话和搜索结果资格的改动，按现行 V3.1 策略完成必要的独立受影响面复核；不要求全仓回归或正式容量认证。
