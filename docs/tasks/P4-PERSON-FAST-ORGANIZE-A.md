# P4-PERSON-FAST-ORGANIZE-A — 人物快捷整理与待归类人脸直接收录合集（优化版）

- 日期：2026-10-15；状态：**设计完成 / 待实施**。
- 核对基线：`szzeng/aisearch` 默认分支 HEAD `b6cc2cff89b2049c5c2789a256e42540a4927109`；当前 `SUPPORTED_SCHEMA_VERSION=31`。**开工重查 HEAD、实际 Schema 和工作区，不照抄迁移编号。**
- 推荐：GPT-6 High；一次功能卡、分两个实施里程碑。只做相关合成测试和聚焦审查，用户自行用本机浏览器少量试用。不扫描真实图库、不运行全量识别。

## 1. 目标、现状与不变原则

用户按多个照片来源/图库分批导入同一个 `PhotoSearchData`，希望快速处理大量已命名/未命名人物和未归类人脸：不关心的直接忽略/明确排除；要留存的直接归入指定人物合集，**不必逐脸命名或创建人物**。未来来源再次出现同一人，希望已经人工确认的身份可以延续匹配。

已确认的仓库事实：

- 人物合集 `person_collection_members` 只保存 `person_id`；已有合集 `instance_token`、`revision`、照片去重分页与 `collection_condition()` 共享过滤，**尚无脸级成员**。
- 已有 `TEMPORARY`（暂时忽略）/`EXCLUDED`（明确排除）的人物和待整理单脸状态，无须创造第三种“不再处理”。人物 `TEMPORARY` 仍能作为自动匹配代表；人物 `EXCLUDED` 从正常参考候选排除。脸级 `EXCLUDED` 阻止该特定检测脸进入常规自动归属，但不能屏蔽未来所有新检测脸。
- 自动识别只以有效 `CONFIRMED` 人物关系及合格、READY、模型空间兼容的代表脸匹配后续照片；仅归入合集的 `face_id`、`SUGGESTED` 以及动态 `candidate:<person_id>` 组不是人物身份，不形成未来匹配参考。`rematch_unassigned` 现有显式补匹配路径主要覆盖旧 v1/v2，**不能用它代替新版 source-crop 处理验收**。
- 当前 `collections.py::edit_members` 移出人物时会顺带清除 `person_hidden`；须改为合集与忽略状态独立，特别不能意外恢复 `EXCLUDED`。

**核心边界**：

1. **加入合集 ≠ 确认同一人物**，不改归属、不暗中把候选组确认为一人。
2. **保存人脸 ≠ 保存该人所有照片**：按脸收录是“选中脸所在照片”的静态收录；按 `person_id` 加入合集才会动态收录此人现在及后续确认的全部照片。
3. **候选组是临时整理视图，不是可训练的人物簇**；同一候选人物下的若干脸可能实际上属于不同人。
4. 不新建“永久不再处理”模型策略、不更换模型/阈值、不做全库无监督新聚类、不重构操作日志或合并拆分契约。

## 2. 用户交互：入口统一，操作不合并身份

### 2.1 卡片与批量操作

- 现有“人物 / 整理一下”下：已命名人物、未命名人物、未归类单脸和动态候选分组保持原浏览/预览方式；卡片快捷入口统一为 **「加入合集」「暂时忽略」「明确排除」**（已忽略处提供「恢复」），高级身份更正继续使用已有“确认是/选其他人/新建未命名人物”。避免同时显示与“明确排除”等义的“不再处理”。
- 批量管理继续复用原有 `person_id` 与 `face_id` 两套选择和 API：点击选择、Shift 在已加载项间连选、选中已加载项、跨页保留选择；**按人物和脸分别计数，每类每次提交最多 500 项**。显示所选类型及具体作用范围；不能把某张合照里的其他脸一起隐式选中。
- **候选组快捷选中**：组标题仅展开/收起；另提供显式“选中本组待整理脸”按钮，按既有待整理/已忽略候选组分页接口逐页、受游标版本约束收集至单批上限，给出精确数量供用户确认。只选择当前服务端返回的有效 `face_id`，不把 `group_key` 直接提交为更改目标；超过 500 须提示分批，失效/冲突要中止并提示刷新。不能将整个组自动 `CONFIRMED` 为候选人物。
- “加入合集”只需选择现有或新建合集，显示“X 个人物 + Y 张脸”；可勾选“加入后**暂时忽略**”，默认不勾。已是 `EXCLUDED` 的对象不能被覆盖为 `TEMPORARY`，更不能自动恢复。重复加入应幂等；可以在当前页面会话内默认选上次使用的合集，不新增持久偏好表。
- 对已忽略人物或脸，也可显式“加入合集”，保留原 `TEMPORARY/EXCLUDED` 状态；归档与忽略互不替代。单独点击“明确排除”仍调用现有 API。
- 保存成功后局部刷新受影响列表并尽量保持滚动、已展开项；失败/取消保留未提交的选择。人物与脸是**独立事务**：混合提交出现部分成功必须分别报告结果，重试不得重复归档或改变已排除状态。

### 2.2 合集显示规则

- **照片页**：现有动态 `person_id` 成员照片 ∪ 本合集脸级收录对应的当前有效照片；必须 **先按 `asset_id` 去重再排序/Keyset 分页**，合照仅一张。集合人数、单脸数、去重照片数各自标注，不把脸数叫作人数。
- **人物页**：现有正式人物卡一个 `person_id` 一个代表头像，进入该人的全部照片；新增默认折叠的 **「单独收录的人脸」** 区域。该区域包括仍未归类以及**后来已经归属人物、但用户只收录这张脸**的记录；不能命名为只含“待整理脸”。
- 对其中**仍未归类**且有有效建议的脸，按原候选目标动态分组，只在该合集的**已收录脸集合**内显示；每张脸最多进入一个展示组、组有一张代表头像，不带入其他未收录脸。无候选、明确排除、质量不足或候选失效的脸可单独显示。**原待整理分组查询本身会过滤已忽略、已归属或不合格的脸，不可直接拿它当合集完整成员来源**；应以新增的脸级收录表为全集，再只对有资格的脸投影候选分组。分组变化只改变视图，不修改归档关系。
- 已收录脸后来归到人物 P：归档仍只覆盖原照片，**不能自动升级为 P 的全部照片**；展示“已归属 P · 仅收此照片”。若 P 同时是此合集正式人物成员，可隐藏重复展示卡（但保留底层脸级记录）；之后 P 被移出，原脸级收录仍在，不能丢失。
- 点击人脸头像查看**原照片及对应人脸**，可移出本合集、继续确认/指定人物；不能假装这是一整个未命名人物相册。照片页的 `person_faces` 原有含义不改，可另返回有界 `archived_faces`，避免显示错误人物头像。

### 2.3 「以后还能自动认出」只做明确入口，不新造复杂向导

- 单脸或候选组附近说明两种选择：**「仅加入合集」**（默认，不会获得未来自动匹配能力）与 **「确认属于人物」**（跳到现有指定人物/创建未命名人物功能，必须逐脸核对）。
- 用户确认一张脸属于已有 P，复用原 `assign`；若无 P，可从**一张明确选中的脸**使用原 `create-person-from-face`，其余脸继续使用原批量 `assign`。**本卡不实现自动确认整个候选组，也不新增多步骤创建/撤销协议或声称现有多次请求是原子的。**
- 人物 P 确认且有 READY、合格、兼容的有效参考脸后，即使**未命名**，后续来源的新脸仍可按现有匹配规则自动归 P；再将 P 加入合集即可动态收录后续照片。创建人物成功不保证所有新照片都能认出，低质量/未 READY/人工锁或歧义时仍只建议或暂不归属。
- 对 `EXCLUDED` 的脸进行身份更正必须通过现有明确的恢复/更正操作，不得由“加入合集”自动清除其排除标记。

## 3. 数据实现：只增加脸级归档，不碰身份事实

### 3.1 增量 Schema

- 当前 v31；实施时若未变化，新增 `0032_person_collection_face_members.sql`，升级至 v32；若已有后续迁移则顺延。**已有 0001～0031 永不改写**。
- 建议**一张新表** `person_collection_face_members`：`collection_id`（合集 FK，删除合集时级联删除成员）、`source_face_id`（原始手工选中的脸标识）、`asset_id`、`input_revision`（归档时内容 SHA）、`created_at`；唯一 `(collection_id, source_face_id)`，按 `(collection_id, asset_id)` 和必要的源脸字段建有界索引。写入前在事务中验证真实存在、当前可用且 `asset_id/input_revision` 一致，重复提交幂等。
- **不要未经核对就设置 `source_face_id → faces` 的级联删除或 RESTRICT FK**。现有人脸重检测、来源删除和 GC 可能改变/清理检测行：级联会静默丢弃人工归档，RESTRICT 可能妨碍正常图库维护。优先保留不可变**软锚点**并在读取时验证可用性；如需要 FK/级联，必须先证明全部维护路径安全。
- 归档事实**不写入** `face_person_links`、`persons`、`face_assignment_controls`、`face_exclusions`、`person_hidden`、`face_inbox_hidden`、`face_embeddings`、人脸候选索引及操作历史。不复制作图像或人脸向量。
- 同一张脸可加入多个合集；不同脸来自同一 `asset_id` 时照片仍只有一张；不能通过 `asset_id` 误认为合照内所有脸都已被收录。

### 3.2 重新检测、内容更改、删除资产

- **同照片、同内容，重检测改变 `face_id`**：先复用既有 redetection mapping/代际有效性规则；只有唯一、可信、非 `OPEN` 争议的映射才允许自动展示新脸。不要求新增跨代人脸匹配算法；无法确定或当前未产生这种映射时原手工归档软锚点保留，照片在内容 SHA 仍相同且资产仍活动时可以继续显示，但人脸卡必须标注“待重新关联”，不得展示另一张错误人脸或自动抹掉归档。
- **照片内容 SHA 改变**：旧归档不自动落到新内容上，标记待修复/不可展示；不能因为 `asset_id` 相同就扩大到新照片。
- **来源移除/资产失效/旧检测 GC**：不显示不存在或非 ACTIVE 的照片；归档软锚点不应被正常后台清理静默删除。允许用户显式移出/清理失效收录；不要求本卡建立通用跨库复原/重新训练机制。
- 原 `person_id` 合并、拆分、撤销、脸级人工移出、后续确认、忽略变化只应改变相应动态投影，不能悄悄修改脸级归档事实。

### 3.3 后端接口与统一查询

- 在原合集实例路径下增加受控的脸级成员 `GET` 分页与 `POST` 批量 add/remove（1～500 个不同 `face_id`），复用 `collection_id + instance_token`、会话/Origin/CSRF、当前 revision/游标和错误模型；同一事务全量校验、失败全回滚、重复操作幂等，删除后 ID 复用不可误操作新实例。
- 扩展 **`persons/collection_sql.py::collection_condition()`** 为唯一的“人物动态成员照片 ∪ 按脸静态归档照片”权威过滤，避免只修 `/photos` 而遗漏搜索、时间轴、计数。集合成员实际变化才推进 `person_collections.revision`、必要的 `catalog_filter_revision`，幂等无变化不应无故使游标失效；旧游标按既有契约报过期。逐项核对 `collections._collection_photo_counts()`、`list_collections()`、`photo_page.photo_count`、`_collection_photo_faces()` 及搜索/时间轴调用链，不出现只有详情正确、目录计数或封面信息错误的情况。沿用现有分页/查询访问门禁。
- 修改 `collections.edit_members` 移出人物的隐藏副作用：**移出合集不自动恢复 `TEMPORARY` 或 `EXCLUDED`**，只有专用“恢复忽略”操作可以改变其忽略状态。**现有“移出合集会恢复人物列表”的旧行为将改变**，须同步修正提示文案并针对 TEMPORARY/EXCLUDED 都测试。保留所有历史状态，不回填旧合集。
- 只返回有界需要的归档脸缩略图；按页聚合读数据，不能按每位人物/每张脸额外请求，不能把合集成员展开到普通查询 `person_ids<=100` 参数中。

## 4. 分图库增量导入：哪些会延续，哪些不会

以下均指**同一份 `PhotoSearchData`/catalog**，先导入来源 A，之后加入来源 B/C；不是多个独立数据库的知识同步：

| 先前行为 | 来源 B 又出现同一人时 | 合集照片是否自动扩展 |
| --- | --- | --- |
| 手工确认 P，P 在合集 C 中 | 新脸若质量 OK、相似度/歧义合格、有效代表 READY 且无人工拦截，可自动归 P | **是**，在成功归 P 之后 |
| P 未命名但已有 CONFIRMED 成员并入 C | 与已命名人物一样可参与匹配 | **是**，若成功归 P |
| P 暂时忽略并入 C | P 仍可作为匹配参考；仍隐藏于日常人物列表 | **是**，若成功归 P |
| P 明确排除 | 不再作为正常参考人物，新脸可能另建组或待整理 | **否，不因被排除身份自动扩展** |
| 仅 `face_id` 静态收进 C（无 P） | 该归档不会生成任何人物匹配参考；新脸仍由普通算法独立判断 | **否，不因这次归档自动扩展** |
| 仅动态候选组/`SUGGESTED` | 未正式确认身份，不能把候选组当稳定人物 | **否** |
| 单脸已被静态收录，后来确认归 P，但未将 P 加入 C | 身份 P 可参与未来匹配 | C 仍**只包含原脸照片**，不自动扩展到 P 的所有照片 |

- 现有来源处理/默认 source-crop 原图人脸、候选发布、自动 `reconcile` 均须经过实际代码路径验证；只刷新前端或调用旧版 `rematch_unassigned` 不等于已经完成最新来源的匹配。
- `MANUAL_UNASSIGNED`、face exclusions、`EXCLUDED`、OPEN redetection mapping、LOW、模型空间不兼容、索引未 READY、合照冲突/近似歧义仍按现有安全规则处理；不得通过合集收录绕开。

## 5. 数据安全：执行门槛与回退

1. **本次只设计/开发，不操作真实 `PhotoSearchData`。** 实施前核对本机停止服务/后台建库和正在运行的维护任务；先用旧版 v31 的隔离数据库副本跑迁移及读写回归。
2. 利用现有 `catalog/migrate.py` 的预检、SQLite 一致性备份、逐迁移事务和 Schema 校验。对**实际库升级前**必须确认有可读取、可恢复的停机态数据库备份，并在隔离目录成功演练恢复（有条件可使用现有停机全 data-root 备份；不强制为此复制原始 30 万张照片）。不能直接拷贝运行中的 SQLite 主文件却忽略 WAL。
3. 升级前后比对原 `persons`、`faces`、人物关联/操作历史、`person_hidden/face_inbox_hidden`、老合集/成员以及现有向量索引的关键行数和人工事实指纹；新增关系表初始为空；无历史重分类和重新建模。
4. 备份/预检/Schema 或迁移失败须停止并报告，不自动继续写生产库。只新增 SQL 表及索引，不改历史 migration、不重建 `persons`/`faces`/向量表、不扫描照片。
5. **回退需停机并恢复升级前匹配版本的数据库备份**：仅 git revert 代码不能降 v32；禁止粗暴删表改 Schema 版本。升级后新录入照片或整理的修改不会出现在旧备份中，必须明确提示；不得承诺无损降级。

## 6. 最小但必须覆盖的定向验收

**阻断用例（必须通过）：**

1. **迁移**：带人物、合并/撤销、人工归属/排除、两类忽略及已有合集的 v31 fixture → v32；旧数据逐项保真、空新表、迁移重复执行幂等；故意失败回滚；备份在隔离目录可恢复；旧程序拒写过新数据库。
2. **合集照片**：人物 P 的 3 张照片 + 8 条静态脸归档（含同图 2 脸、重复加入、同时在动态 P 内），去重后按现有拍摄时间/游标完整分页；普通合集照片、合集限定搜索、时间轴、计数一致；旧合集升级后不变。
3. **候选组/UI**：本合集只收 3 张、全局候选有 20 张 → 页面只能展示这 3 张；同一脸不能重复显示在多个组；组快捷选中最多 500 且提交明确 `face_id`；Shift、多页选择、部分成功、失败保留选择，头像归属正确。
4. **归档与身份独立**：脸仅收录不创建 P、不改变 `CONFIRMED`/排除；后续脸分配到 P 但 P 未进合集，仍只收原照片；P 加入后才动态扩展。曾 `EXCLUDED` 的人/脸加入合集后保持 EXCLUDED；移出人物成员不意外恢复。
5. **来源 A→B**：用隔离合成资产/当前 source-crop 兼容代索引，A 的手工 `CONFIRMED` 人物 P + 合集 C，B 的同人合格且无歧义新脸成功自动归 P 并出现在 C；P 为 TEMPORARY 同样可以，EXCLUDED 则不能作为普通匹配候选；仅静态归档不自动扩展。未 READY、低质量、冲突、人工锁应保留原判定。
6. **重检测/删除**：同内容唯一可信映射正确展示；映射不明或 OPEN 不误指其他人脸、手工归档仍可恢复；资产失效、内容 SHA 改变无幽灵照片或误归档；人物合并/撤销不破坏静态脸收录。

只运行受影响 pytest、必要 Node DOM/`node --check`、Ruff、`git diff --check` 和聚焦代码审查；浏览器走一遍“单脸/候选组入合集 → 收起/恢复 → 合集照片/人物 → 新来源模拟”。**不要求**全仓、30 万真实库、GPU/模型准确率/发行打包测试；未实际执行的项目必须如实标注未验证。

## 7. 交付与明确非目标

**两个里程碑即可：**

- **M1 后端/迁移**：安全新增脸级合集关系，覆盖共享照片过滤和新版查询、保留原忽略状态；相关合成测试通过。
- **M2 前端/收尾**：统一快捷选择与候选组明确全选、合集分区展示、现有指定人物入口、来源 A→B 定向验证及简单浏览器试用。

**不做**：新 `face_group_id` 持久聚类、新聚类模型/人脸阈值调整、候选组自动确认、自动创建大批人物、永久跨代全库排除识别、独立 PhotoSearchData 之间同步、照片“忽略其余所有脸”的新快捷按钮、复杂新建人物多步骤事务向导（这些另行立卡，防止范围失控）。

交付报告：实际 HEAD/Schema 版本、迁移与备份恢复证据、影响文件、定向测试结果、未验证/风险、用户手动试用路径。**实施代码未经单独授权不得提交 GitHub，也不接触真实照片库。**

## 8. UI 两句固定说明

- **「仅加入合集」**：只收藏本次选择的照片/人脸；不代表确认同一个人，也不会因此自动收进今后出现的相似脸。
- **「确认人物并继续识别」**：明确指定/建立未命名人物后，符合现有识别条件的新照片才可能自动归到此人物；需将**人物**加入合集，合集才会随之自动增加照片。
