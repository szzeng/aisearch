# P4-PERSON-HIDE-A — 人物相册批量忽略与恢复

日期：2026-10-09。状态：**IMPLEMENTED / 本卡定向验证通过 / 同会话个人范围影响面复核通过 / 用户前端试用待完成**。计划基线：`d94f3c9bdfd7bea444cd5221bcb27d6d9699580e`；实际实施基线：`02179b90eecbdf1e4b2ffb4541a8f4c8077416bd`。个人相册的独立最小功能卡。**只隐藏人物列表项，不删除照片、不改变人脸归属或识别算法。** 执行记录与复核结论见[实现报告](../reports/P4-PERSON-HIDE-A-implementation.md)。

## 1. 目标与用户操作

- 「人物」和「整理一下」的**人物分组列表**提供「批量管理」：点卡片勾选、多页保留选择、显示已选数、取消或「忽略所选」，操作前给出简短确认。
- 提供「查看已忽略」入口，使用同一套人物卡片/分页组件，列出所有已忽略的活动人物（已命名、未命名均可），支持多选「恢复所选」；不另造管理页面。
- 忽略/恢复立即刷新当前列表、清空已用游标；失败提示且不误报成功。服务重启后保持设置。
- 忽略仅是**人物相册列表可见性**：原照片、脸、向量、确认的归属、人物详情/旧 ID 重定向、照片搜索、显式人物链接均不删除或封锁；被忽略者仍参与以后新照片的自动人脸匹配，匹配成功也**不自动取消忽略**。
- 「整理一下」已有的**待归类人脸收件箱**不是人物分组列表，本卡不隐藏收件箱人脸；不把忽略解释为 `MANUAL_UNASSIGNED` 或人脸排除。

## 2. 最小后端设计

### A. 独立持久化标记

新增连续增量迁移，在现有 `persons` 表之外创建 `person_hidden(person_id INTEGER PRIMARY KEY REFERENCES persons(person_id) ON DELETE RESTRICT)`；**有记录 = 已忽略，无记录 = 可见**。无时间戳、理由、操作历史、独立恢复队列。

当前 `SUPPORTED_SCHEMA_VERSION=21`；若实施时仍为 v21，则新文件用 `0022_*.sql` 并升为 v22；若已有后续迁移，顺延到下一可用版本。只允许加新迁移，不修改旧版本或冻结契约。迁移对既有图库默认全员可见，无需重新建库/跑模型。

### B. 列表过滤与分页

在现有 `GET /api/v1/persons/browse` 添加受限 `visibility=all|visible|hidden`：
- **默认 `all`**，保持原调用者（含 `loadChoices()`）、排序及已有游标行为。
- `visible` / `hidden` 在 **SQL WHERE、ORDER BY、LIMIT 之前**按活动 canonical `p.person_id` 检查隐藏表，不在前端取 40 人后再剔除。
- `kind=all|named|unnamed`、名字/别名 `q`、未命名空组过滤及人数/头像投影仍沿用原语义；「查看已忽略」用 `kind=all&visibility=hidden`。
- 新 visibility 模式的游标绑定模式及既有 `kind/q` 等有效条件，不能跨模式混用；`all` 不传 visibility 的旧游标继续有效。写操作后 UI 重置游标并重读；个人单用户使用不要求并发隐藏操作的长事务快照/新持久版本体系。
- 与 [P4-PERSON-SORT-A](P4-PERSON-SORT-A.md) 兼容：若按照片数全局排序已完成，**先按 visibility 过滤，再全局排序/分页**；不能恢复逐人 N+1、也不能把先取 40 人再隐藏当作正确实现。

### C. 一个批量写 API

新增 `POST /api/v1/persons/visibility`，body 最小形状：`{"person_ids":[1,2],"hidden":true}`。
- 允许 1～500 个 ID；必须是有效正整数、去重；不接受未知/不存在/无效或无法解析的 ID。
- 在一次 SQLite 写事务内解析到**活动 canonical person**、全部校验后再插入/删除隐藏表；任一项失败，整批回滚。重复隐藏/恢复为幂等 no-op；返回实际处理/目标状态的简单摘要即可。
- 沿用现有受保护写请求的会话、Origin/CSRF 门禁和错误风格，不增设复杂操作协议或撤销历史。
- 合并时**不修改隐藏表**：合并后以目标 canonical 人物的标记决定可见性，来源历史标记保留；若原合并被撤销，来源恢复活动身份时保留其先前隐藏状态。旧 source ID 经 canonical 解析后操作作用于当前目标。

## 3. 最小前端改动

主要复用 `src/photo_search/web/persons-albums.js`、`persons.html`、已有 CSS/卡片组件和现有 40 人分页：
- 普通 `loadPeople()` 请求显式带 `visibility=visible`，隐藏页带 `visibility=hidden`；筛选/翻页/重绘不丢失已选 ID，切模式、成功操作或离开页面时清理选择。
- 批量模式点击卡片是勾选而不是打开相册；退出批量模式恢复原打开行为；忙碌时禁重复提交。单次最多提交 500 ID，达到上限明确提示。
- `loadChoices()` **保持默认 `all`**，避免影响现有合并/指定人物；普通相册详情、封面、搜索、收件箱、头像优先级和原本的错误处理不变。
- 不修改 `face/index.py`、识别门限、候选代表、人脸事务、照片/向量索引或 GPU 流程。

## 4. 简单定向验收（个人范围）

只用隔离 SQLite/合成数据，不访问 `PhotoSearchData`、实际照片、GPU，不做全仓/30 万规模/打包/浏览器矩阵。

1. **隐藏/恢复与重启**：10 个测试人物，批量隐藏 5 个，正常列表显示其余 5 个、隐藏页显示 5 个；数据库重开后仍有效；恢复后全员可见；重复写幂等。
2. **列表/合并边界**：在现有分页测试基础上覆盖超过 40 人的边界、`visibility` 游标隔离及默认旧接口不变；隐藏源并入可见目标、可见源并入隐藏目标，展示状态均取目标；旧 ID 可解析、原人脸归属和候选不变。
3. **失败全回滚**：批内混入不存在 ID，确认没有部分隐藏；会话/CSRF 沿用既有写接口保护。保留当前人物列表定向性能检查，不新增 N+1。

仅运行相关定向 pytest、修改面 Ruff、Node `--check`、`git diff --check`；可复用现成测试夹具。真实前端交互由用户手动试用「选择→忽略→查看已忽略→恢复→重启」即可。既有人脸合并后新照片匹配算法不修改，不要求再跑模型做大规模识别率验证；最少静态/合成断言隐藏表不影响候选入口。
