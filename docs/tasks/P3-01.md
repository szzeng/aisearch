## 用户场景

用户有大量截图、文档翻拍与高文字密度图片：他要能用中文/英文数字直接搜到图里的文字（例如
「发票 金额 1280」「车牌 苏A」「护照 MRZ」），能看到每张图的**原文**（不做 VLM 自动纠正）与
**每个识别区域的坐标和置信度**，能对单张或选定范围**强制重新识别**，并且在识别尚未完成或结果过期时
看得到「OCR 仍在追赶」，而不是把「没有结果」当成「图里没有这段文字」。

## 本任务范围

1. **OCR 处理器契约落地**（沿用 ADR-0003 已冻结外壳，不新造协议）：一个 `ocr_model`/`image_ocr`
   `ProcessorSpec`（`device_policy=CPU_PREFERRED`、`runtime_backend=onnxruntime`、权重与
   `config_hash` 取自 P0-04 manifest、`cancellation_supported=true`），`JobRequest/JobResult`
   五字段身份不变；**禁止隐式 fallback**，也不得把 OCR 结果伪装成向量（`embedding` 字段一律不出现）。
2. **固定权重加载**：只从数据根下的固定相对路径加载 P0-04 记录的 det/cls/rec 三个 ONNX 与
   `config.yaml`，启动前逐文件校验 sha256；缺件/哈希不符 → 结构化失败（沿用既有码或按 §“允许修改”
   在 `catalog/errors.py` 增补一个 extra 码），**不得**回退到 wheel 内置的「最新默认模型」。
3. **有界高分辨率输入与切片策略**：不得把整图压到 320/448 px 再识别；给出有界长边/切片上限、
   解码预算与取消检查（CPU 路径，无 GPU 依赖），并如实记录实际用到的尺寸/切片数。
4. **结果与产物**：结构化产物保存**原文**（不改写数字/日期/编号）＋按阅读顺序排序的区域
   （polygon/box、文本、置信度）＋处理器/权重版本/输入 revision；低置信度区域保留并可查询。
   SQLite 侧只保存**检索副本**（Unicode/空白/分词规范化后的 `ocr_text`）与区域元数据，
   原文与坐标不进入普通日志/URL/响应（沿用 P2-03A 的隐私边界）。
5. **FTS 更新**：经既有 `search_projection_queue`/`sync_document` 把 `search_documents.ocr_text`
   投影进 FTS5；写入必须与权威 revision 同事务排队、幂等、可重放；晚到的旧 revision OCR 结果
   **不得**覆盖更新的投影或把内容变化前的旧文本附着到新内容（联测 P1-02/P1-06 与 P2-03 的窗口）。
6. **强制重新识别入口**：至少一个受控入口（CLI 子命令或既有 `catalog ...` 风格工具）对单张或
   选定范围排入 OCR 任务，并复用同一幂等键语义；不新增常驻线程。
7. **如实状态**：`/capabilities`、`/stats` 或既有只读诊断里能看出 OCR 的**就绪/落后**（不撒谎、
   不把「未运行」显示成「没有命中」）。

## 必须保持的不变量

1. **迁移只在确需时新增**：`search_documents.ocr_text` 与 FTS 触发器**已存在**，因此优先不新增
   migration；若必须保存区域/原文，则新增**连续** `0009`，`schema_version 8 → 9`，
   `0001`～`0008` 逐字节不变，且遵守 ADR-0002 §7（只读预检、备份、单事务推进、缺件/过新拒写）。
2. 权威判定只看 SQLite；OCR 结果是可重算的机器产物，不改资产身份、位置、缺失判定与人工地点状态。
3. 原文与检索副本分离：`ocr_text` 只放规范化后的检索副本；数字/日期/编号**不做**自动纠正。
4. 迟到的旧 revision OCR **不得**覆盖新投影、不得附着到新内容；同一逻辑任务重放不得产生第二行。
5. 隐私：区域坐标/原文不进普通日志、URL、错误详情、反馈与向量库；普通响应只给计数/状态；
   精确坐标语义仍只属于既有会话保护入口。
6. 既有 P1/P2 测试原样通过（版本耦合的机械断言除外，需在报告说明）。

必需命令（沙箱内被拒时在沙箱外执行并在报告里记录）：

```text
uv run --no-sync pytest -q -p no:cacheprovider tests/unit tests/integration

```

等级：**B**。若新增 migration / 触及 outbox 投影或人工知识事务 → 加 **D**（具名故障注入：
权重缺件/哈希不符、提交前崩溃、Lance/outbox 未确认窗口、内容变化后旧结果、迟到旧 revision）。
若新增依赖、`workers/**`、打包入口或新增 package-data 目录 → 加 **C**（真实 onedir 构建 +
`tools/diagnostics/packaged_api_smoke.py`，工作目录放 D 盘）。

**真实夹具要求**：用脚本生成**真实含文字**的图片（中文 + 数字，至少一张高文字密度截图）跑通端到端，
断言原文、区域数量/顺序、置信度区间与 FTS 命中；`%TEMP%` 夹具即可，禁止使用真实个人照片。若本机
无法在 CPU 上稳定加载固定权重，如实记录 `IMPLEMENTED / VALIDATION PENDING` 并建议转 C1，
不得跳过验收直接标 PASS。

## 失败与升级

- 需要新的跨模块协议/数据语义（例如原文/区域的持久化形态、OCR 世代的切换与回退）→ 停止并建议手动切
  **C2 / GPT-5.6 Sol / high**；不得自行改 ADR/冻结 schema。
- 问题落在 ONNX Runtime/DLL/Windows 路径/权限/性能或真实模型接入 → 停止并建议手动切
  **C1 / GPT-5.6 Terra / medium**。
- 无法在 `%TEMP%` 夹具里安全复现的场景：标记 `VALIDATION PENDING` 并说明缺的是产品能力还是验收能力。

## 已知继承项（执行时先复核，勿静默忽略）

- 本构建的 API 进程**没有任何真实编码器**：文本查询 409 `QUERY_ENCODER_UNAVAILABLE`、上传搜图 409
  `IMAGE_ENCODER_UNAVAILABLE`（P2-06A/P2-07 记录）；OCR 是**独立**处理器，不得借它绕过该边界，
  也不得把 OCR 文本塞进向量通道。
- `photo_search.geo.extract`/`geo.resolver`/`scheduler.engine` 仍不在冻结包内（无常驻调度线程）；
  本卡若改动导入图或打包资源，必须重跑 C 并复核。
- `search_documents.ocr_text` 目前恒为空串，FTS 触发器已就绪；`rebuild_all`/`catch_up` 是唯一
  投影入口（P2-04 §10 记录 `rebuild_all` 尚未接 CLI/调度）。
- 打包 smoke 每次必须使用**新建**的工作目录；`D:\PhotoSearchSmoke\P2-06B*` 里的遗留 112 B
  `session.json`（旧 `(R,W)` DACL）不要擅自 takeown 或改写 ACL。
- 地名包的进程内 warm cache 边界与「人工地点编辑先降级为 `PENDING_REPAIR`」的投影追赶语义见
  P2-08 报告 §5.1/§5.2；OCR 的投影更新必须遵守同一套语义。
