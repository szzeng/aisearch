## 一、目标、事实与范围

**用户需要的结果**：

1. 打开具体智能合集，照片缩略图规整、可点开、错误状态可理解；横图/竖图/CR2 不再把网格撑乱。
2. 智能合集目录更紧凑，名称突出，操作和技术文案不过度占空间。
3. 合集内照片向下滚动自动加载，通常不用点“加载更多”；失败时仍有明确的手动重试入口。
4. 切换合集、排序、匹配结果/已排除、刷新或模型状态时，照片与提示不串页、不重复、不遗漏。

**源码确认的事实**：

- 普通照片合集有专门的 `#photo-collection-assets img` 宽高/比例样式；智能合集 `#photo-smart-assets` 没有相同约束。智能结果和已排除各自直接创建 `<img>`，错误占位与主图库的缩略图处理不统一。这是**高可信的显示风险**，但具体症状仍以实际复现为准。
- 智能目录沿用来源管理 `.sources` / `.source-card` 大卡，且直接显示 `FILTER/TEXT/COMBINED` 等内部术语。
- 智能详情现有 API 是 `limit<=50`、`next_cursor` / `has_more`；前端只绑定手动“加载更多”。主图库已有 `PhotoScrollPager`，可以复用其滚动触发与失败回退思路。
- `loadPhotoSmartAssets()` 在详情元数据请求返回后，**尚未核对请求版本就写入状态/标题，并可能发起刷新 POST**；随后才在照片页返回时核对版本。目录与详情还共享 `photoSmart.requestVersion`。存在迟到请求污染当前页的风险。
- 非首次加载/切换排序可能重复触发自动刷新；自动刷新发起后缺少可靠的完成后页面更新。`FILTER` 页面把非语义的默认排序写作“相关度”。

**先做一次隔离浏览器复现与网络核对**。若用户所说的“显示异常”实际是 API 报错、图片 404、解码失败或权限失效，不可只改 CSS 就宣称修好；在本卡内定位与照片浏览直接有关的最小修复点，并记录根因。不要推断真实图库已复现。

**范围限制**：首选智能合集 UI 的小范围修复。默认**不改数据库、migration、模型/向量、语义算法、候选上限、搜索规则、持久化人工排除或后端游标协议**；除非经过证据确认必须修改一处直接相关的服务端问题，否则不要改后端。禁止访问或修改真实 `PhotoSearchData`，不下载模型、不重建索引、不做全站 UI 重构。

## 二、实施要求（按顺序）

### A. 照片详情网格与缩略图（P1）

1. 在 `#photo-smart-assets` 的作用域内统一卡片与图片尺寸：响应式列宽、稳定缩略图框（推荐 1:1）、`width:100%`、`object-fit:cover`，纵横照片都不能撑破列宽；保持图片查看器展示原始比例，禁止裁掉原图数据。
2. “匹配结果”和“已排除”尽量共用**轻量的本页卡片生成逻辑**，或共享现有安全工具；确保缩略图加载中、失败、原文件离线等状态有可见且可理解的占位，不出现裸破图图标。图片用懒加载/异步解码；不为每张图增加 SQL、AI 请求或高分辨率图片预取。
3. 缩略图地址沿用现有受鉴权的同源 API，避免 `/api/v1` 重复拼接；不能未经核对改用与当前缩略图 API 不兼容的 Blob/Object URL 逻辑，也不能误用主图库全局 URL 回收状态。
4. 保留单击查看、关闭返回、智能排除与恢复操作。操作可以变得紧凑，但必须始终可发现、有可访问名称、有键盘焦点，触屏可操作；**“从智能合集排除”不是删除原图**。
5. 仅改变智能合集 CSS 作用域，不影响普通照片合集、来源卡片、时间轴、人物和全站图片网格。

### B. 合集目录紧凑布局（P2）

1. 仅给 `#photo-smart-collections-list` 加专用布局类；不要直接缩小公共 `.sources` / `.source-card`。自适应布局：有足够内容宽度时 2～4 列，窄屏一列；卡片适当限制宽度，避免只有一张时独占超宽整行。长合集名要截断或合理换行，不产生水平溢出。
2. 卡片信息：**名称作为主标题**，附简短规则类型与状态；改名/删除用紧凑而清晰的操作入口。类型显示“条件筛选/文字检索/综合搜索”，不向普通用户直接暴露 `FILTER/TEXT/COMBINED`。
3. 状态从现有 API 映射：`CHECK_ON_OPEN` 只提示“打开后检查”，不能伪称当前最新；区分已缓存、待更新、更新中、尚无缓存、模型需重新绑定与错误；`NO_CACHE` 不能误报为“没有匹配照片”。`candidate_count` 只能称**候选数**，不能当作排除/失效复核后的准确匹配照片数。
4. 目录依旧按现有接口每页 20 个拉取，**不新增逐合集 COUNT、搜索、封面查询或模型检查**。保持普通合集与来源管理页原貌。

### C. 自动下滚续页（P1）

1. 匹配结果和已排除列表都支持自动续页。优先复用 `PhotoScrollPager.create()`，加专用 sentinel；浏览器接近底部时读取**下一页 50 张**。先查清本页实际滚动根节点；不能假定 `window` 滚动必然适用于所有布局。
2. 统一分页入口必须明确返回 `Promise<boolean>`：**成功追加或正常到末页返回 `true`；网络/服务器/游标失败返回 `false`**，使滚动组件暂停自动触发并给出“重试加载”。不可像现有某些 `.catch()` 一样吞错误后返回 `undefined`，造成重复触底与请求风暴。
3. 每个活动照片列表只允许**1 个分页请求在途**；仅当 `has_more && next_cursor` 存在且当前视图可见、viewer 未占用、标签和排序未变时加载。重复触发不得并发请求同一 cursor，也不得重复插入同一页。响应中的 `has_more=true` 却没有 cursor 视为协议异常，停止续页并提示，不得死循环。
4. 给本页建立可判断的请求身份：至少包含 `smart_id`、`instance_token`、当前标签、排序、必要的 rule/exclusion/build 版本及本次视图 epoch。切合集、切标签、改排序、离开详情、替换规则、人工排除/恢复后，旧响应（含失败提示）不得再写当前状态或 DOM。可以取消请求，但**不能只依赖 AbortController** 而省略迟到响应检查。
5. 复用滚动组件时移除旧按钮的重复 click 监听，避免一次点击发两页；`IntersectionObserver` 不可用、网络失败或游标冲突时应显示后备“加载更多/重试/重新读取”按钮。首屏容器太短时允许**有限次**自动填充，不得在用户没有新的滚动意图时持续无界翻页。
6. **409/旧游标失效**：保留已经可见的照片作为旧视图，阻止继续拼接，提示“合集结果已变化，点击重新加载”；用户明确重载后从第一页取得新快照。不要无限自动重试或暗中用第一页混到旧列表后面。新构建完成也不得接着旧 build 的 cursor 翻页。
7. **资源管理采用渐进方案，避免把 UI 修复变成虚拟滚动项目**：先做每页 50、请求单飞、图片懒加载与非可见视图停载；用大于 500 张的合成数据检查活动节点、已发图片请求与向上回看。若明显持续增长或卡顿，再在本卡内加入最小的页级回收/恢复机制。若回收旧页，必须支持用户上滚重新显示旧页、维护滚动锚点和版本失效；**绝不直接照搬目前会产生 `li` 占位的 `trimGrid()` 到 `div` 容器，更不可删完旧卡片后留无法恢复的空洞**。无证据不强制实现复杂双向虚拟列表。
8. 已排除列表分页与结果页拥有独立游标/快照边界，切换标签时不沿用另一标签游标；已排除不可用原图的卡片依然可恢复排除。

### D. 刷新与异步竞态（P1）

1. 将**合集目录请求、详情 metadata、匹配结果页、已排除页、刷新 POST 与完成轮询**的生命周期拆清楚；在每个异步阶段**写入 state/DOM 或发起后续请求前**核对当前页面身份。不能只在最后一层照片请求处核对版本。尽量小幅调整现有 `app.js`，不引入全局状态管理框架。
2. 对同一合集、同一规则/缓存状态，自动刷新只提交一次合理请求；切排序/标签或续页不重复自动 POST。`FILTER` 不触发排名缓存刷新；`MODEL_REBIND_REQUIRED` 不反复尝试刷新。后台 runner 的排队、单飞、发布与失败规则仍由后端保证。
3. 手动/自动刷新共用**一个可停止的状态观察流程**。离开详情、切合集或替换规则时停止观察者/定时轮询；反复打开页面也不能累积轮询。完成后重新确认 `build_id` / 最新详情：用户在首屏附近可以自动更新；若正在中段浏览，保留旧视图并提示“有新结果，点击更新”，避免突然跳顶。若服务端拒绝旧缓存或资格复核失败，尊重服务端判定，不能为了保持显示绕开认证、范围或人工排除过滤。
4. 区分加载中、实际零匹配、尚无排名缓存、索引处理中、上次结果、刷新失败、模型不兼容、续页出错。旧刷新请求的状态文字不能覆盖当前照片页状态。错误后可手动重试；没有无限轮询或自动重排队。
5. 纯 `FILTER` 合集默认展示**拍摄时间倒序**（后台已支持 `capture_desc`），或使用明确的非相关度默认顺序；不得声称存在语义相关度。建议 UI 根据 execution kind 初始化：`TEXT/COMBINED` 可选“相关度/拍摄时间”，`FILTER` 仅提供真实适用排序。**只改变 UI 默认选择和文案，不改后台同一 order 的排序真值。**
6. 排除/恢复使用当前有效 `expected_revision`；409 冲突时给出更新提示，不静默覆盖，不自动重复有副作用的写操作。成功后刷新本列表与标记，能保留合理的用户位置或明确提示列表已更新。

## 三、保持不变的合同

- `FILTER/TEXT/COMBINED` 成员资格、相关度计算、稳定排序/平局处理、排除持久记录、规则 identity、`instance_token`、CAS revision 和服务器权威校验不变。
- `psf1`、`psr1`、`pse1` 分页 token 由服务器生成/验证，前端只原样续传；不能修改它们的含义，也不能以客户端去重掩盖后台漏页或先 LIMIT 再过滤的问题。
- TEXT/COMBINED 的**有效已发布缓存**翻页不重新执行 Qwen/CLIP 推理；缓存过期时继续尊重服务端的范围复核与刷新约束。
- 不改变“另存为普通合集”、删除合集、普通合集成员真值、照片本体与用户的人工排除。
- 不新增数据库表、依赖、后台服务或新缓存协议。过期 ranked 缓存逐页重做资格核验只是**待评估热点**：若本次轻量观察发现明显成本，先记录调用数和数据形状；仅在能证明不改变安全/状态合同的前提下做局部小修，否则不在本卡加入跨请求缓存。

## 四、性能设计（PERF-BOUNDED，个人项目轻量）

- **路径与风险**：目录打开 → 50 张首屏 → 滚动续页 → 缩略图可见 → 刷新回显。重点防止重复刷新 POST、触底连续拉取、每张图额外请求、DOM/解码资源随翻页失控、过期候选资格复核被过度重复。
- **做法与边界**：目录 20 项/页、照片 50 张/页、单飞、可见时才触发、有限首屏填充、懒加载，优先使用现成组件；不默认重搜模型、不一次载入全部照片、不先引入复杂虚拟列表或新后台缓存。
- **验证与停止**：在同一份隔离合成库检查首屏/续页请求次数、向下滚动和上回看、500+ 资源增长及失败/409。只在真实热点证据出现时追加简单 SQL/5000 候选对照；完成本卡功能与可接受的实际浏览体验即停。**不增加 30 万、GTX 1660、GPU 或正式 P95 性能认证**，不把小样本说成容量保证。
