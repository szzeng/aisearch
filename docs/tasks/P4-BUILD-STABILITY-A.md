# P4-BUILD-STABILITY-A — 大图库低算力建库并发与恢复可靠性加固

**任务性质：** 稳定性审查 + 最小修复 + 定向并发测试

**优先级：** P0

**目标环境：** Windows / 机械硬盘 / GTX 1660 / 大图库（未来支持 30 万张以上）

**执行要求：** 先审查最新代码，再修复确认的问题。不允许凭推测大范围改造。

## 一、任务目标

解决大图库长期建库过程中可能出现的：

1. SQLite 写锁长期竞争、任务饥饿。
2. Qwen、人脸识别、OCR GPU 任务争抢显存与算力。
3. 后台任务无法及时取消，程序退出时无限等待。
4. 机械硬盘慢 I/O 导致任务长时间没有进度。
5. 任务租约过期、重复执行或恢复异常。
6. 表面显示正在建库，实际已经没有有效进展。

核心目标：

**保证建库可以持续运行、暂停、退出、重启和恢复；任何一个后台任务变慢或失败，都不能拖垮整个图库。**

不追求后台任务始终满负荷运行，优先保证稳定性、可恢复性和前台浏览搜索的正常使用。

## 三、必须处理的四个方面

### A. GPU 资源协调

当前项目已经有：

- `BACKGROUND_MODEL_SLOT`
- `ModelResourceGate`
- `GatedEncoder`

需要核对所有 GPU 推理入口，特别是：

1. Qwen 语义建库。
2. 人脸检测与识别。
3. OCR GPU 推理。
4. 候选模型构建。
5. 前台语义查询。

重点检查 OCR 的 GPU 执行路径是否真正受到后台模型资源协调保护。

**要求：**

- 复用现有资源协调机制，优先避免新增重复锁。
- GPU OCR 执行需要进入正确的共享资源协调范围。
- CPU OCR 不得无故占用 GPU 锁。
- GPU 资源等待必须支持超时、取消和异常释放。
- 保持前台查询现有优先保障机制。
- 候选模型目前的锁获取顺序必须保持一致，不能形成锁顺序反转。
- 保留人脸识别现有 RLock 可重入要求。
- 不允许因为增加锁而让整个后台系统永久排队。

特别注意：

GPU 占用时间较长时，应允许后台任务在安全批次边界让出资源，而不是无限期独占。

### B. 建库停止、取消与退出安全

重点解决两个已经发现的代码缺口：

**1. LibraryRefresher**

当前 `close()` 有 5 秒等待，但没有完整地将关闭请求传递到 `refresh_library()`。

而流水线本身已经支持 `cancel_check`。

要求：

- 增加明确的取消信号。
- `close()` 时设置取消信号。
- 将取消信号传递给 `refresh_library()`。
- 扫描、语义建库、人物识别、OCR 和其他可分批执行阶段，在安全边界检查取消。
- 取消时保留已经完成的结果。
- 未完成任务必须保持可恢复，不得伪造完成状态。

**2. CandidateBuildManager**

当前 `close()` 使用无超时的 `thread.join()`。

要求：

- 关闭时先请求停止。
- 使用有界等待。
- 工作线程仍然运行时，不能提前标记为已经终止。
- 不能清除仍然有效的任务所有权。
- 不能在旧线程仍然访问图库时释放数据目录独占租约。
- 必须处理 `ApiContext.close()` 和应用生命周期中的租约释放顺序。

如果 GPU 推理或文件 I/O 暂时无法中断，必须明确报告关闭未完成，并保持数据目录互斥保护。

禁止使用强制终止 Python 线程的方式解决问题。

**重要：不能为了让程序快速关闭，而造成旧线程和新实例同时写入同一个图库。**

### C. 机械硬盘慢 I/O 与任务租约

重点检查：

`scanner.py::sha256_file()`

目前文件哈希采用分块读取，但读取过程中没有取消检查或独立进度心跳。

需要验证：

- 大型 RAW 文件读取很慢时，是否会超过任务租约。
- 文件读取期间是否可能出现租约过期。
- 原任务执行结果是否可能被新任务合法接管。
- 慢速磁盘是否会造成错误重试或重复处理。

要求：

1. 在安全的文件读取分块边界支持取消检查。
2. 如果确实存在租约过期风险，增加适当的限频心跳。
3. 心跳不能每读取一个小数据块就写一次 SQLite。
4. 文件读取期间不得长期持有 SQLite 写事务。
5. 不得因为超时就把尚未完成的文件标记为成功。
6. 不得强制终止正在执行的系统级磁盘读取。

对于单次操作系统 I/O 阻塞，应该报告等待状态，而不是假装已经完成取消。

### D. 建库进度与卡顿诊断

增加轻量级的进度诊断，不需要重新设计 UI。

至少能够区分：

- 正在扫描文件。
- 正在读取文件及计算哈希。
- 正在等待 SQLite 写锁。
- 正在等待 GPU。
- 正在加载模型。
- 正在执行模型推理。
- 正在提交向量索引。
- 正在等待任务租约。
- 正在恢复之前的任务。
- 已取消或发生异常。

建议记录：

- 当前建库阶段。
- 当前任务 ID。
- 最后一次有效进度更新时间。
- 当前批次的处理数量。
- 最近一次成功提交时间。
- 资源等待原因。
- 最近错误及错误发生阶段。

要求：

- 超过合理时间没有进展时能够识别并提示。
- 区分慢速运行、资源等待、磁盘停顿和真正的异常。
- 不要仅凭进度长时间不变就认定发生死锁。
- 不需要为此增加复杂的独立监控系统。
- 不需要把完整本地照片路径暴露给用户。

## 四、SQLite 与索引安全边界

重点复核：

`IndexCoordinator.process_batch()`

已有 outbox、LanceDB 写入、确认及恢复机制不得被破坏。

特别注意：

1. 不允许随意将 LanceDB 写入移出原有确认事务。
2. 不允许丢失 IN_FLIGHT、PENDING 和 CONFIRMED 状态之间的恢复关系。
3. 不允许重复生成已经确认的向量。
4. 不允许改变 generation 身份和向量维度。
5. 不允许因为 SQLite BUSY 就丢弃后台任务。
6. 不允许为了降低锁竞争而引入新的数据一致性问题。

检查其他数据库写事务是否意外包含文件读取、模型推理或不必要的长时间操作。

已有 P4-02V 的前台让步逻辑和有限重试策略必须保留。

## 五、定向故障注入测试

必须使用独立临时图库，不允许直接拿用户正在使用的真实图库做破坏性测试。

| 测试 | 验收要求 |
|---|---|
| 外部 SQLite 持锁 30 秒 | 后台任务能够等待、恢复，不丢失工作 |
| Qwen 与人脸同时请求 GPU | 资源协调正确，不发生锁死 |
| GPU OCR 与 Qwen 同时请求 GPU | 正确等待或让步，不失控并发 |
| CPU OCR 与 GPU 建库 | CPU 工作不被不必要的 GPU 锁阻塞 |
| GPU 等待期间请求取消 | 在安全等待边界及时取消 |
| 建库期间关闭程序 | 不无限等待，不提前释放数据目录租约 |
| 候选建库期间关闭程序 | 任务状态与实际线程状态一致 |
| 模拟机械硬盘慢读取 | 能报告慢 I/O，取消与租约机制正确 |
| 扫描过程中中断 | 重启后继续处理，不重复确认已完成内容 |
| LanceDB 写入期间模拟异常 | outbox 能正确恢复，无重复向量 |

特别增加锁顺序测试：

- 两个线程分别申请现有资源。
- 使用事件控制获取顺序。
- 检查是否存在循环等待。
- 测试必须有明确超时，不能让测试自身无限挂起。

要求：

如果当前执行环境没有 GTX 1660 和机械硬盘，必须如实标记实机测试未完成，不能用模拟测试冒充实机验证。

## 七、验收标准

以下全部满足才允许标记完成：

1. 没有未经说明的无限期资源等待。
2. GPU 后台推理入口具有一致的资源协调策略。
3. CPU 任务不会被无谓地 GPU 锁阻塞。
4. 取消信号能够传递至建库流水线。
5. 关闭时不会发生旧线程和新实例同时操作同一图库。
6. 数据目录租约只在相关工作线程安全退出后释放。
7. 大文件读取不会因为单次慢 I/O 就错误丢失任务。
8. SQLite 与 LanceDB 的确认、幂等和恢复协议不被破坏。
9. 已完成的任务不重复处理，未完成的任务可以恢复。
10. 前台照片浏览和搜索不因后台维护而被长期阻塞。
11. 定向测试、Ruff、Python 编译和 diff-check 全部通过。

## 八、严格禁止的范围

本任务不涉及：

- 更换 Qwen 或 Chinese-CLIP 模型。
- 改变 512D / 1024D 向量维度。
- 修改语义搜索算法及匹配阈值。
- 修改 OCR 和人脸识别准确度参数。
- 重新建立整个图库索引。
- 删除或重建 catalog.db。
- 删除原始照片。
- 大规模重写任务调度系统。
- 引入复杂的多进程分布式队列。
- 未经必要性证明就增加数据库迁移。
- 为了提高速度牺牲数据一致性。

如果发现问题需要超出以上范围，先停止扩展，说明原因，不要自行扩大任务。
