## 用户场景

用户有大量家人/朋友合影。他要在不联网、不上传的前提下看到「这张照片里有哪几张脸、每张脸的
位置与质量」，让系统**保守地**把明显同一人的脸放进同一个未命名分组（宁可漏、不宁可错），并且
在后续任务里能改名、合并、取消错误归属——人工结论永远优先于自动结果。

## 本任务范围

1. **人脸处理器契约**（沿用 ADR-0003，不新造协议）：一个 `face_model` 处理器
   （`processor_kind=embedding_model`，`task_type=image_face`，`device_policy` 按 ADR-0001 的
   默认 CUDA 路径取 ADR-0003 的 `CPU_ALLOWED`：默认走 GPU，显式 CPU 请求被服务并**记作降级**，
   任何 GPU 故障都**不得**变成隐式 CPU 运行），`space_id`/`dimension=512`/`metric=cosine`/
   `normalization=L2` 取自 P0-04 manifest；`config_hash`/权重 SHA-256 取自同一 manifest。
2. **固定权重加载**：只从数据根下固定相对路径加载 `det_10g.onnx` 与 `w600k_r50.onnx`，启动前
   逐文件校验大小与 SHA-256；缺件/哈希不符 → 结构化失败（沿用 P3-01 的
   `OCR_WEIGHTS_MISSING`/`OCR_WEIGHTS_HASH_MISMATCH` 或按需在 `catalog/errors.py` 增补 extra 码），
   **不得**回退到 InsightFace 自动下载或 bundled 默认包。
3. **检测/对齐/特征**：每张脸产出 `face_id`（稳定、确定性）、方向归一后的 bbox + 5 关键点、
   检测分数、人脸质量（至少尺寸与清晰度口径）、独立 512 维特征。人脸输入分辨率按人脸预处理
   配置处理，**不得**拿 320 px 网格缩略图当人脸输入；来源离线/文件变化 → 阻塞且不写事实。
4. **持久化**：新增连续 migration `0010_face_core.sql`（`schema_version 9 → 10`），保存当前
   每张脸的检测事实与规范向量（`faces` / `face_embeddings` 或等价命名，需在报告中说明最终命名），
   并保证：同一 asset 重跑不产生第二套脸；`face_id` 对同一内容 + 同一检测/特征世代是确定性的。
   人工知识表（人物、归属、锁、排除）属于 P3-03/P3-04，**本卡不实现命名/合并/取消归属语义**；
   但必须为它们预留「人工优先」的读取顺序并在报告中写明边界。
5. **独立候选索引**：人脸特征放进**独立于图片 space** 的派生候选索引（近邻候选或增量代表匹配，
   不做全量两两比较）。若复用现有 `index_entries`/LanceDB 资产级主键会改变其身份或主键语义，
   先停止并建议转 C2；不得静默把多张脸塞进一行或复用图片向量空间。
6. **保守自动关联**：为明显同一人的脸建立**未命名分组**（person 行可为 `name = NULL`）。
   阈值必须用真实夹具校准并记录：同人/异人、年龄变化、侧脸、低清；**不得写死 0.45**。
   关联必须满足：同图多人冲突检查（镜子/拼图等异常允许人工覆盖，本卡先记录冲突而不自动合并）、
   低质量/边界样本进入待确认而不是强行分组、重跑同一内容不产生新分组。
7. **如实状态**：`GET /api/v1/capabilities`（或既有只读诊断）能看出人脸处理的就绪/落后
   （已分析数、未分析数、阻塞原因、候选索引待确认数），**不把「未运行」显示成「照片里没有人」**。
8. **受控入口**：至少一个 `python -m photo_search.face.cli` 风格入口（照 P3-01 的
   `photo_search.ocr.cli`），支持单张/范围/全库排入人脸任务与 `--force` 复用同一逻辑任务；
   不新增长驻线程。`ingestion/**` 仍属禁止修改范围。

## 必须保持的不变量

1. 权威判定只看 SQLite；人脸特征与候选索引都是可重算的机器产物，不改资产身份、位置、缺失判定、
   地点状态与 OCR 文档。
2. 迁移只在确需时新增，并遵守 ADR-0002 §7（只读预检、备份、单事务推进、缺件/过新拒写）；
   `0001`～`0009` 逐字节不变。
3. 人工知识优先：本卡只**创建**未命名分组与自动关联；任何自动结果都不得覆盖（更不得删除）
   人工归属/锁/排除——该读取顺序必须在本卡就成立，即使人工表由 P3-03/P3-04 补齐。
4. 人脸向量与图片向量严格分 space；人脸候选索引的世代切换不重算图文向量，反之亦然。
5. 迟到/过期租约、内容变化前后的旧结果不得写入或覆盖新事实（沿用 P3-01 的
   `STALE_LEASE`/`STALE_INPUT_REVISION`/`input_revision = assets.sha256` 守卫）。
6. 隐私：人脸坐标/关键点/特征不进普通日志、URL、错误详情、反馈与图片向量库；普通响应只给
   计数/状态；精确坐标语义仍只属于既有会话保护入口。
7. 既有 P1/P2/P3-01 测试原样通过（版本耦合的机械断言除外，需在报告说明）。

## 验收

必需命令（沙箱内被拒时在沙箱外执行并在报告里记录）：

```text
uv run --no-sync pytest -q -p no:cacheprovider tests/unit tests/integration
uv run --no-sync ruff check .
git diff --check
uv run --no-sync uv lock --check
```

等级：**B + D**。D 的具名故障注入至少覆盖：权重缺件/哈希不符、租约到期与迟到结果、内容变化后
旧结果、重跑同一内容不产生第二套脸/第二个分组、候选索引写而未确认窗口、来源离线阻塞不写事实。
若新增依赖、改 `workers/**`、改打包入口或新增 package-data 目录 → 加 **C**（真实 onedir 构建 +
`tools/diagnostics/packaged_api_smoke.py`，工作目录放 D 盘）。若本卡改动导入图或打包资源，即使
未触发 C 的四个条件，也要重跑一次 C 并复核 bundle 内的迁移与模块。

**真实夹具要求**：使用公共领域真实人脸（例如 P0-04 已用过的 `skimage.data.astronaut`）＋脚本
合成的同人/异人/侧脸/低清变体，跑通「检测 → 对齐 → 特征 → 独立候选索引 → 保守自动关联 →
只读状态」端到端，并给出阈值校准曲线（同人/异人分布与所选阈值），**不得**直接写 0.45。
禁止使用任何真实私人照片；夹具一律在 `%TEMP%`。若本机无法稳定加载固定权重，如实记录
`IMPLEMENTED / VALIDATION PENDING` 并建议转 C1，不得跳过验收直接标 PASS。

## 已知继承项（执行时先复核，勿静默忽略）

  打包资源，必须重跑 C 并复核。
- 打包 smoke 每次必须使用**新建**的工作目录（工作在 D 盘），且不要接管
  `D:\PhotoSearchSmoke\*` 里遗留的受限 `session.json`。
- P2-03A 的人工地点编辑会先把向量条目降级为 `PENDING_REPAIR` 的投影追赶语义（P2-08 §5.2）：
