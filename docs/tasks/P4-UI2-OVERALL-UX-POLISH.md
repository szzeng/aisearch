## 1. 本卡目标

统一优化 PhotoSearch 的五个方面：

1. **布局**：主要内容更突出，常用入口更容易找到，页面更紧凑。
2. **提示文字**：精简冗长说明，统一术语，准确表达状态、原因和下一步。
3. **页面结构**：区分主要操作、常用条件、低频工具和技术诊断。
4. **下拉菜单与控件**：根据使用频率、选项数量和语义，选择合适的控件。
5. **浏览器回退与状态恢复**：让浏览器 Back、Forward 和应用内部返回入口遵循统一的导航规则，优先恢复上一个有效的用户界面状态。

**总体原则：先复用现有功能，再修复实际问题；以减法式优化为主，不推倒重做。**

本卡不是重建路由系统，也不要求所有页面采用完全相同的布局。不同页面可以有各自的业务操作，但导航、状态恢复、文案和控件选择应遵循一致规则。

## 3. 核心要求：统一浏览器回退规则

### 3.1 统一的用户体验

浏览器回退的目标是回到**上一个有意义、可以继续操作的界面状态**，而不只是回到某个 URL。

例如：

| 用户操作 | 按浏览器 Back 后的目标状态 |
|---|---|
| 搜索结果 → 打开照片 | 原搜索结果、原条件及浏览位置 |
| 照片查看 → 点击关联人物 → 人物相册 | 先回到照片查看状态；再次回退才回到搜索结果 |
| 人物列表 → 人物相册 | 原人物列表、筛选和滚动位置 |
| 人物相册 → 查看照片 | 原人物相册及照片位置 |
| 照片合集列表 → 打开合集 | 原合集列表、筛选和滚动位置 |
| 地点相册列表 → 打开某个地点 | 原地点列表、筛选和滚动位置 |
| 地图 → 查看照片 | 原地图视野、缩放、筛选及有效成员状态 |
| 修改搜索条件并提交新搜索 | 上一次已提交的有效搜索状态 |
| 当前页面内打开照片弹窗 | 先关闭弹窗并恢复原页面，再继续回退 |
| 使用浏览器 Forward | 恢复对应的下一个有效界面状态 |

以上是统一目标。实际实施时，应按各页面已有的路由、查看器和状态协议适配，不得凭空制造不受支持的状态。

### 3.2 什么才算一个历史状态

为避免用户按一次 Back 只撤销一个无意义的小操作，必须区分**有意义的导航状态**和**临时交互状态**。

需要建立历史记录的操作：

- 从一个主页面进入另一个主页面。
- 从列表进入独立相册、人物相册或地点相册。
- 从列表或时间轴打开照片查看器。
- 用户明确提交新搜索，形成新的搜索结果状态。
- 用户明确改变搜索范围或提交筛选，形成新的结果视图。
- 从照片查看器进入人物、地点等独立页面。
- 其他确实改变主要内容视图、且用户合理预期可以回退的操作。

不应单独创建历史条目的操作：

- 输入框中的每个字符变化。
- 鼠标悬停、焦点移动和普通点击选择。
- 图片加载、异步进度和请求完成。
- 普通滚动和连续拖动地图。
- 不改变当前主要视图的临时 UI 展开或收起。

临时变化可以更新当前历史条目；连续操作应适当合并，不能导致浏览器历史记录充满大量无意义步骤。

例如，搜索 A 并提交后，再搜索 B 并提交，Back 应恢复 A；但输入框每输入一个字符都不应产生一次回退。

### 3.3 浏览器历史实现规则

优先使用现有原生 History API、URL、`popstate`、`hashchange` 和已有的轻量快照机制。

- 有意义的新界面状态使用 `pushState` 或现有路由机制建立历史条目。
- 当前条目的临时状态更新使用 `replaceState` 或已有机制。
- 处理浏览器 `popstate` 时，只恢复目标状态，不再次压入相同历史条目。
- 防止同一次导航同时触发两次页面切换、两次搜索或两次查看器打开。
- Back 和 Forward 必须对称；前进到的状态仍然有效时，应能恢复对应页面、查看器或相册。
- 同一个页面内部的列表、相册详情和照片弹窗，应根据现有结构维护正确的历史层级。
- 不因统一回退而强制把所有独立页面改造成单页应用。
- 不增加大型路由框架、全局状态管理系统或第二套导航状态机。

### 3.4 页面状态需要恢复什么

根据页面实际功能，尽可能恢复：

- 当前页面、当前子视图及对象身份。
- 当前图库、人物、合集、地点等有效范围。
- 已提交的搜索条件、条件标签、排序及筛选状态。
- 原搜索结果和已加载页；仅在现有权威校验通过后恢复可复用结果。
- 原滚动位置，或可验证的照片、日期桶等锚点。
- 照片查看器中的当前资产及合法的返回上下文。
- 时间轴的时间依据、分组粒度、年份/月及未知或待就绪分组。
- 地图的中心、缩放、有效范围及相应成员版本。

状态恢复应尽量复用已有快照。不要将完整结果集、全部资产 ID 或大量历史页面内容写进 `history.state`。

可通过轻量状态标识关联现有的 `sessionStorage` 快照，但不得让快照代替服务端对搜索 session、成员版本或游标的验证。

### 3.5 照片查看器的特殊规则

统一处理浏览器回退和查看器关闭之间的关系。

- 在当前页面打开照片时，浏览器 Back 应先关闭查看器并恢复原页面。
- 用户点击关闭、按 Esc 或点击遮罩关闭时，应达到相同的最终页面状态。
- 关闭查看器后不能留下一个必须额外回退才能清除的空白历史条目。
- 关闭操作不能误退到无关页面，也不能清除原搜索结果、地点范围或地图状态。
- 如果照片查看器本身是通过旧的 `/#/asset/{id}` 深链直接打开的，继续支持直接访问、刷新和复制链接。
- 对没有可信应用内返回上下文的直接深链，应用内部的返回按钮应安全进入照片主页或明确的父页面，不得盲目调用 `history.back()` 导致离开网站。
- 浏览器原生 Back 没有应用内历史条目时，应尊重浏览器本身的历史语义，不设置拦截来强行困住用户。
- 旧查看器、人物头像跳转、地图查看照片等路径应沿用现有已验证的上下文校验。

### 3.6 状态失效与安全边界

回退不能以恢复旧状态为理由显示已经失效的内容。

- 搜索 session、cursor、地点或合集成员版本、时间规则等发生真实变化时，拒绝复用不可信结果。
- 失效后尽量保留用户输入、范围标签和可恢复的筛选条件，显示明确的重新搜索或重新选择范围入口。
- 不能在回退时静默扩大搜索范围，也不能将旧的人物、合集或地点范围替换成全库。
- 不得因为返回页面而自动重复运行 NLP、向量搜索、模型推理或昂贵统计。
- 搜索快照的恢复遵守 `P4-SEARCH-RETURN-A` 和 `P4-UI2-CLOSEOUT-FLOW-A` 的既有规则，尤其区分 FILTER_ONLY 与语义候选。
- 异步旧请求不得覆盖用户已经回退到的新状态。
- 不得修改现有数据权限、人工归属、搜索排序或业务协议来实现回退。

## 4. 全站界面优化要求

### 4.1 公共布局与导航

- 保留现有左侧导航、顶部全局搜索和浅色/暗色主题。
- 导航和顶部搜索在长列表浏览时保持稳定。
- 不增加重复的全局搜索入口。
- 统一页面标题、返回入口、主要操作和内容区的层级。
- 复用现有公共 CSS 变量与轻量页面架构。
- 保持各页面独立路由及旧深链兼容。

### 4.2 照片浏览

- 以照片网格和时间轴为视觉主体。
- 常用图库选择、浏览方式及时间轴控制放在紧凑区域。
- 低频精确日期和编号排序等选项可适当收纳。
- 清楚区分时间依据、日期分组、范围筛选和年月定位。
- 保留现有自动加载、分页、资源回收、滚动恢复和照片查看能力。

### 4.3 搜索

优先组织为：

1. 直接搜索与以图搜图。
2. 常用条件和当前搜索范围。
3. 高级筛选。
4. 搜索结果与结果操作。
5. 索引状态及技术诊断。

不新增第二个搜索框，不改自然语言解析、相关度排序、TopK、分页和范围协议。

高级筛选默认不占据大量空间，但常用条件不能全部隐藏。结果摘要只显示用户理解匹配情况所必需的信息；冗长的内部通道名次、调试字段不应占据主要区域。

搜索 A → 搜索 B → Back 恢复 A 时，应尽量复用经过验证的原结果，不应无故重跑搜索。

### 4.4 人物、合集与地点

- 保留人物、照片合集、智能合集、待整理等现有业务分类。
- 普通浏览显示常用操作；进入批量模式后再显示相关操作和选择计数。
- 明确区分人物与人脸、普通合集与智能合集。
- 地点目录、地点相册、地图相册的入口和标题清楚区分。
- 进入相册后只显示当前对象相关的主要操作。
- 保留人工归属、忽略、撤销、地点更正和成员去重等既有行为。

### 4.5 图库管理

优先将现有管理内容组织为三个清晰区域：

- **图库来源**：添加来源、图库列表、建库、刷新与单图库管理。
- **搜索模型**：当前模型、模型选择、索引检查、覆盖状态和切换条件。
- **空间与维护**：空间健康、失效照片、缓存、数据库维护及备份。

优先复用现有页面，不为分组本身强制新增路由。当前模型、检查结果、阻止切换的原因和下一步操作应清楚可见。

### 4.6 照片查看与地图

- 统一照片查看器中主要操作和信息区的层级。
- 保留现有缩放、平移、关闭、键盘操作、OCR、人脸和关联人物入口。
- 地图中的照片查看不应无故重建地图或丢失当前有效视野。
- 不重复开发已有的共享查看器、时间轴或地图成员机制。

## 5. 提示文字与下拉菜单

### 5.1 文案规范

- 按钮使用明确动作，例如“检查索引”“刷新人物列表”。
- 辅助说明尽量一句话表达用途。
- 长篇原理说明可以折叠，但影响操作判断的限制必须可见。
- 错误提示说明发生了什么；必要时说明原因和下一步。
- 内部错误代码放在辅助诊断信息中，不作为主要提示。
- 风险操作保留必要的影响范围和确认。
- 统一“照片合集”“智能合集”“人物合集”“人物”“人脸”“原文件不可用”等术语，不改变其业务含义。

### 5.2 控件选择规则

| 使用场景 | 优先考虑 |
|---|---|
| 选项较多、低频使用、空间有限 | 原生下拉框 |
| 两三个高频且互斥的模式 | 分段切换按钮 |
| 少量选项且需要同时解释含义 | 单选项 |
| 高级筛选、详细说明和低频工具 | 可展开区域 |
| 关键状态、主要操作、风险确认 | 直接可见，不应只藏在菜单里 |

不要求全面替换下拉框。只修改实际影响效率或理解的控件，保留键盘、焦点、选中状态和基本无障碍标签。

## 6. 性能与数据边界

- 不修改数据库 schema、迁移、索引、搜索算法、模型推理或建库流程。
- 不新增无必要的 API、全量 COUNT、预加载、模型调用或后台任务。
- 不将完整资产列表加载到前端以实现回退。
- 不引入大型前端框架或通用全局状态总线。
- 不访问或修改真实 `PhotoSearchData`、原图及人工整理数据。
- 不改变搜索范围、分页游标、成员身份、权限或写操作协议。
- 如果某项回退能力在现有协议下无法安全恢复，先记录限制，不得绕过校验。

## 7. 实施顺序

1. **现状盘点**：核对最新代码，整理全站布局问题和 Back/Forward 的现有行为，标记已完成、缺失及存在回归风险的路径。
2. **回退规则收敛**：明确有意义的历史条目、临时状态更新、查看器关闭及直接深链的处理方式。
3. **修复核心回退路径**：优先修复照片查看器、搜索结果恢复、人物/合集/地点相册返回，以及地图上下文恢复中的实际缺陷。
4. **界面收敛**：统一布局、文案、信息层级和有明显问题的下拉控件。
5. **定向验收**：检查关键 Back/Forward 流程，再验证实际修改的页面与控件。
6. **记录交付**：输出报告并更新开发状态，只记录有实际证据的完成范围。

如果发现现有独立任务已经覆盖某个缺陷，不重复实施。只有在当前卡能明确补齐剩余缺口时才继续；公共协议需要改变时停止相关部分并记录原因。
