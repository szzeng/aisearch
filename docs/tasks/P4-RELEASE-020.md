## 4. 仅做必要的简单测试

本卡是个人预览版的**范围内验收**，不是项目策略中的完整正式发行等级。只做：

1. **版本核对**：软件项目版本、API/OpenAPI 返回版本、界面展示应一致为 `0.2.0`；同步的 `uv.lock` 中本地 `photo-search` 版本相同。
2. **一组定向 pytest**：优先使用现有 `tests/integration/test_api_access.py` 中 OpenAPI 版本检查；输出 JUnit XML，明确结果。若另有版本一致性用例，只补跑它。
3. **静态检查**：`git diff --check`、`uv lock --check`；改动 Python 文件时运行相关 Ruff 检查。
4. **最小启动与搜索检查**：在不接触真实图库的隔离环境中验证应用可启动、页面可访问；若具备已有安全合成搜索夹具则尝试一次搜索。不具备可用环境时记 `NOT VERIFIED`，将现有用户图库的启动/简单搜索列为**用户自行手测**，不得虚报。
5. **近期功能的最低人工抽查说明（用户自行执行，不要求模型访问真实图库）**：在已正常试用的相册里确认人物列表打开且空人物表现合理、视频不会作为新照片入库/显示（注意既有视频需成功刷新后才能按设计失效）、Esc 退出批量管理不会丢失已保存操作。未手测时逐项标 `NOT VERIFIED`，**不阻塞代码版本整理的 SCOPED PASS，但不允许说这些功能已经通过真实验收**。

不运行全量 `pytest`、GPU/OCR/人脸专项、30 万照片容量/性能、备份恢复故障注入、PyInstaller 或 GTX 1660 实机测试。

**历史基线处理**：不因历史全量失败扩大本卡；若定向测试受本次版本修改影响而失败则必须修复。报告只可写 `SCOPED PASS`（满足规定的已执行定向检查）或 `VALIDATION PENDING` / `BLOCKED` / `FAIL`，**不得写全仓/正式发行 PASS**。

## 6. 提交及发布停止点

1. 生成简短执行报告：记录 HEAD、变更文件、`0.2.0` / Schema 版本、JUnit 与检查命令结果、未验证项、已知限制。
2. 只提交本卡允许范围内的代码、更新日志及报告；提交后记录**确切 commit SHA**。
3. 检查有无 `v0.2.0` 同名 Tag/Release，准备 Tag 和 GitHub **Pre-release** 说明。先从最终版本修改提交生成**候选 SHA**；如果在测试后又提交版本相关代码或合并其他任务，必须重新核对受影响范围，不得沿用旧测试结论。后续 Tag 必须指向实际包含 `0.2.0`、更新日志和可追溯发布记录的最终提交，且该提交对应本次验收。
4. **到此停止**：需要用户另外确认，才能推送代码、创建/推送远端 Tag、创建 GitHub Pre-release；禁止强推、覆盖已发布 Tag 或将预览版称作完整正式发行。若远端 `master` 已向前移动，先核对差异；不得静默改用未经测试的最新 HEAD 作为 Tag 目标。
5. 如用户仅要求完成卡面修改，本阶段不自动进入 P4-07/P4-08、不会生成额外功能任务。

## 7. 验收结论

完成本任务的条件：版本和锁文件一致、定向检查通过、可追溯的独立提交与变更日志齐备、候选发布 SHA 冻结清楚、对启动/搜索及近期功能的实测与未验证范围真实记录；未进行远端 Tag/Release 时状态注明 `PUBLICATION PENDING`。**SCOPED PASS 仅是本任务版本整理通过，不能冒充 30 万照片、真实图库或正式发行 PASS。**
