## 1. 用户反馈与定位

用户在「整理一下 → 查看已忽略人脸」中，选择已有候选，点击「确认是她」后，人脸/照片已进入目标人物相册，但**该脸仍在已忽略列表，按 F5 仍在**。这不是期望交互：人工确认归属的脸不应继续作为待处理的已忽略人脸出现。

已核对的代码事实：

- `src/photo_search/web/persons-albums.js` 的 `confirmSuggestion()` 使用 `PUT /faces/{face_id}/assignment`、`action=assign`，成功后调用 `refreshPeopleViews()`；手动「选其他人」共用该归属写入协议。
- `src/photo_search/persons/face_correction.py` 的 `apply_one()` 管理正式归属，但不会删除 `face_inbox_hidden`。
- `src/photo_search/persons/albums.py` 的 `inbox_hidden_page()`、`_inbox_group_cte(hidden=True)` 均从隐藏标记读取；现有查询不排除已有有效成员归属的脸。
- 旧 `P4-PERSON-INBOX-HIDDEN-GROUP-A` 特意规定「有隐藏标记即使已归属仍展示」。**本卡明确调整的是该条“已忽略待整理列表”的可见性规则**；不改变隐藏记录的持久性，也不把忽略当成权威身份信息。

根因已经从源码定位到“已归属仍在隐藏读模型”这一处；但实施前仍需用隔离合成数据验证实际成员归属、列表查询和页面刷新链路，不能只凭按钮文字判断写入成功。

## 2. 目标行为与状态合同

“查看已忽略人脸”代表**尚待人工处理、且带忽略标记的人脸**；不代表全部隐藏历史记录。

| 脸状态 | 已忽略待整理列表 | 正式人物相册 |
| --- | --- | --- |
| 有 `face_inbox_hidden`，无有效人物归属 | 展示；保留 TEMPORARY / EXCLUDED 区别 | 不因此新增成员 |
| 只有 SUGGESTED 候选、无有效归属 | 仍展示，可确认或手选（EXCLUDED 不恢复自动候选） | 不因建议自动加入 |
| 已人工或自动形成**有效**人物归属，仍有隐藏标记 | **不展示** | 按现有有效成员规则展示 |
| 归属被撤销/移出，恢复为无有效归属，隐藏标记仍在 | **重新展示**，忽略类型不变 | 退出原正式人物成员视图 |

“有效归属”的判定必须复用 `MEMBER_PREDICATE` / `_NO_MEMBER` 等权威成员语义，而非按 `mode`、候选是否存在或任意 `face_person_links` 行粗略判断。合照逐脸独立；同一照片的其他人脸不受影响。若真实用户问题中也存在“相册未入库”，需先复现再按实际根因最小修复，禁止用隐藏前端卡片掩盖归属失败。

## 3. 最小实现范围

### A. 后端：从可见查询源头排除已归属脸

在 `src/photo_search/persons/albums.py` 复用一个一致的「隐藏标记 + 无有效成员」SQL 条件，**在分页、候选归组、代表脸选择、COUNT(DISTINCT asset_id) 之前**应用，覆盖：

1. `GET /api/v1/faces/inbox/hidden` → `inbox_hidden_page()`（旧兼容接口的响应结构不变）。
2. `GET /api/v1/faces/inbox/hidden/groups` → `inbox_hidden_group_page()`。
3. `GET /api/v1/faces/inbox/hidden/groups/{group_key}` → `inbox_hidden_group_faces()`。

确保同一候选从两张不同照片减少为一张时正确降级单脸；无成员但有候选的人脸仍显示；零剩余脸的组消失。代表脸不得落到已排除的已归属脸上。分页无重复/遗漏；检查现有隐藏组 cursor 与 `read_filter_revision` 的失效语义，避免操作前的旧游标继续拼接旧分组；旧平铺接口维持合理的 keyset 语义。必要时补充最小缓存失效处理，不改变读 API 字段。

**禁止为这个问题修改 `face_inbox_hidden` 的存储或批量清除已确认脸。** 已存在的历史数据通过新的读过滤立即呈现正确视图，无迁移、无全量修复作业。

### B. 前端：确认/手选后及时反映权威状态

在 `persons-albums.js` 复核并尽量复用 `confirmSuggestion()`、手动 `writeFace("assign")`、`refreshAfterWrite()`、`refreshPeopleViews()`、`loadHiddenFaces()` 和已展开分组的加载：

- **服务端写成功之后**刷新人物目录、已忽略列表及受影响分组；已消失组关闭，仍存在组可保留展开状态，计数从服务端重读。
- 失效旧 cursor / 旧 in-flight GET，避免慢响应重新绘制已确认卡片；下一页和“再看一些”使用当前版本。
- 保持现有确认按钮防重复提交、pendingWrite/不确定结果的安全语义。保存失败不得出现“✓ 已确认”；保存成功但列表刷新失败不得再次提交归属，应提示可重试刷新。
- `refreshPeopleViews()` 是异步流程，核对调用时序和错误处理；不能仅靠前端删除一张 DOM 卡来冒充成功。
- 撤销归属完成后正常刷新，原忽略标记仍在则再次显示。不要要求用户按 F5 才生效。

原则上不需要改动 `face_correction.py`、操作日志、人工锁、数据库 schema 或识别模型；若确有必要扩大范围，先在执行报告说明原因和风险。

### C. 与既有规则兼容

- `TEMPORARY` / `EXCLUDED` 标记、忽略/恢复选择、最多 500 张脸限制不变。
- EXCLUDED 仍禁止**自动候选/自动归属**；若原有合法 UI 允许用户主动指定人物，人工显式确认遵守原协议，成功后同样不显示在待整理列表。
- 普通待整理、人物相册、人物合并 canonical 映射、人工排除、手动移出、操作撤销按原权威合同执行。
- 保留可审计的原始忽略标记；**不新增“历史已忽略”浏览入口**，本次仅修改待整理列表的展示语义。
- 查询必须继续数据库分页，不对整库取回后 JS 过滤；优先利用现有索引与 `NOT EXISTS`，不新增逐脸 N+1 查询或推理任务。

## 4. 聚焦验收（必测）

使用隔离合成图库，至少包含：同一候选的两张不同照片、无建议脸、合照的两张不同脸、一个人工确认目标人物。无需访问真实照片库。

1. **确认与持久化**：TEMPORARY 脸点击「确认是 A」后，`assigned_person_id` 为 canonical A、A 相册有效成员正确；隐藏标记仍在数据库，但三个已忽略读取路径都不返回该 `face_id`；页面立即更新，F5 / 重启后仍不显示。
2. **手选与撤销**：无候选/另选 B 通过原 `assign` 路径归属；再执行现有 `undo` 或合法 `unassign` 后，有隐藏标记的脸重新可见，忽略类型保持不变，不影响合照其他脸；EXCLUDED 显式人工操作遵守现有许可，不恢复自动建议。
3. **候选分组与分页**：确认其中一张使 2 照片候选组降级单脸；剩余脸正常显示，零剩余则组消失；代表脸/照片数正确，多页加载不漏/不重，确认前旧请求与 cursor 不污染新页面。
4. **失败与 UI**：409、网络异常、重复点击、刷新 GET 失败区分写入与刷新结果；不得虚假显示归属成功、重复写入或丢失合法撤销入口。

执行 1 组定向 pytest 后端集成 + 1 组现有 Node DOM 前端用例（可增补现有测试文件），保存 JUnit XML；运行修改面 Ruff、`node --check`、`git diff --check`。测试结果以真实进程退出码/JUnit 为准。不跑全仓、模型、GPU、性能和真实库；若项目当前 UI 浏览器验收策略要求，可在 Codex 内置浏览器用隔离合成数据仅实测“确认 → 列表消失 → F5”这 1 条路径，浏览器工具受限则报告 BROWSER_PENDING，不误写 PASS。
