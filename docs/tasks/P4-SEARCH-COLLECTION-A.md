## 1. 目标与搜索语义

已有「人物合集」可在照片搜索框按真实名称识别，作为**独立的照片资格过滤器**；不是新人物，不改变脸归属，也不自动建合集、复制照片或生成向量。

| 输入 | 预期 |
| --- | --- |
| `同事的照片` | 仅同事合集当前有效成员出现的照片；无内容词，SQLite 全量可分页 |
| `2024年同事的照片` | 合集 AND 拍摄时间 |
| `同事在北京的照片` | 合集 AND 已确定的地点范围 |
| `同事在海边的照片` | 合集 AND「海边」现有语义检索 |
| `2024年家人在海边的照片` | 合集 AND 拍摄时间 AND 语义 |

合集可包含已命名、未命名、已忽略的人物，**合集总人数不设100上限**。同一张合照即使有多个合集成员，也只返回一次（以 `asset_id` 去重）。空合集返回0，不允许退化为全图库。

首版一次只识别**一个**人物合集；不承诺任意多合集交并差，也不将「张三和同事的合照」简单人物交集冒充“存在另一个不同人物”的关系判断；碰到不能明确解释的复杂表达应提示或按现有普通语义处理，不能静默产出错误硬筛选。

## 3. 具体实施

### A. 确定性名称解析与消歧

1. 从 `person_collections` 读取现存合集名称和实例信息；按已有合集保存键口径（NFC / 空白规范 / casefold）匹配，重叠名称优先完整且较长的命中。**不新增合集别名、拼音、模糊相似名或模型猜测**。
2. 仅在明确引用合集的上下文中提取名称（如「同事的照片」「同事合集」「同事在海边的照片」）；避免截取任意普通词子串形成硬筛选。没有可信匹配时保留原普通搜索行为。
3. **跨类型冲突不能静默选错**：同一文字可能同时是人物、人物别名、合集或地点。当前地点解析在前，必须避免地点提前消耗而导致合集永远无法被选择；尽量复用既有地点和人物选择 UI 形成统一的对象选择步骤，用户选定后绑定真实 ID/实例，而不是只凭文本再次猜。
4. 首次查询将确定的合集信息写入个人入口现有 `intent_plan` 或等价内部结构；续页、取消其他条件时使用已解析值，不重复解析「去年」等相对时间。**请求中的 plan 仅作提示，服务端必须重新验证合集存在、实例和 revision**，不能信任任意浏览器传入的 collection_id。
5. 明确多合集复杂表达可识别但不执行任意布尔组合；遇到歧义引导选择或提示限制，不默默只选择第一个。

### B. 复用统一合集成员 SQL

1. 将 `api/queries.py::_collection_condition` 的既有 canonical 成员＋有效人脸归属条件复用到搜索权威谓词；如需解耦，可提取一个小型 `persons/collection_sql.py` 共享只读 SQL helper，让合集相册与搜索共用，不复制两套语义。
2. **禁止**将全部合集成员展开成 `person_ids` 或限制为前100人；不按成员循环调用检索，也不全量把照片 ID 装进 Python 或巨型 `IN (?, …)`。
3. 合集范围通过单个固定参数化子查询/集合谓词约束 `asset_id`，照片唯一，沿用人工归属保护、merge redirect / canonical 解析与现有隐藏人物语义；不引入人脸再匹配。
4. 缺失/删除/实例不匹配的合集必须明确拒绝；合法空合集得到空结果，不能省略条件。简单做一次 `EXPLAIN QUERY PLAN`，避免明显的 N+1 / 重复全表扫描；不要求30万量级性能承诺。

### C. 三条个人搜索路径的权威条件一致

**统一内部分层**：给 `SearchScope` 增加一个默认不启用的可选合集 ID/实例范围，或等价的受控内部谓词，在 `scope_condition` 层与现有人物、时间、来源、地点条件做 AND。普通查询无合集时应继续保持原行为。

- **纯条件、无地点**：`_filter_only_search_page` 复用 SQL keyset 分页，逐页 `page_size+1`，完整去重计数。无语义词时不调用 encoder/GPU，不受1000/5000结果截断。
- **纯地点＋合集、无内容词**：`_place_album_search_page` 现有独立分支必须使用同一合集谓词与正确的地点成员资格（含 CN 特例），不允许丢掉任一过滤条件。
- **合集＋实质内容词**：`search_request` → FTS / Vector / RRF 都在权威合集范围内召回，不能先全库 Top5000 后过滤；维持语义 Top5000 及现有排序/命中统计，不新增检索器。
- 上述每个出口的 `filters` 回显、`total_candidates`、`next_cursor` 与 `intent_plan` 均应体现真正生效的合集范围；不把合集成员人数当照片数。
- 禁止修改冻结 `POST /api/v1/search` 契约；只改加性的 `/search/place-aware` 和内部服务。若当前内部模型不支持，在最小受影响面加可选字段/参数，其他调用保持默认值。

### D. 会话、实例与修改后安全

**特别注意：合集 `edit_members` / `rename_collection` 修改自己的 `person_collections.revision`，不能假设一定增加全局 `catalog_filter_revision`。**

每次请求实际绑定：`collection_id + instance_token + collection_revision + catalog_filter_revision` 以及原有搜索条件指纹；必要时复用 `album_scope_revision` / 搜索会话扩展字段。

- 首次搜索：获得实例＋修订基线 → 执行 → 发布前复核；若跨越合集编辑、删除、身份归属变化，不能发布混合结果，可有限重试或返回明确 stale。
- 续页：在返回结果前检查同一实例/修订（包括纯 SQLite、纯地点和语义会话）；条件变化/合集删除/ID复用必须返回明确过期/不存在错误，不得返回其他合集或全图库照片。
- 纯筛选的游标指纹包含合集实例和修订；语义会话 digest / extra 采用同样口径。前端错误后停止续页并提示重新搜索。
- 若相关人物合并/拆分导致有效成员照片变化，复用全局过滤修订或既有归属安全检查；不修改身份、人工锁、撤销协议。

### E. 最小 UI

仅在 `web/search.js` 的现有搜索条件区域增加可取消的「人物合集：同事 ×」；与现有时间/地点/人物条件并列。取消合集只移除合集条件，保留其他已确认条件并重新搜索。复用原有候选选择区域；结果页→照片详情→返回需保留合集条件/游标状态。无新页面、复杂高级筛选或新框架。

## 4. 最小必要验证（个人试用口径）

使用隔离小型 SQLite 夹具、已有 fake encoder/假向量索引；**不访问/修改 `PhotoSearchData`、真实图库或正在运行的服务**。尽可能复用已有测试文件，不追求增加测试文件数量。只覆盖以下四组关键不变量：

1. **解析/消歧**：真实合集名称、大小写/长短名称、年份＋合集、剩余语义词；人物/地点同名时提供可选对象而非猜测；无合集不误触发。
2. **SQL/分页**：两成员合照只返回一个 `asset_id`，空合集0张，分页小页无重复/遗漏、总数正确；轻量构造101个成员证明不触发普通100-ID限制（无需101张真实图片）。
3. **地点/语义/兼容**：地点 AND 合集、时间 AND 合集正确；fake encoder 验证合集外高相似度照片不会进入 Vector/FTS 召回；无合集普通搜索维持行为；语义 Top5000 不被改变。
4. **失效/前端**：首次结果中途修改合集、续页前添加/移除成员、改名、删除或实例变化后拒绝旧结果/旧游标；条件 chip 可取消，详情返回保留搜索；关键错误不显示旧结果为新结果。

优先用**少量合并测试函数**覆盖，不要求逐个排列所有组合，也不重新编制长测试矩阵。若已有 DOM/合成浏览器证据足够，可复用；只补新增合集条件的简单交互。用户自己按「同事的照片 → 2024年同事 → 同事在海边 → 详情返回 → 取消合集」做少量现场试用即可。

必要命令只跑新增和直接受影响的 pytest 节点（**JUnit XML**）、改动文件 Ruff、JS `node --check`、`git diff --check`；首次工程复核覆盖本次全部新增受影响面与直接调用链，不默认全仓、30万容量、CUDA、OCR、真实模型、全浏览器矩阵、打包或多模型多轮主审。环境限制或未测项如实列明，不以少量 fake 测试声称真实速度已验证。
