# P4-PERSON-ALBUM-PERF-A — 人物相册快速加载（个人试用最小优化）

日期：2026-10-09。状态：**PROPOSED / 未实施、未测试**。用户反馈人物列表和进入人物后的照片加载偏慢；本卡只做加载优化，不包含“按照片数量全局排序”（单独任务，避免改变当前分页语义）。

**推荐执行：DS-H（DeepSeek V4.1 Flash／高推理）**；GPT 备选 **GPT-6 Luna／High**（以实际可用档位为准）。同一会话完成实现、调试和简测；默认不交 Sol，触及 schema／身份／事务／人工归属契约时先停止并单独评估。用户手动选模型。

## 1. 目标和已知疑点

目标：打开人物页尽快看到人物列表、点击人物尽快看到首批照片；以30万张个人照片为长期规模，但本卡不声称已证明30万性能。**根因尚未在真实图库计时证实**，先做小样本请求耗时和SQL次数对照。

- `persons/albums.py::people_page` 每页40人依次调用 `_album_summary`，其 `person_summary → member_counts` 两次计数，加一次有效头像查询：约120次额外SQL。
- `photo_page` 每页60张逐张调用 `asset_view` 和 `_photo_person_faces`，存在逐照片读取。
- `web/persons-albums.js::boot` 同时启动 `loadDetailBatch`；无活动批次时可能进一步调用 `/faces/source-detail-preview`，做不属于普通浏览的全库候选统计。
- 首次人脸头像可能按需生成预览和裁剪；需区分冷图片加载和API/SQLite慢，**不预设媒体路径必须修改**。

## 2. 实施（先定位，后最小修复）

1. **对照定位**：复用小型合成库，分别记录人物列表API、某人物首批照片API、补识别候选统计API、冷/热缩略图请求的耗时；检查主要SQL调用次数。若N+1不是主要瓶颈，以证据调整本卡内相同加载链的最小修复；报告如实写明未测真实库。
2. **人物列表批量读取**：先按现有 `person_id` 游标取最多40人，再对**仅本页人物ID**批量取得计数及头像，避免逐人查询；优先在 `persons/albums.py` 新增局部批量投影，不直接改动共享 `person_summary/member_counts` 的其他API语义。保持 `member_counts` 原有计数口径（勿擅自新增ACTIVE限定）、`MEMBER_PREDICATE`、`_album_summary` 当前ACTIVE封面候选与手动封面优先/回退排序；同图多脸照片去重、同图不同人物分别计数。注意防止JOIN放大计数，避免“先全库聚合再LIMIT”；必要时用 `EXPLAIN QUERY PLAN` 核实访问路径。
3. **照片页批量读取**：保留 `photo_page → asset_page` 原权威scope、按拍摄时间降序、60张有界分页及原游标；仅对当前页照片ID批量取得时间与该人物的人脸，保持每图最多8个及 `has_more`、原人脸排序。缺时间/缺脸回退不变；下一页不提前加载。不得使用全人物照片物化替代分页。
4. **延迟高级整理读取**：普通人物页不自动请求补识别候选总数和仅供高级整理的来源/任务数据；用户进入相应整理入口才读取，活动批次仍在后台运行，不依赖页面轮询继续执行。切换入口、快速返回、重复点击时避免重叠请求和旧响应覆盖当前UI；不改变任务暂停/恢复/API契约。
5. **图片只在证实必要时微调**：继续沿用已有缩略图、预览、人脸裁剪缓存与懒加载；若瓶颈主要是冷缓存，先记证据并限于直接相关小修。禁止为了本卡全图库预生成或重新跑人脸识别。

## 3. 严格边界

- 不改 `schema`、迁移、索引、持久化计数、模型、权重、识别门限、向量检索、全局人物排序、人工归属/锁/排除/撤销。
- 不改变 `GET /persons/browse` 与 `GET /persons/{id}/photos` 的字段、权限、分页游标或过滤revision语义；命名/未命名筛选及空未命名组排除逻辑不变。
- 不读取、重建或修改用户真实 `PhotoSearchData`、不自动启动模型或访问真实照片。
- 仅按需修改 `persons/albums.py`、人物前端与直接相关测试；其他共用模块需改时说明理由、保持原调用方语义。
- 先按 `AGENTS.md → docs/development-status.md → 本卡` 读取，再读主架构 §8.3/10.3、执行策略 §2.2～2.4/3.2/3.4，以及 `persons/{albums,read,members}.py`、`api/queries.py`、`web/persons-albums.js`、对应接口与测试；无需全仓扫描或全文重读架构。

## 4. 最小验收

- **人物**：合成40人以上，含已命名/未命名、空未命名组、人工封面、失效封面、合照、同一人物同图多脸、排除/锁/旧脸替代；列表及计数与原实现逐项等价，40人页面额外SQL不随人物数线性增长。
- **相册**：合成至少61张，验证60张首批/续页、时间与人脸显示、每图8+1的 `has_more`、无重复漏页、上一张/下一张；额外SQL不再逐张增长。
- **页面**：普通打开不请求 `source-detail-preview`，进入相关整理功能后能查看候选数与批次状态；旧响应不污染当前视图。
- **对照**：同一小样本修复前后各测3次，仅记录API耗时和SQL次数；若冷头像为主因，分开记录。不设臆造的毫秒达标值，小样本不代表30万性能。
- 只运行受影响的定向pytest（生成JUnit XML）、Ruff、Node `--check`、`git diff --check`；不跑全量、GPU、长期性能、打包测试。
