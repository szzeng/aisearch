# P4-PERSON-INBOX-HIDE-A — 待整理人脸逐张批量忽略与恢复

日期：2026-10-09。状态：**READY / 待实施**。核对基线：`0732587675368ca0899349c26b275c3778b1a6f1`（实施前复查最新 HEAD）。个人相册小功能，**1 张卡、2 组自动定向测试**。此前只讨论过此任务，现首次提交文档；不表示功能已实现。

## 1. 用户目标与数据界限

「整理一下」共两类不同对象：
- **未命名人物分组**已有 `person_hidden` + `POST /api/v1/persons/visibility` 批量忽略/恢复，不重复实现；
- **「还没认出是谁」待整理人脸**（含「可能是张三」候选合集内的脸）尚无隐藏能力。本卡只新增**按 `face_id` 逐张勾选 → 批量忽略 → 已忽略列表恢复**。

「可能是张三」由人脸建议**动态分组**，内部可能有多个人，**不能点击合集标题便忽略整组**、不能据候选人 `person_id` 隐藏整个候选组，更不能影响张三本人。合照多脸时只隐藏被勾选的脸，不隐藏整张 `asset_id` 照片。忽略只影响待整理 UI，不删除照片、人脸、向量、建议、人物归属，也不更改人工锁、候选索引或自动匹配。未来新检测的相似路人不自动被忽略。

## 2. 最小前端交互

复用当前 `src/photo_search/web/persons-albums.js` 的全局「批量管理」模式及 **P4-PERSON-HIDE-UI-FIX-A（已 PASS）** 的就地选择同步；新增独立 `selectedInboxFaces: Set<face_id>`，不与 `selectedPeople` 混淆。

1. 批量模式下，在 `renderInboxFace()` 的每张待整理脸卡片上放**独立勾选框/按钮**；只点选择控件才增删 Set；点头像仍 `preview(asset_id)` 看原图。原「确认是… / 选其他人 / 这是谁？」在非批量模式照常工作，批量模式避免误触其他整理动作。
2. `renderInboxGroup()` 的 `<summary>` **只负责展开/折叠**，不作为忽略目标；展开后逐张选择，`loadInboxGroup()` 的「再看一些」继续按原 cursor 加载，组内及组间所选 `face_id` 持续保留。普通独立人脸卡片也可直接勾选。
3. 界面分别展示「已选 N 个人物」和「已选 M 张脸」，人物仍调用旧接口，人脸新增独立「忽略所选人脸」提交按钮；**不混合写事务**。人脸选择达到500张提示上限；不提供「全选候选合集」或一次按候选人物 ID 处理整组。
4. 点击勾选/取消、展开/收起、加载更多**不重载已展开的人物或人脸列表、不重置游标或滚动位置**。新追加卡片按当前 Set 显示选中状态；关闭合集再展开时已选状态仍在。
5. 两种选择分别保存；**某一类成功提交后只清理该类已选项并刷新受影响列表**，另一类已选项不丢。切出「整理一下」、退出批量模式或主动取消时清理相应选择。确认取消/接口失败时保持当前选择并提示，不误报成功。
6. 在收件箱下方增加简洁「查看已忽略人脸」列表（分页、缩略图、逐个勾选、「恢复所选」）。与原「查看已忽略人物」入口明确区分，**不是**另做一套人员管理页面。

如需要，只改 `persons.html` / `persons.css` 的必要 UI 与静态资源版本；不要另建状态框架或一次载入全库。

## 3. 最小持久化和接口

现有 Schema v22；若开工时仍为 v22，新增连续 `0023_*.sql` 迁移并升至 v23；已有其他新迁移则顺延。**仅添加** `face_inbox_hidden(face_id TEXT PRIMARY KEY REFERENCES faces(face_id) ON DELETE CASCADE)`。忽略存在、未忽略不存在；旧脸正式清理时自动清掉对应标记，不改已有数据表/旧迁移。

新增 `POST /api/v1/faces/inbox/visibility`，body `{"face_ids":["<64位face_id>"],"hidden":true}`（恢复为 false）：
- 单次 **1–500** 个不同合法 `face_id`，服务端拒绝无效/未知 ID；在**一个 SQLite 写事务**里校验后全量应用，任何错误全部不写；复用现有会话/Origin/CSRF 保护。
- **隐藏**仅接受当前符合收件箱资格的人脸；已经隐藏的同一张脸再次请求视为幂等，不因「它已被收件箱过滤」而报错。**恢复**只校验标记/人脸存在，不要求脸仍处于待整理状态（它可能后来已归入人物）。
- 不接收 `group_key` / 候选人物 ID 作为批量隐藏对象，不允许服务端将「可能是张三」自动展开为整组被忽略脸。
- 提供最小的分页 `GET /api/v1/faces/inbox/hidden`（沿用现有会话及分页风格），可访问原已忽略脸的受控缩略图；恢复清掉标记后，只有**当前仍符合待整理规则**的脸重新出现。

## 4. 查询保持一致

在 `src/photo_search/persons/albums.py` 的**待整理专用谓词**增补 `NOT EXISTS face_inbox_hidden`，分别涵盖：
- `inbox_page()`；
- `inbox_group_page()` / `_inbox_group_cte()`；
- `inbox_group_faces()`；
- `inbox_summary()` 的普通待整理统计（原重检测 hold 口径保留）。

必须**先过滤再分组、统计、ORDER BY 和 LIMIT**，不在前端取完30条才剔除。现有分组阈值是 **至少2张不同照片**，`photo_count = COUNT(DISTINCT asset_id)`；忽略部分脸后合法地可能缩小合集、降级为单张脸卡片，绝不能按被忽略的脸数直接扣照片数。写成功后从第一页重新加载收件箱和当前展开内容，避免沿用旧分组/游标。其余 `_VISIBLE` 人脸可用性、照片详情、识别匹配和原人物列表查询不得增加此隐藏过滤。本卡不建设新版本/快照系统。

## 5. 极简验收（个人相册）

**自动测试只保留2组：**
1. **后端 1 组定向集成：** 隔离合成候选合集混入不同脸/同照多脸，勾选2张按 `face_id` 隐藏，其他脸可见；统计及分组门槛正确；重开 SQLite 后仍隐藏；恢复成功，且照片、已有成员/建议链接不变。加一个无效 ID 整批回滚和重复操作幂等断言即可。
2. **前端 1 组轻量 Node DOM：** 展开「可能是张三」，勾选一张路人脸、再翻页选另一张，预览头像不触发选择，合集标题不整组选中，关开合集保留选中，不会因勾选收起/重载列表；确认取消/失败保持选择，成功调用接口仅携带明确勾选的两个 `face_id`。

运行这2组定向测试、修改面 Ruff、`node --check`、`git diff --check`。**不跑**全仓/30万/GPU/模型/打包/浏览器矩阵，不访问私人 `PhotoSearchData`。由用户个人前端手动走一遍「候选合集逐脸选择→忽略→已忽略人脸→恢复」即可。

## 6. 边界、模型、完成状态

`face_id` 是**单次检测结果的身份**；重检测出现新 `face_id` 不自动继承旧隐藏标记，必要时用户再次忽略。重新识别、人脸匹配、合并人物、人物忽略功能都不是本卡范围。
