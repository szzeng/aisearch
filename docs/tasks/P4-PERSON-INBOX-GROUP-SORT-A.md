## 1. 目标与现状

- 人物页「整理一下 → 还没认出是谁」目前 `/faces/inbox` 按 `face_id` 返回单脸卡片，每页30张；`/faces/inbox/summary` 按原因汇总人脸。已完成 [P4-PERSON-SORT-A](P4-PERSON-SORT-A.md) 是**已命名/未命名人物分组**的 `photos_desc` 排序，不覆盖待整理脸。
- 当前「刷新」只执行 `loadPeople(false)`，在整理页同时执行 `loadInbox(false)`；它不触发检测或补匹配。页面另有明确的「补匹配未归类人脸」，调用 `/faces/rematch`，默认每批20张照片并在完成后刷新两类列表。
- 用户目标：对**已有相同机器候选人物**的待整理脸，临时生成展示组；按组内不同照片数量从多到少排列。无可靠候选的人脸仍独立显示。新建议出现后，刷新自然重分组；**不把 SUGGESTED 当成 CONFIRMED**。
- 这不是“把所有未知人脸重新聚类”：无候选关系就没有人物归组依据，不能把单脸排序伪装成人物照片数排序。

## 2. 分组和统计规则

1. 复用 `persons/albums.py` 现有 `_INBOX_WHERE`（有效可见性、无已确认成员、非 OPEN hold）及 `_INBOX_KINDS`，不要重新发明资格规则。所有卡片都只代表仍待整理的人脸。
2. **只有「有相似人物建议」范围**中的有效 `face_person_links.decision='SUGGESTED'` 才能产生候选展示组。候选人物需 canonical/未并走，排除该人脸对该人物的活跃 exclusion；保留原有人工移出、低质量、OPEN/旧脸替代等门禁，不通过分组暗中改写其行为。
3. 每张人脸最多贡献给**一个**组：在现有合格建议中按 `confidence DESC, person_id ASC` 稳定选择一个展示候选，避免跨组重复。分组标记明确写「可能是某人」，不得假称识别确认或一键整组确认。
4. 同一候选人物至少包含 **2 张不同照片** 才显示组卡；否则该脸保留单独卡片。组内照片数是 `COUNT(DISTINCT asset_id)`，不是脸数，也不包含该人物已确认相册的照片。合照的不同脸仍可逐脸更正。
5. 没有合格建议、低质量/人工移出/尚未匹配等继续单脸显示，按原原因分类保留。单脸只是关联1张照片；**不合并多个「未知的人」为一个假身份**。按数量排序时先显示较大的候选组，再显示剩余单脸；同数按稳定组键/face_id 排序。
6. 原 `/faces/inbox/summary` 仍是**人脸数**统计，不将组内去重照片数代换原原因汇总。前端文字明确区分「张脸」「张待确认照片」。

## 3. 后端与分页：最少增量、旧接口保持兼容

首选在 `src/photo_search/persons/albums.py` 增加独立只读分组页 helper，并由 `src/photo_search/api/routes.py` 暴露，例如 `GET /faces/inbox/groups?kind=all|suggested|quality|manual|pending&limit=30&cursor=...`。保留现有 `GET /faces/inbox` 的默认响应格式、筛选、`faceinbox2` 游标及所有旧客户端，不在原接口上静默改语义。

- SQL 在**完整符合条件的待整理人脸集合**中先选唯一首选候选、分组、统计去重照片数，再按 `photo_count DESC, stable_key ASC` 全局排序后 `LIMIT limit+1`；不能仅在前端已加载30张脸中分组排序。
- 每页最多30张**展示卡片**（候选组或单脸），而非30张原始脸。聚合阶段不加载全库照片/头像/向量。
- 返回卡片明确类型 `candidate_group` / `single_face`、只读临时组键、数量与必要展示字段。当前页才读取代表人脸和候选人物显示信息。代表头像复用已有受保护 thumbnail。
- 点击组卡时按组键、当前过滤及**与聚合完全相同**的候选选择规则，分页读取组内待整理脸，并复用现有 `_face_view`/预览/「这是谁？」；不一次性发送全组无限量人脸，不为分组建立新身份。
- 分组页与组内页使用**新游标前缀**，绑定筛选/候选键/排序和现有可用的版本约束，验证非法、跨筛选、跨组游标；基线稳定时不得漏项/重项。若自动归组/识别新发布未推进现有 `catalog_filter_revision`，不要虚构快照保障：页面刷新重新排序，滚动分页并发变化的边界在报告里如实标注。
- 该新入口复用现有 session/权限，不在 API 暴露内部相似度、向量、原图绝对路径。**只读**：不写人物、face links、exclusions 或 assignment controls。
- 不新增 schema、索引、持久统计表、后台任务或缓存机制。

## 4. 前端与刷新/补匹配交互

主要修改 `src/photo_search/web/persons-albums.js`，必要时调整 `persons.html` 与最少样式：

- 「全部待整理」和「有相似人物建议」用新分组卡片；其余原因筛选单脸展示保持现有使用习惯，且不借低质量/人工移出关系猜测身份。组卡显示「可能是XX · N张待确认照片」；点击展开，原照片预览与「这是谁？」继续逐脸操作。
- 新默认的整理列表按**服务端全局**照片数降序；不再在 JS 中对一页候选脸做局部排序后宣称全局有序。组内头像与脸详情按需加载，保留「再整理一些」。
- **「刷新」职责不变**：仍只调用 `loadPeople(false)` + 整理视图的 `loadInbox(false)`，但新 `loadInbox` 读取最新组和数量，清空旧卡片与游标。刷新不运行 `/faces/rematch`、不做模型推理、不扫描照片、不写关系。
- 人工指定/更正/撤销操作成功后沿用已有局部刷新。原本无候选的新照片不会仅因手工创建一个人物而自动归组，必须先出现实际 `SUGGESTED` 关系。
- 保留「补匹配未归类人脸」的现有 `/faces/rematch`、每批20张照片与完成后自动刷新：直接成为 CONFIRMED 的脸退出 inbox，新生成 SUGGESTED 的脸进入展示组，仍无候选的继续单脸。
- **核对 `rematchAfter` 续批状态**：当前操作使用 `next_after_asset_id || 0`。在用户新增已确认人物之后，如果要明确“重新检查之前无候选的旧照片”，不能继续沿用旧扫描位置误以为全库已重试；允许通过既有从头 `after_asset_id=0` 的请求发起新的补匹配轮次，或在适当的明确人工操作后重置本地续批状态。不得在刷新/进入页面时隐式触发全库 rematch，也不得让重置破坏当前一轮的有界继续处理。
- 注意过滤条件变化、页面离开或返回时的异步响应竞争，保留现有 `inboxSeq` 防旧结果覆盖。

## 5. 性能与范围停止点

本卡仅利用**已经存储的 SQLite 关系**。不重新跑脸模型、不加载向量、不重聚类、不修改阈值、不下载模型、不重建图库，也不访问真实 `PhotoSearchData`。

全局分组会比原按 face_id 索引分页多做汇总工作：复用已有索引，核查 `EXPLAIN QUERY PLAN` 与简单合成 API 耗时；避免每脸 N+1、全量头像读取和重复聚合。若明显退化，优先局部优化；必须新增 schema、缓存/任务调度或修改人工写语义时暂停扩张，记录独立后续建议。

不修改 [P4-PERSON-SORT-A](P4-PERSON-SORT-A.md) 已完成的人物照片数排序、人物相册内 `capture_desc`、人物合并/撤销、人工锁、排除、补匹配模型或既有人脸单脸接口。

## 6. 简单验收与审查

使用合成隔离图库：

1. 3个候选组各10、5、2张照片；全局降序、同数稳定；同图多脸照片数去重，多候选一脸只进一组。
2. 无候选、人工移出、主动排除、低质量、旧脸替代、OPEN映射不被错误聚合；候选组数量与展开的人脸集合一致。
3. 30卡边界及组内分页正确；过滤与游标混用拒绝；旧 `/faces/inbox`、summary、`faceinbox2` 保持兼容。
4. 手动确认/更正后刷新，已确认脸退出 inbox；已有候选变更后新分组生效；**刷新不发送 rematch 请求**。
5. 新建已确认人物后，显式从头补匹配能重新考虑先前无候选的旧照片：CONFIRMED 不再待整理，SUGGESTED 会在下一次加载时重新分组；原有批次继续按钮正常。
6. 当前页显示、展开、照片预览与「这是谁？」仍可用，合成 SQL 计划无明显可避免的退化。
