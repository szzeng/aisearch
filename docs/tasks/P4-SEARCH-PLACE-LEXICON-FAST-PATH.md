# P4-SEARCH-PLACE-LEXICON-FAST-PATH — 地点匹配查询加速

**优先级：** P1
**推荐模型：** GPT-6 High
**类型：** 定向性能优化
**基线：** 当前最新 master，至少包含 `814ffa1`
**执行要求：** 修改代码、定向测试、生成报告；不提交、不推送

## 一、目标

优化综合搜索每次重新读取完整地点目录的问题。

现有实机结果：

| 指标 P50 | 复测 1 | 复测 2 |
|---|---:|---:|
| 后端搜索 | 568.7 ms | 702.7 ms |
| 地点候选处理 | 396.8 ms | 522.6 ms |
| 地点 SQL | 176.3 ms | 244.6 ms |
| 核心检索 | 134.8 ms | 184.9 ms |

当前每轮仍有：

- 129 次地点 SQL 查询。
- 约 78,040 行地点相关数据返回给 Python。
- 约 47,960 个潜在地点候选。
- 普通语义查询实际匹配地点为 0。

**主要目标：减少无地点命中搜索的数据库数据传输和 Python 候选处理，而不是继续减少已经优化过的候选对象创建。**

## 二、FIX-1：先核实诊断开销

检查：

`src/photo_search/places/choices.py`

当前 `perf_metrics` 开启与关闭时，地点名称匹配会进入不同的内部执行路径。

诊断模式额外创建 `normalized_osm`、`normalized_geo` 等临时结构，并执行计数和阶段测量。

本任务开始时：

1. 使用相同 SQLite 测试库、相同搜索词。
2. 对比关闭诊断与开启诊断时的 `choices(text=...)` 执行时间。
3. 比较两条路径的返回结果签名。
4. 测量诊断额外分配的对象和内存。
5. 如诊断带来明显额外耗时，优先统一搜索算法路径，将诊断变为轻量观察，不再单独完整构建一套数据结构。

禁止将诊断自身产生的开销当成普通搜索的性能瓶颈。

不改变现有 JSON 格式；允许增加兼容的可选计时字段。

## 三、FIX-2：实现 SQLite 候选预筛选

### 3.1 设计原则

目前的执行顺序基本是：

1. 读取全部 GeoNames 地点。
2. 读取所有地点别名。
3. 加载 OSM 行政区与旧地点关联。
4. Python 中完成字符串匹配。
5. 只返回最终命中候选。

建议改为：

1. 将搜索文本按当前 `_compact()` 规则正规化。
2. 通过 SQLite 查询筛出可能命中的地点 ID、来源及必要关联。
3. 只获取这些候选的完整资料与相关别名。
4. 保留现有 Python 地点身份和结果验证。
5. 返回与旧实现相同的地点候选结果。

**优先修改 GeoNames 和别名的大规模读取路径。** OSM 行政区约 3,013 条，可在有证据时再优化，不必一次重构所有数据源。

### 3.2 匹配语义

必须保留当前规则：

`_compact(地点名称或别名) in _compact(查询文本)`

可研究使用 SQLite `instr()`、规范化列或其他等价方法进行筛选。

注意：

- `normalized_name` 和 `normalized` 是 NFKC、大小写折叠、空白归并后的存储键。
- 查询必须兼容原 `_compact()` 将空白全部移除的语义。
- 普通 `LIKE` 和已有 B-tree 索引不能直接证明这种子串匹配可以高效执行。
- 不能假定 SQL 预筛选一定使用索引。
- 必须使用参数绑定，不能拼接用户输入。
- 不得引入无上限的查询文本子串枚举。
- 不得出现每个候选再次查询一次别名的 N+1 问题。

正式采用某个 SQL 方案前，先用 `EXPLAIN QUERY PLAN` 和局部基准验证其实际代价。

### 3.3 保持结果顺序与重复身份

必须保留：

- GeoNames 原有排序。
- 同一地点的多个来源引用。
- 同名地点的全部候选。
- 同 `place_id` 时的首次匹配行为。
- 别名按原 `alias_id` 的顺序。
- 原有别名去重行为。
- `selection_ref` 和来源身份。
- `dataset_id`、`dataset_version`。
- 必要的父级信息。

不能使用简单 `DISTINCT place_id` 后丢失多个合法来源引用。

如预筛选阶段需要内部去重，应在构造最终候选时恢复旧接口的完整结果及顺序。

## 四、FIX-3：正确处理旧地点关联与历史兼容

重点检查：

- `cn_legacy_links`
- `geo_dataset_place_refs`
- `place_external_refs`
- `albums._index()`
- `active_geo_dataset`

要求：

1. GeoNames 通过旧关联继承给 OSM 的名称与别名，仍能匹配。
2. 已关联的 GeoNames 不得重复作为独立地点返回。
3. 没有合法关联时保留原有独立地点。
4. 对历史 Catalog，只有经过现有 INDEX 验证的 fallback 才能被使用。
5. 不得将旧 provider 下所有同名记录作为当前活动数据集的合法候选。
6. 无活动数据集或验证失败时保留原有安全行为。

任何预筛选 SQL 都不能绕过现有的数据集来源证明与身份验证。

## 五、FIX-4：不引入长期缓存

**本卡不实现跨请求地点词典缓存。**

理由：

- 地点别名允许编辑。
- 地点数据集允许切换和回滚。
- 还有行政区映射、旧地点关联及来源身份。
- 当前版本机制未证明可以低成本覆盖全部缓存失效情况。

此次优先通过 SQL 预筛选减少 Python 读取的数据量。

允许使用同一请求内的小型临时字典，但不跨请求持有过期候选。

如果 SQLite 预筛选无法保持语义等价，或实测没有明显收益：

- 不强行引入全局缓存。
- 保留上一版正确实现。
- 在报告中记录查询计划、瓶颈和未达成原因。
- 将有界词典快照作为后续独立任务评估。

不要在一张卡中同时实现 SQL 预筛选、长期缓存和新增持久化索引。

## 六、保留现有搜索功能

不得改变：

- `choices(text=None)` 的完整目录结果。
- `text=""`、纯空白文本的既有行为。
- 人物、时间、来源、合集混合搜索。
- `PersonalSearchCoordinator.collect()` 和 `validate()` 的验证规则。
- 地点消歧、手工确认以及已确认搜索计划的过期判断。
- 搜索相关度、RRF 排序和分页。
- GeoNames / OSM 来源及历史关联的安全约束。

地点名称、别名和数据集发生合法更新后，下一次查询必须读取当前有效值。

最终确认地点身份仍以现有权威校验为准，不以 SQL 预筛选结果直接代替。

## 七、定向测试

### 7.1 结果一致性

采用优化前的旧函数作为测试基线，对相同隔离数据库逐项比较结果。

必须覆盖：

| 场景 | 预期 |
|---|---|
| 日落、猫、普通描述 | 不误识别地点 |
| 北京、上海、杭州 | 正确识别 |
| 杭州西湖的日落 | 地点与语义组合保持一致 |
| 中文、英文、NFKC、大小写、空白 | 匹配等价 |
| 同名、重名、包含关系 | 不丢候选 |
| GeoNames 别名 | 识别与顺序不变 |
| OSM 行政区别名 | 识别与顺序不变 |
| `cn_legacy_links` | 继承与排除规则不变 |
| 历史 fallback | 仅返回当前可信数据源 |
| 改名、增删别名、退休 | 下一次搜索立即生效 |
| 数据集切换、回滚 | 不读取旧身份 |
| 完整目录调用 | 不丢数据、不改变顺序 |
| 无效数据集 | 不绕过验证 |

要求比较完整候选签名，不只比较命中数量。

旧地点集成测试此前有 7 项因 manifest Schema 兼容性未进入受测逻辑；优先使用当前兼容的隔离测试夹具补齐必要覆盖，不修改生产数据库，也不为此扩大成完整测试重构。

## 性能设计（PERF-BOUNDED）

- 链路与风险：普通综合搜索的地点意图处理会读取当前活动数据集的大量 GeoNames 引用和别名；高频子串条件未必能使用普通索引。
- 做法与边界：用隔离 SQLite 目录（约 47,960 候选、26,520 别名、274 关联）配对评估诊断开销和参数化 SQL 预筛，按实际 SQLite 执行计划选方案；只返回命中地点完整资料，OSM 及已验证历史兼容路径保持权威约束，不加 schema/缓存，不访问真实图库。
- 验证与停止：保留旧实现作为结果签名 oracle，覆盖 4 种文本命中形状、目录更新/切换及旧关联；以定向 JUnit、SQL 行数/查询计划和多次合成热样本观察 P50/P95。若 SQL 内部全扫描收益不明显或语义无法等价，保留正确路径并报告未达标；不作图库延迟保证。
