## 1. 症状、原因与明确目标

用户反馈：在“地点相册”点击城市/省份/区县/国家卡片后，照片出现在原地点管理长页面后面，体验不符合“进入某个地点的照片相册”。

已核对的现状：
- `src/photo_search/web/places.html` 的 `#panel-albums` 内并列 `#album-cards`、`#album-current-title`、`#album-photos`；同一 `main` 仍有地名包、地点目录、建议/批量与操作日志等管理 `section`。
- `src/photo_search/web/places-albums.js::openAlbum()` 仅将卡片隐藏/照片显示并调用 `currentTitle.scrollIntoView()`；没有真正将浏览模式与管理内容分离，也没有完整 pushState/popstate 导航；“返回地点目录”仅手动切换局部 DOM。
- `places.css` 对 `.album-cards {display:grid}`、`.album-current-title {display:flex}` 有作者样式；这可能覆盖浏览器默认 `[hidden]` 显示规则。必须用实际计算样式确认、定向修复显隐；不能仅修改 `scrollIntoView` 掩盖底层缺陷。
- 当前已有 `/places?album_kind=city&album_key=...` 深链、`SearchScopeEntry` 中 `place_kind/place_key` 范围搜索、`PhotoTimeline.mount()` 共享时间轴、地点更正与照片查看器。应复用，而非重建。

**目标体验**：`地点相册列表 → 某地点独立照片视图 → 点击照片弹窗 → 关闭回同地点/原时间位置 → 返回地点列表/原筛选与滚动位置`。仅一层主要内容可见；地点的成员规则和照片数量均不变。

参考：[最终 UI 2.0 可点击原型](../mockups/ui2-interactive/demo.html#place/shenzhen)、[P4-UI-PLACES-E](P4-UI-PLACES-E.md)、[UI 2.0 总规范](../plans/P4-UI-TIMELINE-V2.md)。本卡纠正产品页面层级与导航，不另起一版全站视觉。

## 2. 页面/URL 合同（本卡主交付）

| 页面状态 | 可见内容 | URL 与行为 |
| --- | --- | --- |
| 地点相册列表 | 原有城市/省份/区县/国家封面卡、地名筛选；管理工具可按原入口访问 | `/places`；无合法选中地点时**不得**显示“搜索此地点” |
| 具体地点相册 | 统一页头/左侧导航；“← 返回地点相册列表”、地点名、父级/来源/有效照片总数，独占主内容的共享时间轴 | 维持现有 `/places?album_kind=<kind>&album_key=<key>` 参数协议；点击卡片产生可后退的历史条目 |
| 地点相册内看照片 | 沿用已有或在后续 Viewer 任务中统一的照片弹窗 | 关闭/Esc/遮罩等依查看器已生效能力回到该地点时间轴，不转去全库或管理页 |
| 从搜索/照片详情等打开地点深链 | 直接进入正确地点照片页，显示有效范围 | 刷新与浏览器直接访问恢复；无效/已失效地点给出可见错误和“返回地点列表”，不可静默显示错误地点/全部图库 |
| 地点列表内管理 | 地名包、普通地点目录、建议、批量操作、日志及撤销继续可用 | 管理面板只属于列表/工具层，不应被移动到地点相册照片下方，也不能因隐藏而删除其操作 |

**术语冻结**：“地点相册列表”= `#album-cards` 的有照片城市等封面卡；“地点目录”= `#panel-directory` 内以 `place_id` 为主的地名管理列表，二者是不同功能。返回按钮应写“返回地点相册列表”，不能将地点管理目录误当相册列表或删除。UI 结构优先采用**现有 `/places` 文档内的两套互斥浏览视图**（相册列表/相册详情），不新建前端框架、新业务路由或第二套相册数据模型。地点管理模块保留现有 DOM/ID 与惰性加载；只在相册详情隐藏非照片管理区域。侧栏“地点”仍为当前页；顶部全局搜索框始终存在。地点列表“筛选地名”仅过滤封面卡，不是自然语言搜图。

### 2.1 二次优化：已有代码中的关键陷阱（必须处理）

**① 深链不依赖当前目录筛选或首屏卡片。** 当前 `places-albums.js` 的 `initialKind/initialKey` 只在 `loadAlbums()` 遍历返回的 `body.albums` 时匹配；`GET /api/v1/places/albums` 的 `name` 参数是名称/别名**模糊过滤**，并没有按 `album_key` 精确取详情的参数。选中相册时必须按 `kind + 原样 key` 匹配；直接深链时按**指定的单一 kind** 读取必要的权威目录元信息或复用已有缓存，不因为正在筛选其他地名而失败，不为了命中一个 key 并行拉取四类相册。对 CN 的 `cn:...` key 视为不透明字符串，使用 URL 编码和精确比较，不去掉 `cn:`、转为数字或按名称反查。点击已有卡片则直接使用已有对象，避免重复读取完整目录；当前列表 API 若有真实性能瓶颈应在报告记录并独立评估，**不得擅自重写地点成员 SQL**。仅靠某次过滤后的列表未命中不能宣称“地点不存在”。

**② 相册状态恢复不能假设已由共享组件解决。** `photo-timeline.js` 的 `scopeViews` 在一次 `PhotoTimeline.mount()` 实例内部；`dispose()` 后该内存视图即消失，而现有 `snapshot()` 仅含年月/分桶等摘要，不含完整可恢复的照片锚点。优先复用同实例的现有恢复能力；跨销毁/页面回退确需恢复时，只允许为**当前或少量近期 scope** 保留轻量 `kind/key + timeBasis/groupBy/bucket/year/month + 可信 asset_id/anchor + revision` 视图提示，不缓存整页/全部 ID 或旧游标。若组件缺少必要的安全复原入口，允许对 `photo-timeline.js` 做**有定向回归的最小只读恢复 API**，不得另写一套时间轴。过期 revision/无锚点时按权威数据重查并可见退化，不静默重放大量历史页；不承诺任意深度位置在进程重启后像素级精确恢复。

**③ 更正照片与异步刷新不能重建导航。** 现有 `reloadCurrentAlbum()` 会 `loadAlbums()` 清空目录卡片，再发一次未带地名筛选的 `GET /places/albums`，随后 `openAlbum(updated)` 再次 dispose/mount 时间轴。必须避免“更正一次→闪现/清空列表→跳时间轴顶部→丢失相册”的路径：刷新当前选中 kind/key 的有效元信息和权威照片成员，只有数据实在消失才进入可见空/已失效态；旧目录刷新请求不得重设当前详情，失败保留详情并给重试入口。必要时把“刷新目录卡”和“刷新当前详情”拆成不同代次；不修改人工写接口。

**④ 定义明确的页面状态机与历史来源。** 状态以 `ALBUM_LIST / ALBUM_DETAIL / DETAIL_LOADING / DETAIL_ERROR` 为主；照片弹窗是详情上层，而非另一地点列表。卡片点击 `pushState` 一次，`popstate` 只还原 URL 所描述的视图、绝不再次 push；列表内返回按钮仅在确有本页列表历史条目时回退，否则安全进入 `/places`（不得跨站盲目 `history.back()`）。浏览器 Forward 返回详情、直接深链刷新、搜图跳转详情后返回、同页 A→列表→B 都必须身份一致。清理只属于地点相册的 query 参数，保留合法其他参数/哈希；不能把搜索 scope 的一次性 token 存进地点 URL 或 history.state。

**⑤ 旧管理锚点保留。** `places.js::setupDeferredPanels()` 目前通过 `hashchange` 和 `IntersectionObserver` 加载 `#panel-datasets` / `#panel-directory` / `#panel-operations`。打开 `/places#panel-directory`、`#panel-suggestions`、`#panel-operations` 等历史入口时，应处于相册列表/工具模式，锚点对应区块仍可访问且按需加载；相册详情时隐藏的管理板块不能因为后台 observer/锚点被自动滚入视野或高成本预载。若 URL 同时有地点详情 query 和管理 hash，应有确定且无闪烁的优先级/规范化处理（建议明确单一可见模式），并在测试中固定该约定。不可粗暴移除原 DOM ID 或管理工作流。

## 3. 实施细则（按优先级）

### A. P0 — 真实视图切换与视觉

1. 在 `places.html` 将**地点相册列表**（卡片、种类、地名筛选）与**单个地点照片详情**明确包成两个互斥的容器；`#album-current-title`、`#album-photos` 及原照片纠错入口可保留。进入详情后列表控件、地点工具、地名包/目录/建议/批量/日志和页内管理导航不显示、不参与键盘 Tab；页头/侧栏/全局搜索保留。
2. 详情顶端放**明确的返回入口 + 地点名称 + 完整父级语境/来源 + 实际有效照片总数**，下方直接是共享 `PhotoTimeline` 日期筛选/分组/网格。标题为“深圳市 · 地点相册”之类，不把内部 `place_key` 当名称；不能重复显示列表“筛选地名”、管理表单或说明长文。
3. 修复目标元素的 `[hidden]` 与 `display:grid/flex` 冲突，隐藏必须真实生效（计算样式为 `display:none`、不可聚焦、无隐藏 DOM 的布局高度）。优先对**本页两层视图根节点和有关显式 display 选择器**建立明确隐藏规则，不改全站 `[hidden]`、配色和容器风格；桌面、窄屏、浅/暗色复用现有 token。
4. 点击地点卡进入详情时滚动到照片内容顶部、聚焦标题或返回入口（`preventScroll`），**移除以长页面 `scrollIntoView()` 作为“进入相册”的假导航**。完整内容可直读，空相册/读取中/失败/重新尝试均有明确状态。

### B. P0 — URL、Back、深链与返回状态

1. 以 `album_kind + album_key` 为**唯一地点选择身份**，复用现有深链。卡片点击使用单一导航函数更新 URL（`pushState`）及视图；`popstate` 读取 URL 反向恢复。禁止仅用地点名、列表序号或 `place_id` 推断详情，尤其是同名不同上级/来源。
2. 页面初始加载/刷新若携合法参数，**先进入详情 loading 壳，再异步解析当前 scope 与加载照片**；不能先显示原页面尾部或闪现整页管理工具。旧入口 `search-place-entry.js` 的 `/places?album_kind=...&album_key=...` 继续生效；非法 kind、缺 key、无结果、活动地点包/归属变化后已不存在的 scope 显示可见错误和目录返回，不执行全库 fallback。
3. 点击“返回地点列表”以及浏览器 Back/Forward 均能恢复正确模式；内部由列表进入时不重复压入历史、避免循环 `popstate`；直接深链进入时按钮安全导航至 `/places`，不可无条件 `history.back()` 跳到不相关网站。多次地点 A→列表→B 后退不能出现 A 照片/B 标题。
4. 进入详情前保存地点列表的**城市类型、局部地名筛选、已渲染卡片、可见锚点/滚动位置**。从相册返回尽量直接恢复原列表 DOM、位置和卡片焦点，不必无条件重新请求整个地点列表。正常同页往返必须恢复；刷新/失效导致精确锚点不可恢复时保留可恢复筛选并给出合理退化，不能无限重放分页或无提示跳顶。
5. 照片预览闭合后优先恢复原照片 `asset_id`/时间轴锚点；当前存活实例复用 `PhotoTimeline` 原恢复接口，跨 `dispose()` 只用第 2.1 节所述轻量快照/必要的最小共享恢复 API，不臆测内部 `scopeViews` 会跨实例保留。年份/月/可信日期/未知/待就绪按当前 `kind/key` 隔离，切换地点不得串状态。地点成员变化、旧 revision/游标过期时服从原时间轴 409 处理，不复用不可信旧页。

### C. P1 — 异步请求、整理操作与跨卡兼容

1. 切换地点/返回/`popstate` 时取消或以 generation 拒绝旧的卡片、照片/时间摘要、范围等迟到响应；离开详情调用 `timeline.dispose()`，断开 observer/listener；同一详情不得挂两个时间轴。隐藏视图不可继续后台无限续页。
2. 保留地点相册内每张照片的“更正地点”、`assign/unassign/restore_auto` 与现有受 CSRF/revision 保护的写协议。操作成功后**刷新当前 scope 的成员/计数与照片，不通过 `loadAlbums()`/`openAlbum()` 的完整重进流程清空正在浏览的视图**，尽量保持相册标题、URL、时间选择和当前照片附近锚点；修正导致资产离开当前地点时给出正常更新，不应自动返回目录或每次跳到页面顶端。失败保留原视图并有明确提示。
3. 顶部“搜索此地点”按钮仅在**有效且可见的地点详情视图**出现，仍使用 `SearchScopeEntry` 的结构化 `kind/key` 与现有单次 `scope_entry` 交接。`全库搜索/Enter` 仍按已经实现的 UI2.0 范围搜索合同；返回目录立即隐藏范围按钮，旧地点不能残留。
4. 与 `P4-UI2-SEARCH-SCOPE-UNIFY-A`、`P4-UI2-SCROLL-LOAD-A/B` 及照片查看器统一任务**串行处理共享文件冲突**；不改搜索结果分页、照片浏览滚动器、地点/人物成员 SQL、地图 viewport、照片弹窗放大缩小的独立实现。原 `PhotoTimeline` 自动续页和资源回收不能回退。
5. 地点目录卡封面、排序、有效照片数、CN/OSM/GeoNames 来源、同名上级、人工归属/排除与照片去重完全按当前后端真值；不加入按地点卡计算年月摘要的 N+1 调用。不读原图完成导航；不增加前端缓存全部资产 ID 的结构。

## 4. 实施文件与最小变更边界

- 复用：`photo-timeline.js`、`search-scope-entry.js`、`photo-info.js`、现有 `/api/v1/places/albums` 与 `/api/v1/timeline/{assets,periods}`。**原则上不改 Python/SQL/数据库**；若当前完整列表接口无法可靠定位合法深链，先调查精确 kind/key 的可用只读能力，提出最小兼容处理并补测试；不得静默“未见于当前页 = 地点不存在”。
