# P2-02 — 持久调度、设备资格与阻塞恢复实现

执行模型：**DS-H / DeepSeek V4.1 Flash / 高推理**。模型切换由用户在 Codex 中手动完成；本卡
不启动其他 Agent、不切换客户端，也不得声称自动切换。

已提交起始基线为 P2-01 `2222450`，本卡随 P2-01A 收口提交一起生成。开始时执行
`git log -1 --format=%H -- docs/reports/P2-01A-place-contract.md` 取得实际 P2-01A 提交，结合
`git status --short` 复核工作树；不得从聊天历史假设。前置条件：P2-01、P2-01A 均 PASS，
ADR-0003/0005 及两个机器可读 schema 已冻结。

本任务实现一个可独立恢复的**通用 scheduler 闭环**：在现有 ADR-0002 jobs/lease 基础上落地
requested/resolved device、健康能力资格、持久暂停、退避、优先级与阻塞恢复；用确定性 non-model
CPU 假执行器证明 GPS／地名类任务不依赖 GPU。不得读取 GPS、导入地点包或实现地点业务。

## 用户场景与完成定义

- GPU 不可用或不健康时，GPU_REQUIRED job 明确 BLOCKED；同一队列里的 CPU_PREFERRED non-model
  job 继续完成，不因 GPU 故障全局暂停。
- CPU_ALLOWED/CPU_PREFERRED/显式 cpu|gpu|auto 的解析只在主进程 scheduler 发生，worker 回显
  provider/device/precision；不符结果零持久副作用。
- 进程退出后，暂停状态、job、退避截止和 lease 仍在；过期 lease 可接管，旧执行者不能提交。
- 用户暂停后台调度时不再领取新任务，已有执行仍可心跳和安全完成；恢复后按持久队列继续。
- 高优先级任务先执行，同时通过可测的 aging／公平规则保证长期 backlog 不会永久饥饿。

完成标准：真实 v1→下一连续 schema migration、调度/资格生产代码、API/诊断投影、确定性假执行器
测试和 D 级故障注入全部通过；不产生 artifact/outbox/LanceDB，也不实现真实 GPS 或模型推理。

## 冻结实现契约

### 1. 增量数据库

新增实际连续 migration（若开始时仍只有 0001，应为 `0002_*`），并同步 schema checker/support
version。不得修改 `0001_initial.sql`。migration 至少持久化：

- jobs 的 `requested_device`（`auto|cpu|gpu`）、可空 resolved_device/runtime_provider/precision/
  runtime_capability_revision、可空 blocking_reason，以及 scheduler 派发所需快照；这些字段不进入
  五字段唯一键。
- runtime capability 不可变快照：revision、规范化 JSON/checksum、health、measured/checked time；
  旧运行记录继续可关联旧 revision，恢复不改写历史。
- singleton scheduler state：paused、revision、updated_at；如公平算法需要持久游标/计数，也在此表
  原子保存。

SQLite 能表达的 NOT NULL/enum/range/唯一/FK/CHECK 下沉到 migration。若 ALTER 无法正确补齐旧行
约束，则用同事务 rebuild/copy/rename 并逐项证明 row count、job_id、五字段、状态、attempts、lease、
priority 和时间完全保留。v1→v2 必须先备份；失败回滚保持旧版本；更高版本只读拒写规则不变。

### 2. Scheduler 与领取

- 主进程单写协调器在一个短事务中选 job、解析资格、写 resolved 快照并领取 lease；worker 不再临场
  改选设备。事务内不解码、不推理、不 HTTP、不 sleep。
- pause 阻止新 claim/takeover，不阻止当前合法 lease 的 heartbeat、结果提交或 cancel；恢复仅改变
  scheduler state，不绕过 job 的 run_after/资格。
- RETRY_WAIT 到期进入可领取；指数退避必须配置化、有上限、由测试固定时钟验证，不能忙循环。
- BLOCKED 不消耗普通重试。只有阻塞条件的 capability/source/model revision 发生且重新资格检查通过，
  才以合法 BLOCKED→QUEUED 恢复；不得提供“忽略条件强行成功”。保留 P1 catalog_scan 的既有
  source-offline 恢复语义，不用 P2 设备检查破坏它。
- 优先级继续以数值高者优先，但加入确定性 aging 或等价公平规则；同等有效优先级按
  created_at/job_id 稳定选择。测试证明持续高优先任务下 backlog 获得有界机会。
- 领取、过期接管、续约、取消、完成和恢复均保留 ADR-0002 attempts/lease_token 语义；旧 lease、
  到期 lease、旧 input revision/processor 结果保持零写入。

### 3. 设备与运行时资格

实现 ADR-0003 唯一矩阵，外部稳定值是 GPU_REQUIRED/CPU_ALLOWED/CPU_PREFERRED 与
auto/cpu/gpu；内部 `cuda` 只是一对一运行时映射。

资格同时要求 ProcessorSpec 支持 device/precision、capability provider available + healthy、当前
runtime package/revision 相符，并有该 processor/device/precision 的 evidence。只有 provider 名称或
别的 processor evidence 不合格。

- GPU_REQUIRED auto/gpu：合格 GPU，否则 BLOCKED；显式 cpu 为 DEVICE_POLICY_CONFLICT。
- CPU_ALLOWED auto：合格 GPU 优先，否则合格 CPU；显式 gpu 不合格时 BLOCKED，不转 CPU。
- CPU_PREFERRED auto/cpu：合格 CPU；显式 gpu 仅专项 evidence 合格时允许，否则 BLOCKED。
- scheduler 把 resolution 写入持久 job/JobRequest；提交核对 JobResult 回显，不一致返回
  RUNTIME_RESOLUTION_MISMATCH 且不写业务结果/终态成功。
- 能力失效生成新 capability revision 并阻塞受影响新派发；恢复也生成新 revision，重新资格后才
  恢复匹配 job。GPU 故障不能阻塞合格 CPU_PREFERRED job。

现有 `runtime/device.py` 的 P0 probe API 可以保留兼容入口，但新 scheduler 不得依赖其“provider
存在即合格”或 worker-owned default。若修改 `workers/**` 或正式运行环境/打包入口，验收自动增加 C；
若只以注入的 fake executor 验证稳定调度协议，则不要为本卡顺带重构模型 worker。

### 4. 执行器边界与确定性地点假任务

定义最小可注入 executor/dispatch 接口，传普通 JSON JobRequest，返回 JobResult；主进程是唯一持久
写者。测试 fake 的 ProcessorSpec 必须是 `non_model`、`CPU_PREFERRED`、无 model/weights/space，
返回 structured payload 或 `artifacts=[]` 的 SUCCEEDED。它只模拟 `geo_extract`/`place_resolve`
资格和取消边界，不读取文件 EXIF、不产生坐标、不创建地点表、不下载数据包。

超大 payload 仍受有界协议限制；取消在安全批次边界生效。P2-02 不持久化 artifact 内容，成功结果
只证明 scheduler 状态闭环；通用 artifact/outbox 原子提交留 P2-03。

### 5. API 与诊断

按现有 `/api/v1` 边界实现：

```text
GET  /api/v1/jobs                  增加 requested/resolved/provider/precision/capability/blocking 摘要
POST /api/v1/scheduler/pause       持久暂停，返回 state/revision；幂等
POST /api/v1/scheduler/resume      持久恢复，返回 state/revision；幂等
GET  /api/v1/capabilities          只增加安全的 scheduler/runtime 健康摘要
```

写接口必须走现有 session + Origin + CSRF；响应不含 lease token、worker ID、绝对路径、模型路径或
credential。新增稳定错误码至少覆盖 DEVICE_POLICY_CONFLICT、RUNTIME_CAPABILITY_UNAVAILABLE、
RUNTIME_RESOLUTION_MISMATCH、SCHEDULER_PAUSED 和 capability revision 冲突，按 409 映射并脱敏。

## 必须保持的不变量

- jobs 逻辑身份仍且仅为五字段；device/provider/precision/capability/priority/worker 均不加入唯一键。
- lease、attempts、BLOCKED 不耗普通重试、迟到提交零副作用；scan_run/job 联动不回归。
- scheduler 解析设备，worker 只执行并回显；禁止隐式 fallback。
- non-model CPU 任务与 GPU 任务资格隔离；成功空结果正常。
- SQLite 是持久权威，进程内队列丢失不丢 job；所有长工作在事务外。
- `schema_version` 只通过连续 migration 推进；更高版本和不一致 schema 继续先只读拒写。
