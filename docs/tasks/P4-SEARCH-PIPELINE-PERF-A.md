# P4-SEARCH-PIPELINE-PERF-A — 搜索隐藏耗时定位与针对性优化

**优先级：** P1
**任务类型：** 性能诊断补强 + 有证据的最小优化
**推荐执行模型：** GPT-6 High
**代码基线：** 当前 GitHub master
**执行要求：** 先定位、再优化、对比验证；暂不提交 GitHub
**测试规模：** 当前约 4,265 张照片，不执行 30 万图库压力测试

## 一、问题背景

用户已经完成真实图库搜索性能测试：

- 模型：Qwen3-VL-Embedding-2B EXIF v2，512D
- 测试：1 次首次观察、2 次预热、20 个有效热搜索
- 搜索模式：综合搜索
- `top_k=5000`
- 扫描照片：4,265
- 首页返回：20 张

本轮 JSON 结果：

| 指标 | P50 |
|---|---:|
| 后端搜索总执行 | 1,396 ms |
| 查询文字编码 | 32.8 ms |
| LanceDB | 67.9 ms |
| FTS | 0.39 ms |
| RRF | 约 3 ms |
| 权威数据检查 | 约 14 ms |
| 待就绪补查 | 约 7 ms |
| 首张缩略图就绪 | 1,418 ms |
| 当前视口就绪 | 1,435 ms |

按每轮总耗时扣除已经单独计时的阶段后，**未拆分残余耗时 P50 约 1,271 ms**。

因此本任务主要排查搜索链路中尚未被计时覆盖的部分。

注意：

- 残余耗时不是已经确定的单一函数耗时。
- 不得仅凭残余值断言 SQLite、地点解析或 Qwen 存在缺陷。
- 不应优先优化 33 ms 的模型编码或 68 ms 的向量检索。
- 不修改当前模型和索引。

## 二、第一阶段：补齐精确计时

### 2.1 覆盖实际搜索路径

重点检查：

- `src/photo_search/api/routes.py`
- `src/photo_search/api/catalog_reads.py`
- `src/photo_search/search/personal_search.py`
- `src/photo_search/search/service.py`
- `src/photo_search/search/sessions.py`
- `src/photo_search/places/choices.py`
- `src/photo_search/places/albums.py`

当前 UI 主要使用：

`POST /api/v1/search/place-aware`

确保新增计时位于真实请求路径，而不是单独写一个不经过正式逻辑的 benchmark。

### 2.2 拆分搜索前处理耗时

新增以下阶段：

| 字段 | 计时范围 |
|---|---|
| `catalog_queue_ms` | 请求进入 Catalog Worker 到实际开始执行 |
| `catalog_open_ms` | Worker 获取 SQLite 连接、构造 Catalog |
| `intent_collect_ms` | 自然语言搜索意图收集 |
| `intent_validate_ms` | 已有搜索计划验证 |
| `place_choices_ms` | 地点候选生成总耗时 |
| `place_index_ms` | 地点索引读取或校验 |
| `place_sql_ms` | 地点候选涉及的 SQLite 数据读取 |
| `natural_intent_ms` | 其他人物、时间等自然语言解析 |

其中需要同时覆盖：

1. 首次没有 `intent_plan` 的搜索。
2. 前端带有已有 `intent_plan` 的搜索。
3. `validate()` 内部重新调用 `collect()` 的路径。

特别注意：不要只记录第一次解析，却漏掉已有搜索计划的验证和再次收集过程。

如果某个字段是其他计时阶段的子集，需要明确嵌套关系，禁止直接将父子阶段相加。

### 2.3 拆分搜索服务耗时

新增或补齐：

| 字段 | 计时范围 |
|---|---|
| `search_prepare_ms` | 搜索条件、Profile、绑定和查询摘要准备 |
| `retrieval_total_ms` | 整个 `search_assets()` |
| `entries_build_ms` | 候选转换为 `SessionEntry` |
| `rerank_ms` | 可选重排处理及资格检查 |
| `session_build_ms` | 搜索会话构造 |
| `page_render_ms` | 首页权威复查、分页和 Cursor |
| `publication_check_ms` | 结果发布前的版本验证 |
| `session_register_ms` | 会话注册 |
| `response_build_ms` | 搜索结果封装 |

还要观察：

- `search_publish_attempts`
- Worker PID 是否改变
- 是否存在不必要的重复查询
- 同一请求中的数据库连接创建次数

诊断应以低开销的粗阶段计时为主。

### 2.4 时间统计必须能对账

增加结构化阶段树，而不是只有一批互相重叠的平铺时间值。

至少能明确区分：

- 搜索前处理
- 核心检索
- 搜索后处理
- Worker 排队与连接准备
- 尚未覆盖的剩余时间

对每轮输出 `unaccounted_ms` 和诊断覆盖比例。

只从互不重叠的阶段计算残余时间。计时边界不同的父子阶段不能重复扣除。

对于不能可靠拆解的部分，明确标记 `not_measured`。

不得虚构阶段耗时，也不得为了让总数相等而强行摊派剩余时间。

## 三、第二阶段：重点确认地点候选构建

目前发现潜在的 N+1 SQL 风险。

`src/photo_search/places/choices.py` 中，地点候选构建涉及：

- 获取中国行政区候选。
- 逐条查询行政区地点映射。
- 获取 GeoNames 候选。
- 逐条读取地点别名。
- 最后根据搜索文本筛选。

因此普通搜索即使没有地点含义，也可能重复做大量候选准备工作。

同时，`PersonalSearchCoordinator.validate()` 在某些路径下会再次调用 `collect()`。

### 必须先验证

记录：

- 单次搜索调用 `place_choices.choices()` 的次数。
- 每次执行耗时。
- 涉及的 SQL 查询数量。
- 行政区与 GeoNames 读取行数。
- 地点别名查询数量。
- 完整候选生成后实际匹配数量。
- `collect()` 与 `validate()` 是否重复执行相同的地点准备。

只记录汇总数字，不将私人搜索文本或地点名称写入导出报告。

### 根据结果决定是否优化

**若地点候选构建确实属于主要耗时来源，则允许进行最小优化。**

优先考虑：

1. 将逐地点查询映射及别名的 N+1 SQL 改为批量读取。
2. 避免同一请求重复生成相同地点候选。
3. 尽可能提前过滤明显无关的候选，但不能改变地点匹配规则。
4. 尽量复用同一轮请求内已验证的候选数据。

特别要求：

- 保留现有地点消歧规则。
- 保留 GeoNames、OSM 数据源身份与版本验证。
- 保留行政区、别名、同名地点的处理顺序和结果。
- 数据源更新后不能沿用旧候选。
- 不引入无界的进程级缓存。
- 不绕过当前活动数据集检查。
- 不因优化而把普通名词错误识别为地点。
- 不改变人工选定地点的语义。

如批量查询可能遇到 SQLite 参数数量限制，须使用合理分批策略。

**如果计时显示地点候选不是主要瓶颈，则不对该模块做无证据的重构。** 转而针对实际最慢阶段做小范围优化。

## 四、优化执行原则

本卡采用明确的两阶段顺序。

### 阶段 A：只加计时，不改搜索算法

先运行基线测试并明确具体瓶颈。

在修复报告中写清楚：

- 哪个阶段最慢。
- 每次调用次数。
- P50/P95。
- 是否重复执行。
- 主要耗时属于 Python 处理、SQLite 查询还是 Worker 等待。
- 是否存在仍未解释的残余耗时。

### 阶段 B：只优化经验证的瓶颈

条件：

- 性能瓶颈有定量证据。
- 能限定修改范围。
- 能保证搜索结果与原逻辑一致。
- 不需要改动数据库结构或模型索引。

若发现主要瓶颈需要大规模架构改造，只完成阶段 A，记录原因并另提方案，不在本卡中扩大修改。

## 五、结果正确性保障

这是搜索性能任务，不能以牺牲正确性换取速度。

优化前后对同一份只读测试数据进行对照。

验证：

- 搜索结果 ID 与排序一致。
- 中文普通语义查询正常。
- 人物名称、时间表达式、地点查询正常。
- 同名地点和别名消歧不变。
- 已选地点、已取消地点的语义不变。
- 已有 `intent_plan` 的验证结果不变。
- 地点数据集切换或版本变化时能正确拒绝旧身份。
- 收藏、人物合集和范围搜索不回退。

如果新旧结果不一致，必须解释差异，不得直接把更快的实现作为成功。

## 六、最小性能验证

不需要真实图库的完整压力认证。

开发环境最小测试：

1. 使用合成数据验证完整阶段计时。
2. 使用带多个地点和别名的测试库，检查 SQL 查询次数。
3. 核对优化前后的地点候选和搜索结果。
4. 确保关闭诊断时不增加性能负担。
5. 验证模型绑定及搜索会话行为不变。

用户真实图库的最终验证：

使用当前 Qwen EXIF v2，同一搜索词与相同 `top_k`：

- 1 次首次观察。
- 2 次预热。
- 20 次有效热搜索。

比较优化前后的：

- 后端搜索 P50/P95。
- `unaccounted_ms`。
- 主要瓶颈阶段 P50/P95。
- 首张图片就绪。
- 视口就绪。

本任务不以任意指定的绝对毫秒数作为强制通过条件。必须先保证结果正确，并证明优化对整体延迟确实有效。

如果没有真实图库环境，不得声称实机速度已达到目标。

## 七、修改边界

- 更换模型。
- 调整 Qwen 或 Chinese-CLIP 推理参数。
- 改变 `top_k`、RRF 权重或搜索阈值。
- 修改原始照片或向量。
- 重建索引。
- 删除数据库。
- 引入数据库迁移。
- 新增复杂的性能管理页面。
- 在普通搜索模式持续记录详细 SQL。
- 进行与本任务无关的大规模重构。

保留现有诊断开关和 JSON 导出方式。

只有明确开启性能诊断时才执行额外阶段计时和 SQL 次数统计。

## 性能设计（PERF-BOUNDED）

- 链路与风险：真实搜索 POST 的 Worker 排队、Catalog 打开、意图/地点准备、检索、会话分页及发布；详细计时和 SQL 计数可能给请求增加开销，因此必须严格受当前诊断开关控制。
- 做法与边界：基线采用用户提供的 4,265 张图库、Qwen EXIF v2、top_k=5000 与 1+2+20 汇总；开发验证用隔离合成 Catalog/地点数据，最多 2–3 次串行观察，不访问真实图库、不跑 30 万压力测试。只做低开销、开关内计时；仅对被量化证实且语义等价的主要瓶颈做最小修复。
- 验证与停止：定向 JUnit/SQL 计数与查询结果等价校验、普通模式零额外详细计时、Ruff/py_compile/Node/diff-check；若瓶颈不能以隔离数据复现或优化可能改变地点/搜索语义，则止于诊断补强并记录实机对比待用户运行。
