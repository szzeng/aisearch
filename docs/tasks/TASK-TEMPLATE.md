# 任务卡编写模板

这是编写指南，不是可执行任务。立卡者将下面结构复制到实际任务卡，填入具体名称、路径、命令、预算与理由后再激活；不得留下待用户填写的占位符。旧卡下次激活时只补本次缺少的性能段，保留历史结果及明确例外。

用户直接提出需求即可；执行者负责按需补齐短设计，不要求用户改卡、填模板或每次提醒性能规范。已有卡不批量重写，任务中修改继续复用原卡与报告。

## 任务与边界

- ID、日期、状态、用户目标、基线和允许/排除范围。
- 必读的主架构/策略章节，以及直接实现、接口、测试与报告。
- 实际执行模型按可确认信息记录；推荐路由仅供用户手动选择。

## 实施与不变量

写清具体行为、改动位置、直接/共享消费者及不可改变的结果、身份、人工状态、排序/游标、故障恢复或权限边界。影响 schema/依赖/协议时记录决策及相应验证。

## 性能设计与验收（每卡必填）

遵循 [性能规范](../performance.md)。个人库日常任务默认只写三行，不强制八字段、数字预算或新增测量：

- 链路与风险：哪里可能整库/逐项重复、首屏阻塞、增加缓存或后台成本？新增/改写高频 SQL 时先简查 N/K/P、关联扇出和索引，即使尚无卡顿；无影响写理由。
- 做法与边界：最简单可行方案、页/候选/全局范围，保留哪些结果与人工状态；沿用已有预算。
- 验证与停止：本次定向测试/必要浏览器及已有证据；出现卡顿或事前风险证据时才按需补计划/小型对照，有明确规模风险且小证据不足时再升档；不新增规模承诺时明确说明。

纯文档一行 `PERF-N/A + 理由 + 文档检查` 即可。实际慢点、复杂共享路径、缓存/并发或容量验收再按需展开下面参考项，没涉及的项不用逐条填“不适用”：

- 分级与理由：PERF-N/A / PERF-BOUNDED / PERF-SCALE / PERF-RELEASE，说明依据。
- 用户链路：关键操作、首屏/续页/后台，以及 API 到可见/可交互的边界。
- 数据与工作边界：N/K/P、扇出/密度、重复工作，以及必要的请求/批次/并发/资源上限；全局工作说明原因。
- 预算与来源：引用产品阈值或可核验基线，指定指标、允许退化边界和事前冻结点；不编造毫秒值。
- 方案与不变量：选择访问路径的理由；状态/分页/缓存失效与结果等价如何保证。
- 验证与复用：具体测试/真实产品入口/数据、复现命令或生成入口、身份核对、需要重测和浏览器范围。
- 审查：V3.1 §2.4 对应方式、输入/输出与范围；无独审要求写依据，不把自检称独审。
- 停止点：必测指标、最大实验范围、缺证据/超预算/需要越界时怎样收口。

不因改查询就自动升为 PERF-SCALE；升档要写风险证据或卡面容量验收依据。未验的非必需规模/发行项记边界，不阻塞本卡局部收口；原卡必测和数据安全要求不削减。

## 验证计划

按 [日常验证](../testing.md) 与 V3.1 §3.2/3.4 写完整受影响 B/D、全量触发判断、UI/真实模型/性能要求。pytest 命令指定独立 JUnit/basetemp；记录真实退出码、初始失败及修复闭合。必要项缺失保持 PENDING/BLOCKED。

## 交付与后续

指定唯一主报告、原始材料目录、状态更新；区分功能完成、局部性能、规模与发行结论。全部必需验收完成后停止。下一任务仅在存在用户已接受的必要闭环时选择，不自动创建优化清单或启动任务。
