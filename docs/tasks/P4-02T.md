## 为什么是这张卡

§12.2 把"上传搜图≤5 秒"列为个人试用门槛，而手机照片基本就是 MPO（安卓人像/连拍）与 HEIC（iPhone）。
P4-02S 的真实库自检索里，被上传闸门拒的 3 个样本后缀全是 `.jpg`（MPO）——"上传搜图"对本机最普通的照片不可用。

## 目标与范围

- `src/photo_search/search/upload.py`：把 `UPLOAD_INPUT_FORMATS` **显式**扩为
  `{JPEG,PNG,WEBP,BMP,GIF,MPO,HEIC,HEIF}`（字面集合，不自动跟随媒体契约）；解码前调用仓库唯一注册点
  `media.heif.ensure_heif_support()`；在 `exif_transpose` 之前套用与媒体侧同一方向归一；`upload_refused_families()`

解码；扫描真实图库；改 §12.2 门槛；把上传写进 catalog（上传仍不产资产、不写索引）。

## 关键不变量（逐条验证）

1. **白名单显式可审**：仍是一个字面集合；新增格式必须再来一次显式协议变更，不会因为媒体契约变化而悄悄放宽。
2. **与库内解码同语义**：MPO 取容器第一帧；HEIF 族先补回 pillow-heif 清掉的方向标签，再走同一个 `exif_transpose`
   ——与 `media.decode.load_normalized` 同序，避免"旋转过的手机照片上传后静默错向"。
3. **坏文件分类不乱**：白名单内的坏文件 → `DECODE_FAILED`；白名单外的已识别家族（TIFF/RAW/AVIF/JXL/PSD/ICO…）
   → `FORMAT_UNSUPPORTED` + `supported_formats`（= 新白名单）。
4. **上传仍不写库**：不新增资产、不写索引、临时目录必回收；上限错误码（`UPLOAD_TOO_LARGE`/`UPLOAD_TOO_MANY_PIXELS`/
   `VALIDATION_ERROR`）与信封形状不变。
5. **依赖方向不变**：pillow-heif 仍只在 `media/heif.py` 一处注册，`search/**` 不 import 重型框架。
