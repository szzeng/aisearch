# P4-01 — 10 万/30 万 exact/ANN 对照、索引维护、过滤分布与并发调度基准

本卡是 **P4 的第一张规模卡**，只做一件事：在**本机真实运行**产品自己的向量索引与检索代码，给出
10 万与 30 万向量的 **exact vs ANN 召回对照**、**索引维护行为**、**过滤分布**与**后台维护/前台查询并发**
的测量事实，并据此判定「30 万规模下到底有没有瓶颈」。本卡**不**做 ANN 参数复杂调优，**不**做正式容量
全流程验证（属 P4-02），**不**改协议。

推荐执行模型：**DS-H / DeepSeek V4.1 Flash / 高推理**（执行 + 证据收敛）。完成后**另开独立 DS-H 会话**
做全量工程主审；命中 V3.1 §2.2 六类条件才升 DS-MAX；**无法解释的 Windows/系统级性能异常转 C1**。
模型切换由用户在 Codex 中手动完成，本卡不要求中途换模型，也不得声称已自动切换。

## 必须交付的测量事实

全部测量必须在**项目内临时 data root**里真实落库、真实查询，并显式记录数据形状、种子、耗时与内存口径。
只有在 pinned 权重已安装时才允许跑真实模型编码；否则用确定性测试编码器/直接合成向量，并写明「非真实模型」。

### 1. exact vs ANN 召回对照（10 万与 30 万）

- 规模：**100 000** 与 **300 000** 条 512 维 float32 向量（`space_id`/`generation_id` 用生产契约值），
  可选追加 **350 000～400 000** 作为非承诺压力观察（主架构 §12.1）；
- 查询集：固定种子生成的 1000 条查询向量（另加至少 50 条「近似命中 / 边界」构造查询），
  与 30 万库内向量分布一致；
- 对照口径：**同一批查询**分别走 exact（暴力 top-k）与生产 ANN 路径，报告 `Recall@20`（主架构 §12.3 的
  初始目标 **≥ 0.95**）、`Recall@50`、P50/P95 延迟、索引大小与构建耗时；
- 索引维护前后各测一次：**ANN 维护未完成时**（主架构 §12.4 第 9 条）必须仍能搜索，并明确它是
  exact/全量还是部分结果，不得把「未维护」写成召回率指标。
- 若 30 万下 `Recall@20 < 0.95`，先给出参数/数据分布的最小归因（例如维度、k、候选数、过滤选择性），
  再做**单变量**调整；不得顺手改成另一套 ANN 方案。

### 2. 索引维护与恢复（D 级）

- 增量维护：10 万→30 万过程里的每批 upsert/update/delete 后，`IndexCoordinator.process_next`/
  `process_all` 与 `audit_and_schedule_repairs` 的行为、outbox 记录数与 `semantic_ready` 一致性；
- 故障注入（逐条记录命令、前后状态、零重复/零丢失证据）：
  1. 维护中途中断进程后重启：无逻辑重复、无静默丢行，恢复后 exact/ANN 结果与中断前一致；
  2. 「Lance 已写入、outbox 未确认」窗口重放（沿用 P2-03 的既有语义）；
  3. 同 `asset_id` 内容变更后的旧向量不得继续命中（新内容未维护前也不得命中旧向量）；
  4. 删除位置/资产后索引内不得残留可检索的幽灵向量。
- 每个注入都要给出「重放/恢复后与权威状态一致」的可核对计数，而不是只写「通过」。

### 3. 过滤分布与组合条件

- 用合成但**贴近生产分布**的过滤维度（来源、`place` 层级、`taken_time`/`capture_desc` 范围、人物、
  排除项）构造至少 4 种选择性档位（例如 90% / 50% / 10% / 1%）；
- 报告每档的候选集规模、过滤后 top-k 正确性（与 SQL 权威页对照）、ANN 在强过滤下的召回保持情况；
- 必须覆盖主架构 §12.4 第 32 条的组合语义：地点 + 人物 + 时间 + 语义的 AND 条件正确；
  以及「投影滞后期间新归类仍能被补回」不被基准夹具绕过；
- 过滤必须**不得**因性能考虑退化为「先召回后丢弃导致缺结果」——若出现，记录为发现并给出最小反例。

### 4. 后台维护 + 前台查询的并发调度

- 场景：后台持续索引维护（`IndexCoordinator`）同时前台执行普通文字搜索；
- 报告前台 P50/P95（主架构 §12.2 的调度目标：后台建库时普通文字搜索 P95 ≤ 1.5 秒，超标需调整并发）、
  后台吞吐（行/秒）、CPU/内存峰值与（若使用真实模型）显存峰值；
- 冷启动/冷缓存单独报告，不混入暖机指标；
- 资源默认值来自主架构 §6.4；若测量显示默认并发需要调整，**只记录测量与建议**，把阈值决策留给后续卡。

## 报告与停止点

- 报告：`docs/reports/P4-01-ann-scale-benchmark.md`，必须包含：机器规格、夹具与种子、数据形状、
  exact/ANN 对照表（含 `Recall@20/@50` 与 P50/P95）、索引维护与 4 项故障注入的前后状态、
  四档过滤分布表、并发调度结果与 §12.2 目标对照、资源峰值口径、结论「30 万下是否存在瓶颈」、
  真实 Git 状态、失败修复记录与未验证项。
- 禁止把「跑得动」当「达标」：未测到 `Recall@20`、未做故障注入、未做并发对照时不得标 PASS。
- **停止条件（必须停下并交回，不得夹带）**：
  1. 30 万下出现瓶颈且修复需要新增依赖、改 schema/migration、改检索语义或扩大支持承诺 → 停止，输出最小
     反例 + 测量数据，交回用户决定是否单开设计卡；本卡不擅自复杂化 ANN；
  2. 出现无法解释的 Windows/系统级性能异常（路径长度、文件系统、DLL、显存、权限）→ 按 V3.1 §2.2/§9 建议
     转 **C1**，只保留复现数据；
  3. 命中 §2.2 六类条件之一 → 建议 **DS-MAX**，报告写明命中编号、已有证据与待回答问题；
  4. 发现既有语义（RRF/过滤正确性/游标/投影补查）被本卡基准绕开或与 ADR 不符 → 停止，输出最小反例。
- 正常收尾：更新报告与 `docs/development-status.md`，并按 `docs/task-launcher.md` 生成下一任务卡
  （预期 **P4-02 — 1 万→10 万→30 万正式容量验证**，**DS-L 执行 + 独立 DS-H 全量工程主审**）。
