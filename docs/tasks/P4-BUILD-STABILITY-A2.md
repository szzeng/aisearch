## 二、核心任务 A：统一 GPU 资源协调

这是本卡最重要的部分。

### 2.1 先厘清 GPU 资源模型

现有机制包括：

- `BACKGROUND_MODEL_SLOT`
- `ModelResourceGate`
- `GatedEncoder`

必须先检查实际调用链，明确：

- Qwen 查询及建库。
- 人脸检测与识别。
- OCR GPU 初始化。
- OCR GPU 推理。
- 候选模型构建。
- 模型 Session 缓存。

特别区分三个不同问题：

| 资源类型 | 需要解决的问题 |
|---|---|
| GPU 执行权 | 同一时刻哪些任务可以进行 GPU 推理 |
| GPU 初始化权 | 哪些任务可以创建或初始化 GPU Session |
| 显存占用 | 已创建但暂时没有推理的模型是否仍占用显存 |

**取得 GPU 执行锁不等于显存已经释放。**

不能只增加一把锁，就声称完成 GPU 资源管理。

### 2.2 修复 OCR GPU 路径

重点检查：

- `record_runtime_evidence()`
- `run_queue()`
- `OcrEngineCache`
- `PinnedOcrEngine`

要求：

1. CPU OCR 能力检测与 GPU OCR 能力检测分离。
2. CPU OCR 不应无故初始化 CUDA Session。
3. GPU OCR 初始化必须经过统一资源协调。
4. GPU OCR 实际推理必须经过统一资源协调。
5. 不得出现绕过资源协调的 GPU 初始化入口。
6. GPU 资源繁忙时应报告等待，而不是误报 GPU 故障。
7. 保留真实 Provider 检测，不能伪造 GPU 健康状态。
8. 保留现有 OCR Processor 身份及任务持久化协议。

GPU OCR 是可按实际收益启用的能力，不得为了完成本任务强制改变 OCR 原有设备配置。

### 2.3 正确处理任务领取与 GPU 等待

重点防止：

**任务已经领取 → 长时间等待 GPU → 租约过期 → 重复领取或任务失效。**

要求：

- 优先在领取 GPU 任务之前取得资源许可。
- 如果现有 Scheduler 无法做到，设计有界等待及租约续期方案。
- 等待 GPU 时不能持有 SQLite 写事务。
- 等待期间不能无意义地消耗任务重试次数。
- 取消、超时和异常时，任务必须保持可恢复。
- GPU 资源释放使用可靠的 `finally` 边界。
- 不得因 GPU 暂时繁忙触发错误的 CPU fallback。

CPU OCR 必须保持独立，不应被 GPU 等待队列长期阻塞。

### 2.4 Session 显存生命周期

必须查清 OCR Session 的实际创建、缓存、使用和释放过程。

要求：

- 优先延迟初始化 GPU Session。
- 避免每批任务反复加载、卸载模型。
- 明确 Session 是否会在推理结束后继续占用显存。
- 明确 OCR 与 Qwen 是否允许同时驻留显存。
- 如果不允许同时驻留，应采用有证据支持的互斥或切换策略。
- 如果允许同时驻留，必须有真实显存预算依据。

不能仅通过 `del`、垃圾回收或清除缓存引用，就声称 ONNX Runtime 已经释放显存。

如果底层运行时没有可靠的显式释放接口，应明确记录限制，并采用可验证的资源调度方案。

**不得为了显存管理引入不必要的多进程架构。**

### 2.5 锁顺序和前台优先级

输出一份简短的锁关系说明：

- 资源获取顺序。
- 资源释放顺序。
- 是否存在嵌套锁。
- 是否存在锁顺序反转。
- 取消和超时如何释放资源。
- 前台查询如何获得优先权。

必须保留：

- 现有前台搜索优先策略。
- 人脸识别现有 RLock 可重入要求。
- 候选建库已有资源协调规则。

不得因为增加 OCR 锁而造成新的循环等待或后台任务饥饿。

## 三、核心任务 B：建库进度诊断

目标是让用户知道图库究竟在做什么，而不是只看到一个长期不变的建库进度。

### 3.1 最小状态设计

复用现有建库状态，不另建复杂监控系统。

需要能够区分：

- SCANNING：扫描文件。
- HASHING：读取文件和计算哈希。
- WAITING_SQLITE：等待数据库。
- WAITING_GPU：等待 GPU。
- LOADING_MODEL：加载模型。
- INFERENCE：模型推理。
- INDEX_PUBLISH：提交向量索引。
- RECOVERING：恢复任务。
- CANCELLING：安全停止。
- IDLE：当前没有执行任务。

如果现有状态已经能准确表达某个阶段，不重复新增。

### 3.2 必要诊断字段

尽量复用现有状态对象，必要时增加：

- 当前阶段。
- 当前任务 ID。
- 当前批次处理数量。
- 最后一次有效进度时间。
- 最近一次成功提交时间。
- 当前等待的资源。
- 等待原因。
- 最近错误及发生阶段。

不需要保存完整本地照片路径。

不需要每张照片都写一次诊断记录。

优先采用内存状态与现有持久化进度相结合的方式，不为诊断轻易增加数据库迁移。

### 3.3 长时间无进展识别

必须区分：

1. 正常慢速运行。
2. 正在等待 GPU。
3. 正在等待 SQLite。
4. 正在执行不可立即中断的文件 I/O。
5. 正在执行长时间模型推理。
6. 任务真正发生异常。

要求：

- 使用有效进度时间识别长期无进展。
- 资源等待必须能显示具体原因。
- 正常的慢速操作不得误报为死锁。
- 不允许只凭进度百分比不变就判定任务卡死。
- 对真正异常的任务提供明确的失败原因。

### 3.4 UI 修改

只调整现有建库状态和任务明细显示。

让用户能够看懂：

- 当前正在做什么。
- 正在等待什么。
- 最近什么时候有进展。
- 是否发生异常。
- 是否可以安全取消或恢复。

保持界面简洁，不新增独立的复杂监控页面。

## 四、核心任务 C：关闭失败后的资源清理

重点检查：

- `ApiContext.close()`
- `_finish_shutdown()`
- `defer_data_root_lease_release()`
- 应用生命周期中的资源释放顺序。

要求：

1. 资源关闭成功之前，不清空对应引用。
2. 关闭失败后能够安全重试。
3. 已成功关闭的资源不能重复释放。
4. 事件循环已经关闭时，不得假装异步清理成功。
5. 工作线程仍然运行时，不得提前释放数据目录租约。
6. 清理失败需要明确记录。
7. 不能为了快速关闭程序而强制终止 Python 线程。
8. 不能出现旧实例仍在操作图库，新实例却已经获得图库独占权的情况。

优先修复现有生命周期，不重新设计整个应用启动与关闭架构。

## 五、必须执行的定向测试

全部使用独立临时图库。

### 5.1 GPU 协调

| 场景 | 预期结果 |
|---|---|
| Qwen 与 OCR GPU 同时请求 | 资源协调正确 |
| 人脸与 OCR GPU 同时请求 | 不发生未经许可的并发 |
| GPU 被占用时执行 CPU OCR | CPU OCR 独立运行 |
| CPU OCR 启动 | 不无故初始化 GPU Session |
| GPU 等待期间取消 | 任务安全取消 |
| GPU 等待期间租约接近过期 | 不发生错误接管 |
| GPU Session 初始化失败 | 真实记录失败原因 |
| GPU Session 持续缓存 | 显存占用策略明确 |
| GPU 资源释放 | 后续任务能够正常执行 |

### 5.2 锁与恢复

- 使用事件控制两个线程的资源获取顺序。
- 检查是否存在循环等待。
- 每项并发测试必须有明确超时。
- 验证 SQLite 等待期间没有长期持有写事务。
- 验证取消、异常和超时后的资源释放。
- 验证前台查询不会被后台 OCR 长期阻塞。

### 5.3 进度诊断

- 慢速哈希能够反映有效进度。
- SQLite 等待能够准确识别。
- GPU 等待能够准确识别。
- 长时间推理不会误报死锁。
- 任务取消状态正确。
- 任务恢复状态正确。
- 真正无进展时能够提供明确诊断。

### 5.4 关闭恢复

- Encoder 首次关闭失败、第二次成功。
- 成功关闭后不会重复释放。
- 事件循环提前关闭。
- 后台线程未退出时尝试启动新实例。
- 所有线程退出后正常释放租约。
