# P4-PHOTO-SMART-STRONG-MATCH — 智能合集高度匹配收录优化

**状态**：IMPLEMENTED / SCOPED PASS
**日期**：2026-10-21
**优先级**：P2
**建议模型**：GPT-6 High
**仓库**：`szzeng/aisearch`，执行前检查最新 master。

**主架构/策略依据**：V3.0 §3.2、§4.2、§7、§8.5、§12.1～12.4；V3.1 §2.4、§3.2、§3.4。涉及跨模块缓存身份和 schema 语义，按实际变更审查。

## 1. 目标

让 AI 语义智能合集只收录符合当前搜索模型「高度匹配」标准的照片，减少低相关结果。

核心原则：

1. 直接复用搜索系统已有的高度匹配阈值，不重新标定。
2. 不增加用户可调选项、滑块或额外 AI 判断。
3. 新建与已有 AI 智能合集统一生效。
4. 保持现有智能合集按需刷新及增量索引变化检测机制，不改为每次打开强制搜索。
5. 不重新建库、不重新计算照片向量、不修改原始图片。
6. 不影响正常搜索、普通合集、文字合集和纯筛选合集。

本卡只完成一轮功能闭环，不扩展为新搜索系统。

## 2. 模型阈值

直接调用现有：

`search/service.py::strong_match_max_distance(space_id)`

| 模型 | 高度匹配 squared-L2 |
|---|---|
| Chinese-CLIP | ≤ 1.3 |
| Chinese-CLIP EXIF v2 | ≤ 1.3 |
| Qwen3-VL-Embedding-2B | ≤ 1.5 |
| Qwen3-VL-Embedding-2B EXIF v2 | ≤ 1.5 |

规则：

- 使用本次真实搜索绑定的 `space_id`，不能根据模型名称或向量维度猜测。
- 边界使用 `<=`，包含等于阈值的照片。
- 不复制一份新的阈值常量。
- 未知模型空间不允许静默降级为全部候选。

**模型切换：**

智能合集原有模型绑定继续有效。当前活动模型发生变化时，沿用 `MODEL_REBIND_REQUIRED`，必须重新搜索并确认替换规则后才能使用新模型的高度匹配结果。

不能使用新模型阈值筛选旧模型生成的结果。

## 3. 高度匹配的精确定义

当前系统采用向量搜索、FTS 和 RRF 融合排名。

高度匹配智能合集的成员定义为：

**原始融合排名候选 ∩ 向量距离符合当前模型阈值的候选。**

实施要求：

- 仅使用同一次检索产生的向量距离。
- 通过 `asset_id` 匹配向量候选和最终融合候选。
- 没有合格向量距离的纯 FTS 命中不予收录。
- 不允许根据融合分数、排名位置或 `strong_match_count` 推测哪些照片高度匹配。
- 不额外执行模型编码、向量扫描或逐照片 SQL。
- 保留被收录照片在原融合排名中的相对顺序。
- 高度匹配统计数量与最终收录数量可以不同，不必强求相等。

搜索页仍保留原有全部候选结果和「约 N 张高度匹配」统计。

**不要为了智能合集改变正常搜索结果。**

## 4. 最小实施方案

### 4.1 搜索阶段

修改 `search/service.py`，从已有向量检索结果中取得符合阈值的照片 ID。

优先通过现有 `SearchSession` 内部信息传递高度匹配集合，例如有界的 `session.extra` 字段。

要求：

- 只记录本次已确认搜索的真实匹配证据。
- 与 Session、模型空间及生成代绑定。
- 只允许服务端使用，不相信前端传入的高度匹配名单。
- 与已有排名 Session 生命周期一致。
- 不产生第二份完整的候选对象。
- 最多处理现有 5000 个候选。

抽取一个内部公共函数完成：

`select_strong_match_candidates(session)`

由新建和刷新两个入口共同复用，避免出现两套不同的筛选逻辑。

函数职责是验证匹配证据，并按 `session.entries` 原有顺序返回符合条件的 ID。

如果没有可用的距离证据，明确区分：

- 有效搜索但高度匹配为零：合法空结果。
- 向量索引尚未就绪：部分结果，保留 INDEXING 状态。
- 模型阈值或匹配证据不可用：拒绝发布，不得误当成零匹配或全部匹配。

### 4.2 创建智能合集

修改：

`api/routes.py::create_photo_smart_collection_from_search()`

对于 `COMBINED`：

1. 验证原有搜索凭据与 Session 身份。
2. 从确认的 Session 提取高度匹配照片 ID。
3. 保留当前候选顺序。
4. 发布筛选后的智能合集缓存。

当本次搜索有普通候选但没有高度匹配照片时，可以创建合法的空智能合集，显示「暂无高度匹配照片」。

保留当前创建幂等性、过期凭据拒绝、依赖版本复核和初始缓存发布失败后的安全恢复行为。

### 4.3 智能合集刷新

修改：

`photo_smart_collections.py::SmartRefreshRunner._run()`

原有搜索和刷新逻辑不变，只在最终缓存发布前筛选高度匹配候选。

保留：

- 有效缓存复用。
- 自动检查缓存有效性。
- 进入过期合集时按需后台刷新。
- 手动刷新。
- 全局 1 运行 + 2 等待队列。
- 原子发布、租约和迟到 worker 防护。
- 人工排除与恢复。
- 最多 5000 候选、每页 50 张。

不新增周期性扫描、后台持续分类或独立任务系统。

## 5. 已有智能合集升级

**这一部分是本卡的重点。**

现有 `COMBINED` 缓存包含所有融合排名候选，不能直接视为新的高度匹配缓存。

建议采用最小的持久化缓存策略身份：

- 为 `COMBINED` 缓存记录高度匹配策略版本及其模型阈值身份。
- 通过现有 dependency signature 加入该策略身份。
- 旧缓存因没有新策略身份而自动需要刷新。
- 新缓存发布时写入策略身份。
- 未来高度匹配阈值改变时，旧结果自动失效。

优先考虑在现有 `photo_smart_cache_state` 中增加一个可空的缓存策略标识，使用最小加性迁移；不得修改历史 migration。

**旧缓存安全规则：**

1. 升级后保留原智能合集名称、搜索规则和人工排除。
2. 旧全候选缓存不可继续当作高度匹配结果显示。
3. 旧缓存刷新失败时提示「需要重新生成高度匹配结果」。
4. 已使用新策略生成的缓存，普通数据变化导致的 stale 状态仍沿用原来的旧结果浏览机制。
5. 若缓存策略身份不一致，无论 CURRENT、STALE、REFRESHING，均禁止旧照片经详情分页、时间排序或另存普通合集入口泄漏。
6. 新缓存成功发布后，原缓存按现有规则原子替换。
7. 不删除普通合集成员、收藏、人物数据、原照片及向量索引。

若执行者发现更简单且能满足上述兼容边界的方式，可以采用，但必须在报告说明，并通过迁移与旧缓存测试。

## 6. 界面调整

不新增复杂设置。

对于 AI 智能合集：

- 目录：显示 `仅高度匹配`
- 详情：显示 `高度匹配 · XX 张`
- 无结果：显示 `暂无高度匹配照片`

`XX` 表示实际发布的缓存候选数量，不宣称全图库准确总数，也不强制等于搜索页面的高度匹配统计。

保留已有紧凑卡片、无限滚动加载、分页重试、已排除照片管理及照片查看器。

不要修改普通合集、TEXT 或 FILTER 的页面文案。

## 7. 性能设计（PERF-BOUNDED）

**链路与风险：** 搜索 Session → 高度匹配 ID 筛选 → 智能缓存发布。重点防止重复编码、额外向量扫描、逐照片 SQL、全库查询和新增模型占用。

**做法与边界：** 直接使用已获取的距离和原候选顺序，通过集合查找及单次遍历完成筛选，复杂度 O(K)，K ≤ 5000。已有有效缓存读取不应增加模型调用。

**验证与停止：** 对比改动前后模型调用数、向量检索次数及缓存读取路径，确保没有新增重型工作；复用已有 SQL 批量写入和 50 张分页。不要求 30 万图库压测或固定毫秒级性能认证。

若发现实际新增搜索或明显增加数据库查询，必须修正后再完成任务。

## 8. 最小验收

### 核心功能

1. Qwen / Chinese-CLIP 及各自 EXIF v2 正确复用对应阈值。
2. 阈值边界、纯 FTS 命中、混合候选筛选准确。
3. 筛选不改变正常搜索排名和候选结果。
4. 新建合集正确，零匹配可保存为空合集。
5. 首次创建缓存和后续刷新使用相同筛选规则。
6. 新照片符合阈值后，随正常索引发布和缓存刷新进入合集。
7. 低匹配照片不进入，高度匹配照片顺序保持原排名。
8. 人工排除和恢复仍然有效。

### 兼容与故障

9. 旧智能合集升级后保留规则与人工数据。
10. 旧全候选缓存不能从正常读取、stale 浏览或另存入口泄漏。
11. 模型切换、索引未就绪、未知阈值及刷新失败不误发布。
12. 版本变化、重复创建、重启和旧 worker 迟到不破坏新缓存。
13. TEXT、FILTER、普通合集行为不变。
