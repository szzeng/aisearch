## 1. 目标及成功边界

1. 统一纯照片浏览的纵向续页体验：**用户向下滚动接近末尾时自动请求下一批**，无需持续点击「加载下一页」。保留原服务端 `cursor`、原排序、原成员范围与每页上限；不能一次性获取整套结果。
2. 这张卡**只覆盖两类主入口**：
   - `/search` 搜索结果网格：文字/语义、以图搜图、无词 `FILTER_ONLY`、已固定人物/合集/地点/图库范围及服务端候选「按时间查看」。
   - 首页/照片浏览 `/` 的**普通列表/照片网格**与按图库、排序、拍摄时间范围的子视图；时间轴模式已自动续页，只做必要回归，不重新实现。
3. 用户始终能看出“已加载多少、是否还有更多、正在加载/失败/已经到底”；正常状态不以按钮为主操作，异常时可见手动重试/继续按钮。
4. **30 万级图库友好**仅指 UI 增量读取、请求节流及长滚动资源有界，不宣称在本卡完成或验证 30 万完整语义检索。服务端语义 session 候选上限和 TTL 保留。
5. 本卡不处理人物/合集目录、地点目录/建议整理、地图视口成员、历史/维护列表的自动续页；后续目录类工作见 `P4-UI2-SCROLL-LOAD-B`。

## 3. 统一的产品行为合同（P0）

### 3.1 触发与反馈

1. 首次主动搜索/进入普通网格只取**一批**。搜索沿用现有用户指定 `page_size`（默认 20），普通网格沿用 50；不要未经后端核对自动提高分页数量或强制改变用户选择。
2. 在可见的结果末尾增加与缩略图观察器**独立**的 sentinel；优先 `IntersectionObserver`，建议 `rootMargin` 600–900px，必须正确选择实际滚动容器；支持鼠标滚轮、触摸、键盘滚动。没有 Observer 时展示手动「加载更多」。
3. 仅在 `has_more && next_cursor && !loading && 当前视图可见 && 当前查询身份仍有效` 时取下一页。**单列表同一时刻最多 1 个续页请求**；触发 10 次不能并发发 10 个请求。observer 在加载完成后重新判断是否接近底部，避免丢页，但不能因为初始页面短而无用户滚动就循环请求到 5000/30 万：最多有限次数补足首屏，其后要求真实滚动/继续操作。
4. 正常自动续页不跳焦点、不重排旧卡、不滚动到顶部；加载中显示细小状态；失败冻结自动重试并显示明确的「重试加载」，不自动无限重试；到末尾显式显示「已显示 X 张 · 已到底」。
5. 正常显示范围与结果计数沿用服务端语义：语义页使用“当前候选/可能截断”，纯筛选才使用“完整匹配总量”；不能把 5000 候选当成全库总数。保留现有原因提示/时间来源/固定 scope chip。
6. 页面容器隐藏、弹窗打开、查询尚未完成、筛选选择还未提交时不应偷偷加载无关的下一页；弹窗自身的“下一张”请求与列表自动续页需要**共用同一请求互斥/版本校验**，不能抢占或重入。

### 3.2 查询身份、会话和过期（P0）

1. 续页只能沿用**同一次**搜索/列表的原始后端合同：绑定 `requestGeneration`、固定范围 identity、结构化筛选指纹、排序/时间依据、搜索模式、session_id、cursor 和权威 revision。以图搜图沿用原文件选择、原 session 续页，不重新创建不相干查询。
2. 关键词/图片/范围 chip、人物/地点/图库、日期、排序、相关度↔候选时间模式变化时：立即使旧 observer 触发无效、清除旧页游标/状态，并阻止所有迟到响应追加。使用 generation + 对应身份双重检查，必要时 `AbortController`；仅防重复请求不足以避免串页。
3. `INVALID_CURSOR`、`SEARCH_SESSION_EXPIRED`、`CATALOG_FILTER_REVISION_STALE`、地点/合集成员与包 revision 过期、时间规则变化等，**停止自动续页**；按既有合同保留可保留的关键词/筛选/scope，提供重搜/刷新入口；不得静默重跑并将新结果追加到旧结果。
4. 维持 `FILTER_ONLY` 的 SQL 无界权威分页及语义最多 5000 候选机制，保留 `candidate_time` 的服务端冻结集合/排名提示。**不得改搜索 FTS/向量召回/TopK、排序权重、成员 SQL、cursor 编码、会话 TTL 或数据库 schema**。
5. 搜索页面高级筛选中**人物选项列表** `#person-more` 不是照片结果，继续保留原手动加载；不要用照片 observer 误触发人物选项的翻页。

### 3.3 长滚动与返回定位（P0）

1. 不能只在 `renderPage()` 之后永久 `appendChild` 数万卡片。为照片结果建立**有界 DOM 渲染策略**：按页/行进行回收或虚拟窗口（参考时间轴但不直接套时间轴 UI），目标长滚动过程中的实际缩略图卡片节点维持约 **400–600** 范围以内；如果最后实现采用不同阈值，应有测试证明浏览器节点数不会随已浏览页数无限增长。
2. 虚拟化/回收时必须保持列表项目的原顺序、稳定 `asset_id`、可见滚动锚点和大致滚动高度；向上滚动到旧页时应能安全恢复已验证页，或提供明确的定位/重新读取提示。**禁止**出现“旧卡悄悄丢失、滚动条跳回顶部、之前的照片被另一张替换”现象。
3. 不要为 30 万照片常驻整个 `hits`/`assetIds`、缩略图对象 URL 或未回收 DOM；预览弹窗可以持有当前页及有限邻近页导航上下文。若为兼容旧搜索 preview 必须保留有限候选 ID，区分语义最多 5000 与纯筛选无界、不可将纯筛选完整 ID 集 materialize 到浏览器。
4. 返回位置：同一页弹窗关闭尽量恢复同一个 `asset_id` 与屏幕相对位置；进入详情再返回，保留已**权威验证**的筛选和可恢复锚点。原 `app.js` 的 `returnTargetCount` 批量回放需要设置合理恢复预算，不能因为用户深度滚动而在返回瞬间无上限请求几十/几百页。无法可靠恢复深页时保留条件并明确提示“已返回首屏/重新定位”，不能冒充已恢复。
5. 滚动定位不能触发对用户未选择/未看到的所有照片做预览、详情、GPU 解码或文件读取；缩略图懒加载仍只观察进入窗口附近的卡。切换视图、离开页面及取消查询时 disconnect observer，释放不再持有的资源与 listener。
6. **边界取舍**：若现有 `ol.grid` 结构使安全虚拟化必须改写过多交互，可选择分阶段提交，但本卡不能在无内存保护证据时宣称“30万友好/完整自动滚动 PASS”；只能标 `FUNCTIONAL_ONLY / PERF_GUARD_PENDING` 并在报告给出独立后续事项。不可通过固定自动停在 2 页来冒充完成自动滚动。
