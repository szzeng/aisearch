## 1. 用户目标与现状依据

日常只需要三类入口：人物相册、照片中的「更正这张脸」、人物页的「整理一下」。旧高级区的四个分栏「人物列表 / 重检测待确认 / 脸与拆分 / 最近操作与撤销」目前混合了重复的浏览和仍有价值的维护功能，不宜整体直接删除。

已具备、必须复用的能力：
- 人物相册：取名、改名、单人物合并、封面、合集、忽略/恢复、照片查看及单脸 assign/unassign、快捷撤销；未归属脸可创建未命名人物，但 CREATE_PERSON_FROM_FACE 不可撤销。
- 高级工具：按人分页查看 face、原子批量 assign/unassign/restore_auto、显式多人合并、1～500 人脸拆分、映射 confirm/reject/undo、操作历史及过期撤销快照的手动清理。
- 人物性能：头像和 DOM 复用；按有效照片数与最新有效照片首次入库时间全局排序；人物/未命名/待整理独立加载、合集按需加载、待整理 summary 不阻塞卡片。
- 当前人物照片预览中，查看识别更新的按钮仅在没有返回有效人脸时出现，并且点击后只是展开高级区，未直接定位该照片映射；另一个照片即使显示其他新脸，仍可能存在 OPEN 映射。
- 当前 GET /face-mappings 仅支持全局 OPEN/ALL、旧脸 ID 游标，不提供按照片定位；旧高级区展开会初始化旧人物管理和操作历史。

目标是**替代入口、复用既有数据安全规则**；不重新做人脸模型、身份数据库或全局 UI 框架。

## 3. A — 合并人物与逐脸整理入口

### A1. 从人物相册直接整理人脸

在人物相册添加可见但次级的「整理人脸」入口。直接复用 GET /faces?person_id=... 的有界分页与旧 face 列表投影，显示该人有效成员脸的裁剪、所属照片的查看入口、按脸选择。

支持跨页保留选择、取消选择和选择计数；不要把「选中照片」偷换成「选中这张照片的全部人脸」。不可对每张照片额外请求全量人脸制造 N+1。原照片 /assets/{asset_id}/faces 的 200 脸展示上限不等于 split 最多 500 脸，二者按各自语义处理。

选中后提供：
1. 「移到其他人物」——复用既有批量 assign 或单脸 assign，按已有 canonical/排除逻辑。
2. 「从当前人物移出」——复用批量 unassign，标明日后在待整理中可处理。
3. 「拆成新人物」——复用 POST /persons/{source_person_id}/split 的原子事务，1～500 张明确人脸、源人物成员约束、revision/有效成员及撤销全部沿用。
4. 「恢复自动判断」——放在次级菜单，复用 restore_auto，**明确不会删除旧 exclusion，也不会立即重新识别或自动确认**。
5. 「取消选择」——仅 UI，零写入。

**批量操作必须调用现有原子批量接口**，不可前端循环多次单脸请求再宣称原子。合照其他脸不受影响；空选、重复脸、过量、跨人物错选、已有更改后 revision 失效时拒绝/刷新并保留安全状态。不覆盖用户后续人工更正。

### A2. 已有照片里的单脸更正

统一照片预览、人物相册和待整理脸卡片里的「更正这张脸」文案及保存/失败/返回反馈，但只复用一个已有权威单脸写协议。不新增第二套识别或归属逻辑。

已有「确认机器建议 / 选其他人 / 新建未命名人物」继续存在；机器建议仍是建议。CREATE_PERSON_FROM_FACE 只处理一张未归属脸且不可撤销，不能因统一弹窗假装支持撤销。

### A3. 多人物合并不可丢失

当前人物相册有单人物并入功能，旧高级区还有**多源人物一次合并同一目标**。在现有人物批量管理中增加一个明确次级「合并所选人物」入口并复用已有 /persons/merge 原子 API；若实际无法完成，则保留可见旧入口，整卡相应标 PARTIAL，不得为退场而丢失能力。

### A4. 保留整理页已有流程

不重做人物合集、批量忽略/恢复、未命名人物、机器建议、低质量过滤、待整理分页、原图补识别与补匹配。后台运行的补识别任务状态继续可见；复杂控制按需展开但不能隐藏正在运行的真实任务。任何切换/批量管理不能使已加载的多页选择无故折叠或丢失。

## 4. B — 「识别更新待确认」融入照片上下文

### B1. 入口规则

「整理一下」只有实际存在 OPEN 待确认记录时才显示入口/准确数量或待处理提示；无数据则不显示假待确认。

人物照片详情只要当前 asset 存在 OPEN 映射，就应出现「识别结果更新，需要确认」的轻提示；**即使这张照片已经有其他可见新人脸，也必须能找到其旧脸映射**。取代现有单纯以 page.faces.length === 0 判断显示与否的逻辑。点击后直达该照片对应的旧脸候选，而不是简单展开高级区让用户重新找。

没有识别更新的日常合照仍直接更正单脸，不强制经过映射审核。

### B2. 照片定向只读接口，仅在确有需要时新增

优先核对是否已有同等安全只读投影可复用。若无，在现有映射读取层添加**薄、只读、有界**的照片定向接口，例如 GET /api/v1/assets/{asset_id}/face-mapping-reviews?limit=...&cursor=...。

- 只读 OPEN 映射及必要定位信息：旧脸、该 asset、候选状态、原人工状态、受控裁剪 URL、revision 和候选数量；具体候选仍可按旧脸读取原有详情接口。
- 严格限定 asset_id，按旧 face_id 排序分页，游标与原全局 fm1 查询互不混淆；请求数据无效、照片不存在等走当前项目一致的会话/错误惯例。
- 没有 N+1/全局逐页扫描；使用既有 groups.asset_id 数据做有界 SQL。先用合成数据及 EXPLAIN QUERY PLAN 验证，不因缺量化依据而增加迁移/索引。
- 不返回本机路径、人脸框/坐标、向量、评分、操作前后快照或无关私人信息。
- **旧冻结的 GET /face-mappings、GET /face-mappings/{old_face_id} 和 POST /face-mappings/decisions 形状与语义保持不变。**

单照片预览可并行读取原人脸和映射概况，保留 previewSeq/assetId 防旧请求污染；其他人物列表绝不因此新增首屏全量映射请求。

### B3. 审核动作和人工保护

界面显示旧脸与新候选裁剪，以及旧人工归属/排除的简明说明，提供：
- 「是同一张脸」：明确选择合法候选，再用原 POST /face-mappings/decisions confirm；有多候选时不能默认选最高候选，继承 person 的标志按原协议显式选择。
- 「不是同一张脸」：原协议 reject。解释可能解除该映射的 OPEN hold，**不等于指定其他人物**。
- 「暂不处理」：零写入，OPEN/hold 继续保留。

零候选时只允许原协议支持的拒绝或暂缓，不制造新脸。继承禁止超出旧映射矩阵（人工指定、人工移出、排除、冲突、新人工更改、映射撤销及重排队均保留）。

**不得未经人工确认自动转移任何旧人脸人工知识**；高可信单候选也不得自动确认。OPEN hold 必须继续阻止不安全自动归人；mapping undo 后重新 OPEN/hold。

映射确认与之后的普通脸归属修改属于既有不同事务：允许界面引导顺序完成，但不要假装一次双请求原子提交。任一步失败必须显示哪个步骤已经生效，提供重新读取和继续整理，而非静默重复写入或错误显示成功。

## 5. C — 撤销与历史简化

「整理一下 → 更多 → 操作历史」作为唯一普通入口，复用 /person-operations、原 undo 与 retention 接口。显示中文操作类型、时间、影响数量、当前状态与可操作按钮；ID/revision 只在展开诊断信息时出现。

保留新版已经存在的快捷撤销。提示约 10 秒后消失**不等于**永久不能撤销；历史按服务端资格执行。CREATE_PERSON_FROM_FACE 不可撤销；UNDO 不允许任意二次撤销；已撤销、冲突、过期快照只显示准确状态/原因。旧映射 confirm/reject 的撤销仍能找到。

手动清理旧撤销快照留在历史页次级操作，必须先预览后确认，保留「超过 30 天、且不在最近 200 条」及既有服务端逐批保护；不可清理的拆分、映射及其关联保护不动。不新增自动清理、SQL VACUUM 或图片/向量 GC。

## 6. 旧高级 UI 的分阶段退场

先逐项对照以下能力在新界面的可达性：
- 已命名/未命名/人工移出列表；命名与显式合并；
- 单/批量 assign、unassign、restore_auto；
- 1～500 脸拆分与多源人物合并；
- OPEN 映射列表、候选审核、confirm/reject/undo；
- 操作历史、撤销及旧快照清理。

**全部对应能力有新入口并完成定向验证后**才移除其重复 DOM、事件与旧分栏。不得提前整体删除旧高级组件；缺口须保留一个清楚标记的「高级整理」次级入口并报告 PARTIAL。

旧锚点须转到新的真实可见功能或提供明确导航，不可跳向隐藏/删除的节点。核对 persons.js、persons-albums.js 初始化和事件监听，避免二次绑定、空元素报错与双重读请求；有旧功能依赖就不移除脚本引用。不能借机重构整个大型 JS、统一全部查看器或更换页面技术栈。

## 7. 性能硬约束

- 人物/未命名人物按 photos_recent_desc 的服务端有效照片数+assets.created_at+ID 排序及独立分页维持原样。
- 头像 DOM 和图片 60 秒复用、同模式重复操作不重载。
- 合集仍按需加载；整理人脸与未命名人物/待整理 summary 仍独立响应。
- 未展开的映射、历史、维护工具不请求全部记录。
- 按人脸分页跨页选择、列表 revision 失效、切换视图的过时响应拦截保持正确。
- 真实首屏不额外拉取全局人物明细、全部人脸或全局映射/历史。

## 8. 最少定向验收（六组）

只复用直接相关 tests/unit 与 tests/integration，必要时新增小型合成 fixture；生成本任务 JUnit XML，不要求全仓、GPU、真实图库、30 万压力或打包。

T1 **合照单脸更正**：三人合照只修改一张脸；人工排除/锁仍保护其他脸；按 asset 去重的照片数一致。
T2 **批量/拆分**：跨两页选脸、原子批量 assign/unassign/restore_auto、多人并入与 split；无冲突可撤销；过量/空源/旧 revision/失败零部分写；restore_auto 仍保留 exclusions。
T3 **新旧映射**：单候选、多候选、零候选；确认/拒绝/暂缓/撤销；OPEN hold 与人工知识继承矩阵保持，后来人工修改不能被旧结果覆盖。
T4 **照片直达**：当前照片已有其他可见脸时仍检测到 OPEN 映射；无映射不显示假入口；切换照片迟到响应不可串页；新只读查询只取指定 asset、正确分页/隐私。
T5 **历史与维护**：旧操作历史可达；CREATE_PERSON_FROM_FACE 不可撤销；已撤销/冲突/已清理准确说明；清理预览及确认不误清受保护快照。
T6 **前端/性能基线**：旧锚点可到新入口；人物头像复用、排序、合集默认不加载、三区块分开请求、至少两页选择及照片预览/返回正常。

执行检查：相关 pytest -q --junitxml=test-results/P4-PERSON-UX-UNIFY-A.xml，受影响 Python Ruff，修改的 JS node --check，git diff --check；用隔离合成图片一次基本浏览器点击验证。无实际浏览器证据如实记 PENDING，不能用 DOM 桩冒充用户实测。具体测试文件以实际受影响面选择，不复制整套旧基线。

如果**需要改写身份/映射/undo 的冻结业务协议或数据库 schema**，不能以「个人项目小测」为理由绕过项目原风险审核：停止该子项，另立卡并按 V3.1 风险等级要求复核。原协议只做入口重接线时，优先定向验证受影响 UI→API 链和安全拒绝反例。
