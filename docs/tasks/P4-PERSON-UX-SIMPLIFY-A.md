## 2. 核心目标

- 取消重复的旧人物管理界面。
- 所有人脸归属更正都能从照片、人脸卡片或人物相册进入。
- 人物拆分不用输入 `person_id`、`face_id` 或 revision。
- 重检测审核按实际待确认记录显示，直接定位到具体照片。
- 保留原有人工锁、排除、确认、拆分和撤销规则。
- 保留操作日志和手动过期清理，但默认不显示数据库技术字段。
- 不降低人物相册现有加载速度。

不新增第二套人物数据库，不重写人脸识别、自动归组或模型调度。

## 3. 阶段 A — 统一日常整理操作

### A1. 人物相册

在人物相册保留命名、改名、更换封面、合并、照片浏览与局部搜索。

新增或整合清晰的「整理照片」入口。

支持从当前人物照片中逐脸选择，提供：

1. 移到已有的人物：复用现有人工 `assign`。
2. 从此人物移出：复用 `unassign`，明确后续仍需整理。
3. 拆成新的未命名人物：复用现有 `split`。
4. 取消选择：不写入数据库。

只有用户选中的 `face_id` 被修改。合照里的其他脸不得连带变化。同一人同图重复脸、照片计数和人物相册的有效成员规则保持不变。

拆分依然使用原服务端 1～500 张人脸限制及源人物有效成员限制。失败时显示具体原因，不用非原子循环模拟一次拆分。

**补充：批量合并（复用现有功能，不新增合并算法）。** 在现有「批量管理人物」里，选中多个源人物后提供「合并到…」；用户选择一个已存在的目标人物，确认源人物及目标名称，再调用原有多源一次合并的服务端原子 API（`/persons/merge`，以最新路由为准）。不得循环调用多次单人物合并，不能把合照中相同 asset 的照片重复统计，也不能绕过 canonical 人物、人工排除、当前成员和 undo/revision 约束。遇到目标也被选为源、未命名/隐藏对象或 stale revision，按服务端真实资格提示并安全拒绝；合并后按已有局部失效规则刷新列表，保留本次可撤销的操作记录。若本阶段无法完整迁移多源合并，先保留它的旧入口，不能因退出高级工具而丢失该能力。

### A2. 普通照片详情

保留现有「更正这张脸」入口，和人物相册的更正动作使用同一套操作与反馈逻辑。

- 指定到已有的人物。
- 移出错误人物。
- 对符合条件的待整理脸新建未命名人物。
- 支持撤销的动作显示统一快捷撤销。
- 从待整理脸新建未命名人物仍然只处理一张脸，而且明确不可撤销。

不增加任意手动画人脸框功能。未检测到的人脸不能通过填写名字伪造成已识别人脸。

### A3. 整理一下

保留现有未命名人物、机器建议、低质量脸、人工移出、已忽略人脸及恢复功能。

机器建议仍只属于建议，不自动成为人工确认。

保留候选组分页、多页选择、忽略/恢复、原图补识别、补匹配的能力，不重新建立另一套整理列表。

将复杂的识别批处理控件放入按需展开区域；运行中的批处理状态仍然可见，不因折叠停止任务。

## 4. 阶段 B — 识别更新待确认整合

### B1. 入口

去掉作为独立日常导航的「重检测待确认」。

- 在「整理一下」有待确认数量时显示「识别更新待确认」。
- 没有待确认时隐藏此入口。
- 在照片详情中，只有当前照片存在待确认映射才显示提示。
- 点击直接进入对应照片/旧脸审核，不再只打开旧的高级区域。

当前照片有其他有效人脸时，同样必须能够发现待审核映射。不能使用 `page.faces.length === 0` 代替映射资格判断。

### B2. 复用服务端

优先复用已有：

- `GET /face-mappings`
- `GET /face-mappings/{old_face_id}`
- `POST /face-mappings/decisions`
- `POST /person-operations/{operation_id}/undo`

为避免单张照片打开时扫描全局映射列表，可以增加一个**只读、按 asset_id 有界查询**的薄接口，例如 `GET /assets/{asset_id}/face-review`（真实路径按项目 `/api/v1` 前缀及最新约定确定）。

此接口只返回当前照片的待确认摘要及必要定位信息。内部使用已有映射表和身份规则，不新增映射真值来源。

若实施时已有同等能力可复用，则不增加接口。

**补充：照片定向识别审核的查询和交互边界。** 查询应按 asset_id 精确限定 OPEN 映射，采用有界分页/稳定游标，不能为了判断一张照片是否待审核而把全局待确认映射全部下载到浏览器。只暴露审核所需的旧脸、新候选、人工状态、revision、裁剪访问地址等安全字段，不泄露本地路径或向量。照片切换、关闭预览及重试时校验当前 assetId 与请求序号，防止旧响应串到新照片。若照片有多张旧脸待审，按旧脸分别显示对应候选并允许逐项处理；更新后复查服务端状态，不能以本地减少数量当作审核成功。

### B3. 审核界面

每条显示：

- 原来的人脸裁剪。
- 新检测的人脸候选。
- 原来明确的人工归属或人工排除状态。
- 对应整张照片的查看入口。
- 是同一张脸 / 不是同一张脸 / 暂不处理。

多候选时必须让用户明确选中实际对应的新脸，不自动挑最高候选。原脸对应多个候选时继续遵守继承基数和冲突矩阵。

无候选时显示「重新检测没有找到对应人脸」，只开放原协议允许的拒绝/暂缓，不伪造新脸。

### B4. 绝对保留的安全规则

- 任何新旧脸映射都不能未经人工确认直接继承旧人工事实。
- 映射确认只转移协议允许的人工知识，不复制机器判断。
- 映射拒绝不会自动指定一个人物。
- `OPEN` hold 状态继续阻止受影响新脸被自动误归类。
- 映射撤销恢复 `OPEN` 和 hold。
- 用户随后对新脸作出的人工修改不能被过期映射覆盖。
- 旧、新检测版本和旧人脸身份记录继续保留。
- 网络失败、重复提交、revision 冲突必须遵循已有幂等和零写入规则。

**补充：人工归属保护验收要求。** 区分机器建议、已确认人工 assign、人工 unassign、人物排除、已忽略、OPEN hold 和恢复自动判断；不准因为 UI 合并流程混淆这些状态。普通人脸归属更正不得隐式确认/拒绝旧映射；`restore_auto` 若保留为次级操作，只按现有协议解除可解除的人工控制，不偷偷清空 exclusion 或立即调用重新检测。跨合照逐脸更正不能影响同张图其他人的人工身份。服务端拒绝、重复提交或撤销冲突时，UI 必须呈现实际生效状态，不能错误显示操作全部完成。

普通人物归属更正和映射确认可连续在同一个交互流程完成，但后端仍是两个既有事务；不得用两个可能只成功一半的请求伪装成一个原子操作。若要求真正一次提交，需要另行设计并验证原子写入协议，本卡不做。

## 5. 阶段 C — 操作历史与旧界面退场

### C1. 精简操作历史

在「整理一下 → 更多 → 操作历史」提供统一入口：

- 显示中文操作名称、时间、影响数量与实际状态。
- 对允许撤销的操作提供撤销入口。
- 已撤销、发生冲突、过期和本来不可撤销的操作分别标记。
- 从单张脸新建未命名人物明确不支持撤销。
- 不允许撤销一次 `UNDO` 操作。
- 撤销资格由服务器最终决定，前端不可仅凭时间推测。

原有快捷撤销保留。快捷提示消失不代表历史操作立刻失去撤销资格。

### C2. 清理旧记录

将已有手动清理功能收进历史页的「清理旧记录」。

保留当前规则：

- 严格超过 30 天。
- 不属于最近 200 条操作。
- 先预览，再由用户确认。
- 每批保持既有服务端上限。
- 拆分、重检测映射及不具备安全清理资格的记录继续跳过。
- 已清理撤销快照的操作不可恢复撤销能力。
- 保留操作身份、幂等及历史摘要。

不新增自动定期删除，不顺带执行数据库 VACUUM 或图片 GC。

### C3. 旧高级界面退出

完成新流程验证后，取消旧「人物列表 / 脸与拆分 / 重检测待确认 / 最近操作与撤销」的重复页面结构。

不直接删掉仍被调用的后端业务和历史数据。

处理 `#panel-persons`、`#panel-faces`、`#panel-mappings`、`#panel-operations` 旧页面锚点：可以安全重定向到新入口，不允许点击进入不可见的已删除内容。

核对 `persons.js` 和 `persons-albums.js` 的启动与监听关系。旧模块确实没有业务调用方后，移除页面脚本引用；不得留下空 DOM 初始化错误或双重事件绑定。

**旧功能覆盖核对：** 独立旧列表的已命名/未命名人物浏览、多源合并、批量 assign/unassign/restore_auto、1～500 脸拆分、映射 confirm/reject/undo、历史/清理都必须在新入口可达后才允许对应旧 DOM 退场。尚有缺口时保留明确标注的高级整理入口，整卡状态记 PARTIAL，不能删掉无法替代的功能。

## 7. 个人项目最小验收（六组）

以现有单元/集成夹具为基础，只补直接相关测试。六组合并覆盖新增要求，不扩大成完整回归。

### T1 — 普通人物更正与人工保护

一张合成合照有张三、李四、王五。将误归张三的李四脸指定给李四，其他两张脸不变；按 asset_id 去重的相册照片数量正确。已确认的人工归属、排除与机器建议不混淆，失败不覆盖原记录。

### T2 — 批量合并与拆分

跨页选中多个人物，一次原子合并到明确目标；合并后重复合照只算一张，成员/canonical 正确且有可用撤销。再从人物分组选两张脸拆出未命名人物，刷新后正确，无冲突时撤销恢复。全选导致原组无有效成员、超出既有限制、stale revision、原子写失败等均安全拒绝且不产生部分成功。

### T3 — 识别更新确认/拒绝/撤销

旧人工指定脸与一个新脸匹配时，界面能直接确认并按协议继承；多候选要求人工选择；无候选只能按协议拒绝或暂缓。确认、拒绝、撤销后状态正确。验证 OPEN hold、人工排除和新脸后来人工修改不被错误覆盖。

### T4 — 照片定向审核直达

当前照片即使已有其他有效人脸，仍能看到该 asset 上的 OPEN 映射；从提示进入对应旧脸审查，不需扫描全局列表。另一照片无映射不显示假入口；切换照片的过期请求不得串页；只读查询限定 asset、稳定分页且不暴露非必要私人信息。

### T5 — 历史、撤销与清理

普通更正、批量合并、拆分与映射操作的历史可找到；新建人物不可撤销，UNDO 不重复撤销；冲突、过期和清理后不显示虚假成功。清理必须先预览/确认，不误删受保护快照。

### T6 — 页面兼容与轻量性能

人物/人脸跨至少两页选择、取消、刷新、错误重试、照片关闭/返回和旧锚点可达；旧高级功能替代矩阵逐项核对。未进入整理模式时不预加载完整映射、历史和旧人物列表；保留头像复用、人物正确排序、合集按需请求、整理区块独立加载。

执行：
- 对实际修改的 Python/JS 运行定向测试及 JUnit。
- 修改的 JS 运行 `node --check`。
- 修改的 Python 运行 Ruff。
- 执行 `git diff --check`。
- 用合成照片做一次简短真实浏览器操作，确认菜单、单脸更正、批量合并、拆分、映射和撤销的实际点击链路；不能以 DOM 模拟代替真实浏览器测试。

不用全库回归、30 万照片压力测试、模型/GPU 测试或打包专项。合成测试不能冒充真实图库或真实运行性能验证。

## 8. 性能与数据边界

- 人物首屏保持现有有界分页和头像复用。
- 合集继续按需加载。
- 未命名人物和待整理人脸继续独立加载。
- 映射审核、历史及维护数据仅在需要时请求。
- 单张照片审核只查当前 asset，不能拉取全局全部映射。
- 不在浏览器一次性装载所有人物及人脸。
- 保留独立游标、revision 失效与旧异步响应防串页规则。
- 任何失败不能静默覆盖人工整理记录。

默认不访问或修改真实 `PhotoSearchData`，不运行实际模型。真实图库交由用户自行少量验收。
