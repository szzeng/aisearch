## 用户场景

用户搜到一页结果后，对某几张照片显式标记"相关/不相关"；这个反馈必须被**如实记录**（可读、幂等、
可审计），但在本卡里**不自动改变**权威归类、可见性或下一轮排序（在线学习属后续阶段）。当用户为
某个 profile 配置了精排模型时，只有在资格证据存在时才允许激活；精排结果单独返回、单独计时，
基础 RRF 结果先返回，且精排分数**绝不**与 RRF/BM25/距离相加。

## 冻结实现范围

### 1. 显式相关性反馈（新增 migration `0008_search_feedback.sql`）

- 连续 migration（不改 `0001`～`0007`），`SUPPORTED_SCHEMA_VERSION` 推进到 **8**。
- `search_feedback` 只追加：`feedback_id` 主键、`request_id`（唯一，幂等键）、
  `search_session_id`、`asset_id`（外键 RESTRICT，必须存在）、`rank`、
  `relevance`（至少 `RELEVANT`/`NOT_RELEVANT` 两个稳定枚举，CHECK）、`note`（可空、有长度上限）、
  `created_at`；禁止 `UPDATE`/`DELETE`（触发器拒绝），保证审计链不丢。
- `POST /api/v1/search/feedback`：同一 `request_id` 同载荷返回原结果（幂等）；同一 `request_id`
  不同载荷 → 结构化冲突（复用 `PLACE_IDEMPOTENCY_CONFLICT` 的语义或新增 `FEEDBACK_IDEMPOTENCY_CONFLICT`
  并在报告里写明）；未知 `asset_id`/非法 `relevance`/超长 `note` → 422。
- `GET /api/v1/search/feedback`：只读、分页、只返回反馈自身的字段（不得回显地点/坐标/路径）。
- 反馈**不得**：改变 `catalog_filter_revision`、`suggestion_revision`、可见性、`space_id`、
  `search_documents` 或任何向量行；不得让"被标记不相关"的照片从后续查询里消失（那是新的产品决策）。

### 2. 精排适配器接入（不实现真实模型）

- `src/photo_search/search/rerank.py`：按 ADR-0003 §7 定义 `RerankerAdapter` 的**最小查询侧**
  协议（`spec()`、`score(query, candidates, cancellation)`），与 P2-05 的 `QueryEncoder` 同风格，
  业务层不 import ONNX/PyTorch。
- 结果结构：基础 `hits` 始终先返回；只有显式请求精排（例如 `rerank: true`）时才追加
  `reranked` 块（逐行 `asset_id` + `reranker_score` + `reranker_processor_id`），
  **不得**把该分数加进 `score`/RRF，也不得把它显示成百分比。
- profile 门禁：`reranker_processor_id` 非空的 profile，只有在 P2-02 记录的
  `RuntimeCapabilities` 健康且存在该 processor/device/precision 的专项 evidence 时才允许激活，
  否则 `RUNTIME_CAPABILITY_UNAVAILABLE` 且零写；未通过时搜索仍可用（回退到基础 RRF 结果，
  但必须显式标注 `rerank_state=UNAVAILABLE` 而不是静默忽略）。
- 精排超时/失败：结构化错误或 `rerank_state=FAILED`，基础结果不受影响（§9.2「基础结果先返回」）。

### 3. 明确的非目标（本卡不得实现）

- 不得实现搜索页面、上传搜图、反馈 UI（P2-07）；不改任何前端资源。
- 不得实现真实 VLM/精排模型权重、在线学习、自动相关性训练或反馈驱动的排序调参。
- 不得实现自然语言条件解析（年份/人物别名/显式筛选语法）。
- 不得改动：ADR-0001～0005 与冻结 JSON schema、`0001`～`0007`、五字段 job 身份、lease/attempts/
  迟到提交、资产/位置/缺失判定、P2-03A/B 的人工锁/排除/幂等/批量/撤销语义、P2-04 的 tokenizer
  世代/MATCH 策略/`place_text` 来源规则、P2-05 的 RRF 公式/并列规则/`hit_reason` 语义、
  P2-06A 的会话/游标/profile 绑定语义、`space_id` 语义、`ingestion/**`、`workers/**`、打包入口、
  `pyproject.toml`、`uv.lock`。

## 必须保持的不变量

1. `0001`～`0007`、冻结 ADR/JSON schema 逐字节不变；migration 连续到 `0008`；
   `schema_version = 8`。
2. 反馈与精排**都不**是权威分类：地点/来源/可用性/可见性判定仍只看 SQLite；
   `catalog_filter_revision`/`suggestion_revision` 不因反馈或精排改变。
3. 精排分数与 RRF/BM25/距离严格分离（不同字段），不得相加、不得当作概率。
4. 引用未通过资格门禁的 reranker 的 profile 不能被激活（零写），且不影响未引用 reranker 的 profile。
5. 隐私：反馈与精排响应没有绝对路径/坐标；日志与错误不出现原始查询向量。
6. P2-06A 的会话/游标绑定与过期语义不变；既有 P2-05/P2-06A 测试原样通过。

## 验收（B + C + D）

必需命令（沙箱内被拒时在沙箱外执行并在报告里记录）：

```text
uv run --no-sync pytest -q -p no:cacheprovider tests/unit tests/integration
uv run --no-sync ruff check .
git diff --check
uv run --no-sync uv lock --check
uv run --no-sync python tools/packaging/build_onedir.py
uv run --no-sync python tools/diagnostics/packaged_api_smoke.py --bundle dist/PhotoSearch --work-dir <D 盘目录>
```

**C 级证据（必须）**：bundle 内包含新模块与新 migration；smoke 至少覆盖
「`POST /api/v1/search/feedback` → 201/200 + 幂等重放」「`GET /api/v1/search/feedback` 分页」
「无 session → 401」「`rerank: true` 在无资格证据时 → 基础结果 + `rerank_state=UNAVAILABLE`」。

**D 级故障注入（必须，逐项记录实测）**：

1. v7→v8 迁移：备份（内含 `schema_version=7` 且无 `search_feedback`）、单事务推进、旧行不变；
   注入损坏 `0008` → `MIGRATION_FAILED` 且版本仍 7；缺件 → `SCHEMA_INCONSISTENT`；过新 → 零写。
2. 反馈幂等：同一 `request_id` 同载荷 → 同一结果且只有一行；不同载荷 → 结构化冲突且零写；
   非法枚举/未知 asset/超长 note → 422；`UPDATE`/`DELETE` 被触发器拒绝。
3. 反馈不影响权威：写入反馈前后 `catalog_filter_revision`、`suggestion_revision`、
   `search_documents`、`assets.created_at`、向量行数逐项不变，后续查询结果不变。
4. 精排门禁：reranker profile 在无 healthy capability/无专项 evidence 时激活被拒（零写，
   活动指针与 `is_active` 不变）；注入中途异常 → 全部回滚。
5. 精排失败/超时：基础 `hits` 仍返回且与不请求精排时一致（逐字段对比），`rerank_state` 如实标注。
6. 分数分离：`reranked` 行的 `reranker_score` 不进入 `score`；同一请求两次结果一致；
   精排顺序由确定性假适配器复算一致。
7. 继承回归：P2-06A 的会话过期/游标隔离/切换后过期用例原样通过。
