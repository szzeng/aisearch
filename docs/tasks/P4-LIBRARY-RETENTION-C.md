# P4-LIBRARY-RETENTION-C（V2）— 失效照片安全分级与只读清理预览（C1）

**状态**：SCOPED PASS / C1 已完成；**C2 任何业务数据/向量的逻辑或物理删除仍需另立卡、重新授权**。**日期**：2026-10-11。**参考**：`szzeng/aisearch master @ 3b9d472`，开工重核 HEAD 和当前 schema。**推荐**：GPT-6 High（资格和人工记录交叉引用风险较高）；本次按用户指定采用 LUNA / High 独立复核，记录为路由例外而非 DS-H。

## 一、先确定“失效”与“可清理”绝不是一回事

- 文件**位置** `file_locations.availability='MISSING'`：本来源上次完整成功扫描没看见。资产 `assets.asset_id` 可以拥有多个来源和位置。
- **全局无可用位置**：资产不存在任何 `PRESENT` 位置。这个集合还可能包含来源被取消登记后形成的**零位置资产**；它们不能直接称为用户永久删除。
- **待观察**：原图在已登记位置消失，但可恢复同 SHA；保留向量、OCR、人脸及所有人工归属。
- **可进一步人工审核**：有足够可信的失效证据、观察期结束、没有其它可用副本，且所有人工/共享/任务/代际/历史引用可判定。**C1 仅显示候选信息，不执行清理**。

## 二、必须复用的既有能力

1. `catalog/store.py::reconcile_missing_detail` 在成功扫描最终事务标 MISSING；中断/离线扫描没有权力做相同推断。
2. `CatalogService.delete_source` 删除注册及位置，保留 assets、OCR/人脸/地点事实、人工操作、artifact、语义向量。不能把“用户删除来源登记”当作原文件已删除。
3. GC-A (`storage.py`) 清理没有任何正式引用的物理孤儿/缓存；GC-B (`storage_maintenance.py`) 整理 LanceDB 旧物理版本和 SQLite 空闲页。二者**不承担业务资产向量删除**。
4. SQLite outbox `event_type` 即使允许 `DELETE_VECTOR`，当前仍无经过审计闭环的“业务资产永久删除”生产者、消费一致性与恢复屏障，不准直接调用 LanceDB 表删除。
5. `api/queries.py`、`search/retrieval.py` 已支持 `availability=any/present/missing`；C1 不擅改默认列表或搜索过滤语义。

## 三、C1 最小交付（默认**不迁移 schema**）

### C1a. 新增只读入口

在现有“图库管理 → 存储与维护”折叠区增加“失效照片与数据占用”入口，点开才执行有界只读查询；不加载原图、不启动模型、不递归枚举原图库。显示：

- **本次按数据库计数**：MISSING 文件位置数、没有任何 PRESENT 位置的唯一 asset 数、零位置（删除来源或遗留）asset 数、还有 PRESENT 副本的资产数。这些数量不可相加当总数；要按 `asset_id` 去重。
- **安全分类**：`已有有效副本`、`全局无可用位置但证据不足`、`来源已取消登记/零位置`、`包含人工信息或受保护引用`、`待审核候选`。任何查询失败、引用种类未知时归为“待核实/受保护”，不能隐去。
- **小型资产列表**：只读 keyset 分页（例如 50 条/页），展示安全的 asset_id、缺失状态/原因摘要、人工记录保护标记；不返回绝对路径，不批量生成预览图；避免按全部资产装载 Python 集合或向量。
- **空间展示**：仅报告可准确取得的数据大小；SQLite 字节逻辑估计与实际回收量、Lance 逻辑行数与文件回收量各自区别，**未知用“无法准确估计”**。不得凭资产比例分摊全部 Lance 表大小。
- C1 UI 必须写“此处不会删除原图、索引、机器识别或人工记录”；不出现“立即清理”“永久删除”按钮，不与现有 GC-A/B 维护操作勾选联动。

### C1b. 30 天规则**先作为保留资格规则，不假装历史时间可信**

- 默认建议 30 天保护期，但**没有真实首次确认失效时间的旧记录全部记为 `时间未知 / 不具备清理资格`**。
- `assets.created_at`、照片 EXIF、文件 `mtime`、最后一次成功扫描时间，只能代表各自原有含义，**不得冒充首次 MISSING 时间**。
- 若 C1 无法用已有事件/历史事实可靠推导首次失效日期，**首版不为现有旧资产回填 30 天，也不强行新增迁移**：只读 UI 报告“观察期起点未知，暂不建议清理”。这是有意的保守结果，而不是功能失败。
- 如确实需要在 C1 开始收集未来首次失效时间，先独立提交**最小加性迁移与事务设计**，经用户另行确认才实施：新表记录资产级首次确认失效、证据种类与恢复；只有成功扫描的完整事务或其受控幂等后置步骤产生事实，恢复同 SHA 后撤销候选，且跨源存在 PRESENT 时不得启动计时。避免为这项追踪拖慢目前的快速刷新。

## 四、必须检查的安全保护

1. **共享资产**：任何来源存在 PRESENT，绝不可归为全局失效；同 SHA 多副本只算一张资产。
2. **离线/扫描失败**：来源 OFFLINE、扫描被中断、根目录权限问题不能推断永久删除；若全部来源证据不可信，则“待核实”。离线标志不等于把已有 PRESENT 位置强行变 MISSING。
3. **人工知识**：检查并标注人工人脸归属、更正/拆分/合并、人物合集、地点人工指派/排除、忽略、撤销历史、OCR 人工修正（若当前库有）、合照多个 face 等；查询不到一种引用的确定保护规则就标“未知”。**不为首版预览实现跨表级联删除算法**。
4. **写入及恢复引用**：jobs（QUEUED/RUNNING/RETRY_WAIT）、artifacts 各生命周期、index_outbox、当前/候选 SearchProfile/generation、恢复审计未完成等保护。不能仅根据 `index_entries` STALE 或 `artifacts/pending` 目录名判定没有有效引用。
5. **来源被删除**：零位置孤儿独立分类，不自称“用户删除了原图”；即使超过 30 天也不能未经额外用户确认进入自动清理。
6. **不会被 C1 写坏**：只读预览重复调用必须零业务数据写入；旧人物/搜索/地点页面语义和现有可用性筛选保持不变。

## 五、5 组小型合成验收

1. X 同内容在 A/B 各有一份，A 成功扫描标 MISSING、B 仍 PRESENT ⇒ X 不可归为全局失效；复制/同 SHA 还原后自动不属于缺失资产。
2. Y 仅 A 一份，成功扫描后 MISSING；不造日期，展示“无可用位置，时间未知”，不冒充满 30 天；模拟真实有时间证据的未来事件时 29/31 天仅影响**展示资格**，绝不删除。
3. A 整个来源离线/扫描中断：没有把 PRESENT 批量改 MISSING 的写入，也没有虚假的“永久失效”结论；删除来源后形成的零位置资产单列。
4. Z 存在人工人物/地点/忽略/合集及活动 jobs、outbox（拆成最少几条 fixture） ⇒ 显示受保护或未知，不允许写“可以安全删除”；另一来源有效副本必须优先保护。
5. 两次 API 预览前后 SQLite 业务表及向量/产物引用一致；分页完整不重不漏，鉴权和错误态简测。若本次不做计时迁移，就不运行迁移测试。
