# P4-LIBRARY-RETENTION-C2-FIX — 一键清理完整性与性能最小修复

**状态**：IMPLEMENTED / ACCEPTANCE PARTIAL
**优先级**：P1
**推荐执行模型**：GPT-6 High
**代码基准**：`szzeng/aisearch` / `master @ 24fb0f7`（2026-10-20）
**任务性质**：现有 C2 功能修复，不重做清理系统，不自动拆分后续任务。

## 性能边界

- **流程/风险**：一键清理沿保留状态 keyset 遍历候选；风险在候选漏检、无界物化和全局 outbox 积压阻塞。
- **方案/上限**：每批最多 20 个资产、单资产最多 100 个向量事件且最多 5 次 drain；候选按索引游标读取，不物化全库。
- **验证/停止**：用 150/65 个合成候选验证完整分页与 20 项批界，检查 EXPLAIN、隔离小型 Lance 删除及受影响测试；不扩展到真实图库或 30 万容量承诺。

## 1. 修复目标

现有 C2 已实现失效证据、30 天观察、清理屏障、DELETE_VECTOR、机器数据回收和一键清理 UI。

本卡只解决尚未闭合的功能问题：

1. 一键清理只能从第一页最多 50 张中筛选，并且整次最多处理 20 张。
2. 机器识别及索引记录被错误视为人工保护，导致合格照片无法进入清理流程。
3. 向量删除遇到普通索引积压时可能停在 PARTIAL，单次操作不能持续完成。
4. 自动与手动清理任务可能相互复用，造成授权模式不匹配。
5. 清理进度、资格统计和旧提示不完全符合当前功能。

目标：**点击一次，一直分批处理本次范围内所有符合安全条件的失效资产。**

“全部”指经过完整候选遍历和实时安全复核后，能够安全清理的资产；不包括来源异常、有效副本、人工保护或未知引用的资产。

每批最多 20 张继续保留。

## 2. 禁止破坏的现有能力

保持 C2-A～F 的现有协议：

- 可信成功扫描确认 MISSING。
- 30 天观察期及到期后二次扫描。
- 来源离线、异常批量失效保护。
- 跨来源相同 SHA 副本保护。
- 人工记录默认禁止自动删除。
- `asset_retention_barriers` 持久防复活。
- DELETE_VECTOR 的 generation、revision、事务确认与重放。
- 原图零修改。
- 现有 GC-A/B 停机物理空间回收规则。

**手动一键清理仅跳过 30 天等待，不得跳过上述安全资格。**

不修改 Chinese-CLIP、Qwen、EXIF v2 模型算法，不改变搜索模型切换语义。

## 3. F1：修复全量候选遍历

### 3.1 当前问题

`create_library_retention_run()` 直接复用 `_preview_snapshot(limit=50)`，再取前 20 条。

导致后续资产漏检，同时把 UI 展示分页错误地用于后台业务删除。

### 3.2 修复方案

清理候选选择脱离 C1 预览：

- 从 `asset_retention_state`、`assets` 和必要的来源事实中读取有资格进入复核的资产。
- 使用 `asset_id` Keyset Cursor。
- 只取有失效观察证据的候选，不逐个扫描整个原始文件系统。
- 预筛选只用于降低候选数量，最终删除仍由 `_cleanup_preflight()` 权威验证。
- 候选无效时记录原因并向后继续，不能中断整次遍历。

点击时持久化：

- `run_id`
- `mode=MANUAL|AUTOMATIC`
- `selection_max_asset_id`
- `selection_cutoff_at_ms`
- `selection_after_asset_id`
- 必要的当前批次和执行状态

以点击时的资产 ID 上界与资格时间为本次遍历围栏。执行期间新增或后来首次取得资格的资产不进入本轮；已经在范围内的资产仍以执行时最新事实为准，可因恢复、保护或来源变化而跳过。

如果资产清理后主行被删除，仍按原始 `asset_id` 推进游标，不因资产消失而回退。

### 3.3 批次控制

- 每批最多 20 张。
- 一批结束继续获取下一批。
- 遇到人工保护继续向后。
- 最后不足 20 张正常完成。
- 当前范围遍历完毕后才标记本轮完成。
- 不提前一次性将 30 万资产全部写入 Python 内存或持久任务明细。
- `run_items` 保留必要的当前批次和有界最近结果，累计统计由 `runs` 权威保存。

不得简单写无限 `while True`。必须满足有界单批工作量、进度单调前进、停机响应、无候选时结束。

### 3.4 幂等与崩溃恢复

游标、累计数量与当前批次结算必须使用一致的持久协议。

特别覆盖：

- 清理资产成功后，游标尚未提交就崩溃。
- 一批部分成功、部分跳过。
- 重启后重复看到已经完成的资产。
- 同一资产有 COMPLETE tombstone，但当前 run 尚未记账。
- RUNNING 状态因退出中断。
- 上一批失败后需要继续检查后续资产。

利用已有 tombstone 和 run_items 防重，不重建新的审计框架。

所有成功、跳过、失败都不能重复累计。

如果当前资产出现可恢复错误，应保存失败原因，在规定的重试预算内处理，并允许其他资产继续推进。

**验收**：第一页 50 张全部受保护，后面 100 张可以清理；一次点击最终检查到全部 150 张，并清理后面符合条件的 100 张。

## 4. F2：统一清理资格及引用分类

### 4.1 当前问题

`_human_or_protected()` 将大量机器记录视为保护。

`create_library_retention_run()` 用这个判断过滤候选，而 `_cleanup_preflight()` 是另一套实际执行规则。

两套判断不一致。

### 4.2 统一分类

建立一套共享的权威分类逻辑，至少返回：

- `HUMAN_PROTECTED`：真实人工记录。
- `MACHINE_CLEANABLE`：可随资产安全删除的机器数据。
- `TEMPORARY_BLOCKED`：活动任务、未完成维护或其他可恢复条件。
- `UNKNOWN_BLOCKED`：无法解释的引用、schema 或业务身份。
- `SOURCE_BLOCKED`：来源、扫描证据或副本问题。
- `ELIGIBLE`：资格通过。

具体实现优先复用 `_cleanup_preflight()` 的真实检查，不要求新增独立分类服务或把所有状态持久化。

预览、候选过滤和最终清理必须共享基础业务判断，但最终事务始终重新核验。

### 4.3 机器数据不再永久保护

仅有以下机器事实不得成为永久保护原因：

- `asset_metadata`
- OCR、自动 GPS 等派生事实
- `artifacts`
- `index_entries`、普通 index outbox
- 自动 `faces` 与人脸向量
- 自动人物关联和候选
- 可重建的搜索、智能合集缓存

这些数据是否能当场删除，仍取决于相应清理阶段和引用安全性。

对 `upgrade_targets`、face redetection、face operation 等容易混合人工与机器语义的表，必须核对真实生产者和记录类型。能够证明是机器维护目标的按可解除引用处理；无法证明的继续阻塞。

### 4.4 人物保护

重点检查 `face_person_links`：

- 自动候选或自动归属不应仅因存在链接就被认作人工确认。
- `MANUAL`、人工确认、人工覆盖、人工排除、撤销及相关操作历史继续保护。
- 共享人物身份不能随一张照片删除。
- 删除纯机器面部数据时，需要维护有效人物相册计数、封面和缓存修订。

不能简单删除 face protection 检查，也不能把所有 `CONFIRMED` 当成机器记录。

### 4.5 预览与执行一致

候选构造可以只做便宜的 SQL 预筛选；复杂关联允许由单资产权威检查完成。

但不能再用 C1 混合保护字段直接排除所有候选。

UI 显示的保护原因应与实际执行阻塞保持一致。

若两者之间发生新扫描、人工收藏或其他状态变化，以执行时权威事实为准，并显示“状态已变化，已跳过”。

## 5. F3：修复 DELETE_VECTOR 积压与持续执行

### 5.1 当前问题

`RetentionCleanupRunner._run()` 针对一个资产调用全局：

`IndexCoordinator.process_all(limit=100)`

此调用可能优先处理大量无关 UPSERT，导致本次 DELETE_VECTOR 尚未确认，清理任务却结束在 PARTIAL。

同时每张资产都创建协调器并调用全局维护入口，存在重复索引维护成本。

### 5.2 修复要求

优先在现有 IndexCoordinator 上增加最小的目标删除事件推进能力。

允许限定：

- 当前 run 的已授权资产。
- `event_type=DELETE_VECTOR`。
- 正确的 `(space_id, asset_id, generation_id)`。
- 原有 claimable、revision 和 tombstone 校验。

**不得重新实现一套绕过 IndexCoordinator 的 LanceDB 写入路径。**

保留现有 SQLite 单写者事务、LanceDB 删除、确认以及崩溃重放语义。

目标清理不应先处理大量无关 UPSERT，但也不能破坏正常索引队列中同一资产的版本顺序。

目标删除消费成功后，自动进入最终 SQLite 清理。

### 5.3 等待与恢复

区分：

- 正常待删除：本次 worker 有界继续处理。
- SQLite BUSY：按现有有限退避规则重试。
- LanceDB 真实故障：持久记录 FAILED，允许安全重试。
- 事件不可领取：给出具体阻塞原因。
- 应用关闭：保存状态并退出，下一次启动恢复。

不允许无限占用 worker 反复检查同一个 PENDING 事件。

如果已经耗尽当前合理重试预算，必须真实显示为“可恢复失败/等待继续”，不能伪装成功。

有可处理的其他资产时，不得被一个长期失败的 DELETE_VECTOR 永久阻塞。

本轮只在全部候选结算且没有待继续的清理项目时进入最终完成状态。

### 5.4 效率

目标删除批次应尽可能复用一个协调器及必要的 generation 连接。

不要每清理一张资产都重复检查或重建所有 generation 的标量索引。

无关索引 backlog 不应成为本次清理工作量的主要来源。

## 6. F4：手动与自动任务互斥

当前有一个授权问题需要修正：

如果已有 `AUTOMATIC` run，用户点击手动清理，不能直接返回自动任务并让 UI 误以为已经开始手动提前清理。

规则：

1. 重复请求同一运行任务可以安全复用。
2. `MANUAL` 和 `AUTOMATIC` 的授权模式不能相互替换。
3. 不同模式冲突时，最小方案是返回明确的 `RUN_IN_PROGRESS` 及现有任务信息，提示用户待当前任务完成后再执行手动清理。
4. 不允许因为手动请求而静默扩大已运行自动任务的清理权限。
5. 不能同时启动两条写同一 catalog/LanceDB 的清理执行链。
6. `PARTIAL` 但仍有未完成项目的旧 run，也必须纳入互斥和恢复判断，不能被新的 run 绕过。

优先复用现有唯一索引和持久状态；确实不足时做最小加性迁移。

## 8. 性能限制

### 必须遵守

- UI 列表继续按原有 50 张分页。
- 清理每批最多 20 张，但整个 run 不限一批。
- 候选通过 `asset_id` Keyset 单调推进，避免反复从第一页开始。
- 不做每批全库计数。
- 不做全库 Python 对象物化。
- 不做全量 LanceDB 向量读取。
- 不为清理单张照片重建索引。
- 不长期占用 SQLite 写锁。
- 复用现有来源与失效证据索引。

### 性能验证

检查候选 SQL 的 `EXPLAIN QUERY PLAN`，确认分页查询可从游标位置继续，不随批数增加而反复扫描已处理前缀。

对人工保护密集的图库，允许必要的权威引用检查，但应先以简单有界方案实现；只有出现明确 N+1 瓶颈时才进行批量化优化，不提前开发新的引用缓存层。

不跑 30 万照片压力认证。
