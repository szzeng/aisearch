# P4-02B — 1 万→10 万→30 万正式容量验证（35～40 万可选压力观察）

本卡是 **P4-02 的主体**：在**真实产品代码路径**上完成 1 万 / 10 万 / 30 万三档正式容量验证，
并按主架构 §12.2 的口径分别报告发现、目录可查、语义索引、人脸、OCR 各阶段耗时与资源峰值。
30 万是唯一的正式 PASS 门槛；35～40 万只在成本允许时作为**非承诺**压力观察。

推荐执行模型：**DS-L / DeepSeek V4.1 Flash / 低推理**（按 V3.1 §9 的 P4-02 行：DS-L 执行 +
独立 DS-H 全量工程主审）；命中 §2.2 六类条件才建议升 **DS-MAX**，无法解释的 Windows/系统级异常建议转 **C1**。
**Sol 非必选**：本卡默认 `SOL_NOT_REQUIRED`；只有主审把某条发现升级为协议/ADR 裁决时才改记
「Sol high 聚焦终审必选」并把状态停在 `ENGINEERING REVIEW PASS / SOL FOCUSED REVIEW PENDING`。
模型切换由用户在 Codex 中手动完成。

## 起始状态与依赖

- 观察基线：**P4-02A 收口提交**（执行第一步先跑 `git log -1 --oneline` 与 `git status --short` 记录真实基线；
  若用户已另行入库则以实际提交号为基线并在报告写明）。
- **硬依赖**：P4-02A PASS —— 语义 outbox 的生产维护入口已接线，且「检查/引擎写/确认同一写事务」
  在并发下的争用与 busy-timeout 边界已有实测。未接通前本卡只能用夹具模拟，**不得**据此标容量 PASS。
  - 入口已就绪（P4-02A 交付，待其主审/Sol 终审）：`python -m photo_search.indexing.cli drain
    --data-root <root> --json`，或同函数 `photo_search.indexing.maintenance.drain_semantic_outbox`。
    本卡的语义阶段必须走该生产入口，不要自建 replay 循环；入口的 `batches`/`lock_wait_ms`/
    `write_hold_ms`/`write_rejections`/`scalar_index` 字段可直接入表。
  - P4-02A 已有两条须带入本卡的实测发现：**F1** `--repair` 修复审计实测 13.7 ms/工件
    （224 工件 5 480.2 ms），故入口默认 `repair=False`，30 万档审计成本**未测**，若要纳入容量口径须
    先单独测量；**F2** 冻结领取协议下并发维护者**不分工**（第二个维护者领取在途集合后被串行化并跳过），
    正确但无吞吐提升，若要并行维护吞吐需在本卡另立裁决而不是假设。
- 已有事实（P4-01/P4-01B/P4-01C，不要重测）：
  - 30 万（300 000 行、块 5 000、无 ANN 向量索引）生产遍历 **18 080 ms / 60 块 / Recall@20 = Recall@50 = 1.000**；
    加 `asset_id` 标量索引后同量级 4.3 s；四档过滤 walk 1 878 / 3 295 / 399 / 887 ms；
    候选数 215 998 / 114 000 / 30 000 / 2 000；§12.4 第 32 条组合校验 6 397 + `sql_agrees=true`；
    维护逐行 31.25 ms/行、`process_next` 重放 28.39 ms/事件（合成夹具）；
  - 索引策略按 P4-01B 裁决 **B1 保持不引入 ANN**：本构建内 30 万档 ANN（IVF_PQ/IVF_FLAT/IVF_SQ）
    Recall@20 只有 0.08～0.15 量级，§12.3 的 **0.95 仍未验证**；`nprobes`/`ef_search` 未暴露；
  - A3（无过滤时一次全局查询，30 万约 0.37 s）**未授权、未实现**。
- **执行第一步必须检查环境并如实标注**（当前工作树全量套件有 48 条环境跳过）：
  - pinned 模型权重是否已安装（buffalo_l 人脸、PP-OCRv4、P0-03 模型）；
  - GTX 1660 6 GB 实机是否可用（当前机器为 RTX 4060 Laptop）。
  任一缺失 ⇒ 对应「真实模型吞吐 / 显存峰值 / 查询 P95 / 最低配置」条目记 **BLOCKED**，
  其余条目用可用编码器或确定性合成向量完成并**逐处标注「非真实模型」**；不得用合成数字宣称容量或性能 PASS。
- 严禁扫描真实照片库：三档容量一律使用**项目内临时目录里的合成夹具**（seeded、可复现、可重建）。

## 必须交付的测量事实

全部测量必须在**项目内临时 data root** 内真实落库、真实走产品代码路径（不是只调工具函数），
并显式记录数据形状、种子、机器规格、耗时与内存口径；冷启动/冷缓存单独报告。

1. **三档正式容量（1 万 / 10 万 / 30 万）**，按 §12.2「新增 1 万」的报告形式分别给出：
   发现（scan）、目录可查（catalog + FTS/投影）、语义（embedding + `IndexCoordinator` 维护 + `asset_id`
   标量索引 + `semantic_ready`）、人脸、OCR 各阶段的完成时间、有效图片/秒、CPU/内存峰值
   （真实模型时另记显存峰值）与长时稳定性；每档给出行数、库大小与 generation 状态。
2. **查询侧**：普通文字搜索的暖机 P50/P95、冷启动单列；后台建库同时前台搜索的 P95
   （§12.2 调度目标 ≤ 1.5 s，未达标要给出调整建议而不是放宽门槛）；第一屏可见 ≤ 2 s 若可测
   （浏览器侧属可选，测了才写）。
3. **检索质量与承诺对照**：精确路径 Recall@20/@50 = 1.000 的复核；ANN 若仍不采用，必须写明
   「§12.3 的 0.95 未验证」而不是「通过」；A3 未授权时同样写明。
4. **35～40 万可选压力观察**：仅在成本允许时做，报告拐点与资源增长；不影响 30 万 PASS。
5. **D 级注入与恢复**（沿用 P2-03/P4-01 的口径，逐条给前后计数）：
   1. 维护中途中断进程后重启：零逻辑重复、无静默丢行；
   2. 「Lance 已写、outbox 未确认」重放；
   3. 同 `asset_id` 内容变更后旧向量不得继续命中（含并发新 revision，P4-01C 第二轮语义）；
   4. 位置离线/资产删除后索引内不得残留可检索幽灵向量；
   5. 新增向量在维护未完成时仍可搜索（§12.4 第 9 条），并说明它是 exact/部分结果。
6. **未达标项的决策记录**：任何未达 §12.2/§12.3 目标的项，都要给出测量、原因与明确决策
   （接受、另开卡、或转 C1），不得自动放宽门槛。

## 报告与停止点

- 报告：`docs/reports/P4-02B-capacity-validation.md`，包含：机器规格与种子、三档数据形状、
  各阶段耗时/吞吐/资源峰值表、查询侧 P50/P95、D 级注入前后计数、§12.2/§12.3/§12.4 对照表、
  未达标项决策、真实 Git 状态、未验证项（含 BLOCKED 项）。
- 禁止把「跑得动」当「达标」：三档未全部跑完、未做故障注入、未记录 `semantic_ready`/generation
  一致性时不得标 PASS。
- **停止条件**：30 万出现瓶颈且修复需要新增依赖、改 schema/migration、改检索语义或扩大支持承诺 ⇒
  停止交回（最小反例 + 数据）；无法解释的 Windows/系统级性能异常 ⇒ 建议转 **C1**；
  命中 §2.2 六类条件 ⇒ 建议 **DS-MAX**（写明编号、证据、待回答问题）；
  发现既有语义（RRF/过滤正确性/游标/投影补查）被基准绕开 ⇒ 停止并给最小反例。
- 正常收尾：更新报告与状态，并生成下一卡（预期 **P4-03 — UpgradeRun/targets、预算、暂停恢复、
  profile 原子激活**）。
