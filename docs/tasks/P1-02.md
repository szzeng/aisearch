## 任务定位

P1-01 已经冻结并实现了数据身份、约束、迁移、WAL、租约与状态机，并用“每次重新 hash 全部文件”的最小
确定性扫描证明了这些不变量。P1-02 把那个最小闭环升级为**可用于真实图库的扫描器**：流式、有界内存、
带稳定等待、hash 前后双重 stat、只在完整成功扫描后做缺失判定，并让“移动/改名”尽量不产生误判删除。

本任务仍然**不实现** AI、缩略图、搜索、HTTP sources/assets API 或前端页面。

## 用户场景

用户把本机/外接盘的照片目录作为来源，第一次扫描几十万文件：

- 扫描过程中程序被杀或断电，重启后继续，不会因为“只扫到一半”就把其余照片判定为已删除；
- 正在写入/复制中的文件不会以半截内容被固化，等它稳定后再计入资产；
- 文件在扫描期间被改名或移动到同盘其他目录，不产生误判删除；
- 大目录扫描时内存占用有界（不把整个文件树一次性读进内存）；
- 权限失败、目录消失或单个坏文件不会让整批位置被判定缺失。

验收一律使用 `%TEMP%` 下的临时夹具，**不得**读取真实照片库。

## 必须交付

### 1. 流式、有界内存扫描（架构 §5.1、§5.4）

- 枚举与处理改为流式：文件清单不得一次性全量驻留内存；目录级深度优先遍历仍沿用 P1-01 的边界规则
  （不跟随目录联接/符号链接、保留展示路径、只用 `path_key` 做比较键）。
- 内存占用与目录规模解耦：允许保留每个文件一行观测的临时状态，但必须能在十几万级文件下稳定运行；
  交付时必须给出峰值内存/耗时测量方法或实测数字（可用 `tools/` 下新增只读诊断脚本）。
- 新增进程级取消/中断路径：收到中断时保持 P1-01 的语义——不写负向事实、job/`scan_run` 不进入 `SUCCEEDED`。

### 2. 稳定等待与 hash 前后校验（架构 §5.1、§5.2、§12.4 第 5 条）

- 文件 `size/mtime_ns` 在提交前必须经过至少两次间隔检查（可配置的稳定窗口，默认值写进报告）；
  未稳定的文件本次不产生资产绑定，重新排队而不是固化半截结果。
- hash 前、hash 后都要重新 stat；两者与提交时的观测不一致时，丢弃该 hash 结果并重新处理该文件。
- 该规则必须由测试锁死：模拟“文件在 hash 期间被写入/替换”时，位置不得绑定到旧内容，
  旧资产与人工信息不得被覆盖。

### 3. 缺失判定与移动/改名（架构 §5.2、§5.4、§12.4 第 1/5/7 条）

- 缺失判定必须仍然只在**完整成功扫描**的最终事务中产生，并与 `scan_runs=SUCCEEDED`、
  `finished_at`、`source_roots.last_successful_scan` 同一事务提交（P1-01 已建立该边界，不得放松）。
- 改名/同盘移动优先保证 `asset_id` 不变；若无法无歧义证明是同一次移动，允许“新建位置 + 旧位置缺失”，
  但**不得**把移动误判为“内容删除”，也不得因此删除资产。
- 最后一次完整成功扫描之后新增的文件不得被计入任何缺失结论。

### 4. 错误、恢复与可观测性（架构 §5.3、§6.3）

- 目录枚举错误、权限失败、来源消失按 P1-01 的分类保持：可重试的外部条件进入 `BLOCKED`（不产生 MISSING），
  确定性完整性失败（如 `PATH_KEY_COLLISION`）进入 `FAILED`。
- 扫描进度写入 `jobs.progress`（0.0～1.0，单调不减），心跳沿用 P1-01 的租约规则；
  恢复执行不需要目录级断点游标，但不得产生第二个并发 `scan_run` 或重复逻辑 job。
- 内部入口（`python -m photo_search catalog scan|status --json`）新增可观测字段时必须保持既有字段与退出码语义，
  错误仍为结构化 JSON + 非零退出码。

### 5. 明确不做

- 不做缩略图/预览/缓存分片（P1-03）、不做 HTTP API（P1-04）、不做前端（P1-05）、不做重复/断盘/重映射验收（P1-06）。
- 不提前创建人物、向量、FTS、outbox、索引世代表或 P2 调度协议。
- 不引入新依赖（预期仍只用标准库）；若确需新依赖，必须说明理由并更新 `uv.lock`。

## 正常行为 / 异常行为 / 边界情况（验收时逐条覆盖）

**正常行为**

- 大目录流式扫描完成：`assets` = 去重后内容数，`file_locations` = 实际文件数，同字节多位置共享资产。
- 稳定文件在第二次 stat 相同后绑定内容并标记 `PRESENT` / `last_seen_scan_id`。
- 改名与同盘移动后再次扫描：`asset_id` 不变，不出现误判删除；旧位置按规则处理。

**异常行为**

- hash 期间文件被修改：本次结果被丢弃并重新处理，不绑定旧内容。
- 扫描中途被杀：重启后继续同一个 `scan_run`，无重复 job、无半成品资产。
- 目录枚举/权限失败：`BLOCKED`，现有位置不批量转 `MISSING`，`last_successful_scan` 不前进。
- 路径键碰撞：`FAILED`，报告 `PATH_KEY_COLLISION`，不静默合并两个路径。

**边界情况**

- 正在写入的文件、0 字节文件、只读文件、损坏/非图片文件、中文/空格/长路径、目录联接、自指联接。
- 同一内容在两个来源（两个目录）→ 共享资产；移除其中一个位置后另一个仍可用。
- 空目录、只有子目录、扫描期间新增文件、扫描期间目录被重命名。

## 验收等级与命令

本任务涉及扫描、hash 与缺失判定，按 **D 级** 验收（B 级 + 对应故障注入/恢复测试；不涉及打包，故不加 C）。

```text
uv run pytest -q tests/unit tests/integration
uv run ruff check .
git diff --check
```

必须真实执行的故障注入/恢复场景：

1. 稳定等待：正在写入的文件本次不被固化，稳定后再次扫描可正确绑定。
2. hash 前后 stat 变化：结果被丢弃并重排，不绑定旧内容、不覆盖旧资产。
3. 扫描中途进程被杀：重启后继续同一 `scan_run`，无重复逻辑 job、无半成品资产。
4. 目录枚举/权限失败：`BLOCKED`，位置不批量转 `MISSING`，`last_successful_scan` 不前进。
5. 完整成功扫描的缺失对账 + `SUCCEEDED` + `last_successful_scan` 仍为同一最终事务。
6. 改名/同盘移动：`asset_id` 不变；无法证明移动时也不得把内容判成删除。
7. 大目录流式：给出峰值内存/耗时实测或可复现测量命令，证明内存与文件数解耦。
8. 路径键碰撞仍使扫描不能进入 `SUCCEEDED`。

成功时只保留 quiet 摘要、退出码与必要计时；失败时先读失败测试名与 traceback 尾部，只重跑失败目标。
任一必需场景未真实完成，不得标记 PASS（可用 `IMPLEMENTED / VALIDATION PENDING`、`BLOCKED`、`FAIL`）。
