# P4-01C — 按裁决实现瓶颈修复：块大小/标量索引、批量维护、修复审计、过滤计数

本卡是 [P4-01B](P4-01B.md) 设计阶段的实现卡；设计证据与四个待裁决项见 P4-01B 报告 §6
（[docs/reports/P4-01B-bottleneck-decision.md](../reports/P4-01B-bottleneck-decision.md)）。

**第一步先确认裁决**：读用户在本卡上的裁决；若用户没有给出不同选择，则**按 P4-01B 报告 §6 的推荐**执行：

- 决策 1：**A1 + A2**（`SCOPE_BLOCK_SIZE` 1 000 → 5 000；`asset_id` 标量索引 + 缺失时确定性回退）。
  **A3（无过滤时一次全局查询）默认不做**，除非用户明确授权。
- 决策 2：**B1**（不引入 ANN，保持精确路径与召回 1.0）；B2/B3/B4 不在本卡。
- 决策 3：**C1 + C2**（批量 `merge_insert` 200 行/批 + `has()` 定点查询）。
- 决策 4：**D2 优先**（在不改语义的前提下修计数计划）；D1/D3 属协议面，未获裁决不得实现。

推荐执行模型：**DS-H / DeepSeek V4.1 Flash / 高推理**。完成后另开独立 DS-H 会话做全量工程主审；
**因为本卡会改 `IndexCoordinator` 的写路径（幂等/确认边界），Sol high 聚焦终审按 §11 记必选**，
状态先停在 `ENGINEERING REVIEW PASS / SOL FOCUSED REVIEW PENDING`。

## 起始状态与依赖

- 基线：P4-01B 收口提交（执行第一步先跑 `git log -1 --oneline` 与 `git status --short` 记录真实基线）。
- 依赖事实（P4-01 / P4-01B 实测，不要重测）：30 万无索引单次搜索 92～112 s；块 5 000 = 19.8 s、

  500 行批写 0.115 ms/行；`COUNT(*)` 在 half/thin 档 >20 s 而同样条件的分页只 0.2 ms。

## 本卡禁止修改

`SearchFiltersEchoV2`（11 + 2）与 `search_projection` 键集；`POST /api/v1/search` 的信封、`query_hash`、
游标/摘要语义与全部错误码；RRF/BM25/距离公式；`taken_time`/`capture_desc` 既有含义；
P1～P3 人物/地点信封与人工状态；`PhotoSearch.spec`、`tools/packaging/**`、`packaged_api_smoke.py`。
不得引入 Redis/Celery、分布式调度、多 GPU、第二向量后端或手工分片。

## 必须保持的不变量

1. 检索结果不变：同一查询在修复前后的 top-k（`asset_id` 序列）必须逐条相同（A1 的块合并本身是精确的，
   A2 只改访问路径）。给出修复前后对照的机器可读证据。
2. `index_outbox`/`index_entries` 的逐事件幂等与确认顺序不变：批量写入**不得**产生部分确认；
   同一批重放必须无逻辑重复（沿用 P2-03 的注入方式）。
3. `semantic_ready`、`index_generations` 状态机不变；批处理失败时整批可重放。
4. 标量索引缺失或不可用时必须有确定性回退（正确但慢），不得静默返回不完整结果。
5. `authoritative_page` 若改计数，必须在报告中说明语义变化并等 Sol 裁决；**本卡默认不改**。
