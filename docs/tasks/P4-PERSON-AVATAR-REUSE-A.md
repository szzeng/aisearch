# P4-PERSON-AVATAR-REUSE-A — 人物头像重复加载优化

日期：2026-10-10。状态：**READY / 仅立卡，尚未实施或测试**。
推荐执行：**GPT-6 Luna / High**，同一会话实现、修复和小范围验收；个人项目，不要求全仓回归。
范围：人物相册前端加载与显示复用。**先做 A+B，C 仅在不扩大改动时补充。**

## 1. 目标与边界

解决人物列表、人物相册返回及「整理一下」页面反复显示“正在加载图片…”的问题。目标是**无数据变化不重复加载，必要刷新时保留未变化的头像 DOM**，同时维持人物排序、人工整理、撤销、合集、分页和正确的头像更新。

本卡不承诺首次冷缓存提速，不修改人脸模型、识别策略、SQLite schema、搜索/向量、GC、原图补识别或媒体后端。**不得删除已有缓存，也不得为提速修改 HTTP 缓存协议**。

## 2. 当前仓库依据（实施前以最新 HEAD 复核）

- `src/photo_search/web/persons-albums.js::backToLibrary`：返回人物列表时无条件执行 `refreshPeopleViews`；该函数会调用 `loadPeople(false)`、`loadCollections(false)`，整理模式还会刷新待整理分组。
- `setView`：重复点击已经选中的「人物」或「整理一下」，仍会重置条件并重新请求。
- `loadPeople`：`readLoadedPages` 顺序回放先前已加载的页数，随后使用 `replaceChildren` 重建全部人物卡片和 `<img>`。当前图片前四张 eager，其余 lazy，原有图片元素本可保留。
- `loadInbox`：重新创建待整理分组及人脸头像，展开分组可能重复读取旧页；不能只优化普通人物列表。
- `api` 的 JSON fetch 使用 `cache: "no-store"`；它与图片缓存不同。图片接口 `/faces/{face_id}/thumbnail` 通过 ETag、304 和磁盘 `face-crops` 复用，响应采用 `private, no-cache, must-revalidate`，防止重建 catalog 后旧 ID 错图。
- 现有 `aisearch.persons.changed`、`listSeq/inboxSeq`、`peopleBinding/inboxBinding`、已加载页数与滚动锚点是可复用的状态边界。参照 `tests/unit/test_person_loaded_pages_ui.py` 的回放及旧请求保护用例。

## 3. 实施顺序

### A. 无变化返回和重复点击不刷新（必做）

1. 进入人物相册只隐藏父列表，不丢弃已显示的卡片、头像、分页和滚动锚点；从相册返回时，如**列表已成功加载、当前视图/筛选未变、没有已知写入或跨标签变更、没有待处理的刷新、且仍在新鲜窗口内**，直接恢复 DOM，不执行 `refreshPeopleViews`。
2. 再次点击当前模式按钮不重复调用 `setView` 的清空/加载分支；不得意外清除查询、筛选、已加载页、滚动位置或批量选择。
3. 最简过期策略：记录列表成功加载时间，默认 60 秒内可直接复用；过期后在返回或获得焦点等自然入口复核，无需新增定时轮询。跨标签 `storage`、本页 `notifyPeopleChanged`、成功写入/撤销、人工确认后的延迟刷新、明确点击“刷新”，均优先于时间窗口，必须重新读取。失败不能记为已刷新。
4. 当列表尚未加载、直达人物链接后需返回初始列表、请求进行中或筛选条件已变时，走正确的请求路径；不能因为“缓存存在”跳过必要加载。
5. 保留现有防竞态序号；同时抵达的返回、焦点和刷新事件尽量合并同一条件的重复请求，但新的显式刷新/条件变化必须能覆盖旧结果。

### B. 刷新时按人物复用头像 DOM（必做）

1. 对相同查询条件内的已有列表，以 `person_id` 查找旧卡片；新数据中的 `thumbnail_url` 及需要校验的有效头像身份未变时，**保留原 `<img>` 元素及已完成的加载状态**。
2. 姓名、照片数、合集标签、勾选状态变化时更新相关文字和属性；排序改变时移动旧卡片；新增建卡，移除无效卡片。禁止重复 ID / 重复卡片。
3. **点击事件必须读取最新人物对象**，不得沿用初次创建时的旧闭包，导致打开过期人物、旧 revision 或旧相册。
4. 头像 URL 或可信版本信息变化时必须更新头像。显式刷新、过期复核或库重建后不得永久锁住旧像素：保留现有 ETag/304 与 URL 版本保护，必要时让浏览器按现有协议重新验证；不可只用 URL 相同就把缓存视为永远有效。
5. 多页数据应完整获取成功后再提交新的卡片集合和游标；某一页请求失败时保留原完整列表。只接受当前 `listSeq` 的响应，避免过时异步结果覆盖新的筛选/滚动。
6. 首屏 eager、其余 lazy 的优先级继续正确；不新增 Base64/Blob、全局图片缓存池或 IndexedDB。

### C. 「人物 / 整理一下」轻量复用（可选、不得扩范围）

- 优先复用 A 中本来就未销毁的页面 DOM 与状态；如能小改动安全实现，只保留最近访问的普通人物和默认整理视图各一份会话内状态。查询条件、可见范围、质量筛选、合集筛选和人物变更必须参与有效性判断。
- 对待整理分组保存已展开状态和已加载的脸，**只有无变更时**直接恢复；成功确认/移出/撤销等发生后使用原有 `loadInbox` 安全刷新，继续遵守旧游标失效、组内分页和人工操作保护。
- 不为了双视图缓存引入新的通用状态管理器、庞大 DOM diff 框架或全量缓存。若 C 涉及大量重构，停止扩展，提交 A+B 并在报告中说明 C 未做。
- 不把“一键原图补识别”入口调整混入本卡。

## 4. 不可退化行为

- 人物有效照片数降序、人物/未命名/已忽略分类及总数准确。
- 一次加载多页后仍能返回原范围、维持滚动位置并继续“加载更多”；真实刷新必须拿新 revision 游标，不续用旧游标。
- 命名、合并、封面更换、人物归属/忽略、加入/移出合集、撤销后可看到权威最新数据；“只看未加入任何合集”筛选不串页。
- 待整理人脸确认、展开、分组、批量勾选不回退；写操作失败不能错误失效或清空页面。
- 焦点/跨标签变化、快速切换筛选、迟到请求不得覆盖最新页面；有真实变更时不能被 60 秒缓存挡住。
- 重建数据库后不能恢复曾经一年 immutable 缓存的错图行为；不改媒体路径的访问控制和裁剪语义。

## 5. 个人项目最小验收

自动测试仅跑直接相关 Node/pytest 桩，不访问真实 `PhotoSearchData`：

1. **无变化返回**：列表→人物相册→返回两次；第二次不额外请求 `/persons/browse`，已有头像 `img` 对象保持相同；重复点击当前模式也不重载。
2. **头像与资料更新**：权威结果不变时即使显式刷新也尽量复用图片 DOM；照片数、名称、合集、排序变动后内容更新，点击卡片使用新 revision；头像确实改变时更新图片。
3. **分页与过期**：已有 2～3 页、滚动锚点和展开分组能恢复；60 秒过期、明确刷新或外部变更后确实重新请求；刷新第二页失败仍保留旧完整列表。
