# P4-STORAGE-UI-A — 个人相册存储与维护 UI（仅手动备份）

日期：2026-10-11。状态：**IMPLEMENTED / 定向验收完成；自动维护执行保持关闭，待独立窄审**。
立卡仓库基线：szzeng/aisearch master eee605f（实施前核对新 HEAD）。推荐 GPT-6 High。
原则：**个人相册、复用已完成的 GC-A/GC-B、轻量 UI、简单定向测试、用户手动备份且绝不自动删除备份**。

## 1. 目标和最重要的定案

把现有文件 GC、向量维护、SQLite VACUUM 变成相册内可理解的「检查—选择—确认—下次停机启动时维护」流程；不再要求日常输入 PowerShell。

**备份只允许手动触发：**
- 在 UI 中提供「备份人工整理数据」按钮，用户点击后才创建备份。
- **不**在 GC 前、应用启动时、退出时、固定周期内自动备份。
- **不**设置自动保留两份/轮换、自动清理旧备份、自动覆盖已有备份。
- 用户可以自行设置备份文件夹；每个快照保留到用户在文件管理器主动删除。
- **是否做过手动备份不构成 GC 执行门禁**；维护确认时仅提示「建议先手动备份」，不能悄悄自动备份，也不能因为未备份就伪称安全。
- 备份旨在保留 SQLite 内人工整理成果，不是完整 data root/原图/模型/向量的灾难恢复包。

## 2. 仓库已有可复用实现

- src/photo_search/storage_maintenance.py：storage_optimize_vectors、storage_vacuum；活跃 generation、index coverage、碎片、14 天版本保护、空间和 SQLite 完整性检查。
- src/photo_search/runtime/data_root_lease.py：受管服务的独占数据根租约。
- src/photo_search/api/routes.py、api/security.py：现有 Session、Origin、CSRF 保护。
- src/photo_search/web/index.html、app.js：现有「存储空间」折叠区和快速概览。
- src/photo_search/__main__.py、tools/dev/start_personal_trial.ps1：服务/个人试用启动入口。

保持现有 GC-A、GC-B 算法、保护期、修复/删除资格不变；不新建另一套清理器，不修改 schema、搜索与机器识别模型。

## 3. UI（保留现有管理折叠区）

将「我的图库 → 图库管理与分析明细 → 存储空间」更名「存储与维护」，设三个简单区：

1. **空间与健康**：数据库大小、最近深度扫描时的向量/Artifact/预览/缓存占用和时间；用户手动「检查空间」才触发有界深扫，页面打开只快速读取。深扫不得阻塞 HTTP 事件循环，busy/partial 如实显示。
2. **可选维护**：分项展示 Artifact 过期孤儿、旧媒体缓存、向量碎片/索引覆盖、SQLite VACUUM；可重建的预览缓存、人脸裁剪缓存使用独立确认入口，不勾选为默认垃圾。每项显示「正常/可优化/无法维护」及明确原因，不承诺性能提升。
3. **手动备份**：备份目录输入框、保存并检查、按钮「备份人工整理数据」、最近一次手动备份时间/文件及成功失败状态。普通网页无法可靠取得任意本地绝对路径，首版用路径输入框即可，不引入桌面文件选择器。

只读 UI 与写入操作严格分开；不得在页面自动执行维护或备份。

## 4. 备份位置与范围（只有用户点击才备份）

默认目录：PhotoSearchData 的同级 PhotoSearchBackups；例如 D:/SZ/project/PhotoSearchBackups；允许修改为 E:/PhotoSearchBackups 等 Windows 本机绝对目录，一次保存后以后沿用。

- 只生成**整个 SQLite catalog 的一致性快照**，保留人工人物命名、手工脸归属/锁/排除、人物合并拆分、隐藏标记、人物合集/成员、地点人工归属/定义/排除、操作历史及所需的 asset/person/face 身份联系；不枚举几十张表做脆弱导出。
- 使用 SQLite backup API 或等价一致性快照，不能直接复制在线 catalog.db 而漏掉 WAL。使用独立数据库连接/后台执行，避免阻塞 API；写到独立临时文件，验证可打开和 integrity_check=ok 后原子发布。
- 目录必须是合法绝对路径、可写且有空间；拒绝落在 PhotoSearchData 内或已登记原图来源内、拒绝符号链接/junction/越界和异常文件。必须做服务端校验，UI 传参不能变成任意文件写入接口。
- 文件使用时间戳+唯一 ID 防重名；不覆盖已有文件。**不提供自动清除备份功能**，更改路径不搬迁、不删除旧文件。
- 备份按钮仅创建快照，不执行 GC。备份失败显示错误，不影响原数据。
- UI 明示：SQLite 快照不包含原图、LanceDB/人脸外部产物或模型；不能直接覆盖任意重建后的图库并保证人工归属可还原。完整恢复/跨库映射不在本卡。

## 5. 一次性离线维护（不自动备份）

1. UI 读取现有 GC 预览，用户明确选择一项并确认影响。白名单仅 clean:artifacts、clean:media-cache、clean:previews、clean:face-crops、optimize-vectors、vacuum。
2. 仅保存**一个待执行维护请求**，支持取消；无确认不落盘；请求有短有效期、操作类型固定，不接受脚本、任意路径或自定义 data-root。
3. 用户正常关闭相册。下一次通过正常受支持的服务启动入口，**在 HTTP 服务取得 data-root lease、会话生成和模型/GPU 初始化之前**检查请求。
4. 重新核对请求和数据身份，执行现有停机互斥、WAL、引用、路径、索引与空间检查；条件不满足就跳过。不能根据上次 UI 预览直接删除。
5. **不自动调用备份**，也不以是否存在旧备份替代健康检查；只显示人工备份提醒。
6. 通过安全协调入口调用已有 GC-A/GC-B 维护逻辑，保存真实结果，再正常启动 UI；失败或中断不得自动重复危险操作，需用户重新确认。

注意：当前 GC 函数自己取得 data-root lease。新协调器**不能先持有同一非可重入 OS 锁，再调用重复加锁的公开函数**；应设计最少的可信停机入口复用现有锁保护并做定向验证，禁止通过去掉锁解决。

执行许可与一次性请求状态不能从旧 data-root 备份中意外复活；尤其现有 backup.py 会包含 runtime 目录。必要时将执行授权放到不进入现有备份成员的受控位置，或明确排除，旧授权不可重放。

## 6. 数据安全与结果口径

- 绝不删除、移动或修改来源照片；不删人工人物/合集/地点/人脸锁或业务操作历史。
- Artifact 仅删确实无引用、且通过身份二次核对的受控候选；来源临时离线不等于可删除。
- LanceDB 仅按原 GC-B 维护**活跃且健康**的图像 generation；不删逻辑向量或整个旧 generation；旧物理版本保留至少 14 天。
- SQLite VACUUM 仅在现有门限建议有价值、停机与 integrity_check 通过时执行；建议 skip 时 UI 明确显示无需整理。
- 报告实际删除/释放 bytes、前后碎片、索引覆盖与状态。预计值≠实际值，清理 0 bytes 不自动算失败。partial/failed/skipped 均要准确呈现。
- **未做手动备份的维护风险由 UI 如实提示**，不暗示自动存在可恢复快照；不实现自动回滚、自动全库重建。

## 7. 最小验收（合成 data root，四组）

- **A. UI/预览**：显示正确，打开页不深扫；主动检查使用有界后台扫描；正常/可维护/跳过提示正确。
- **B. 手动备份**：自定义路径保存和可写性检查；**仅点击按钮才产生 catalog 快照**；含人工人物、合集、地点及依赖身份；SQLite integrity_check 成功；连续手动备份不会自动删除旧快照；不存在定时/GC 前自动备份调用。
- **C. 停机确认/防重复**：未授权/非法请求/CSRF 失败/服务持锁/数据身份改变/重复启动都不得执行；正常请求一次执行、失败或中断不自动重试；不出现重复加锁死锁。
- **D. GC 调用一致性**：复用 GC-A/GC-B 的合成验证，人工事实和当前搜索结果不变、无源照片写入、结果状态真实；**未手动备份时不会隐式创建备份**。

只跑相关 pytest、少量 UI DOM/JS、Ruff、Python/Node 编译或语法、diff-check；不触碰真实 PhotoSearchData、不跑全量测试/GPU/30 万图库。

## 8. 实施顺序和交付

先完成 UI 只读诊断与手动 catalog 备份，再接入一次性停机维护。自动执行路径在独立窄审通过前不得开放；审查只聚焦权限、锁、一次性消费、路径边界、未授权误删和人工事实保护，不扩展成全仓回归。

交付 UI、少量受保护 API、路径设置与手动快照、单次维护入口、简短测试报告及 development-status 更新。

**验收关键：用户手动点击才备份；所有手动备份由用户管理，软件不自动轮换/清理；垃圾清理仍由用户明确确认并遵守已有 GC 安全规则。**
