## 1. 目标

给个人试用版增加真正适合日常使用的 **“刷新图库”**：

> 已有约 30 万资产时，日常只增加/删除/移动/替换几百张，刷新不得重新读取并 SHA-256 全部 30 万原图，也不得让 semantic / thumbnail / face / OCR / GPS 等模块再次各自扫完整个 30 万资产集。

本卡实现：

1. **日常快速刷新**：完整枚举来源目录，但仅对“需要重新确认内容”的位置计算完整 SHA-256；
2. **增量派生**：扫描阶段产生内部 delta，后续处理器只处理 delta，而不是重新遍历整个图库；
3. **批量 unchanged observation**：稳定未变化文件不再一文件一提交，降低 30 万 no-op 的 SQLite 提交成本；
4. **先可搜索、后补增强**：semantic/search projection 完成即进入 SEARCH_READY，不等待 face/OCR 等重处理；
5. **完整校验能力保留**：既有 full scan 语义不删除，仍可手动执行全量 SHA-256 校验。

本卡到此封口；**不实现实时 watcher / USN Journal**。

## 2. 关键设计：快速刷新 ≠ 用 size/mtime 建立身份

ADR-0002 的核心不变量不变：

- 完整 SHA-256 仍是唯一内容身份；
- 新内容绝不能只凭 size/mtime 建立或命中永久 asset；
- 原图只读；
- 只有完整成功扫描才能产生 MISSING；
- 来源离线不得被解释为“文件都删除了”。

快速刷新只允许复用**此前已经由完整 SHA-256 确认过的既有绑定**。

一个位置只有同时满足以下条件，才允许本轮跳过重新 hash：

- 该 path_key 已存在；
- 上次状态为 PRESENT；
- asset_id 非空，说明内容身份曾完整确认；
- 当前 size 与记录值相同；
- 当前 mtime_ns 与记录值相同。

以下情况必须重新执行完整 SHA-256：

- 新路径；
- size 变化；
- mtime_ns 变化；
- asset_id 为空；
- MISSING → PRESENT 恢复；
- 任何无法证明满足快速复用条件的情况。

因此：

> size/mtime 只作为“是否需要重新验证既有绑定”的 freshness hint，绝不能成为内容身份。

已知限制必须在报告中明确：

> 若同一路径文件内容被外部工具替换，同时故意保持完全相同的 size + mtime_ns，日常快速刷新可能无法发现；需要“完整校验扫描”重新 hash 全库来覆盖这个极端情况。

既有 full scan 路径必须继续保留，行为不退化。

## 3. 扫描实现：最小改动优先

优先复用当前 scanner 两阶段结构，不另写第二套扫描器。

当前实现已经有：

- enumerate 时的 observe_location_detailed；
- changed 时清空 asset_id；
- unchanged 时保留 asset_id；
- count_unbound_locations；
- 完整 SHA-256 + hash 前后 stat；
- reconcile_missing。

### 快速模式的核心修改

当前 content pass 会处理本次 scan 看见的**全部位置**。

快速模式应改为：

> content pass 只遍历“本次已看见且 asset_id IS NULL”的位置。

即：

- unchanged + 已确认绑定 → 不进入 hash pass；
- new / changed / recovered / pending → 进入现有完整 hash + stat 守卫；
- 最终仍要求 count_unbound_locations == 0 才允许 SUCCEEDED。

建议新增等价的 bounded iterator，例如：

iter_unbound_seen_locations(...)

不要改变现有 full scan 默认语义；可让 refresh orchestrator 显式使用 fast/delta confirmation mode。

现有 POST /sources/{id}/scan 若没有明确变更需求，保持现在的完整扫描语义，作为“完整校验扫描”。

## 4. Delta 必须从扫描阶段一路传到派生阶段

**不能只优化 SHA-256，然后让每个处理器再扫 30 万资产。**

刷新内部至少区分两类 delta：

### A. content_delta

内容身份需要新确认、并最终绑定成功的资产。

用于：

- semantic embedding
- thumbnail
- face
- OCR
- GPS/EXIF 内容提取
- 其他纯内容派生

### B. location_delta

位置/可用性/文件观察发生变化的资产，例如：

- 新位置；
- rename/move；
- delete → MISSING；
- MISSING → PRESENT；
- size/mtime 变化；
- 同内容新增副本位置。

用于：

- taken-time（其 input revision 包含 location observations）；
- search document / filename / availability projection；
- 其他依赖位置事实的派生。

### Delta 传递要求

- 这是 refresh 内部实现细节；
- 公共 API 只返回数量/状态，不泄漏完整 asset_id 列表；
- 小增量可以用内存集合；
- 必须有有界上限；
- 若 delta 超过上限，允许退回现有全量 selector，但不得 OOM，也不得改变正确性。

**no-op 快速刷新时 content_delta=0、location_delta=0。**

### Web

“来源与扫描”页增加：

**刷新图库**

作用：快速刷新全部已登记来源。

每个来源卡可增加：

便于用户明确知道只有某个目录发生变化时，不必扫描其他来源。

保留既有“扫描”入口作为完整校验能力；若文案需要区分，可显示为：

**完整扫描 / 校验**

但不得删除既有 API 行为。

### API

增加一个本机维护入口，例如：

POST /api/v1/library/refresh

可选接受 source_ids；不传即刷新全部来源。

返回 **202**，不得让 HTTP 请求一直阻塞到 AI 全部结束。

再提供只读状态入口，例如：

GET /api/v1/library/refresh

具体路径可按现有 routes 风格调整。

要求：

- 同一进程最多一个 active refresh；
- 重复点击不得启动第二套并发刷新；
- 重复请求可返回当前 refresh 状态；
- 不为了 UI 进度新增持久 schema；
- 进程被杀后 UI 进度可丢，但再次 refresh 必须依赖底层幂等性安全继续；
- 状态至少能表达：SCANNING / INDEXING / SEARCH_READY / ENRICHING / COMPLETE / PARTIAL_FAILED（命名可按现有风格调整）；
- **SEARCH_READY 与 COMPLETE 必须区分**：前者表示本轮新增/变化内容已进入当前搜索路径，后者才表示可用的增强阶段也已处理完。

## 6. 快速刷新流程

顺序：

### A. 快速扫描来源

按 source_id 稳定顺序串行。

每个来源：

- 完整枚举路径；
- 对 unchanged confirmed PRESENT 位置复用既有 asset binding；
- 仅 hash 新/变/恢复/未绑定位置；
- 完整成功后才 reconcile MISSING；
- SOURCE_OFFLINE / ACCESS_DENIED 只记录该来源失败/阻塞，继续其他来源。

记录：

- enumerated
- unchanged_reused
- hash_targets
- hash_bytes
- new_assets
- rebound_assets
- locations_added
- locations_missing
- content_delta_count
- location_delta_count
- scan wall time

### B. search projection / catalog 派生

先让已有 catalog/search document catch-up 处理 location_delta/content_delta，保证：

- 新文件名可搜；
- rename/move 后第一次重搜就看到新名字；
- MISSING/PRESENT 状态及时反映；
- 不改变 P4-02V 的 LAGGING/争用语义。

### C. semantic — SEARCH_READY 前置阶段

只对 content_delta 优先补齐。

必须复用当前真实：

- model / manifest
- processor_id
- space_id
- generation
- outbox / confirmation
- search profile

如果 content_delta 超过内部上限，可退回现有 semantic_selection，但必须循环 build_index 的 5000 有界批次直到 coverage complete / targets=0，不能只做第一批。

旧 CONFIRMED + 当前 input_revision 不得重算。

当且仅当本轮 location/search projection 已追上，且 content_delta 对当前活动 semantic generation 已完成确认后：

> refresh 状态进入 **SEARCH_READY**

此时用户必须已经能通过正常搜索找到本轮新增照片。**不得等待 thumbnail / taken-time / GPS / face / OCR 全部完成才宣告“可搜索”。**

SEARCH_READY 之后 refresh 可以继续处于 **ENRICHING**。

### D. thumbnail — SEARCH_READY 后增强

只给 content_delta 资产调用当前 thumbnail 生成入口。

- 已发布当前 version artifact 直接复用；
- 不全库生成 preview；
- deterministic failure 不无限重试。

缩略图可以在 SEARCH_READY 前后穿插，但**不得成为 semantic 可搜索的硬前置**。

### E. taken-time — 增强阶段

优先只处理 location_delta ∪ content_delta。

不得 force 已完成同 revision job。

### F. GPS / place — 增强阶段

对 content_delta 的新内容执行现有 GPS extraction。

若 resolver 数据集可用，则增量跑已有 place resolver；不可用则明确记 SKIPPED_UNAVAILABLE，不阻断 SEARCH_READY。

### G. face / OCR — 增强阶段

只处理 content_delta。

- 不 force；
- 已存在同 logical job 不重复推理；
- 权重/设备不可用时该阶段明确 SKIPPED_UNAVAILABLE；
- 不因此回滚 catalog / semantic；
- **不得阻塞 SEARCH_READY**。

所有当前可用增强阶段完成后进入 COMPLETE；某增强处理器不可用/失败但核心搜索已可用时进入 PARTIAL_FAILED 或等价状态，并保留 SEARCH_READY=true 的事实。

## 7. No-op 刷新是核心性能验收

完整成功一次后，不修改任何原图，立即再次“刷新图库”。

必须满足：

- enumerated ≈ 全部当前文件数；
- unchanged_reused ≈ 全部 PRESENT 已确认位置；
- hash_targets = **0**；
- hash_bytes = **0**；
- content_delta = **0**；
- location_delta = **0**；
- semantic encoded = **0**；
- thumbnail generated = **0**；
- taken-time 新 logical jobs = **0**；
- GPS / face / OCR 新 logical jobs = **0**；
- generation/profile 不发生无意义切换；
- 搜索结果保持一致。

这比单纯“AI 没重算”更重要：必须证明**30 万原图没有被重新完整读取做 SHA-256**。

## 8. 小增量验收

在稳定库上制造：

- +100 真新照片；
- +10 已存在内容的重复副本；
- rename/move 10；
- delete 10；
- 同路径替换 10。

快速刷新后必须证明：

### 新照片
- 只 hash 新文件；
- 新 asset 按 SHA 正确建立；
- 只对新内容做 semantic/thumbnail/face/OCR/GPS 等派生。

### 重复内容
- 新 location；
- assets 不增加；
- 允许为识别重复而 hash 新路径；
- 已存在 asset 的 semantic/face/OCR 不重做。

### rename/move
- 新位置 hash 后复用同一 asset；
- 旧位置最终 MISSING；
- embedding 不重做。

### delete
- 完整成功扫描后才 MISSING；
- 不删除 asset / embedding / 人工事实。

### 同路径替换
只要 size 或 mtime 变化：

- 必须清空旧绑定并完整 hash；
- 新内容绑定到正确 asset；
- 不继承旧内容的派生结果。

另加一个明确限制测试/文档：

- 人工构造“内容变化但 size+mtime 完全伪装不变”时，fast refresh 允许不发现；
- full scan 必须能发现并纠正。

## 9. 完整校验扫描必须保留

既有 full scan 不删除、不弱化：

- 对全部 seen 位置重新完整 SHA-256；
- hash 前后 stat 守卫保持；
- 极端 same-size/same-mtime 内容替换可被发现；
- 中断/恢复/MISSING/离线语义保持现状。

快速刷新是**新增的日常模式**，不是取代完整校验。

Web 不需要自动定时 full scan；个人用户需要时手动执行即可。

## 10. Unchanged observation 批量提交

这一步属于本卡，不再留作后续性能研究。

原因：当前 scanner 在 enumeration 阶段基本是一文件一个短写事务；P1-02 实测 20k 文件 enumeration = 14.851 s。跳过全量 SHA-256 后，这会成为 30 万 no-op 的主要固定成本之一。

### 实现原则

仅对“本批内已 stat 完成”的 observation 做数据库批量处理；**文件枚举/stat/hash 仍不得放进 SQLite 写事务**。

增加等价的 batch observation 路径，优先复用 observe_location_detailed 的全部判断：

- path_key collision 语义不变；
- changed size/mtime 仍立即清空 asset_id；
- unchanged confirmed binding 仍保留；
- last_seen_scan_id 正确推进；
- MISSING→PRESENT 正确；
- 返回本批 created / changed / unchanged / unbound 信息供 delta 汇总；
- lease/submission qualification 必须在每个批事务内保持；
- progress 单调；
- 最终 reconcile_missing 原子边界不变。

### batch 选择

只比较：

- 128
- 256

使用 30 万 no-op 夹具交错/重复少量测量，记录：

- enumeration wall；
- transaction count；
- 最大单事务 wall；
- refresh 期间搜索合法请求拒绝；
- 最终 catalog 逐项等价。

固定一个更合适的默认值后停止。

**禁止继续扫 64/512/1000/5000 等参数网格。**

如果 128 与 256 差异很小，默认选 **128**，优先降低单事务写锁时间。

### 安全门槛

任何 batch 实现只要造成：

- PATH_KEY_COLLISION 漏报；
- changed 文件保留旧 asset_id；
- MISSING 对账错误；
- lease/中断恢复退化；
- 刷新期间新增合法搜索拒绝；

则撤回 batch 优化，保留逐文件 observation；不得为了速度放宽正确性。

## 11. 性能目标

本卡不追求秒级 watcher 体验，但要达到“个人日常可用”。

### 必测 A：30 万 no-op fast refresh

记录：

- total wall
- enumeration wall
- hash wall
- unchanged_reused
- hash_targets / hash_bytes
- delta counts
- 各派生阶段实际 targets / new jobs
- 刷新期间合法搜索拒绝数

硬正确性门槛：

- hash_targets=0
- hash_bytes=0
- 所有 AI 新工作=0
- 搜索合法请求拒绝=0

时间作为产品体验指标记录。

目标方向：

> 本机本地 SSD/NVMe 下应进入“几分钟级”，而不是重新读完整图库导致几十分钟/小时级。

若仍 >10 分钟，先归因 enumeration / SQLite commit / filesystem metadata，再决定是否执行 §10 batching；不得直接引入 watcher。

### 必测 B：30 万 + 几百张变化

建议：

- +300 真新照片；
- delete 50；
- rename/move 50。

要求：

- 全库不重新 hash；
- hashed files 应接近新/变化路径数量，而不是 300k；
- AI targets 应接近真正新增内容数量，而不是 300k；
- 记录 **start → SEARCH_READY** 的 wall time；
- 达到 SEARCH_READY 时，新照片已经可以通过真实 HTTP 搜索到；
- face/OCR/GPS 等增强可以继续后台执行，不计入 SEARCH_READY wall；
- 另记录 SEARCH_READY → COMPLETE 的增强耗时，但不把它混进“新增照片多久能搜到”的指标。

个人体验目标（不是架构硬契约）：

- 30 万 no-op：优先争取 **1–3 分钟级**；
- 30 万 + 约 300 张新增：优先争取 **2–5 分钟进入 SEARCH_READY**。

若明显超出，先做阶段归因；本卡只允许处理 skip-hash / delta fan-out / 128↔256 batching 这三个已冻结方向，不得继续引入 watcher/USN/新后端。

## 12. 失败与恢复

必须验证：

- refresh 中断后再点一次可恢复；
- 已完成 delta 派生不重复；
- 单坏图不终止其他正常资产；
- 一个 source 离线时其他 source 继续；
- 离线 source 不产生错误 MISSING；
- 磁盘不足沿用结构化失败，不删用户数据；
- semantic/profile 旧可服务 generation 不因新 delta 失败而失效；
- 搜索期间沿用 P4-02V：可正常服务或明确 LAGGING，不新增内部争用拒绝。

## 13. 明确不做
