# P4-PHOTO-MEMORIES-A — 智能回忆相册第一版

**状态：已实施，验收部分完成 · 不自动提交**

**目标：** 在现有个人图库中增加轻量智能回忆功能，自动发现往年今日及往年同月的照片，让用户方便地回顾和保存过去的时光。

**核心原则：** 不增加新的 AI 计算负担；不建立独立回忆索引；优先复用现有 SQLite 日期索引、照片浏览器和普通合集；以30万张照片为本次新增查询的性能验证规模。

## 2. 第一版范围

只实现以下功能：

### A. 往年今日

- 根据应用所在电脑的本地日期，查找往年同月同日拍摄的照片。
- 按年份生成回忆卡片，例如「8年前的今天」。
- 使用可信 EXIF 拍摄日期，不使用入库时间、文件修改时间或 AI 推测日期。
- 当天没有命中时，可以推荐「那年这个月」，但必须使用正确的标题，不能把相邻日期称为「往年今日」。
- 2月29日只匹配历史闰年的2月29日，不自动映射2月28日或3月1日。
- 同一日期仅有1～2张照片时仍允许展示，不人为排除稀有回忆。

### B. 那年这个月

- 查找过去各年份当前月份的照片。
- 每个年份最多生成一张该月回忆卡片。
- 尽可能覆盖不同日期和不同周，避免只选月初或月底的照片。
- 同一年已有「往年今日」卡片时，该月回忆封面尽量避免重复使用相同照片。
- 不将精选张数误认为整个月的照片总数。

### C. 回忆详情

每组默认精选最多24张照片。

支持：
- 逐张查看。
- 使用现有共享照片查看器。
- 查看照片详情。
- 从详情、查看器返回原回忆，保留卡片、已加载结果和滚动位置。
- 点击「查看该日期全部照片」，进入权威日期范围浏览。
- 点击「保存为相册」，把当前精选固定保存为普通照片合集。

**必须明确区分：**

- 「精选24张」表示本组挑选出的照片数量。
- 「查看全部」表示该日期范围内满足照片资格的全部照片。

不得用24张精选冒充日期范围内的完整结果。

## 3. UI 与路由

### 3.1 导航位置

左侧主导航顺序：

照片 → 回忆 → 收藏 → 照片合集 → 人物 → 地点。

保持其他次级导航顺序不变。

所有共用侧栏的 HTML 页面同步加入入口，避免人物、地点、搜索、地图等页面缺少回忆入口。

采用主应用现有路由方式：

`/?view=memories`

不新建完全独立的应用外壳。

### 3.2 页面布局

- 页面标题为「回忆」。
- 第一组为「往年今日」。
- 第二组为「那年这个月」。
- 首屏合计最多展示约4～6张卡片。
- 卡片展示封面、回忆标题和实际精选张数。
- 使用现有缩略图、卡片比例、间距、颜色及 UI 2.0 设计规范。
- 使用统一空状态、错误状态和刷新操作。
- 历史年份不足时展示实际找到的内容，不制造空白占位卡片。

第一版不在照片首页主动查询回忆。可以保留以后增加首页推荐条的扩展位置，但本卡不实施首页自动加载。

### 3.3 导航与状态

- 左侧回忆入口的激活状态必须正确。
- 浏览器 Back/Forward 复用项目现有导航语义。
- 回忆卡片 → 照片查看器 → 详情 → 返回应正确恢复上一级。
- 不把回忆照片列表压入不必要的多层浏览器历史。
- 离开页面、切换卡片、刷新时，旧请求不得覆盖当前内容。

## 4. 关键查询设计

这是本卡最重要的性能部分。

### 4.1 数据真值

使用现有：

- `assets`
- `asset_metadata`
- `file_locations`
- `asset_favorites`

复用图片资格规则 `photo_asset_sql()`。

只接受当前版本可信的：

- `EXIF_ORIGINAL`
- `EXIF_DIGITIZED`

必须检查 `taken_time_rules_version` 与运行版本一致。

不能直接把 `EXIF_ROOT`、`FILE_MTIME` 或待抽取状态认定为准确拍摄日期。

按现有 civil-time 时间键生成半开区间，不将无时区 EXIF 当作 UTC 时间戳转换。

同一 asset 即使有多个路径也只出现一次，视频专属资产不得混入。

### 4.2 访问路径

优先复用：

`idx_asset_metadata_capture(time_source, taken_at_sort, asset_id)`

按来源分别进行索引范围检索。

推荐使用「年份 + 指定日期范围」的查询方式，不允许每次执行全库 `strftime()`、`substr()`、`GROUP BY` 或将所有照片读入 Python 后过滤。

日期查询必须在 SQL 中限制候选，再批量读取必要的照片摘要。

**需要注意：LIMIT 只限制返回行数，不一定限制索引扫描量。**

必须检查图片资格过滤、离线比例和索引执行计划，确认不会因大量无效候选产生明显退化。

不强制指定单一 JOIN 顺序；应依据实际执行计划选择正确且高效的访问路径。

### 4.3 发现与详情分离

使用两层读取：

**第一层：发现回忆**

- 优先向过去查询最近10个历史年份。
- 每种可信 EXIF 来源、每个目标日期范围都采用有界查询。
- 每个年份只获取判断是否值得生成卡片所需的少量信息。
- 找到足够的卡片后停止。
- 用户点击「查看更多往年回忆」时，再继续更早年份。

**第二层：打开详情**

- 用户点击某张回忆卡片后，再计算其精选照片。
- 每组最多24张。
- 不在卡片目录阶段提前查询全部精选或原图。
- 不提前生成所有历史月份。

10年是首批发现窗口，不是最多支持10年的限制。更早年份必须可以继续浏览。

跨年份游标或查询状态绑定当前日期与相关图库修订，避免新旧结果混合。

### 4.4 选片规则

采用简单、确定性、可复现的规则：

- 精选按多个时间子区间分散取样。
- 同一短时间段的连拍尽量减少连续出现。
- 已收藏照片可以适当提高优先级。
- 保留不同日期、时段的代表照片。
- 不能只读取一个时间段的前24张就认为完成精选。
- 各子区间都有候选上限，不为了完整质量评分扫描整月。
- 同一图库状态、日期和选片规则下结果稳定。

第一版不新增图像质量模型、感知哈希计算、场景识别或向量相似度评分。

普通连拍分散不是严格的视觉重复检测。若候选超过预算，应返回确定性精选，并允许通过「查看全部」访问其他照片，不声称已经评估该日期的所有照片质量。

### 4.5 长事务保护

复用现有受控只读执行方式。

- 不在 ASGI 事件循环上执行长期同步 SQLite 查询。
- 单个读快照必须短。
- 不把10年或更多年份的完整回忆生成放入一个长期持锁快照。
- 批次间校验必要的图库修订；检测变化时丢弃不一致批次或提示刷新。
- 并发请求不得形成多个重复的大型查询。
- 不使用无上限线程池或后台队列。
- 数据库正在更新时，不无限重试直至产生额外负担。

## 5. 自动生成与缓存

### 5.1 自动生成策略

**采用按需自动生成，而非后台预生成。**

- 软件启动：不执行回忆计算。
- 正常照片浏览：不执行回忆计算。
- 点击回忆：自动计算需要显示的卡片。
- 打开详情：自动计算该组精选照片。
- 新照片入库：沿用已有日期提取，不创建额外回忆任务。
- 后续再打开：按更新后的权威数据重新判断。

不增加新的定时扫描、任务调度器、GPU任务、向量生成或独立回忆数据库。

### 5.2 缓存

第一版使用有界的进程内结果缓存。

建议默认：
- 最多缓存32个回忆结果键。
- 每个精选结果最多保存24个资产ID及少量摘要。
- 不缓存原图二进制或大量缩略图。
- 重复同键请求合并执行。
- 缓存最长有效期不超过当天，并设置适当的短期TTL。

缓存身份至少包含：
- 服务端本地日历日期。
- 回忆类型、目标年份。
- 图库过滤修订。
- 拍摄时间规则版本。
- 收藏修订（当收藏影响排名时）。
- 选片算法版本。

缓存命中和发布前都应保证结果没有越过相关修订，不能依靠TTL代替必要的一致性判断。

若建库期间修订频繁变化，不应无限清空并重新执行；应完成有界请求、拒绝过期结果或提示刷新，避免缓存抖动增加负担。

关闭应用时缓存自然释放。

## 6. 保存为普通合集

使用现有：

`POST /api/v1/photo-collections`

通过 `asset_ids` 创建普通合集。

不另建回忆成员表。

必须保证：
- 只保存当前展示的精选资产ID。
- 保存顺序确定。
- 使用符合现有协议的 `create_request_id` 支持幂等重试。
- 由服务端重新校验照片资格。
- 部分照片已失效时明确提示，不悄悄保存不完整结果。
- 保存失败不产生半成品合集。
- 保存成功后成员不随明日回忆重新生成而变化。
- 不更改照片原文件、人工标记或智能合集规则。

## 7. API建议

实施者先核对现有路由和服务边界，再决定最小新增接口。

建议只新增两类只读入口：

`GET /api/v1/memories/cards`

返回有界回忆卡片目录及继续查询游标。

`GET /api/v1/memories/preview`

根据合法的回忆类型、年份和服务端日期返回最多24张精选照片及必要状态。

两者均使用现有会话、鉴权、错误格式、数据库读调度和修订校验。

不允许前端传入任意 SQL、文件路径或任意未校验的选片规则。

尽量复用现有照片摘要、缩略图和详情接口，不建立第二套照片模型。

## 8. 30万张照片专项性能验收

**性能分类：PERF-SCALE，范围仅为本次新增回忆链路。**

旧30万合成夹具若没有可信 EXIF 时间数据，不得用其空结果速度宣称通过。

优先复用现有合成夹具，必要时制作隔离的日期元数据副本。

至少覆盖：

1. 30万张照片跨多个年份正常分布。
2. 某个历史月份有大量照片。
3. 某一天照片非常密集、连拍集中。
4. 大部分照片没有可信日期或不符合展示资格。
5. 新照片加入、日期提取更新和缓存失效。

### 8.1 查询指标

建议冻结以下初始验收目标：

| 场景 | 30万合成图库目标 |
|---|---|
| 首批回忆卡片元数据 | 热 P95 ≤ 500ms |
| 单组精选24张元数据 | 热 P95 ≤ 500ms |
| 有效缓存命中 | P95 ≤ 100ms |
| 重复打开 | 不重复执行完整日期查询 |
| 普通照片首页 | 不新增回忆API请求 |
| GPU资源 | 无额外占用 |
| 回忆后台任务 | 0个 |

以上为本任务建议目标，非当前代码实测成绩。编码前冻结预算；如果初步测试显示环境或访问路径不适配，必须记录原因及用户体验影响，不得验收失败后静默放宽指标。

需要分别测量 SQL、API、缓存及真实浏览器可见内容，不能用SQL运行时间冒充照片可见时间。

正式延迟验收每个关键场景至少30次有效样本，记录 P50、P95、最大值和环境。

### 8.2 必须检查

- `EXPLAIN QUERY PLAN` 是否使用适当索引范围。
- 是否出现不必要的全库扫描与临时排序。
- 每次回忆卡片请求触发多少SQL。
- 查询时间是否随年份数量、同日照片密度异常增长。
- 是否存在逐照片 N+1 查询。
- 内存缓存大小是否有界。
- 连续打开多个回忆后资源是否能回收。
- 日期查询与建库同时发生时，有无明显数据库锁等待。
- 取消页面请求后是否停止不必要的工作。

重点对比新增功能运行前后的普通照片页面，确认没有因初始化和共享代码变化产生明显退化。

如果查询明显缓慢，优先调整有界采样、索引驱动和资格过滤。只有实际证据表明现有索引无法满足目标，才评估新增索引或持久化派生表。

不得为了通过性能指标静默减少应展示的回忆年份，或把精选结果冒充完整日期命中。

## 9. 正确性与回归测试

### 日期测试
- 2月29日及非闰年。
- 12月与1月的跨年边界。
- EXIF拍摄日与文件日期不同。
- 缺少时区的可信 EXIF 时间。
- 日期尚未提取。
- 拍摄时间规则版本失配。
- 未来日期、异常日期和空图库。

### 资产测试
- 同资产多文件路径。
- 普通图片与视频专属资产。
- 离线或失效照片。
