# P4-01B — 检索路径与索引维护瓶颈的修复设计与最小实现

本卡由 [P4-01](P4-01.md) 的**停止条件 1** 触发：P4-01 已用真实运行证明 30 万规模下存在确定性瓶颈
（详见 [P4-01 报告](../reports/P4-01-ann-scale-benchmark.md)），而修复需要触及检索路径选择、索引维护
策略与索引参数承诺，超出「只改索引参数」的范围，因此交回用户先做**一次设计与决策**，再做最小实现。

推荐执行模型：**DS-H / DeepSeek V4.1 Flash / 高推理**（设计 + 最小实现 + 取证）。完成后**另开独立
DS-H 会话**做全量工程主审；命中 V3.1 §2.2 六类条件才升 DS-MAX；若主审把「检索语义/召回承诺」升级为
协议或 ADR 裁决，则必须补 **C2 / GPT-5.6 Sol / high** 聚焦终审。模型切换由用户在 Codex 中手动完成。

## 起始状态与依赖

- 观察基线：`P4-01` 收口提交（执行第一步先跑 `git log -1 --oneline` 与 `git status --short` 记录真实基线）。
- 依赖已通过：P2-03（outbox/索引确认）、P2-05（两路召回 + RRF）、P2-06A/B（SearchProfile 绑定）、
  P4-00B（拍摄时间）、P4-00C（HEIC）。本卡**不**依赖新模型下载。
- P4-01 已确立的事实（本卡的设计输入，不要重新测一遍）：
  1. 生产候选遍历 `vector_channel` 是 `ceil(候选数/1000)` 次引擎查询 × 每次全表扫描 ⇒ 10 万 11.5 s、
     30 万 **112.2 s**（§12.2 目标 1.5 s，差约 75×）；
  2. 当前 IVF_PQ（585 分区/64 子向量）把遍历降到 11.0 s，但 Recall@20 只有 **0.10**（20 万归因实验最好
     也只有 0.395；clustered/uniform 差 ≤0.02，量化精度是主因，锁定版 API 不暴露 nprobes）；
  3. 单条 `merge_insert` 50.9 ms/行 vs 同数据批量写入 0.0051 ms/行（差 4 个数量级）；
     `audit_and_schedule_repairs` 因 `has()` → `rows()` 全量物化而为 `O(资产数 × 行数)`；
  4. 两个 AND 过滤档位的权威 SQL 从 ~150 ms 退化到 **>60 s 未返回**，并使 §12.4 第 32 条组合校验在
     30 万档无法完成；
  5. 3 万档「后台重放 + 前台搜索」的 P95 已经是 5.0 s。
- 硬件事实：本机 RTX 4060；GTX 1660 6 GB 仍为 **BLOCKED**（主架构 §9.1）。

## 本卡必须先给的「设计决策」（写进报告，交用户确认后才实现）

1. **检索路径策略**：无过滤的全库查询是否允许「一次全局 ANN/精确查询」快路径？有过滤时如何在
   「候选 ID 精确检索」「向量预过滤」「按块扫描」之间选择，且**不违反**主架构 §9.3 第 4 条
   （禁止全库 Top-K 后过滤）？给出阈值来源与反例。
2. **索引参数与召回承诺**：§12.3 的 `ANN Recall@20 ≥ 0.95` 用什么配置达到？若锁定版 API 无法暴露
   `nprobes`，是换索引类型（仍属单变量归因后的方案选择）、还是加标量索引/位图预过滤、还是先如实下调
   承诺并写进 ADR？说明每种选择的代价与反例。
3. **索引维护策略**：批量发布（把 N 个事件合并为一次批量写入）由谁驱动、如何保持 outbox 幂等与
   `semantic_ready` 诚实；`audit_and_schedule_repairs` 如何从 `O(N²)` 收敛到可运行。
4. **过滤 SQL 退化**：两条退化查询的最小归因（`EXPLAIN QUERY PLAN`）与最小修复（索引/谓词改写），
   且**不得**改变过滤语义（ADR-0005/0009/0011）。

以上任意一条若需要改 schema/migration、改 `POST /api/v1/search` 信封/错误码/游标/`query_hash`、
改 RRF/BM25/距离公式或扩大支持承诺，**必须停止并交回用户**，不得在本卡内顺手实现。
