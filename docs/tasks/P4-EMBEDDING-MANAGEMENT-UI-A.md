# P4-EMBEDDING-MANAGEMENT-UI-A

**图库管理：搜索模型显示、分批建库与安全切换**

**优先级**：P1
**推荐模型**：GPT-6 High
**仓库基线**：`7842b34`（执行时 master 最新；工作树含用户未提交修改）
**状态**：IMPLEMENTED / ACCEPTANCE PARTIAL；已按后续用户指示本地提交
**验收**：个人项目，定向测试＋隔离浏览器检查，不跑大规模性能认证


## 性能设计与验收

- **链路与风险**：模型区域首屏可能叠加 provider/generation/覆盖统计，后台候选编码和停机切换会占用模型与数据根资源；统计避免逐资产查询并限制为必要元数据，完整校验只在显式检查/切换执行。
- **做法与边界**：复用既有批处理、jobs、artifact、outbox、generation 与 DataRootLease；批次按可配置上限（初始不超过 100–500，执行时据 worker 能力定），同数据根单执行者，暂停只在提交边界生效；不做 30 万性能认证或新的延迟承诺。
- **验证与停止**：对受影响状态/故障/恢复组合做隔离合成 JUnit、Ruff、Node 语法和一次真实内置浏览器短流程；只在卡面要求的小样本条件允许时做 Qwen smoke。所有身份、原活动 profile、写锁连续持有、崩溃/恢复必需项通过才结束；不访问真实 PhotoSearchData。
## 一、目标与范围

让用户在「图库管理」中完成三件事：

1. **查看模型**：清楚知道当前使用 Qwen 还是 Chinese-CLIP，查看安装与向量覆盖状态。
2. **建立索引**：为候选模型分批建库，支持暂停、继续及异常中断恢复。
3. **切换模型**：在界面安排切换，正常退出并重新打开应用后安全执行。

重点解决用户曾删除 `catalog.db`，导致 Qwen 的 Profile 丢失、旧向量表可能残留的问题。

不做模型下载、模型参数编辑、多模型融合、在线热切换或通用 GPU 调度系统。

## 二、界面设计

### 1. 图库管理 → 搜索模型

在「我的图库」下方增加简洁的模型区域。

默认直接显示：

**当前搜索模型：Chinese-CLIP**

展开后展示各模型：

| 模型 | 状态 | 主要操作 |
|---|---|---|
| Chinese-CLIP | 正在使用 | 查看详情 |
| Qwen3-VL-Embedding-2B | 已安装，未建索引 | 开始建库 |

实际内容必须读取真实状态；EXIF v2 配置放在「其他配置」折叠区域。

每个模型按需展示：

- 安装状态。
- 有效向量覆盖数。
- 建库进度和错误。
- 是否具备切换条件。

操作按钮按状态显示：**开始建库 / 暂停 / 继续 / 检查 / 安排切换**。

### 2. 搜索页面

在顶部「索引状态」旁显示：

`当前：Chinese-CLIP` 或 `当前：Qwen`

点击进入图库管理的模型区域。

模型名称始终从活动 SearchProfile 获取，不能从 installed 或 generation 列表顺序猜测。

## 三、覆盖率与轻量读取

复用 `registry.py`、`search/profile.py`、`indexing/selection.py` 和现有 capabilities。

对每个模型分别检查 provider、processor、space、generation 和 Profile：

- 未安装。
- 已安装但无 generation。
- 索引部分完成。
- 已完成但尚未核验。
- 可切换。
- 正在使用。
- 存在错误或孤儿表。

默认页面只读取必要元数据和有界数据库统计。

准确分母必须以当前可索引图片为准，排除不支持的文件类型。无法轻量得到可信分母时显示「待检查」，而不是假定 100%。

完整 artifact、Lance、索引一致性检查仅在用户主动检查或实际切换时执行。

## 四、候选模型分批建库

### 1. 复用现有建库逻辑

抽取现有 `embedding build-candidate` 的核心业务方法，供 CLI 与网页共用。

继续使用现有：

- `semantic.build_index`
- job 和租约
- artifact
- index_outbox
- index_entries
- index_generations
- `ensure_search_profile`

不得新建另一套逐图调度、产物或向量索引系统。

**特别要求：候选建库始终不得自动切换活动模型，即使当前尚无活动 Profile。**

### 2. 最小持久任务状态

新增一份候选建库任务状态，优先使用数据根 `runtime` 下原子写入的 JSON 文件，避免仅为 UI 任务状态增加数据库迁移。

至少记录：

- task_id、幂等请求 ID。
- catalog 身份及 provider/processor/space/generation。
- `RUNNING / PAUSE_REQUESTED / PAUSED / INTERRUPTED / COMPLETED / FAILED`。
- 当前执行者、版本或租约、更新时间、错误信息。

同一数据根同一时间只允许一个候选建库执行者。不建立多任务队列。

任务状态用于控制与展示；**实际完成进度以 SQLite 中已确认的 job、artifact、outbox 和 generation 为准**，不能相信单独保存的百分比。

如果 catalog 已被替换或重建，旧任务记录失效，必须重新核验身份。

### 3. 执行与恢复

- 用户点击开始后，后台循环执行有界批次；建议初始每批不超过 100～500 张，最终按现有 worker 能力确定。
- 每批提交并核对结果后，再检查暂停、退出及资源冲突。
- 暂停只在批次安全边界生效，不中断发布事务。
- 普通刷新页面、重复点击、关闭浏览器，不会重复创建任务。
- 正常退出停止领取新批次，并释放资源。
- 异常退出后，下一次取得数据根所有权时对账已完成与待处理工作，标记为可继续。
- 中断后**等待用户点击继续，不自动重新编码整库**。
- 失败的照片明确报告，可使用已有 `--retry-failed` 对应业务机制处理，不无限重试。

网页后台任务与独立 CLI 建库也必须服从同一数据根写入互斥，避免服务运行时从外部 CLI 同时写入候选索引。

## 五、GPU 资源协调

当前 `BACKGROUND_MODEL_SLOT` 和查询 worker 内部锁都不能证明所有模型共享 GPU 资源互斥。

实施前检查真实执行链：语义搜索、图库刷新、人脸/OCR 后台任务、候选模型编码。

采用以下明确策略：

1. 已经开始的前台搜索不得被新候选批次强行中断。
2. 候选建库在批次开始前检查相关资源状态，冲突时等待安全边界或返回 BUSY。
3. **优先保证正确性，不强求两个不同模型同时驻留显存。**
4. 如果不能安全共享 GPU，要求用户确认进入候选建库占用模式；此期间需要 GPU 语义搜索的请求应明确等待或拒绝，并允许用户暂停建库。
5. 禁止静默改用 CPU、Chinese-CLIP 或纯文字结果来冒充 Qwen 搜索。
6. 任务结束、暂停或异常时，确保候选模型及 worker 资源按实际生命周期释放。

可以采用小型专用资源协调器，但不能仅把 `BACKGROUND_MODEL_SLOT` 包到候选任务外层就声称完成互斥，也不要引入大型通用调度框架。

## 六、删除数据库后的孤儿 Lance 表

本卡必须处理以下场景：

**SQLite 没有 Qwen generation，但 `vectors` 中仍有对应 LanceDB 表。**

建库前，按目标 space 和 processor 计算稳定 generation ID，再检查对应物理表。

发现孤儿表时：

- 禁止直接追加新资产向量。
- 禁止将旧向量计入新图库覆盖率。
- 显示「发现旧索引残留，需要处理」。

### 安全隔离

提供单独的「安排隔离旧索引」操作，不能和 VACUUM、缓存清理等维护任务混批。

申请绑定 data-root、catalog 文件身份、目标 generation、Lance 表名、物理表身份及有效期。

停机取得排他锁后：

1. 重新核验上述身份，确认没有合法 generation 引用。
2. 创建独立备份并验证完整性；空间不足或校验失败不得移动原表。
3. 使用同一文件系统的受控隔离位置，确保不覆盖已有表或备份。
4. 记录操作阶段与结果。
5. 成功隔离后才允许正常建库。

备份、隔离改名、结果保存的中途崩溃，都必须能够根据实际文件及记录判断完成程度；无法判断时停止并提示人工处理。

**不开发孤儿索引自动复用、跨数据库资产 ID 映射或通用向量 GC。**

## 七、停机切换及启动锁

### 1. 在线安排

只有候选索引通过必要检查时，才允许安排切换。

请求记录：

- 目标 Profile 与 generation 身份。
- 当前活动 Profile。
- data-root 和 catalog 身份。
- 用户确认、请求 ID、有效期。

用户可以取消未执行的请求。在线阶段绝不修改活动模型。

### 2. 启动前的排他锁

现有 `_serve` 在应用 lifespan 加锁之前执行维护，而普通存储维护函数内部又会自行获取同一把锁。

因此采用**独立模型切换停机入口**：

- 模型切换申请与已有存储维护申请互斥；存在冲突时拒绝或延期，不混批。
- 只有模型切换入口在消费申请前取得 `DataRootLease`。
- 在持有该锁期间核验、切换、完成模型接线并启动应用。
- 将实际已持有的锁交给 `app.py` 的 lifespan 复用，不重复加锁。
- 锁从切换开始连续覆盖到应用关闭，不允许释放后再获取形成空窗。
- 其他直接创建 FastAPI 应用的入口保留现有自行取得 lifespan 锁的行为。
- 旧的 VACUUM、向量优化和清理操作保留各自互斥行为，不因为本卡新增外层锁而失效。

不要用一个简单的布尔参数允许任意调用者跳过加锁；应传递真实的受控锁所有权或等效的内部凭据。

### 3. 正式切换

在停机锁下复用现有 `select-profile` 完整校验：

- 目标 Profile/space/generation 匹配。
- 模型权重、manifest、图文编码健康。
- 当前索引覆盖完整。
- artifact、outbox、repair、Lance 状态合格。
- runtime 资格及原子激活前置检查合格。

检查全部通过后，才在原子事务中更新活动 Profile。

**必须区分两类失败：**

- **激活事务提交前失败**：保持旧活动 Profile，记录错误，继续用旧模型启动应用。
- **激活成功后新编码器启动失败**：如实报告「新模型已激活但不可用」，不得伪装成旧模型；后续需要用户重新安排受控回退。

一次性请求不得无限自动重试，失败不得删掉旧索引或人工数据。

## 八、影响边界

- 原图、人物、人脸、OCR、地点、收藏、普通合集不因切模型而重建。
- Chinese-CLIP 和 Qwen 使用独立向量空间，不转换或混用 512D 向量。
- 候选建库期间原活动 Profile 不变。
- 切换后新搜索会话使用新的模型身份。
- 绑定旧空间的 COMBINED 智能合集保持旧缓存及人工排除，提示重新绑定规则。
- 旧模型及索引保留；将来切回时仍需重新检查当前图库覆盖率。

## 九、实施顺序

在一张任务卡内完成，按以下顺序推进，不拆成多个独立项目：

**第一段：模型查看与只读状态。** 完成图库管理展示、搜索页模型标识、轻量覆盖率及孤儿表检测。

**第二段：候选建库。** 完成持久任务状态、有界执行、暂停恢复和 GPU 协调；证明活动模型不变。

**第三段：停机维护。** 完成孤儿表安全隔离、模型切换申请、启动锁连续持有和结果展示。

每段只验证直接相关代码。前一段发现模型身份或数据根锁问题时先修正，不能绕过安全检查继续实现后续操作。

## 十、必要验收

使用隔离合成图库完成定向测试：

| 测试范围 | 重点 |
|---|---|
| 显示 | 活动模型、已安装未建库、覆盖率待检查 |
| 分批建库 | 单批边界、重复提交、暂停/继续、正常与异常退出后对账 |
| 争用 | 搜索、刷新、人脸任务与候选模型的冲突行为 |
| 孤儿表 | SQLite 无登记、有旧表、身份变化、备份失败及隔离中断 |
| 切换 | 成功、过期、取消、换库、锁被占用、模型故障、索引不完整 |
| 锁生命周期 | 持锁跨越离线维护与应用启动，普通维护不发生重复加锁 |
| 浏览器 | 显示 → 建库 → 暂停/继续 → 检查 → 安排 → 重启 → 查看结果 |

真实 Qwen/CUDA 仅在本机条件允许时补一次小样本 smoke；不能运行则报告 PENDING。

测试只要求受影响 pytest、Ruff、Node 语法检查和一次简短浏览器验收。不进行 30 万图库压测、全仓测试或 GTX 1660 性能认证。

**不得自动测试或修改真实 `PhotoSearchData`。**

## 十一、完成标准

用户能够从界面准确看到活动模型，安全建立另一模型的索引，并在正常退出、重启后完成受控切换。暂停、崩溃、GPU 冲突、删库残留和切换失败都有明确结果，不丢失原数据，不发生错误向量混用。
