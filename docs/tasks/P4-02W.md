## 5. 正式性能场景

所有延迟场景遵循主架构 §12.2：

- 固定版本；
- 固定数据；
- 固定查询 / 输入；
- 至少 30 个正式计时样本；
- 记录 P50 / 样本 P95 / max；
- 保留所有失败；
- 不得用补跑成功样本覆盖失败。

若出现非预期合法请求失败，该场景直接 FAIL。

样本 P95 统一使用：

`sorted_samples[ceil(0.95 * N) - 1]`

冷启动、首次模型加载、冷缓存单独记录，不混入暖机结果。

### A. 30 万暖机普通文字搜索

真实链路：

`文本 → 真实文本编码器 → HTTP API → 检索 → 融合 → metadata → response`

门槛：

**P95 ≤ 5 秒**

记录：

- HTTP 总延迟；
- query encoding；
- vector retrieval；
- text / OCR channel；
- fusion；
- projection catch-up；
- metadata / response assembly。

若现有产品无法提供某项分量，不为此修改 `src/**`，只标：

`NOT OBSERVABLE`

### B. 30 万浏览器第一屏图片可见

使用真实浏览器入口。

计时：

`用户提交搜索 → 第一屏结果图片实际可见`

门槛：

**P95 ≤ 6 秒**

至少记录：

- API response 时间；
- 首张图片可见；
- 第一屏完成；
- 缩略图请求情况。

不得以 API response 时间代替浏览器第一屏时间。

不得为了本卡引入新的大型前端或浏览器依赖；优先复用当前已有入口与可用测量方式。

### C. 默认 CUDA 上传图片搜索

真实上传入口：

`图片 → 上传 → 解码 → 真实图像编码器 → 检索 → response`

门槛：

**P95 ≤ 5 秒**

使用固定、受支持的测试图片集合，真实 CUDA。

不得用预计算向量直接调用检索代替上传链路。

### D. 后台建库同时普通文字搜索

这是本卡重点场景。

条件：

- 30 万规模索引 / 目录存在；
- 后台通过真实产品维护 / 建库入口运行；
- 后台在 30 个正式样本期间必须持续发生实际进度；
- 每个正式样本记录是否与后台工作真实 overlap。

不要求重新编码完整 30 万张照片；允许准备一个足够长的合法 backlog，使后台工作持续覆盖全部正式搜索样本。

门槛：

**API P95 ≤ 8 秒**

并且：

**合法验证请求因内部争用被拒 = 0**

记录：

- 前台延迟；
- overlap；
- background before / after progress；
- batches / applied / confirmed；
- lock wait / write hold 等现有指标；
- `search_projection.state`；
- 所有失败原文。

不得暂停所有后台任务后把结果记为后台场景 PASS。

## 9. 判定

只有以下全部通过：

1. 暖机文字 API P95 ≤ 5 s；
2. 浏览器第一屏 P95 ≤ 6 s；
3. CUDA 上传搜图 P95 ≤ 5 s；
4. 后台建库 + 文字搜索 P95 ≤ 8 s；
5. 后台场景内部争用合法请求拒绝 = 0；
6. 来源离线最小冒烟无明显阻断；

才记录：

`PERSONAL TRIAL PERFORMANCE PASS`

### 若 PASS

停止性能专项。

不得自动启动：

- P4-02I / A3；
- P4-02L / ANN；
- P4-03B；
- P4-04；
- 其他性能加速卡。

进入实际日常使用，以真实使用反馈决定是否恢复后置任务。

### 若 FAIL

不得在本卡修代码。

只确定**主要失败场景**并生成一张最小修复卡。

报告必须给出：

- 失败场景；
- P50 / P95 / max；
- 距门槛差值；
- 失败数量；
- 已知主要耗时分量；
- 现有证据能够证明的根因；
- 下一张卡建议修改的最小面；
- 明确不需要启动的方向。

典型分流：

- 普通搜索失败 → 只处理当前最大检索执行分量；
- 只有后台搜索失败 → 只处理后台调度公平性 / 写锁占用；
- API 达标而浏览器失败 → 只处理首屏 / 缩略图链路；
- 上传失败 → 只处理上传解码 / 编码 / 排队链路。

不得一张卡同时启动 SQL + A3 + ANN + scheduler + model。
