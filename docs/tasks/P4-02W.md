## 4. 30 万验收口径

不要求准备或重新编码 30 万张真实个人照片。

**优先复用 P4-02F/U 已验证形状的 30 万夹具副本**：

`tmp/p402f-阶段0/scale-300000-wave/data`

不得修改历史证据目录本体；使用副本隔离。

若本地该夹具已不存在，或与当前 schema / profile 不兼容，再复用现有：

`tools/diagnostics/capacity_validation.py`

按相同 seeded wave shape 重建；不得另造一套新的 30 万数据形状。

正式性能结论必须走：

- 真实产品入口；
- 真实 HTTP API；
- 真实查询编码器；
- 当前实际 CUDA GPU；
- 当前固定模型。

合成向量、内部 service、NumPy 或单独 Lance 调用只能用于归因，不能替代端到端 PASS。

每个正式延迟场景：

- 至少 30 个正式计时样本；
- 固定版本 / 数据 / 查询；
- 记录 P50 / 样本 P95 / max / 所有失败；
- 非预期合法请求失败 ⇒ 该场景 FAIL；
- 冷启动、模型首次加载、冷缓存单列，不混入暖机统计。

样本 P95：

`sorted_samples[ceil(0.95 * N) - 1]`

每个场景允许先跑 **3～5 次 smoke** 检查入口、CUDA、数据与输出结构；smoke 不计入正式 30 样本。

## 5. 执行顺序：A → D → B → C，任一步失败即停止

### A. 30 万暖机普通文字搜索

真实链路：

`文本 → 真实文本编码器 → HTTP API → 检索 → 融合 → metadata → response`

门槛：

**P95 ≤ 5 秒**

记录 HTTP 总延迟；已有可观测分量可顺带记录，但不得为了埋点修改 `src/**`。

如果 A FAIL：

- 立即停止，不执行 D / B / C；
- 记 `PERSONAL TRIAL PERFORMANCE FAIL / PARTIAL`；
- 聚焦当前最大检索执行分量提出一张最小修复卡。

只有 A PASS 才进入 D。

### D. 后台建库同时普通文字搜索

这是 P4-02V 留下的正式补测面。

后台必须使用**具有个人实际建库代表性的真实产品工作**，至少包含实际的：

- embedding 发布 / 待发布队列；
- outbox / claim；
- drain；
- index apply / confirmed 推进。

不得仅用：

- 纯文字投影；
- 人为轻量 re-projection；
- 暂停大部分后台工作；
- 只制造锁但不发生实际索引推进；

来冒充 §12.2 的“后台建库”。

后台必须：

- 通过真实产品维护 / 建库入口运行；
- 在正式样本期间持续实际推进；
- 每个正式样本证明与后台工作真实 overlap；
- 至少取得 **30 个有效真 overlap 前台搜索样本**。

本场景按个人单用户形状验收：后台真实建库 + 普通文字搜索；P4-02V 的 4 并发压力形状可作诊断旁证，但**不是本卡 PASS 的强制并发条件**。

门槛：

**API P95 ≤ 8 秒**

且：

**合法验证请求因内部争用被拒 = 0**

记录：

- 前台延迟；
- overlap；
- background before / after progress；
- batches / applied / confirmed；
- 已有 lock wait / write hold；
- `search_projection.state`；
- 所有失败原文。

如果 D FAIL：

- 立即停止，不执行 B / C；
- 记 `PERSONAL TRIAL PERFORMANCE FAIL / PARTIAL`；
- 聚焦后台调度公平性 / 写锁占用提出一张最小修复卡。

只有 A + D 都 PASS 才进入 B。

### B. 浏览器第一屏图片可见

真实浏览器入口：

`提交搜索 → 第一屏结果图片实际可见`

门槛：

**P95 ≤ 6 秒**

正式 PASS 证据需要至少 30 个可重复计时样本，并至少记录：

- API response；
- 首张图片可见；
- 第一屏完成。

不得：

- 以 API response 代替浏览器首屏；
- 用人工秒表 30 次制造伪精确 P95；
- 为本卡引入 Playwright / Selenium 或新的浏览器自动化依赖。

优先复用仓库现有“记录式真实浏览器”能力与当前可取得的浏览器 timing。

若当前环境**无法取得可靠、可重复的浏览器第一屏 timing**：

记录：

`BROWSER_TIMING BLOCKED`

本卡不得因此宣称 PASS，也不得为了解除 BLOCKED 扩成浏览器自动化开发任务。

如果 B FAIL 或 BLOCKED：

- 立即停止，不执行 C；
- FAIL 时聚焦首屏 / 缩略图链路；
- BLOCKED 时只记录缺少的最小测量能力，不改产品。

只有 B PASS 才进入 C。

### C. 默认 CUDA 上传图片搜索

真实链路：

`上传 → 解码 → 真实图像编码器 → 检索 → response`

门槛：

**P95 ≤ 5 秒**

使用固定、受支持图片集合。

不得用预计算向量代替上传链路。

如果 C FAIL：

- 立即停止；
- 聚焦上传解码 / 编码 / 排队链路提出一张最小修复卡。

## 7. 判定

### PASS

只有以下全部成立：

1. 暖机文字 API P95 ≤ 5 s；
2. 后台建库 + 文字搜索 P95 ≤ 8 s；
3. 后台合法请求因内部争用被拒 = 0；
4. 浏览器第一屏 P95 ≤ 6 s；
5. CUDA 上传搜图 P95 ≤ 5 s；
6. 来源离线快速 smoke 无明显阻断；

才记录：

`PERSONAL TRIAL PERFORMANCE PASS`

随后：

- 结束性能专项；
- 不自动启动 P4-02I / A3；
- 不自动启动 P4-02L / ANN；
- P4-03B / P4-04 继续后置；
- 转入真实日常使用。

### FAIL / BLOCKED

任一核心场景失败即可记录：

`PERSONAL TRIAL PERFORMANCE FAIL / PARTIAL`

浏览器等必要证据无法可靠取得时记录相应 `BLOCKED`，不得把未测写成 PASS。

本卡不修代码。

报告只需明确：

- 已执行到哪个场景；
- P50 / P95 / max；
- 失败数量；
- 距门槛差值；
- 当前可证明的主要原因；
- 未执行 / BLOCKED 项；
- 下一张最小修复卡建议；
- 明确哪些方向当前不需要启动。

不得一张卡同时启动 SQL + A3 + ANN + scheduler + model。
