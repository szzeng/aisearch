# P4-PERSON-OPLOG-GC-A — 人物操作撤销历史过期清理

日期：2026-10-09。状态：**PLANNED / 待实施**。立卡基线：`00f9deb3134d8fc5d784cd92cd8a4e4a24833c3a`（实施前以最新 `master` 复核）。**个人相册、一张卡、仅三组定向轻量测试**。

推荐执行模型：**GPT-6 High**。本卡仅为任务设计；**立卡/实施均不得擅自清理真实 `PhotoSearchData`**，真实图库清理须用户在应用界面明确预览与确认。

## 1. 目标与现状

目前 `person_operations` 是持续追加的操作记录，`person_operation_items` 保存人物、人脸归属、拆分和重检测映射等 before/after JSON 快照。没有自动过期清理。较早的快照占用空间，但对个人相册的撤销价值通常已很低。

目标：**只回收失去撤销价值的历史快照，保留稳定操作身份、幂等和引用，不更改现有人物、照片、归属、人工锁或搜索事实**。清理后仍可查看精简历史，明确标为“已过期·不可撤销”。

## 2. 固定保留策略（首版不做配置系统）

- **保留最近 30 天内的所有操作**；另**保留按 `operation_revision` 倒序的最新 200 条操作**，含 `UNDO`。
- **只有同时超出这两项保护范围**，才是过期候选；时间依据权威 `committed_at`（毫秒时间戳）。
- 以整条 `operation_id` 为单位清理快照，不能只删一个批量操作中的部分 `FACE_CONTROL` / `PERSON_BUNDLE` 项。
- 不因到期自动运行；首版仅提供手动“预览 → 确认清理”。
- 不承诺超期记录一律可压缩：若某操作类型无法在保持历史重放等既有契约的前提下安全过期，则**跳过并列明原因**，不得强删。

## 3. 数据与协议安全边界

### 3.1 保留主记录，绝不直接整表清空

保留 `person_operations` 的现有 `operation_id`、`request_id`、`payload_sha256`、`type`、`operation_revision`、`state`、`undo_of_operation_id`、`undone_by`、时间、`target_person_id` 和已有外键引用，防止：

1. `person_aliases.last_operation_id` 等引用失效；
2. `UNDO` 与原操作的关系失效；
3. 历史 `request_id` 被当成新请求再次执行；
4. 单调 `operation_revision` 倒退或历史列表分页混乱。

现有 `persons`、`face_person_links`、`face_assignment_controls`、`face_exclusions`、`face_redetection_*`、人物合集与图库事实不得因历史清理改变。

### 3.2 轻量“过期凭证”与增量迁移

优先新增小型伴随表（暂定 `person_operation_retention`），以 `operation_id` 为主键，记录过期时间、**清理前提炼的安全历史摘要**、**可维持原有 API 重放语义的精简回执**。开工时复核最新 Schema（立卡时 v26），新增连续 migration；不修改旧 migration，不重建原 `person_operations` / `person_operation_items` 表。

**重点：** `person_operation_items` 当前存储的 before/after JSON 为 NOT NULL，且普通操作、脸级操作、`SPLIT`、`FACE_MAPPING_*`、`UNDO` 的响应/重放流程各不相同。不能删除 item 后继续沿用“items 为空就是 no-op”的旧代码。

每个允许清理的操作必须在**同一 SQLite 写事务**中按如下顺序：
1. 判断当前是否仍符合过期条件，以及该操作与相关 `UNDO` 引用是否可安全过期；
2. 从原始快照生成并验证精简历史摘要/重放回执，确保必要字段和 `changed` 语义仍可正确返回；
3. 写入过期凭证（幂等）；
4. 删除该 `operation_id` 的全部 `person_operation_items`；
5. 提交后才算清理成功。任何中途异常应整体回滚。

如果紧凑回执无法完整保留某操作的既有幂等响应语义，**该操作不得清理**。不允许以“返回一个随意缩短的成功对象”替代受约束的重放结果。压缩后的数据是否真比原始快照小，需在预览中核算；不增空间时可跳过。

### 3.3 兼容旧记录、读历史与撤销

- 普通未过期操作走原路径：`read.operation_page`、各操作族 replay/undo 均保持原行为。
- 已过期操作从伴随凭证投影历史摘要；显示“已过期·不可撤销”，不显示有效撤销操作入口。分页顺序仍用主表 `operation_revision`。
- 所有撤销入口（相册快捷撤销、`persons.js` 历史页、统一后端 `POST /person-operations/{id}/undo`）必须在读取缺失 item 或进入操作族分发前**一致拒绝过期操作**，返回明确业务冲突，**零写入**，避免“空快照撤销成功”。
- 对过期操作，重复 `request_id` + 同 payload 必须仍按现有操作族契约识别 `replayed`，不同 payload 必须继续拒绝，均不产生重复人物修改。
- 对已撤销的原操作与补偿 `UNDO`，保持双向引用与状态一致；过期前对关联项采用必要的成组校验或跳过，不得留下悬空逻辑。
- 前端不预测过期资格：以服务端状态为准；若操作在页面打开后过期，撤销接口也必须安全拒绝。
- 不更改既有人脸锁、排除、归属更正、同名合并、拆分与旧 ID 重定向语义。

## 4. 最小页面交互与清理流程

在现有**人物操作历史**页面提供“清理过期撤销历史”（不要另开管理系统）：

1. **只读预览**：显示过期候选操作数、实际可安全清理数、跳过数及原因、待删除 item 数、原快照 JSON 字节数和预计净节省字节数；提示“过期后不可恢复撤销能力”。
2. **人工确认**：用户明确点击确认后执行；复用现有本地 API 的 Origin/CSRF 保护，不允许 GET 修改数据库。建议预览 `GET /api/v1/person-operations/retention-preview`，执行 `POST /api/v1/person-operations/retention-cleanup`（开工时核对 API 路由命名与现有接口）。
3. 后端每批处理**至多 100 条**候选操作，每批独立事务；失败仅回滚本批，前面提交的批次保留。客户端显示已完成、跳过和失败数；再次执行只继续未清理记录，不能重复清理或重置状态。
4. 写事务内复查过期资格与相关引用，避免预览与确认之间出现新操作导致误清理；与实际人物修改共用现有 SQLite 写串行化入口。
5. 不调用模型、不触发人脸重识别、重建库、投影刷新或新一轮候选匹配。
6. **首版不自动跑 `VACUUM`**：仅回收 SQLite 内部页供后续复用，不保证 `catalog.db` 物理文件立即缩小。后续如需压缩，另行讨论安全时机与磁盘余量，不并入本卡。

## 6. 个人范围最小验收（三组）

1. **过期边界**：少量合成 SQLite 记录覆盖第 30 天、最新第 200 条、两个条件的交集、`UNDO` 和 no-op。只清理真正超期且安全的操作；预览与实际一致或明确说明并发变化。
2. **数据与撤销安全**：至少一条普通人物操作、一条单脸纠错，以及拆分/映射各一个代表性样本（不支持清理的类型须验证安全跳过）。断言清理前后人物/人脸/排除关系不变；过期历史可读、旧 request 幂等重放不重复执行、过期撤销零写入、近期历史仍能正常跳步撤销。
3. **迁移与故障**：旧 Schema 升级、原有外键与 `UNDO` 关系保真；注入一次批次中途失败验证整体回滚；重复清理安全。简单 DOM 验证“预览→确认→完成/失败提示”，不做真实浏览器矩阵。

仅跑相关定向 pytest/JUnit、修改面 Ruff、Node `--check` 和 `git diff --check`。**不跑**全仓回归、30 万图库、CUDA/GPU/模型、正式打包；测试禁止读写真实 `PhotoSearchData` 或启动/重启用户当前服务。

## 7. 完成标准与交付

- 默认 **30 天或最新 200 条保留**，只有二者均不满足才过期；
- 能预览并由用户手动确认；操作可重试、事务原子；
- 旧快照实际减少，数据库关系/身份与权威事实不变；
- 已过期历史能读、不能撤销；同一 `request_id` 幂等仍正确；
- 正常近期撤销、人物更正/合并、拆分、映射不倒退；
- 报告列出实际可清理类型、跳过类型与原因、节约估算、三组测试证据及未验范围。
