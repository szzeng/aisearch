# P4-PERSON-INBOX-COMPARE-A — 待整理人脸与候选人物头像并排对照

日期：2026-10-12。状态：**SCOPED IMPLEMENTED / 定向合成验收通过，待用户实际页面观察**。基线：`master` 开工时工作树干净。

**类型**：个人相册小型 UI 改进。**推荐实施模型**：GPT-6 / Medium。**验收**：最少必要定向测试 + 用户真实页面手测，不跑全仓。

## 1. 目标与当前证据

人物相册「待整理」发现某张脸可能属于已有的人物时，让用户直接看到**待确认的人脸**与**该候选人物在人物相册中的现有头像**，减少反复切换页面的操作；只帮助人工判断，不改变自动识别/归属。

已核对仓库现状：

- `src/photo_search/persons/albums.py::_face_view()` 返回 `face.thumbnail_url` 与 `suggestions[]`，后者已有 `person_id`、姓名和人物 `thumbnail_url`。
- `src/photo_search/web/persons-albums.js::renderInboxFace()` 只展示待整理脸，首条建议对应「确认是某人」；`renderInboxGroup()` 的分组摘要目前展示**待整理代表脸**，不是候选人物头像。
- `inbox_group_page()` 返回 `group_key=candidate:<person_id>`、`candidate_name`、`photo_count` 和 `face`；组内逐脸分页通过 `inbox_group_faces()`。分组和脸级候选可能不完全相同，**不得仅根据姓名或不加验证的 `suggestions[0]` 把头像贴到组卡**。
- 人物浏览头像投影已有有效成员封面选择与受保护缩略图 URL；现有 `picture()`/浏览器缓存/lazy loading 可复用。

## 2. 显示方案

### A. 候选分组卡（折叠状态）

显示两列紧凑圆形人脸，左「待整理」、右「参考头像」，下方保留「可能是张三 · N 张待确认照片」。左边使用组代表人脸 `group.face.thumbnail_url`；右边**必须是组键中 person_id 指向的 canonical 候选人物的有效头像**，而不是随意选的相似人脸。原 `<details><summary>` 点击展开行为不变。

优先从已返回的 `group.face.suggestions` 中**按 `person_id` 精确匹配**，有正确头像时不发额外人物请求；若缺失，显示「暂无参考头像」，或在证明确有必要时为分组响应增加**可选、只读、有界批量投影** `candidate_thumbnail_url`（与同一 `group_key` 绑定），保持旧字段、游标、分页与筛选兼容。不得对每张卡额外请求一次 `/persons/{id}`，也不得错误回退到其他人的头像。展开列表不需要整体请求所有成员头像。

### B. 展开后的逐脸卡与独立单脸卡

在现有待整理头像旁并排显示**当前确认按钮实际使用的首选建议人物**头像，下面明确标「待整理 / 可能是张三」。优先使用 `face.suggestions[0].thumbnail_url`，姓名、头像、确认按钮必须来自**同一个候选对象/person_id**。有多个候选时，默认仅展示首选，不同时加载多个参考头像。若没有有效候选，仍保持原单头像与「这是谁？」操作。

右边仅用于比较：不作为脸选择的点击区域，不触发整图预览、确认、改归属或批量勾选。左边点击继续预览该脸所在的整张照片。「确认是」「选其他人」的现有流程和人工写保护完全不改。

### C. 异常和其他视图

- 候选无封面/缩略图不可用：明确显示「暂无参考头像」，不误用别的人的图片；文本仍可操作。
- 人物改名、换头像、合并或候选变更后，沿用原有刷新/异步过期响应拦截机制，不沿用错位旧头像。
- 批量管理时仍只允许勾选**待整理的人脸**；参考头像绝不带 checkbox；Shift 跨范围选择、已加载全选、最多 500 脸、原先的选择状态与确认限制不变。
- 已忽略人脸视图共用绘制组件时只做必要的兼容，不能出现点击/选择回归；不扩展其身份业务语义。

## 3. UI / 性能约束

- 现有 `.pa-people-grid` 是最小 `9rem` 卡宽，不能直接把两个 `6.5rem` 头像并排；新增局部紧凑双头像样式，优先用约 3–3.5rem 或 `minmax(0,1fr)` 自适应，保证卡片内容、文字和标签不溢出。
- 继续复用 `picture()`、安全缩略图 URL、浏览器缓存、`loading=lazy`；不新增全量人物加载、不对候选逐卡 N+1 请求、不重新识别/补匹配/建库。
- 未展开组仍只请求当前页代表脸；分页、展开、收起、保留已加载页数、滚动位置恢复和筛选响应竞态行为保持不变。
- 无有效参考脸时按单头像/占位展示，不因资源失败阻断确认或列表显示。

## 4. 文件范围与停止条件

**优先仅改**：
- `src/photo_search/web/persons-albums.js`（`renderInboxFace`、`renderInboxGroup`，必要的局部 helper）
- `src/photo_search/web/persons.css`（局部双头像、提示、小屏布局）

**只有证明已有数据不足且无法安全对齐组键时**，允许最小只读扩展 `src/photo_search/persons/albums.py::inbox_group_page`（必要时同样考虑 hidden 分组），通过当前页批量取得 canonical 候选头像；不得改变分组资格、排名、游标/计数或旧响应含义。该情形需同步增加后端定向测试、API 兼容测试及 Ruff。不要无理由修改 `api/routes.py`。

不得改 schema/迁移/向量/模型/阈值/识别排队、候选排名、自动分组、人工归属、排除、合并、撤销、照片权限。若发现必须触及这些高风险语义，**停止扩大本卡**，报告阻碍并建议单独任务，不擅自引入协议或写逻辑改动。

## 5. 最简验收

在合成数据/DOM 桩中定向检查：

1. 组键对应人物 A、代表脸存在 A/B 多候选时，右头像**只会是 A**；找不到 A 时占位，不错配；组内照片数/展开结果不变。
2. 单脸有首选候选、多个候选、无候选、候选无头像/图片错误四种情形：姓名/头像/按钮人物一致；只有待整理脸可打开原图。
3. 展开分组与「再整理一些」、重新加载/刷新后参考头像仍正确；旧异步响应不会覆盖最新候选。
4. 批量状态和 Shift 选择正常；右参考头像不影响 selection、最多 500 限制、确认/改归属。
5. `9rem` 网格/640px 窄屏不横向溢出；无额外逐脸人物 API、无模型或后台识别调用。

复用并按需最少补充 `tests/unit/test_person_inbox_confirm_ui.py`、`test_person_inbox_hide_ui.py`、`test_person_loaded_pages_ui.py` 的相关用例。运行受影响的少量 pytest（输出 JUnit XML）、`node --check src/photo_search/web/persons-albums.js`、`git diff --check`；仅修改 Python 时运行对应 Ruff 与后端定向回归。**不跑全仓、GPU、规模或真实 PhotoSearchData，不做打包**。实际图片观感由用户手工验收，未跑不能声称 PASS。
