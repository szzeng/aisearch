## 1. 唯一目标

从 UI 2.0 的统一照片弹窗中，直接管理**当前照片已经检测出来**的所有有效人脸：查看每张脸的归属、指定/更正人物、移出、新建未命名人物、暂时忽略、明确排除与恢复。

同一个入口适用 1、5、20、30 人的照片，**不设置“15 人以上”触发开关**。例如已检测 20 张脸（已归属 5、待整理 10、暂时忽略 3、明确排除 2），用户不跳离照片弹窗便可完成必要操作。照片真实人数可能更多，本卡不尝试检测漏掉的脸。

**明确不做**：加大检测力度、多尺度/原图重新检测、阈值/模型/向量调整、自动重新匹配、重建人脸索引、识别效果认证、原图标注框/手动画框、单独的已忽略管理页、跨照片批量整理或人物合集业务扩展。

## 3. 界面与操作合同

### 3.1 默认清爽，按需展开

在当前照片信息栏显示既有**“照片中的人物”摘要**，旁边增加明显但不喧宾夺主的 **“管理人脸”** 入口。默认不渲染 20 张脸的大网格；用户点开才挂载管理卡片、懒加载裁剪缩略图。信息栏已经取得的当前 \`asset_faces\` 数据可复用，不能为了折叠面板重新逐项请求。

管理面板使用现有 viewer 内部可滚动区域，桌面优先右侧、窄屏在信息区内收纳，**不另外打开一个完整照片 modal，也不改变 viewer 外框尺寸**。保留图片缩放/平移、上下张、完整详情、Esc/Back、焦点返回及原各页面来源上下文。已有照片详情/识别更新待确认链接不得误删。

面板顶部展示：\`已检测 N 张脸 · 已归属 A · 待整理 B · 已忽略 C\`。计数指**本接口当前有效、去重后的 face_id**，不是照片真实人数，也不是人物数；当 \`has_more=true\`，只显示“当前已返回的前 200 张脸”，不能声称全量数量。

分组及默认展示：

1. **已归属**：逐脸显示真实当前归属；同一人物若有两张脸仍是两张可分别操作的脸卡，但上层人物入口按 canonical person ID 去重。
2. **待整理**：当前无有效归属且未忽略。疑似低质量仅作为折叠子组/附注，不作人工忽略，也不删数据。
3. **已忽略**：默认折叠，仅展示数量；主动展开后再分 \`TEMPORARY\` / \`EXCLUDED\`。**明确排除默认不展开、不下载该组人脸缩略图、不显示候选推荐**；用户明确进入后才允许看和恢复。

若历史忽略标记和有效人工归属同时存在，展示归类以**有效人物成员优先**，不能把已确认的脸重新放回待整理；保留原标记及既有权威读取/恢复规则，不暗中清理历史记录。任何因检测世代失效/映射待确认而不应操作的脸必须保持只读或给出“识别更新待确认”原入口，不能被笼统视为普通待整理脸。

每张卡只显示裁剪头像、状态/当前姓名及对应动作。不要暴露 \`face_id\`、原始 bbox、相似分、embedding、本机绝对路径或 SQL revision。

### 3.2 单脸操作（只写指定 face_id）

| 状态 | 按钮/结果 |
| --- | --- |
| 已归属 | **更换人物 / 移出人物 / 查看该人物相册**。更换/移出走现有 FACE_CONTROL；不直接显示待整理专用忽略按钮 |
| 待整理 | **指定已有的人 / 新建未命名人物 / 暂时忽略 / 明确排除**；搜索人物用既有 \`/persons/browse\` 有界分页 |
| 暂时忽略 | **恢复**；可沿用既有已忽略候选的人工确认路径，但须保留它的原子写入/显示优先级，不偷偷改写忽略状态 |
| 明确排除 | 默认无普通整理动作；用户主动展开并点击 **恢复** 后才可重新指定人物 |
| 低质量或映射待确认 | 前者允许按正常合法动作人工处理；后者遵守既有 hold/版本保护，不绕过权威资格校验 |

\`POST /faces/inbox/visibility\` 只允许当前符合收件箱资格的人脸新增忽略；**不是通用的“隐藏任意已归属脸”接口**。已归属脸要先显式移出，随后重新读取资格，才能考虑忽略。任何展示时的“可操作”标记都不是写入许可，服务端必须在写事务里复核。

新建人物复用 \`/faces/{face_id}/create-person\` 的原幂等和期望版本语义；不能直接插库，也不能把网络超时当作失败后换 \`request_id\` 重试而导致重复创建。

### 3.3 当前照片轻量批量整理

只有按“批量整理”才显示勾选框。仅从当前**实际显示并有合法待整理资格**的人脸选中真实 \`face_id\`，不得选候选参考头像、人物封面、合集静态收录锚点或尚未加载的脸。

仅提供：**暂时忽略所选 / 明确排除所选 / 清空 / 取消**。调用现有单批最多 500 张脸、整批校验且原子写入接口；不能把任何已归属或受保护脸混进去。失败保持选中和明确错误，成功才重读当前资产结果。暂不新增 Shift 跨分组范围选择、批量改归属、批量建人物、忽略“照片中的其他所有人”等快捷按钮。

### 3.4 不复制人物相册操作系统

**优先最小修改现有共享层**，只有确有复用价值时才新增 \`web/photo-face-manager.js\`；不得因“组件化”强制重拆 \`persons-albums.js\` 大状态机。

人物相册现有 \`extension\` 中的人脸更正、封面、识别细节、待确认入口，按单一来源明确职责：在普通管理模式复用共享人脸操作；封面等人物页专属模式继续由人物模块控制。消除重复的人脸网格/请求，但不删除能力。人物合集的“单独收录的人脸”是静态收藏语义，**不等同于待整理人脸**，不得误写或混算。

针对普通照片、搜索、人物/合集、地点、地图、时间轴的入口，优先通过共享 viewer 一次接线；\`people:false\` 不能使这些入口完全失去管理按钮，也不能造成两套“照片中的人物”。如某专属模式因写保护不允许编辑，提供明确只读态/安全退化，不默默开放危险写入。

## 4. 查询性能与前端状态（本卡限定范围）

**问题现状**：\`asset_faces()\` 先对当前照片有界查询，随后 \`_face_view()\` 对每张脸读取忽略、有效归属、候选、姓名及候选摘要；\`photo-info.js::renderPeople()\` 另按人物逐个取详情。多人合照会明显放大 SQLite 往返与 HTTP 次数。

在**单照片读取路径**实现有限预取或有界批量投影（如按本次返回 face IDs 批量获取忽略/归属/候选，并按少量 distinct canonical 人物批量取名称/头像必要字段），保留 \`_VISIBLE\`、\`_NOT_HELD\`、superseded、\`MEMBER_PREDICATE\`、人工排除及 \`FACE_DETAIL_SPEC_REVISION\` 的现有实际语义。不能因性能优化复活失效机器脸、泄露排除建议或错误更改有效人物成员。

- 先复用已合入索引和现有 API；允许追加**兼容的只读字段**，不强制修改全局 \`_face_view()\` 调用方/分页合同。
- 摘要与管理面板尽量复用本次 \`asset_faces\` 读取及 canonical 人物信息；不得变成每脸或每人物新增 HTTP 请求。
- 仅当前 \`asset_id\` 有界查询，保持 \`LIMIT 201 → 200 + has_more\`；列表/时间轴首屏**零新增逐卡资产脸请求**。
- 低质量/已排除组折叠时不得创建隐藏的几十张缩略图网络请求；切换照片清理旧 DOM/图片引用/事件及请求序列。
- 当实现只改局部、未改共享查询时，可报告剩余非本卡 N+1；但**本卡实际接入后的当前照片查询/API 调用不能随 face 数接近线性恶化**，要用可复现的调用数比较证明。无需制定毫秒基准或做 30 万图库性能认证。
- 不新增全库 \`COUNT(*)\`、新 schema/index/migration、持久缓存、查询定时轮询，也不借机改 SQLite 全局连接层。

### 异步、写入和刷新

请求绑定当前 \`asset_id\`、viewer generation 和当前管理面板状态；A→B 快切、关闭再开、缓存过期时丢弃 A 的迟到读写回显。**写请求未知结果**不得自动以新 request_id 重放；参考现有人物整理的 \`writing/pendingWrite\` 安全处理方式。

保存成功后只重读当前照片脸、分类数及必要人员摘要，并通过既有轻量刷新通知更新人物相册；**不刷新全库人物列表或重建索引**。保留图片 zoom/pan、已打开的 viewer、原照片导航和滚动。服务端 409、422、404、超时/5xx 明确区分，不乐观宣称成功；严格使用已有 CSRF/会话/权限规则。共享信息组件 \`dispose\` 继续回收地图等资源。
