# P4-SEARCH-RETURN-A 搜索结果返回恢复

## 目标

修复搜索页进入图片详情后，再返回搜索页时原搜索结果丢失的问题。

期望体验：

1. `/search` 完成一次搜索。
2. 点击某张照片「查看详情」进入 `/#/asset/{id}`。
3. 浏览器返回后：
   - 原搜索条件仍在；
   - 已加载的搜索结果仍在；
   - 不自动重新执行搜索；
   - 尽量恢复到离开前的滚动位置；
   - 原搜索 session/cursor 仍有效时，可以继续「加载更多」。

这是个人项目，只做简单可靠实现，不扩展为通用前端状态框架。

## 实现范围

主要修改：

- `src/photo_search/web/search.js`

必要时可少量修改：

- `tests/unit/test_api_frontend.py`

### 建议实现

使用 `sessionStorage` 保存搜索页临时现场。

至少保存：

- 搜索表单条件；
- 已加载的 `hits`；
- `search_session_id`；
- `next_cursor`；
- 当前结果数量；
- `total_candidates`；
- `placeAware` 等继续分页需要的最小状态；
- 当前滚动位置。

点击「查看详情」前写入现场。

重新进入 `/search` 时：

- 如果存在有效现场，直接恢复表单和已有结果；
- 使用现有 `buildHit()` 重新渲染结果；
- 恢复滚动位置；
- **不得自动调用搜索 API**。

用户主动执行新的「搜索」或「重置」时，清除旧现场。

如果恢复后旧 `search_session_id/cursor` 已过期：

- 已显示结果继续保留；
- 用户点击「加载更多」时按现有错误处理提示重新搜索；
- 不因为分页失效而立即清空旧结果。

图片上传搜索若保存 `File` 较麻烦，本卡**不要求恢复上传文件本身**；不要为此引入 IndexedDB 等复杂方案。

## 非目标

不做：

- 数据库持久化；
- 跨程序重启保存搜索结果；
- 多标签页同步；
- 新增后端 API；
- 搜索算法修改；
- IndexedDB；
- 通用状态管理框架；
- 大规模浏览器自动化测试。

## 最小验收

人工验证即可：

1. 搜索任意关键词，确保出现多张结果。
2. 向下滚动一段距离。
3. 点击其中一张「查看详情」。
4. 浏览器返回。
5. 确认：
   - 搜索词仍在；
   - 原结果仍在；
   - 页面大致回到原浏览位置；
   - Network 中没有因为返回而重新发起一次搜索请求。
6. 如果原结果有下一页，再点一次「加载更多」，确认仍可正常工作。

## 最小自动测试

只补必要的静态/单元契约即可，例如确认：

- `search.js` 使用 `sessionStorage` 保存/恢复搜索现场；
- 新搜索会清除旧现场。

然后执行：

```powershell
uv run --no-sync pytest -q tests/unit/test_api_frontend.py
node --check src/photo_search/web/search.js
git diff --check
```

不要求跑全量 pytest。
