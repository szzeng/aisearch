## 一、任务目标

PhotoSearch 是个人日常使用的本地照片管理软件。

本次以普通用户的理解和使用效率为第一目标，让界面做到：

- **正常时简洁**：照片、人物和搜索结果是主体，不要大量显示技术说明。
- **异常时明确**：解释实际问题、影响以及下一步。
- **操作时可靠**：保存、删除、忽略、清理、切换模型等提示必须准确。
- **技术信息可查**：保留必要诊断能力，但不让内部协议占据普通界面。
- **减少重复打扰**：没有需要处理的问题，就不重复展示警告。

最终目标不是让文字更少，而是让用户不必理解程序内部机制，也能知道当前应该怎么做。

## 三、先审查，再修复

进行一次全站用户可见文案检查，按以下维度逐项核对：

1. 文案是否与当前按钮名称、入口和实际功能一致。
2. 是否出现过时名称或已经不存在的操作入口。
3. 是否错误描述当前状态。
4. 是否泄露不必要的内部术语。
5. 是否告诉用户有效的下一步。
6. 是否存在重复、冗长、没有帮助的提示。
7. 是否在不需要提醒的时候持续占据页面。
8. 是否错误暗示照片、人工数据或索引已经被删除。
9. 保存结果不确定时，是否错误声称成功或失败。
10. 错误码和请求编号是否妥善保留供诊断。

对每个待修改项，先确定：

**触发条件 → 当前文字 → 问题 → 新文字 → 是否影响操作行为**

按照优先级实施：

- **P1：必须修复**。错误引导、错误状态、误导性风险说明、实际入口不匹配。
- **P2：优先优化**。普通界面的技术术语、重复解释、缺乏行动指引。
- **P3：可保留**。纯文字风格差异，没有实际使用收益。

不为增加修改数量而重写正常文案。

## 四、第一组：明确存在的问题

### 4.1 图库管理的过时入口

当前空图库提示仍提及旧入口“图库管理与分析明细”。

实际页面已使用“添加图库来源”。

修复为类似：

> 还没有添加图库。展开“添加图库来源”，填写照片文件夹路径后开始建库。

注意：当前程序是手工输入目录路径，不要暗示已有系统文件夹选择器。

同时检查其他页面是否还引用旧入口“来源与扫描”等过时名称。

### 4.2 照片浏览的空状态

严格区分：

- 没有登记图库。
- 已登记但尚未扫描。
- 正在扫描或建库。
- 当前筛选无结果。
- 日期信息尚未处理完成。
- 原文件不可用。

例如已经存在正常图库，但筛选后无照片时，应提示：

> 当前条件下没有找到照片，可以调整或清除筛选。

不能错误地要求重新添加图库或建库。

不应把“暂时没有搜索结果”表述为“确定不存在照片”。

### 4.3 “照片已回收”的含义

检查照片浏览、时间轴与搜索列表中有关节点回收的提示。

如果只是浏览器释放较早的显示节点，应表达为：

> 为保持浏览流畅，部分较早的照片已从当前页面暂时移除，原照片没有删除。

允许根据显示空间缩短，但必须保留“不代表文件被删除”的含义。

不得修改虚拟滚动、节点回收、分页、历史或返回行为。

### 4.4 搜索条件与协议术语

普通搜索页面不应长期显示：

- `canonical`
- `person_ids=[]`
- `person_match=any`
- `capture_from`
- `capture_to_exclusive`
- `multipart`
- `null`
- `revision`

建议：

“未选择人物，当前搜索不限制人物。”

“已选择 2 个人物，照片中出现任意一人即可匹配。”

“以图搜图暂不支持人物和拍摄时间筛选。”

保留真实匹配方式、日期边界及服务端实际生效条件。

不可把“结束日期不包含”错误简化为“包含结束日期”。

技术回显可以收纳进已有高级或诊断区域；只有确实需要时才调整其展示容器，不新建大型调试系统。

## 五、第二组：高频功能体验优化

### 5.1 搜索状态与结果

重点检查：

- 正在搜索。
- 搜索完成。
- 没有匹配结果。
- 查询条件已改变。
- 会话或快照已失效。
- 搜索模型尚未就绪。
- 部分照片无法编码。
- 结果数量和候选数量。
- 保存智能合集的资格失效。

用户应区分：

“没有找到符合条件的照片。”

“当前索引还没有准备好，暂时无法判断匹配结果。”

“搜索条件已保留，请重新搜索恢复结果。”

不得将“候选总数”错误称为“实际匹配照片数”，也不得承诺重新搜索一定能解决模型问题。

### 5.2 搜索模型与索引管理

对已知状态提供明确说明：

| 状态 | 提示方向 |
|---|---|
| 未安装 | 需要准备模型 |
| 未建索引 | 需要建库 |
| 索引待检查 | 点击检查 |
| 正在检查 | 正在核验，不重复操作 |
| 检查通过 | 可以使用或安排切换 |
| 覆盖不足 | 说明哪些照片未准备好及适用的处理方式 |
| 检查失败 | 显示实际原因及可靠的恢复方法 |
| 切换待重启 | 提醒何时生效 |

保留原来的安全边界和模型切换资格判断。

不能把所有切换失败都解释成“索引覆盖不足”；离线照片也不能被错误计为在线覆盖缺失。

### 5.3 普通与智能合集

保留普通合集和智能合集的本质区别：

- 普通合集：由用户手工确认收录，新照片不会自动加入。
- 智能合集：按保存的规则动态筛选，或使用需要更新的排名结果。

重点优化：

- 尚无匹配结果。
- 结果正在更新。
- 仍可使用旧结果。
- 旧结果不可安全使用。
- 模型变化导致规则需要重新确认。
- 排名缓存需要更新。
- 结果被截断。
- 部分照片已排除。

普通用户优先看到：

> 正在更新匹配结果，完成前继续显示上次有效结果。

或：

> 搜索模型已变化，需要重新搜索并更新合集规则。

具体文案必须对应实际状态。

不要把所有“刷新排名缓存”都改成容易误解的“刷新照片”；不改变规则、缓存、排除和相关度排序的现有机制。

### 5.4 人物管理与人脸整理

重点检查：

- 已命名人物 / 未命名人物 / 未识别人脸。
- 机器建议与人工确认。
- 暂时忽略与明确排除。
- 人物级排除与单张脸排除。
- 恢复自动判断。
- 加入人物合集。
- 人脸归属修改。
- 撤销操作。
- 保存结果未确认。

必须保证用户能够理解：

“确认人物”和“加入合集”不是同一个操作。

“暂时忽略”和“明确排除”有不同后果。

保存成功但列表刷新失败时，不能提示用户重复保存。

重要人工数据保护说明不得删除。

可以减少重复帮助文字，但不能将人物和人脸混称。

## 六、第三组：低频高级功能

### 6.1 地点管理

普通按钮优先使用自然中文：

- 确认所选照片的地点。
- 取消地点归属。
- 恢复自动判断。
- 重新加载建议。

`place_id`、`revision`、`assign`、`unassign`、`restore_auto` 等保留在必要的高级信息中。

如果某些高级功能确实需要输入地点 ID，不要擅自删除字段或伪装成已经有地点选择器。

需要准确区分：

- 照片没有 GPS。
- 未配置有效地名包。
- 地名包不可用。
- 尚无建议。
- 地点尚未人工确认。
- 地点相册暂无照片。

### 6.2 地图相册

统一地图不可用提示：

> 地图底图暂不可用，仍可通过照片列表浏览。

需要用户操作时，说明实际步骤，例如检查 Key、网络或服务配置。

不反复弹出同一个地图错误。

不因地图底图不可用而误报照片丢失。

保留地图 Key 的安全提示。

### 6.3 照片查看器与 OCR

准确区分：

- 大图不可用，但缩略图仍可显示。
- 原文件暂时不可用。
- 原文件位置缺失。
- 照片预览完全失败。
- OCR 尚无结果。
- OCR 读取失败。
- 人物识别未完成。
- 人物识别没有找到人脸。

对于预览错误，普通页面优先使用可理解的说明；内部错误码可在详情中保留。

不能把“尚未识别到文字”显示成“OCR 读取失败”。

### 6.4 空间维护与失效照片

这是数据安全要求最高的文字范围。

保留：

- 清理范围与资格限制。
- 原图是否会被删除。
- 人工整理数据是否保留。
- 已完成、部分完成、失败、状态未知的区别。
- 自动清理与手动清理的区别。
- 是否可撤销。
- 备份是否包含原图。
- 是否需要重启。

仅压缩冗长或重复的技术说明。

不可改变维护、失效照片清理、备份与删除的真实执行逻辑。

## 七、统一提示的呈现原则

### 7.1 普通状态

简短显示结果或必要数字。

例如：“已显示 120 张照片。”

没有需要用户处理的问题，就不重复出现长段提示。

### 7.2 操作成功

局部给出确认，不反复覆盖页面内容。

例如：“已加入收藏。”

### 7.3 操作失败

采用：

**问题 → 影响 → 下一步**

例如：

“图库来源暂时无法读取。已显示的照片不会因此删除，请检查本地程序是否仍在运行，然后重试。”

只有真实状态支持时才能描述影响和恢复方式。

### 7.4 写入结果未确认

必须与明确失败区分。

例如：

“保存结果暂时无法确认，请先刷新检查，不要重复提交。”

### 7.5 危险操作

保留准确的范围和后果。

不隐藏原图、人工记录、撤销与备份方面的关键说明。

### 7.6 提示位置与频率

- 与当前操作直接相关的提示留在操作区域。
- 普通成功反馈不长期占用主要页面空间。
- 不重复出现同一警告。
- 不自动进行额外检查来制造提醒。
- 不新增全局 Toast 系统、消息中心、定时通知或后台轮询。

只有现有展示方式明显不合理时，才进行必要的小范围 HTML/CSS 调整。

## 八、性能与安全边界

**影响链路**：前端页面文字、已有状态映射和必要的显示控制。

**实施方式**：优先修改现有 HTML/JS 字符串及少量展示代码，复用已有 API 响应和 CSS。

**验证与停止**：以受影响的定向测试和少量隔离浏览器流程为准，不做大规模图库或模型性能认证。

明确禁止：

- 修改数据库、schema 或迁移。
- 修改搜索算法、排名、分页和模型切换协议。
- 修改人工人脸、地点、收藏或合集的写入规则。
- 增加新的 API、查询、模型调用或后台任务。
- 增加全局通知框架。
- 访问或修改真实图库、原图和人工记录。
- 将错误或诊断字段直接删除到无法排查问题。
- 为适配新文案而降低或删除旧测试的有效断言。

如果某条文案需要改变业务逻辑才能真正修复，单独记录问题，不在本任务擅自扩大范围。

## 九、测试和验收

按修改风险选择定向测试，不重跑已经稳定且未受影响的功能。

重点确认：

1. 空图库提示指向真实入口。
2. 有图库但筛选无结果时，不提示错误操作。
3. 缩略图回收不会被描述成原照片删除。
4. 搜索条件实际生效内容与界面文字一致。
5. 日期范围边界没有改变。
6. 搜索会话失效后条件保留，提示的恢复操作有效。
7. 模型就绪、未就绪、检查失败和不能切换的原因不混淆。
8. 智能合集的正常、更新中、不可用状态区分准确。
9. 人物和地点的人工操作反馈不误报成功。
10. 删除、清理和备份的风险说明完整。
11. 照片预览失败与原文件丢失不混为一谈。
12. 修改后的按钮与提示文字指向实际存在的操作。

浏览器验收复用当前 `AGENTS.md` 规则和项目内隔离合成图库。

优先实际检查 2～3 条代表性流程：

- 空图库 / 现有图库的空状态。
- 搜索筛选、搜索结果及异常提示。
- 一个涉及智能合集、人物整理或模型状态的实际修改场景。

其他高风险文案可以使用现有合成 fixture 与定向断言验证。

危险操作只检查确认与取消路径，不执行真实清理。

运行修改文件对应的 `node --check`、相关 pytest/JUnit 和 `git diff --check`。

不要求全仓测试、GPU、30 万图库压力测试或重新跑三阶段 UI 验收。

无法实际复核的项目保留 PENDING，不把静态测试冒充浏览器验证。
