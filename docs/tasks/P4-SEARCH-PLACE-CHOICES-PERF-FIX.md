# P4-SEARCH-PLACE-CHOICES-PERF-FIX — 地点候选构建性能修复

**优先级：** P1
**推荐执行模型：** GPT-6 High
**任务类型：** 定向性能优化
**范围：** 地点候选构建与搜索意图处理
**代码基线：** 本地实际最新工作树
**执行要求：** 修改、定向测试、生成报告；不提交、不推送

## 一、任务目标

解决普通综合搜索反复构建大量无关地点候选，导致搜索响应时间过长的问题。

真实 Qwen EXIF v2 测试显示：

| 指标 | P50 | P95 |
|---|---:|---:|
| 后端搜索 | 1,201.9 ms | 1,356.4 ms |
| 地点候选构建 | 1,026.0 ms | 1,209.8 ms |
| 地点 SQL | 176.7 ms | 215.2 ms |
| 核心检索 | 165.0 ms | 193.9 ms |

以上使用现有性能面板的最近秩百分位统计口径，样本为 20 次有效热搜索。

每次普通搜索：

- 生成约 47,960 个地点候选。
- 处理约 45,217 条 GeoNames 记录。
- 处理约 3,013 条 OSM 行政区记录。
- 读取约 26,520 条别名。
- 处理 274 条旧地点关联记录。
- 地点匹配结果为 0。

**目标不是减少合法地点数量，而是避免为不相关的搜索词重复进行大量无意义处理。**

```python
legacy = next(
```

### 实施要求

3. 重复 `place_id` 必须保留原实现的首次匹配结果。
4. 保持原对象引用，以维持别名合并行为。
5. 保留原始候选顺序。
6. 保留旧地点与 OSM 的关联关系。
7. 保留别名去重顺序和 `linked_local` 排除规则。

此项不引入跨请求缓存。

## 四、FIX-2：消除普通搜索中的大量无效地点处理

这是本任务最重要的性能目标。

目前 `place_choices.choices(text=...)` 可能先构建完整地点列表，再逐条正规化并检查搜索文本。

对「日落」等非地点查询，这种工作方式仍然可能处理数万个候选，但最终匹配 0 个。

### 4.1 先定位 Python 内部耗时

在性能诊断开启时，补充少量内部计时：

- 读取后的候选对象构造
- GeoNames / OSM 关联合并
- 名称及别名正规化
- 搜索文本匹配和过滤
- 其他 Python 处理残余

这些是 `place_choices_ms` 内部子阶段，不得与父阶段重复相加。

只对需要诊断的请求记录，不在普通搜索中增加详细追踪。

### 4.2 优先优化有文本条件的查询

对于 `choices(text=...)`：

研究能否采用**先确认候选名称或别名匹配，再补充完整地点信息**的方式。

要求：

1. 查询无地点命中时，不再为所有地点反复构造完整候选对象。
2. 尽量避免每次重新正规化数万个相同的地点名称和别名。
3. 不改变 `_compact()` 的 NFKC、大小写和空白处理语义。
4. 保持现有匹配方向，即地点名称或别名必须能在查询文本中匹配。
5. 保留旧地点关联产生的别名。
6. 同名城市、省份、区县必须保留全部合法候选。
7. 保留 `selection_ref`、来源、数据集身份及父级地点。
8. 不破坏搜索计划的验证和地点消歧。

尤其注意：

**不能在处理 `cn_legacy_links` 之前提前丢弃可能通过继承别名匹配的地点。**

### 4.3 保持完整候选接口

现有调用 `choices(text=None)` 的地方可能需要完整地点目录。

不得为了普通搜索提速，直接改变这些调用的返回范围。

可以在内部拆分：

- 查询文本匹配需要的轻量候选查找。
- 需要完整地点资料的候选构建。

但优先复用现有代码，避免创建两套互不一致的地点身份规则。

### 4.4 缓存策略

优先采用无全局缓存的算法优化。

只有确认每次重建仍然成为瓶颈，且存在可靠的数据版本与失效机制时，才允许考虑有界缓存。

禁止：

- 仅按文本缓存搜索结果。
- 不带数据版本的永久地点缓存。
- 忽略别名、地点映射或活动数据集更新。
- 直接缓存 SQLite 游标或连接对象。
- 为提升速度绕过地点身份验证。

如果不能证明缓存安全，则不实施缓存。

## 五、FIX-3：仅在有收益时继续优化 SQL

新报告显示：

- 地点 SQL：129 次。
- 映射查询：8 次。
- 别名查询：114 次。
- 地点 SQL P50：176.7 ms。

这些数字表明当前版本很可能已经使用部分批量查询。

因此本任务不预先要求重新批量化所有 SQL。

执行 FIX-1、FIX-2 后，重新观察：

- SQL 次数是否下降。
- SQL 耗时是否下降。
- 返回的数据行数是否下降。
- 是否仍然读取大量明显不会匹配的地点数据。

如 SQL 仍为明显瓶颈，可以考虑：

1. 使用活动数据集身份约束，减少不必要的旧地点 fallback 记录。
2. 减少重复读取的地点别名或映射。
3. 在保证 Unicode 匹配语义的前提下，缩小需要从数据库获取的候选范围。
4. 保留原 SQL 排序语义和重复地点的首次匹配规则。

不得直接用不等价的 SQLite `LIKE` 替代 `_compact()` 匹配。

不得为了减少查询次数引入更大的无条件全表扫描。

如果 SQL 不再是明显瓶颈，则停止优化，不扩大范围。
