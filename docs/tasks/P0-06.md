# P0-06 — GPU runtime bring-up + authorized model evaluation

执行模型：**DS-H / DeepSeek V4.1 Flash / 高推理**。

- GPU runtime、Windows、ONNX Runtime、CUDA provider、DLL、驱动、依赖或显存问题：推荐用户手动切到 **C1 / GPT-5.6 Terra / medium**，继续同一个 P0-06 任务。
- 如果评测结果需要改变核心模型路线或架构约束：提交证据后交 **C2 / GPT-5.6 Sol / high** 做决策审查。
- 不得因为当前客户端没有自动切换能力而虚报已经切换模型。

本任务分成两个**串行阶段**：A 必须先通过，才允许执行 B 的正式质量评测。

2026-09-11 文档交接：依据主架构需求修订 3、V3.1 策略修订 2 和 [ADR-0001](../decisions/ADR-0001-gpu-required.md)，CUDA 为首版必选，最低支持目标为 GTX 1660 6 GB；当前开发机为 RTX 4060 Laptop GPU / 8188 MiB。正式图文/人脸默认 GPU，CPU 仅作对照与显式降级。本任务在当前 RTX 4060 验收，GTX 1660 实机验证最迟 P4-07/P4-08；不能用当前机限显存实验冒充最低配置通过。

## A. GPU runtime bring-up（硬门槛）

目标：把当前“RTX 4060 硬件可见 + CPU 模型可运行”推进到“本项目真实模型通过当前 runtime/worker 在 RTX 4060 上执行”。默认执行设备必须为 CUDA；CPU 路径保留为基线与显式降级，GPU 不可用时明确失败，不静默整图回退。

### A0. 用户已完成的 GPU 预验证（直接作为本任务起点）

用户已在 Windows 主机上完成独立 GPU probe，以下事实已经人工实测，不需要从零重新研究驱动是否支持 CUDA：

```text
GPU: NVIDIA GeForce RTX 4060
VRAM: 8188 MiB
NVIDIA driver: 616.56
CUDA UMD: 13.4
Python: 3.12.10
probe env: D:\gpu-probe
onnxruntime-gpu: 1.30.0
nvidia-cuda-runtime: 13.4.49
nvidia-cuda-nvrtc: 13.4.59
nvidia-cublas: 13.7.0.27
nvidia-cudnn-cu13: 9.26.0.51
nvidia-cufft: 12.4.0.34
nvidia-curand: 10.4.4.49
nvidia-nvjitlink: 13.4.52
```

用户执行：

```powershell
uv venv D:\gpu-probe --python 3.12.10
uv pip install --python D:\gpu-probe\Scripts\python.exe "onnxruntime-gpu[cuda,cudnn]"
D:\gpu-probe\Scripts\python.exe -c "import onnxruntime as ort; ort.preload_dlls(directory=''); print(ort.__version__); print(ort.get_available_providers())"
```

实际结果：

```text
1.30.0
['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']
```

因此已经确认：

- 独立 probe 已加载运行包并列出 CUDA provider；驱动/runtime 的真实模型可用性仍须 A1～A9 验收；
- Python 3.12.10 下 `onnxruntime-gpu 1.30.0` 可以加载；
- `CUDAExecutionProvider` 已在独立 probe 环境中出现；
- CPU provider 仍可用；
- 暂无必要安装完整 CUDA Toolkit、nvcc、Visual Studio CUDA 工具链或额外 TensorRT；
- `uv` 安装时出现的 hardlink fallback 只是缓存跨文件系统复制警告，不属于 GPU/runtime 故障。

**执行要求：**不要重复花时间从零验证“这台电脑是否支持 CUDA”。直接进入正式项目 runtime 接入、真实模型 GPU 推理和 worker 闭环。只有当正式项目环境与上述 probe 结果不一致时，才进入环境差异排查。

注意：A0 是用户的独立预验证证据，不替代 A1～A9 的项目内正式验收。正式报告仍需记录项目实际环境、正式依赖方案、真实模型 provider/fallback 证据、数值一致性、性能和显存。

### A1. 环境事实

以 A0 为已知起点，在**正式项目环境**重新记录本次真实环境，不沿用 P0-01 旧记录冒充当前验证，也不要把 `D:\gpu-probe` 直接当成正式项目环境：

- `nvidia-smi` 输出摘要；
- GPU 型号、驱动版本、显存；
- Python、ONNX Runtime、相关 CUDA runtime/DLL 版本；
- 当前 CPU/GPU ONNX Runtime 依赖方案与安装/切换命令；
- 正式项目环境与 A0 probe 的差异（如有）。

优先使正式项目依赖方案与 A0 已验证组合保持一致或可解释兼容；若需要改变版本，必须说明原因。

正式路径锁定 onnxruntime-gpu 与匹配 CUDA/cuDNN DLL；优先使用同一 GPU 包中的 CPUExecutionProvider 做对照/降级。检查 RapidOCR 等传递依赖，不得在同一正式项目环境里混装互相覆盖、无法解释来源的 CPU/GPU ONNX Runtime 发行包；依赖变更必须更新 uv.lock。记录最低 GTX 1660 目标的兼容计划，不把本机 616.56 驱动当成所有机器的最低版本，不要求完整 CUDA Toolkit/TensorRT。

### A2. CUDA provider

GPU 环境必须满足：

```text
onnxruntime.get_available_providers()
```

包含：

```text
CUDAExecutionProvider
```

如果正式项目环境只有 `CPUExecutionProvider` / `AzureExecutionProvider`，本阶段不能 PASS；此时优先比较正式环境与 A0 probe 的依赖/DLL 差异，而不是重新怀疑硬件或驱动。

### A3. Chinese-CLIP 真 GPU 推理

复用 P0-03 已冻结模型和 manifest，不修改模型身份：

- image tower 在 CUDA 上真实推理；
- text tower 在 CUDA 上真实推理；
- 输出维度仍为 512；
- L2 normalization 契约不变。

至少使用一种方式排除“声明 CUDA、实际静默 CPU fallback”的假阳性：

1. 优先在可行时禁用 CPU fallback 完成一次推理；或
2. 使用 ONNX Runtime profiling/provider 证据，记录实际执行 provider 和任何 fallback 节点。

不能只创建带 `CUDAExecutionProvider` 的 session 就宣称 GPU 已验证。

### A4. CPU/GPU 数值一致性

使用 P0-03 同一批固定 fixture，CPU FP32 与 GPU FP32 对照，记录精度/provider 配置（RTX 4060 严格 FP32 对照需禁用 TF32），并记录：

- image max absolute difference；
- text max absolute difference；
- 每个对应向量 cosine；
- P0-03 固定查询 Top-K。

初始硬门槛：

- CPU/GPU 对应向量 cosine `>= 0.9999`；
- P0-03 固定查询 Top-K 一致。

如达不到，先定位算子/精度/provider 差异，不得直接降低门槛来过关。

### A5. GPU 性能与显存

预热后重复推理，至少记录：

- image tower latency；
- text tower latency；
- CPU 对照 latency；
- GPU 显存占用；
- 重复执行的稳定区间或 P50/P95。

不得用单次最快值作为性能结论。记录 GPU 总占用/worker 峰值的测量口径、桌面及其他进程的占用，并给出 6 GB 最低目标的显存预算；ORT 单 session arena 限制不等于整个进程显存上限。

当前模型固定 batch=1，从单 worker、小批次开始；动态 batch、FP16/量化另验收，不在本任务擅改冻结 manifest。最低路线不依赖 Tensor Core/BF16/TF32/FlashAttention/TensorRT；显存限制预检仅证明预算，不替代 GTX 1660 实机测试。

### A6. P0-05 worker GPU 闭环

P0-05 当前 worker 是 CPU 路径。本任务必须让 managed spawn worker：

- 不指定设备时默认 CUDA，可显式选择 CPU；
- 返回实际 device/provider；
- 完成 GPU text encode；
- 完成 GPU image encode；
- 完成一次 worker 内 GPU `demo-search`；
- CPU 基线和显式降级仍可复现；
- 模拟 CUDA 不可用、加载失败或 OOM，确认默认路径明确失败、不静默整图回退；允许减小已支持批次/卸载闲置模型后有限重试，仍失败返回结构化错误；
- 明确记录用户显式 CPU 降级的实际 provider 和原因；后续 P2 调度器据错误暂停相应 AI 任务，非 AI 浏览/管理继续可用，不在本任务提前实现调度业务。

不能只写一个独立 CUDA 探针，而产品 worker 继续固定 CPU。

### A7. InsightFace GPU smoke

复用 P0-04 固定的 `buffalo_l`：

- detection graph 在 CUDA 上运行并得到有效 detection；
- recognition graph 在 CUDA 上运行并得到 `[1,512]` embedding；
- 记录实际 provider 和最小延迟/显存信息。

这里只证明 runtime/接口可用，不提前承担 P3 的人物阈值和准确率校准。

### A8. RapidOCR GPU 状态

记录 RapidOCR 当前实际 provider、CPU/GPU 可用性和最小延迟。

如果当前依赖方案不能安全地让 RapidOCR 使用 CUDA，不强行为了“全 GPU”破坏稳定性；报告必须写明原因、影响和后续处理点。OCR 是否最终 GPU 化由实测收益决定。

## B. 授权评测集与更强候选比较

只有 A PASS 后才开始 B。

首先确认用户明确授权的样本来源和范围；不得自行扫描真实照片库。

### B1. 本阶段范围

建立可复现的评测工具与数据契约，在至少：

- 2,000 张明确授权图片；
- 100～200 条中文查询；

上，将 P0-03 固定的 Chinese-CLIP baseline 与一个更强且当前硬件/Windows 环境可实际运行的候选比较。

要求：

- tuning 与 holdout/保留集必须分开；
- 记录模型 revision、预处理、向量维度/度量；
- 记录检索指标、query/image latency、VRAM/RAM、磁盘和回归项；
- Chinese-CLIP baseline 的正式性能数据以 GPU 路径为主，同时保留 CPU 对照；
- 候选优先验证 CUDA 与 6 GB 预算；只能 CPU 运行的候选仅作研究，不能成为基础版默认；只适合更高配置的候选单列可选增强，不改变最低要求，不直接把 CPU/GPU 或不同 GPU 性能横比；
- 数据与模型权重全部放在仓库外；
- P0-03 manifest 保持不变；
- 不实现 catalog、LanceDB 产品索引、搜索 API、前端、人物业务或全库建库。

### B2. 无授权样本时

如果当前没有用户明确授权的 2,000 图样本来源：

- A 阶段仍必须照常完成；
- 可完成 evaluator、数据格式、query schema、split 逻辑和公开授权 fixture 测试；
- B 的质量评测状态必须写 **BLOCKED**；
- 整个 P0-06 不得写 PASS；
- 不得生成 P0-07 作为可执行下一任务；
- 不得因为缺样本而扫描用户真实图库。
