# 数据库迁移基本保障（个人项目）

适用于新增或修改 SQLite 表、列、索引、约束及 migration 的任务。目标只有两个：**旧图库升级后能打开，已有人工数据不丢失**。沿用 [ADR-0002](decisions/ADR-0002-catalog-identity-migration-scan-contract.md) 的只读预检、备份、事务迁移与严格校验，不另建流程。

## 1. 已用过的迁移不再改

- 已提交到主分支，或已经在不可随意丢弃的数据库执行过的 migration，视为冻结；后续变更使用下一个连续编号，不回改旧 SQL（包括补字段、补索引或补表）。
- 仅允许修改**尚未提交、且只在可丢弃合成测试库中使用**的迁移。如果不确定是否已经被使用，按已使用处理。
- 同时检查 `SUPPORTED_SCHEMA_VERSION` 与迁移编号连续一致；发现并行任务占用同一版本号，先协调，不能让同一版本代表两种结构。

## 2. 修改前后做最小检查

- 开工时查看 `git diff`、现有 migration 与当前支持版本；提交前确认没有意外修改历史 migration。
- 迁移要保留既有照片身份、人物归属、收藏、合集及其他人工状态；使用现有备份和事务回滚机制。不能靠删除图库、重扫照片、重跑模型、直接改 `schema_version` 或跳过 `verify_schema` 解决兼容问题。
- 如果碰到已经存在但结构不一致的真实数据库，正常启动继续拒绝写入；先只读定位，再通过隔离副本验证专门修复。**未经用户明确授权，不修改真实图库。**

## 3. 只做三项必要测试

在隔离合成数据库运行，优先复用 `tests/unit/test_catalog_migrations.py` 和现有 fixture：

1. **新库**：从空库初始化到最新版本，并能正常重新打开。
2. **旧库升级**：使用修改**之前的代码/冻结夹具**生成上一版本数据库，放入至少一组需要保留的数据；升级后版本、结构、数据和打开读取都正常。不要用修改后的同一套 migration 临时造“旧库”，那样可能漏测兼容性。
3. **失败回滚**：注入一次迁移失败，确认版本号、结构及原有数据不被部分改写。

以上属于 schema 变更的最低检查；原有 [日常测试](testing.md) 对受影响面或高风险变更的其他要求继续有效。普通 UI、查询或性能优化未改 schema 时不额外跑这三项；不要求真实图库、GPU、模型和 30 万照片压测。

## 4. 完成条件

提交说明简要写明“旧 migration 未改、目标版本、三项测试结果”；任一必要测试未通过则不能标 PASS。检查出现未知 schema 差异时应拒绝继续，而不是放宽校验。

*这是一份轻量防事故规则，不要求单独 CI 平台、迁移登记表、所有历史版本测试矩阵或额外任务卡。*
