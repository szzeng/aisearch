# ADR-0019：人物姓名保存忽略大小写

- 日期：2026-10-10。
- 产品决策：用户明确要求修复大小写被认为是不同人物的问题；实施与复核证据分开记录。
- 任务：[P4-PERSON-NAME-CASE-A](../tasks/P4-PERSON-NAME-CASE-A.md)。

## 决策与兼容

覆盖 ADR-0006 §2 与主架构 §8.3.2 中“英文大小写参与同名比较”的旧产品规则。用户保存姓名时，先沿用 NFC、Unicode 空白折叠，再用 Python Unicode `casefold()` 比较活动人物正式姓名键；`Alice` / `alice` / `ALICE`、`Straße` / `STRASSE` 视为同名。不做 NFKC、拼音、模糊拼写、繁简、别名比较。只读搜索与后台识别均不触发人物合并。

显示名、数据库 `nfc1:` 键、操作意图摘要和历史快照仍保留规范后的大小写。schema 保持 28，唯一索引保持原有精确键约束；没有大小写折叠唯一索引或数据库迁移。大小写碰撞由现有 `Catalog.write()` 的 `BEGIN IMMEDIATE` 写事务统一检查。历史操作重放仍先于 canonical / revision / 同名检查；不同显示大小写的请求意图仍不同。

查找同名目标时排除当前 canonical 人物，防止历史大小写重复被自己掩盖。历史多目标先选与提交键完全相同的活动目标，否则选 person_id 最小者；仅合并当前提交的来源，不自动合并其他候选。不扫描或批量改写历史图库。仅自己且显示名字完全相同是记录请求的 no-op；仅自己且修改大小写是普通改名，保留 person_id / 成员，允许撤销。

个人相册 `/label` 沿用 `merge_by_name=False`：碰撞返回 `NAME_IN_USE` 和目标 ID，整库零写入，前端进入既有显式合并确认。旧 `/name` 沿用 `MERGE_BY_NAME`。两个入口复用同一目标查询及原合并用例；目标 ID / 正式名字默认保留，源 ID 重定向、人工控制、排除、照片计数、派生追赶及补偿撤销均沿用原规则。

撤销恢复历史精确大小写和键，不用新比较规则拒绝恢复旧状态，可能重新形成历史大小写重复；后续用户显式保存/合并再处理。同名只是用户命名时的产品规则，不作为模型识别事实或真实身份判断。

## 验证与审查

新增合成测试覆盖 Unicode / NFC / 空白、自己改写大小写 / exact no-op、历史重复目标顺序、别名和已合并旧名不触发、全宽/近似名字保持分离、接口零写入及显式合并、重放优先 / 不同意图冲突、人工否定及 undo、后续改动拒绝 undo、注入关闭操作失败全事务回滚。用户明确指定仅做个人相册相关测试并在当前会话简单复核，覆盖原默认全仓及独立 DS-H / Sol 安排。相关 JUnit 109/0/0/0，当前会话复核通过；见 [复核报告](../reports/P4-PERSON-NAME-CASE-A-current-session-review.md)，不冒称独立审查或总项目 PASS。
